# 골격: P-C-C 구조와 MCP·Mod 핫리로드 기반

이슈: GitHub #30

## 무엇을, 왜

KSP1을 LLM이 MCP로 제어하는 브리지를 처음부터 다시 만든다. 이전 구현(`legacy-dev`)은 보정 로직이 주 기능 안에 쌓여 구조가 엉켰고, 단계적 정비 대신 새로 구현하기로 했다.

구조는 세 계층이다.

- **Planner**: MCP 클라이언트의 LLM. 상태를 보고 계획을 세워 제출·교체·중단한다.
- **Coordinator**: KSP 안에서 계획을 단계별로 실행하고 단계 완료·중단을 판정한다. LLM 응답이 늦거나 연결이 끊겨도 제출된 계획은 계속 진행된다.
- **Controller**: KSP 물리 프레임마다 기체를 실제로 제어한다.

개발 중 반복을 빠르게 하려면 MCP 서버와 KSP Mod 모두 핫리로드가 되어야 한다. 즉 코드를 고쳐 빌드하면 KSP와 MCP 클라이언트를 다시 시작하지 않고 바뀐 동작과 도구가 반영되어야 한다.

이번 작업은 **골격**만 만든다. 솔루션 구성, 두 쪽의 핫리로드, MCP↔Mod 통신, 상태 조회, P-C-C 뼈대와 확장 지점까지다. 실제 비행 기능(상승, 궤도 진입 등)은 다음 작업에서 이 골격 위에 모듈로 얹는다.

범위 밖: 기체 설계 도구, 비행 단계(자세·스로틀 제어 모드), 이전 구현 코드 이식.

## 완료 조건

- C1. 저장소 루트에서 한 번의 빌드 명령으로 MCP 서버와 KSP Mod 산출물이 만들어지고, 배포 명령 한 번으로 KSP `GameData`와 MCP 서버 폴더에 놓인다.
- C2. KSP를 다시 시작하지 않고 Mod 쪽 로직(Coordinator·Controller·요청 처리)을 고쳐 빌드·배포하면, 다음 요청부터 바뀐 동작이 반영된다. `get_status`에 로직 버전과 로드 시각이 바뀐 것으로 보인다.
- C3. MCP 클라이언트를 다시 시작하지 않고 MCP 서버 쪽 도구 코드를 고쳐 빌드·배포하면, 바뀐 도구 동작과 새로 추가한 도구가 클라이언트에서 쓰인다.
- C4. 계획 실행 중에 Mod 로직을 다시 읽으면, 실행 중이던 계획은 중단 사유(`reload`)와 함께 끝난 상태로 남고, 이전 로직이 걸어 둔 기체 제어 입력(스로틀·조종 콜백)이 남지 않는다.
- C5. `get_status`가 게임 씬, 브리지 준비 여부, MCP 서버·Mod 로더·Mod 로직 각각의 버전, 활성 기체 요약(이름, 상황, 고도), 현재 계획 상태를 돌려준다. MCP 서버와 Mod 사이 통신 규약 버전이 맞지 않으면 그 사실을 알린다.
- C6. KSP가 꺼져 있거나 Mod가 응답하지 않으면 MCP 도구는 수 초 안에 원인이 담긴 오류를 돌려주고 멈추지 않는다.
- C7. Planner가 계획을 제출·조회·중단할 수 있다. 골격에는 시간 대기 단계만 있으며, 이 단계로 된 계획을 제출하면 Coordinator가 단계를 차례로 완료 처리하고 계획을 완료로 끝낸다. 단계 시작·완료·계획 종료가 이벤트로 남아 MCP로 조회된다.
- C8. 새 비행으로 바뀌거나(발사·되돌리기·씬 변경) 활성 기체가 바뀌면 이전 계획은 사유와 함께 끝나고, `get_status`에 이전 비행의 계획 상태가 남지 않는다.
- C9. 새 단계 종류(Coordinator 판정 + Controller 제어)와 그에 대응하는 MCP 도구를, 코어 코드를 고치지 않고 별도 모듈 파일로 추가할 수 있다. 골격의 시간 대기 단계와 MCP 도구가 이 방식으로 구현되어 있다.
