# 조립 점검 결정

### D001 점검 도구를 새 모듈 쌍과 새 기능(assembly-check)으로 둔다
- 단계: spec
- 질문: 조립 점검 도구는 에디터 기체를 읽기만 하는데, 어느 모듈에 두고 어느 기준 spec에 요구를 적을지 정해야 했다. editor 모듈은 이미 3,600줄 가까이 되며 부품 배치·편집을 맡고 있다.
- 선택지:
  - A. 새 모듈 쌍: Mod와 MCP 서버에 점검 전용 모듈을 새로 만들고, 요구는 새 기준 spec `docs/features/assembly-check.md`에 적는다. editor 모듈 코드는 바꾸지 않는다.
  - B. editor 모듈에 추가: editor 모듈 쌍에 점검 도구를 더하고, 요구는 기준 spec `docs/features/editor.md`에 R23부터 더한다.
- 결정: A
- 이유: Planner에게 조립 편집과 구분된 점검 도구를 주고, 계산·점검 로직이 조립 편집 코드에 섞이지 않게 한다(P-C-C 구조에서 도구를 뚜렷이 나누는 원칙). B는 프로젝트가 늘지 않지만 editor 모듈이 계산·점검까지 맡아 커지므로 고르지 않았다.
- 반영: spec.md 기능 줄, C11

### D002 점검 대상은 에디터에서 조립 중인 기체만으로 한다
- 단계: spec
- 질문: 이슈 #41은 "발사 전" 판단만 말한다. 점검 대상을 에디터 기체로 한정할지, 저장된 craft를 불러오지 않고 점검하거나 비행 중 활성 기체까지 넓힐지 정해야 했다.
- 선택지:
  - A. 에디터 기체만: 에디터에서 조립 중인 기체만 점검한다. 저장된 craft는 `editor_load` 뒤 점검한다.
  - B. 에디터 + 저장 craft: craft 이름만으로 불러오지 않고 점검한다. craft 파일로 기체를 따로 구성해야 한다.
  - C. 에디터 + 비행 중 기체: 비행 중 활성 기체의 남은 스테이지도 점검한다. 비행 장면 검증이 더 필요하다.
- 결정: A
- 이유: 조립 → 점검 → 수정 흐름에 맞고 범위가 가장 작다. B는 craft 파일로 기체를 따로 구성하는 구현이 크고 `editor_load`로 같은 일을 할 수 있어서, C는 비행 장면 검증이 늘고 이슈 범위(발사 전)를 넘어서 고르지 않았다.
- 반영: spec.md C1, C9

### D003 Δv·TWR 등 스테이지 값은 게임 내장 계산기와 같은 값으로 한다
- 단계: spec
- 질문: 스테이지별 질량·Δv·TWR·연소 시간을 직접 계산할지, 게임 내장 계산기(`VesselDeltaV`, 에디터 기체의 스테이지별 질량·해면·진공·지정 상황 Δv·TWR·연소 시간을 계산함. 디컴파일로 확인)와 같은 값으로 할지 정해야 했다.
- 선택지:
  - A. 게임 계산기와 같게: 완료 조건을 게임 내장 계산기의 값과 같은 값으로 둔다. 연료 흐름 규칙(크로스피드·분리기)을 다시 만들지 않는다. 계산이 여러 프레임에 걸쳐 끝나므로 끝나기를 기다려야 한다.
  - B. 자체 계산: 질량·Isp·추력으로 직접 계산한다. 연료 흐름 규칙을 다시 구현해야 하고 게임 표시와 다를 수 있다.
- 결정: A
- 이유: 게임 화면의 Δv 표시와 대조할 수 있고 연료 흐름 규칙을 새로 만들어 게임과 어긋나는 일이 없다. B는 계산 시점을 직접 정할 수 있지만 규칙 재구현이 크고 어긋날 위험이 있어 고르지 않았다.
- 반영: spec.md C2, C3

### D004 이슈의 네 가지 점검에 조종 부품 없음·발사 TWR<1·남는 연료·낙하산 없음 경고를 더한다
- 단계: spec
- 질문: 이슈 #41의 구조 점검 네 가지(분리되지 않는 스테이지, 연료 공급 끊김, 엔진 없는 스테이지, 무게중심 비대칭) 말고 더할 경고를 정해야 했다. 경고가 많을수록 발사 전에 더 잡지만 범위와 검증이 늘어난다.
- 선택지(여럿 고를 수 있음):
  - 조종 부품 없음: 명령 모듈·프로브 코어가 없거나, 분리 뒤 남는 쪽에 조종 부품이 없으면 경고한다.
  - 첫 스테이지 TWR<1: 발사 스테이지의 지정 천체 해면 TWR이 1 미만이면 경고한다.
  - 남는 빈 연료: 엔진이 쓰지 못하는 추진제(공급 끊김이 아닌, 엔진 추진제와 맞지 않거나 비율이 맞지 않는 추진제)가 남으면 경고한다.
  - 낙하산 없음: 유인 기체에 낙하산이 없으면 경고한다.
- 결정: 네 가지 모두 더한다.
- 이유: 모두 발사하고 나서야 드러나는 실패(조종 불가, 이륙 불가, 불필요한 질량, 귀환 불가)를 발사 전에 잡아 발사-실패 반복을 줄인다는 이슈 목적에 맞는다. 더하지 않는 선택은 그만큼 실패를 발사 뒤에 알게 되므로 고르지 않았다.
- 반영: spec.md C7

### D005 무게중심 비대칭은 짐벌로 회전력을 상쇄할 수 있는지로 경고한다
- 단계: spec
- 질문: 무게중심이 추력선에서 비켜 있으면 비행 중 기체가 돌지만, 얼마나 비켜야 문제인지는 엔진 짐벌이 그 회전력을 상쇄할 수 있는지에 달렸다. 경고 기준을 정해야 했다.
- 선택지:
  - A. 짐벌 상쇄 가능 여부: 스테이지마다 무게중심과 추력선의 어긋남(거리·각도)을 돌려주고, 그 회전력을 엔진 짐벌 범위로 상쇄할 수 없을 때 경고한다.
  - B. 고정 각도 임계값: 추력선과 무게중심 방향의 각도가 정해진 값(예: 1°)을 넘으면 경고한다.
  - C. 값만 돌려줌: 어긋남(거리·각도)만 숫자로 돌려주고 경고는 내지 않는다.
- 결정: A
- 이유: 기체 크기·짐벌과 상관없이 실제로 회전을 막지 못하는 기체만 잡는다(원인 기준 판단). B는 단순하지만 짐벌이 큰 기체에는 헛경고, 작은 기체에는 놓침이 생겨서, C는 구현이 가장 작지만 경고 목록에서 빠져 Planner가 매번 따로 판단해야 해서 고르지 않았다.
- 반영: spec.md C6

### D006 편집 진행 중 판단은 게임에서 보이는 상태(기체 재로드·시설 전환 중)로 한다
- 단계: spec
- 질문: spec 검토 1회차 지적 1. C10의 "조립 편집이 진행 중이면 `not_ready`"를 판단하려면 editor 모듈의 private 상태(`ShipEditor.pending`, `EditorModule.requestedFacility`)를 봐야 해서, editor 모듈 코드를 바꾸지 않는다는 C11·D001과 모순됐다. 편집 도중(craft 재로드 중) 점검하면 중간 상태 기체의 값을 돌려줄 수 있다.
- 선택지:
  - A. 게임 상태로 판단: C10을 "게임이 기체를 다시 불러오는 중(부품이 아직 에디터에서 시작되지 않음)이거나 시설을 전환하는 중이면 `not_ready`"로 고친다. 정확한 게임 필드는 plan에서 디컴파일로 확인한다.
  - B. editor 상태 공유: C11에 예외를 두어 editor 모듈이 편집 진행 상태를 다른 모듈에 내보내게 한다.
  - C. 조건 빼기: C10에서 편집 진행 중 조건을 뺀다.
- 결정: A
- 이유: editor 모듈을 바꾸지 않는 D001을 지키면서, 편집이 craft 재로드 방식이라 그동안 게임 상태로 드러나는 중간 상태를 막는다. B는 editor 코드와 모듈 간 공유 경로(코어 변경 가능성)가 생겨서, C는 Planner가 도구를 겹쳐 부르면 중간 상태 기체의 틀린 값이 나와서 고르지 않았다.
- 반영: spec.md C10

### D007 손 계산 기대값은 부품 설정의 자원 현재량과 게임 자원 밀도로 만든다
- 단계: spec
- 질문: spec 검토 1회차 지적 3. C3 손 계산의 근거로 든 `editor_list_parts`는 건조 질량과 자원 최대량만 주고 자원 밀도를 주지 않아, 치올콥스키 식의 시작·끝 질량을 만들 수 없었다.
- 선택지:
  - A. 밀도·현재량으로: 연료 질량 = `editor_get_part_settings`의 탱크 현재량 × 게임 자원 밀도(LiquidFuel·Oxidizer 0.005 t/단위), 건조 질량·Isp·추력은 `editor_list_parts`. 스테이지별 진공 Δv·진공 TWR이 1% 안에서 같고, 맨 먼저 작동하는 스테이지 시작 질량이 `editor_get_ship`의 `mass_t`와 같은지 확인한다.
  - B. C2 질량 사용: C2 결과의 시작·끝 질량과 `editor_list_parts` 진공 Isp로 식만 확인한다.
- 결정: A
- 이유: 질량과 Δv를 모두 도구 출력과 독립적으로 확인한다. B는 질량 값이 독립적으로 확인되지 않아 고르지 않았다.
- 반영: spec.md C3

### D008 결과의 스테이지 집합은 editor_get_stages와 같게 한다
- 단계: spec
- 질문: spec 검토 1회차 지적 4. C2 결과에 들어갈 스테이지(`editor_get_stages` 전부 / 게임 계산기 전부 / 엔진 스테이지만)와 엔진 없는 기체의 답이 정해지지 않아 C2·C9의 통과 기준이 없었다.
- 선택지:
  - A. `editor_get_stages`와 같은 집합: 결과의 스테이지 번호 집합을 `editor_get_stages`와 같게 하고, 엔진 스테이지가 아닌 스테이지의 Δv·TWR·연소 시간은 0, 스테이지 대상 부품이 없는 기체는 스테이지 없이 답한다.
  - B. 엔진 스테이지만: 추력이 있는 스테이지만 결과에 넣는다.
- 결정: A
- 이유: 편집 도구의 스테이지 번호와 1:1로 대조되고 분리 스테이지의 질량 변화도 보인다. B는 분리 전용 스테이지가 빠져 질량 흐름이 끊겨 보여 고르지 않았다.
- 반영: spec.md C2

### D009 이슈의 "엔진 없는 스테이지"는 "엔진 없는 부분"(쓸 엔진 없이 연료를 실은 분리 단위)으로 점검한다
- 단계: spec
- 질문: spec 검토 1회차 지적 5. 이슈 #41과 D004는 "엔진 없는 스테이지"라고 썼는데 spec은 "연료가 실린 분리 단위가 떨어질 때까지 그 연료를 쓸 엔진을 갖지 못함"으로 바꿔 썼고, 그 해석이 결정으로 남아 있지 않았다. 문자 그대로 "엔진 없는 스테이지"를 경고하면 분리기·낙하산만 있는 정상 스테이지에도 경고가 난다.
- 선택지:
  - A. 엔진 없는 부분 확정: 지금 해석을 결정으로 남기고 spec "무엇을, 왜"에 이슈 용어와의 대응을 적는다.
  - B. 문자 그대로: 마지막 엔진 스테이지보다 먼저 작동하는데 추력이 0인 스테이지를 경고한다.
  - C. 둘 다: A와 B 경고를 모두 낸다.
- 결정: A
- 이유: 실제 결함(쓰지 못하는 연료를 싣고 다님)만 잡는다. B와 C는 분리 전용 스테이지 같은 흔한 정상 구성에 헛경고를 내서 고르지 않았다.
- 반영: spec.md "무엇을, 왜", C5

### D010 엔진 스테이지는 게임 계산기 기준 실제 추력(연료를 받아 내는 추력)으로 정한다
- 단계: spec
- 질문: spec 검토 2회차 지적 1. 용어 "엔진 스테이지"의 "추력이 0보다 큼"이 엔진의 명목 추력인지, 연료를 받아 실제로 내는 추력인지 정해지지 않아, 연료 공급이 끊긴 엔진만 있는 스테이지에서 C2(Δv 0 여부)·C5(다음 엔진 스테이지)·C6(어긋남 값)·C7(발사 TWR 판정 스테이지)의 판정이 갈렸다.
- 선택지:
  - A. 실제 추력 기준: 게임 계산기 기준으로 연료를 받아 실제로 추력을 내는 작동 엔진이 있는 스테이지를 엔진 스테이지로 한다. 연료가 끊긴 엔진만 있는 스테이지는 엔진 스테이지가 아니며, 그 결함은 연료 공급 끊김 경고가 알린다.
  - B. 명목 추력 기준: 연료와 상관없이 엔진이 작동하는 스테이지를 엔진 스테이지로 한다.
- 결정: A
- 이유: C2 값(게임 계산기)과 같은 기준이라 서로 어긋나지 않는다. B는 Δv가 0인데 엔진 스테이지로 분류되는 모순이 생겨 고르지 않았다.
- 반영: spec.md 용어 "엔진 스테이지"

### D011 TWR은 스테이지 시작 질량 기준으로 한다
- 단계: spec
- 질문: spec 검토 2회차 지적 2. C2 TWR과 C3 손 계산식의 "질량"이 스테이지 시작 질량인지 끝 질량인지 정해지지 않았다. 두 기준의 차이가 1%보다 훨씬 커서 C3(1%)와 C7(발사 TWR<1) 판정이 갈렸다.
- 선택지:
  - A. 시작 질량 기준: C2에 "TWR은 스테이지 시작 질량 기준"을 적고, C3 손 계산식을 "추력 ÷ (시작 질량 × 지정 천체 해면 중력)"으로 고친다.
  - B. 시작·끝 둘 다: 시작 TWR과 끝 TWR을 모두 주고, C3·C7은 시작 기준으로 판정한다.
- 결정: A
- 이유: 발사 가능 여부는 시작 TWR로 정해지고 게임 Δv 표시의 TWR도 같은 기준이다. B는 결과와 검증만 늘고 판단에 더하는 것이 적어 고르지 않았다.
- 반영: spec.md C2, C3

### D012 무게중심 비대칭 판정(C6)의 추력은 엔진 진공 추력으로 한다
- 단계: spec
- 질문: spec 검토 2회차 지적 3. 용어 절의 추력선·짐벌 최대 회전력과 C6 "합성 추력"의 추력이 해면인지 진공인지 정해지지 않았다. 엔진마다 해면/진공 추력 비율이 달라, 종류가 다른 엔진이 섞인 스테이지에서 추력선과 경고 여부가 하나로 정해지지 않았다.
- 선택지:
  - A. 진공 추력: 모든 엔진 스테이지에서 엔진 진공 추력을 쓴다.

### D013 C6과 C3 손 계산의 엔진 추력에 추력 제한 설정을 반영한다

### D015 C3 손 계산에 모든 자원의 질량을 넣는다
- 단계: spec
- 질문: spec 검토 3회차 지적 3. C3 손 계산은 LiquidFuel·Oxidizer만 다루고, 명령 모듈의 MonoPropellant나 SolidFuel 같은 다른 자원 질량을 어떻게 할지 없었다. `mass_t`와 게임 계산기는 모든 자원 질량을 포함해 상단 스테이지 Δv가 1% 넘게 어긋날 수 있었다.

- 결정: A
- 이유: 일반 기체로 바로 확인할 수 있다. B는 시험 조건이 인위적이라 고르지 않았다.
- 반영: spec.md C3

### D019 "엔진 없는 부분"은 분리 단위 안에 쓸 엔진이 없고 다른 엔진에도 공급되지 않는 연료로 정의한다
- 단계: spec
- 질문: D018 대체(엔진 없는 부분 정의 부분만, 배타·C8 시험 기체 구성은 유지). spec 검토 5회차 지적 1. D018로 바꾼 "엔진 없는 부분"(그 연료를 추진제로 쓰는 작동 엔진이 기체 어디에도 없을 때)은 크로스피드 없는 방사형 탱크를 놓쳤다. 코어 엔진이 같은 추진제를 쓰므로 엔진 없는 부분이 아니고, 코어는 추력을 내므로 연료 공급 끊김도 아니어서 이 결함에 어떤 경고가 나는지 정해지지 않았다. D009가 잡으려던 바로 그 결함이다.
- 선택지:
  - A. 공급 불가 연료로 정의: 분리 단위 안에 그 연료를 추진제로 쓰는 엔진이 없고, 떨어지기 전까지 게임 연료 흐름 규칙상 다른 작동 엔진에도 공급되지 않는 연료가 있으면 경고한다. 엔진과 탱크가 같은 분리 단위에 있는데 공급만 끊기면 연료 공급 끊김만 낸다(배타 유지). 크로스피드로 코어에 대는 방사형 탱크는 경고하지 않는다.
  - B. 남는 연료로 넘김: 이 경우를 C7 남는 연료 경고에 넣는다.
- 결정: A (D018의 "엔진 없는 부분" 정의 부분을 대체)
- 이유: 원래 목적(쓸 엔진 없이 실린 연료)을 정확히 잡고 정상 구성(크로스피드 방사형 탱크)에 헛경고를 내지 않는다. B는 남는 연료가 모든 스테이지를 마친 뒤 기준이라 의미가 섞이고 이슈의 "엔진 없는 스테이지" 경고가 사실상 사라져 고르지 않았다.
- 반영: spec.md C5

### D020 C3 시험 기체는 액체 연료 엔진만, 탱크는 기본 적재량으로 한정한다

### D021 "엔진 없는 부분"은 탱크 기준(어떤 작동 엔진에도 공급하지 못하는 연료 탱크)으로 정의한다
- 단계: spec
- 질문: D019 대체. spec 검토 6회차 지적 1. D019의 "분리 단위 안에 그 연료를 추진제로 쓰는 엔진이 없고 …" 정의는 부스터 엔진과 같은 분리 단위에 연료관 없는 방사형 탱크가 있는 경우(엔진은 다른 탱크로 추력을 냄)를 어느 경고도 잡지 않았다. 단위 안에 엔진이 있어 엔진 없는 부분이 아니고, 엔진이 추력을 내 연료 공급 끊김도 아니며, 남는 연료는 모든 스테이지를 마친 뒤 기준이라 중간에 떨어진 연료를 다루지 않는다. 5·6회차에 걸쳐 같은 정의를 고친 원인은 "단위 안 엔진 유무"를 기준으로 삼은 데 있고, 실제 결함은 "어떤 엔진에도 공급되지 않는 연료를 싣고 다님"이다.
- 선택지:
  - A. 탱크 기준 재정의: 연료가 실린 탱크 가운데, 떨어지기 전까지(끝까지 남는 탱크는 모든 스테이지가 끝나기 전까지) 게임 연료 흐름 규칙상 어떤 작동 엔진에도 공급하지 못하는 탱크를 경고한다. 단위 안 엔진 유무는 보지 않는다. 같은 분리 단위에 그 연료를 추진제로 쓰는데 공급이 끊긴 엔진이 있으면 그 탱크는 빼고 연료 공급 끊김 경고 하나로만 알린다.
  - B. 남는 연료로 넘김: C7 남는 연료 범위를 "분리로 떨어지는 부분에 남는 연료"까지 넓힌다.
- 결정: A
- 이유: 결함의 정의 자체를 바로잡아 같은 빈 곳이 다시 생기지 않는다. B는 남는 연료와 엔진 없는 부분의 경계를 다시 흐리고 이슈의 "엔진 없는 스테이지" 경고가 사실상 사라져 고르지 않았다.
- 반영: spec.md C5

### D022 끝까지 남는 루트 쪽 부품 묶음도 하나의 분리 단위로 본다
- 단계: spec

### D023 지정 천체의 해면 값은 게임 Δv 창의 천체를 점검 동안만 바꿔 게임 계산기로 얻고 되돌린다

### D024 계산 완료는 완료 이벤트 시점의 calcsDirty만으로 판정하고 그 자리에서 스냅숏·천체 되돌리기를 한다

### D027 부품의 연료 질량은 계산기 질량에서 연료가 아닌 자원 질량을 빼서 구한다

### D029 C6의 엔진 추력은 공기 흡입 엔진에 지정 천체 해면 추력을 쓰고, 엔진 추력 합이 0인 스테이지는 어긋남 값·경고를 내지 않는다

### D030 추력 엔진과 엔진 스테이지는 연료 소모 기준으로 정하고 추력 값과 상관없게 한다

### D031 스테이지 연료 질량은 D028 연료 기준으로 직접 구하고, 건조 질량은 시작 질량에서 연료 질량을 뺀 값으로 준다
- 단계: plan
- 질문: plan 검토 3회차 지적 1. 엔진이 있는 경로는 계산기 `DeltaVStageInfo.fuelMass`를 그대로 썼는데, 이 값은 비연료 자원(MonoPropellant 등)과 그 스테이지 시작 때 떨어지는 부품의 연료까지 더한다(`DeltaVStageInfo.cs` 598~621·3018~3029행, `DeltaVPartInfo.cs` 1021행). 엔진이 없는 경로는 D028 기준으로 직접 구하므로 같은 `fuel_mass_t` 필드의 뜻이 경로마다 달랐고, `start ≠ dry + fuel`이었다.
- 선택지:
  - A. 연료 직접, 건조 = 시작 − 연료: 두 경로 모두 `fuel_mass_t` = 스테이지 시작 때 남은 부품의 연료 질량(D027·D028) 합, `dry_mass_t` = `start_mass_t − fuel_mass_t`(비연료 자원 포함 연료가 아닌 질량).
  - B. 연료 직접, 건조 = 계산기 값: `fuel_mass_t`만 직접 구하고 `dry_mass_t`는 계산기 `dryMass`(자원 없는 부품 질량)를 쓴다.
- 결정: A
- 이유: `start = dry + fuel`이 늘 성립하고 두 경로의 뜻이 같아 Planner가 값을 비교할 수 있다. B는 "건조"의 일반 뜻(자원 없음)에는 가깝지만 비연료 자원이 있으면 세 값이 맞지 않아 혼동되어 고르지 않았다.
- 반영: plan.md 결정 "스테이지 값", "결과 응답 형식"

### D032 엔진이 있는 스테이지의 연료 질량은 계산기 시작 질량과 같은 부품 집합으로 더한다
- 단계: plan
- 질문: plan 검토 4회차 지적 1. 엔진이 있는 경로에서 `start_mass_t`는 계산기 `startMass`로, 계산기 `DeltaVPartInfo.decoupleStage` 기준 부품 집합(`<= s`를 넣고 `== s`를 뺌, `DeltaVStageInfo.cs` 465·611~620·3030행)에서 나온다. 그런데 `fuel_mass_t`는 결정 "분리 단위·남은 부품"의 집합(`d < s`)으로 더했다. 두 집합이 어긋나면 그 차이가 `dry_mass_t`에 섞여 틀리거나 음수가 되는데, `start = dry + fuel`은 정의상 맞아 드러나지 않는다.

  - B. 진단 항목만 추가: 계산 방식은 그대로 두고 단계 1에서 두 집합을 비교만 한다.
  - C. 시작 질량 직접 계산: 엔진 경로도 시작 질량을 plan 집합으로 구한다.
- 결정: A
- 이유: `dry_mass_t`가 Δv·TWR에 쓰인 시작 질량과 같은 부품 집합에서 나와 늘 맞다. B는 진단하지 않은 분리기 배치에서 조용히 틀릴 수 있고, C는 보고한 시작 질량과 계산기가 Δv·TWR에 쓴 질량이 달라질 수 있으며 C3 판정에도 영향을 주어 고르지 않았다.

- 이유: 사용자가 #41에서 함께 고치기로 했다. 점검 도구의 핫리로드(C11)가 실제 클라이언트에서 성립해야 이 기능이 완료되기 때문이다. A는 #41의 C11을 채우지 못한 채 남겨 고르지 않았다.
