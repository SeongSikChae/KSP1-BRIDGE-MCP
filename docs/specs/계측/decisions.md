# 게임 검증용 계측 결정

### D001 표본 항목에 조종 입력(피치·요·롤)을 넣는다
- 단계: spec
- 질문: 표본에 모을 항목에 조종 입력(기체에 적용된 피치·요·롤 명령값)을 넣을지 정해야 했다. 이슈 #46 범위의 항목 목록(스로틀, 추력, 자세, 각속도, 스테이지, 고도·속도, 질량 등)에는 없지만 #32 기본 제어의 검증에 필요할 수 있다.
- 선택지:
  - A. 넣지 않음: 이슈 범위의 항목만 모은다. 조종 입력이 필요해지면 나중 변경에서 더한다.
  - B. 넣음: 물리 프레임마다 기체에 적용된 피치·요·롤 입력(각 −1~1)을 표본 항목으로 더한다.
- 결정: B
- 이유: 사용자가 말하지 않음
- 반영: spec.md C6

### D002 도구·단계 이름에 `debug_` 접두어를 붙이지 않는다
- 단계: spec
- 질문: 계측 도구와 계획 단계의 이름을 정해야 했다. 기존 검증용 도구는 모두 `debug_*`이다.
- 선택지:
  - A. 접두어 없음: 도구 `measure_start`·`measure_stop`·`get_measurement`, 계획 단계 `measure_start`·`measure_stop`. 계측은 기체를 바꾸지 않는 조회라 `debug_*`와 구분한다.
  - B. `debug_` 접두어: 도구를 `debug_measure_start`처럼 지어 검증용임을 이름으로 드러낸다.
- 결정: A
- 이유: 사용자가 말하지 않음
- 반영: spec.md C1

### D003 계측은 한 번에 하나만 실행하고 끝난 계측은 가장 최근 하나만 보관한다
- 단계: spec
- 질문: 동시에 실행할 수 있는 계측 수와 끝난 계측의 보관 수를 정해야 했다.
- 선택지:
  - A. 하나씩: 한 번에 하나만 실행하고, 끝난 계측은 가장 최근 하나만 보관한다. 실행 중에 다시 시작하면 `bad_request`이다.
  - B. 이름 붙인 여러 계측: 계측에 이름을 붙여 여러 개를 나란히 실행하고 보관한다. 계측마다 메모리 상한을 따로 관리해야 한다.
- 결정: A
- 이유: 사용자가 말하지 않음
- 반영: spec.md "만들지 않는 것", C2, C7

### D004 표본 상한을 계측을 시작할 때 옵션으로 받는다
- 단계: spec
- 질문: 계측 하나가 모을 수 있는 표본 수의 상한을 어떻게 정할지 정해야 했다. 초안은 30,000개(물리 프레임 50 Hz 기준 600초) 고정이어서 그보다 긴 구간은 중간에 `sample_limit`로 끝나고 피할 방법이 없었다.
- 선택지:
  - A. 고정: 모든 계측의 상한을 30,000개로 둔다. 인자가 없다.
  - B. 시작 옵션: `measure_start`(도구·계획 단계)가 표본 상한을 옵션으로 받는다. 생략하면 30,000개이고, 받을 수 있는 최대값을 넘으면 `bad_request`이다.
- 결정: B
- 이유: 사용자가 말하지 않음
- 반영: spec.md C2, C4, C7, C9, C10, C11

### D005 표본 상한의 최대값은 180,000으로 둔다
- 단계: spec
- 질문: D004로 표본 상한을 시작 옵션으로 받게 되면서, 옵션이 받을 수 있는 최대값을 정해야 했다. 상한 없이 받으면 잘못된 값 하나로 게임 메모리를 계속 쓰게 된다.
- 선택지:
  - A. 180,000: 물리 프레임 50 Hz 기준 1시간 분량이다.
  - B. 다른 값: 사용자가 정하는 값으로 둔다.
- 결정: A
- 이유: 사용자가 "일단 180,000으로 하고 나중에 모자라면 늘리는 것을 고려한다"고 말함. B를 고르지 않은 이유는 말하지 않음
- 반영: spec.md C2, C10, C11

### D006 발사대 스로틀은 0이 아니라 `get_flight` 값과 같은지로 판정한다
- 단계: spec
- 질문: spec 검토 1회차 지적 1. 검토 의견: C11 정지 상태 값이 발사대 스로틀의 최소·최대를 0이라고 단정하는데, 발사대 스로틀 초기값은 게임 설정 `PRELAUNCH_DEFAULT_THROTTLE`이 정하고 그 전제가 없다. 왜 문제인지: 설정이 0이 아닌 환경에서는 구현이 맞아도 완료 조건이 불합격이 되어, 조건이 구현이 아니라 검증 환경에 따라 갈린다.
- 선택지:
  - A. `get_flight` 값과 비교: 스로틀은 최소와 최대가 같고 계측 뒤 `get_flight`의 스로틀과 같은지로 판정한다. 추력·조종 입력의 0 판정은 그대로 둔다.
  - B. 설정 전제 추가: "게임 설정 `PRELAUNCH_DEFAULT_THROTTLE`이 0일 때"라는 전제를 붙이고 스로틀 0 판정을 유지한다.
  - 고치지 않음: 스로틀 0 단정을 그대로 둔다.
- 결정: A
- 이유: 사용자가 말하지 않음
- 반영: spec.md C11

### D007 시작·끝 UT를 물리 프레임의 UT로 정의하고 구간 한계를 프레임 5개로 넓힌다
- 단계: spec
- 질문: spec 검토 1회차 지적 5. 검토 의견: C11 구간 경계의 한계가 "5초 + 물리 프레임 간격 최대값 × 3 이하"인데, 코어가 한 물리 프레임에 한 단계만 처리해 정상 구간이 5초 + 프레임 2개 이상 3개 미만이라 한계와 사실상 같고, 끝 UT를 무엇으로 잡는지도 정해져 있지 않다. 왜 문제인지: 맞게 구현해도 프레임 하나 차이로 불합격이 날 수 있다.
- 선택지:
  - A. UT 정의와 한계 확대: 시작 UT는 계측을 시작한 물리 프레임의 UT, 끝 UT는 끝낸 물리 프레임의 UT로 정의하고 한계를 × 5로 넓힌다.
  - B. 한계만 확대: 정의 없이 한계만 × 5로 넓힌다.
  - 고치지 않음: 한계 × 3을 그대로 둔다.
- 결정: A
- 이유: 사용자가 말하지 않음
- 반영: spec.md C2, C3, C11

### D008 각속도와 조종 입력의 부호를 자체 기준으로 정의한다
- 단계: spec
- 질문: spec 검토 1회차 지적 6. 검토 의견: 새로 더하는 각속도(피치·요·롤 축)와 조종 입력(−1~1)은 어느 방향이 +인지 없다. 왜 문제인지: 제어 기능 검증이 용도인데 부호가 없으면 값을 해석할 수 없고, 부호가 뒤집혀도 C11로는 드러나지 않는다.
- 선택지:
  - A. 자체 기준: 각속도는 기수가 올라가는 방향(피치), 기수가 오른쪽으로 가는 방향(요), 오른쪽으로 기우는 방향(롤)이 +이고, 조종 입력은 그 방향의 회전을 명령하는 입력이 +이다. 게임 값의 부호는 plan 단계에서 확인해 맞춘다.
  - B. 게임 값 그대로: 게임이 가진 조종 입력·각속도 값을 그대로 내고, 방향은 도구 설명에 밝힌다.
  - 고치지 않음: 부호 기준을 정하지 않는다.
- 결정: A
- 이유: 사용자가 말하지 않음
- 반영: spec.md 용어, C6

### D009 물리 프레임 콜백은 계측 모듈이 게임의 타이밍 훅에 직접 건다
- 단계: plan
- 질문: 계측 모듈이 물리 프레임마다 표본을 모으려면 콜백이 필요한데, 모듈에는 그 길이 없다(물리 프레임 호출은 코어 `Coordinator`에만 전달된다). 콜백을 어디서 받을지 정해야 했다.
- 선택지:
  - A. 게임 타이밍 훅: 계측이 시작될 때 모듈이 게임의 `TimingManager.FixedUpdateAdd`로 콜백을 걸고, 계측이 끝나거나 Mod를 다시 읽을 때 뗀다. 코어 파일은 바꾸지 않는다. 계획 단계가 실행되는 코어 호출과 이 콜백 사이의 실행 순서는 확인하지 못했고, 순서에 따라 첫 표본이 한 프레임 달라진다.
  - B. 코어에 콜백 추가: 코어 `ModuleContext`에 물리 프레임 구독을 더하고 `Coordinator` 다음에 구독자를 부른다. 코어 파일이 바뀌어 flight-plan 기능도 바뀌므로 spec.md 기능 줄을 고치고 spec 검토와 확인을 다시 한다.
- 결정: A
- 이유: 사용자가 말하지 않음
- 반영: plan.md 결정, 인터페이스·데이터

### D010 자세·스테이지 계산은 계측 모듈이 flight 모듈을 참조해 쓴다
- 단계: plan
- 질문: 표본의 자세(피치·헤딩·롤)와 마지막으로 작동한 스테이지는 `get_flight`와 같은 계산이어야 한다. 그 계산(`Attitude`·`StageRef`·`Vec`)은 flight 모듈에 공개 형식으로 있고 스테이징 아이콘 판정(`FlightSnapshot.IsStaged`) 한 줄만 내부 전용이다. 모듈끼리 참조하는 프로젝트는 지금 없다. 계측 모듈이 이 계산을 어떻게 쓸지 정해야 했다.
- 선택지:
  - A. flight 모듈 참조: 새 계측 프로젝트가 flight 모듈 프로젝트를 참조해 공개 형식을 그대로 쓰고, 아이콘 판정 한 줄은 계측 모듈에 같은 식으로 둔다. flight 모듈 파일은 바꾸지 않는다.
  - B. 아이콘 판정도 공개로 바꿈: A에 더해 flight 모듈의 `IsStaged`를 공개로 바꿔 계측 모듈이 부른다. flight-observation 기능의 파일이 바뀌어 spec.md 기능 줄을 고치고 spec 검토와 확인을 다시 한다.
  - C. 복제: 참조 없이 자세·스테이지 계산을 계측 프로젝트에 복사한다. 같은 계산이 두 벌이 된다.
- 결정: A
- 이유: 사용자가 말하지 않음
- 반영: plan.md 결정, 바꿀 파일·구조

### D011 단계 실패·제출 거절·장면 전환은 게임에서 확인하고 이벤트와 사유의 연결은 단위 테스트한다
- 단계: plan
- 질문: plan 검토 1회차 지적 2. 검토 의견: plan.md 검증 전략에서 다음 동작은 게임 검증에도 단위 테스트에도 없다. 실행 중에 단계 `measure_start`가 오면 `step_failed`, 실행 중인 계측 없이 단계 `measure_stop`이 오면 `step_failed`, 단계의 표본 상한이 틀리면 계획 제출이 `bad_request`, 장면 전환이 `scene_change`·활성 기체 변경이 `vessel_change`로 끝나는 것. 왜 문제인지: 이벤트와 사유의 연결이나 단계 실패 경로가 틀려도 검증을 통과하고, 완료 조건 C4·C9의 그 문장이 확인 없이 완료로 처리된다.
- 선택지:
  - A. 게임 검증과 사유 규칙 테스트: 단계 실패 둘, 제출 거절, 장면 전환(`scene_change`)을 MCP 호출로 게임에서 확인한다. 이벤트에서 사유를 정하는 규칙은 게임에 닿지 않는 함수로 떼어 단위 테스트한다. `vessel_change`는 게임에서 일으키기 어려워 단위 테스트로만 확인한다.
  - B. 단위 테스트만: 단계가 활성 기체 유무를 주입받게 만들어 게임 형식 없이 돌게 하고, 단계와 사유 규칙을 단위 테스트한다. 게임 검증은 그대로 둔다.
  - 고치지 않음: 검증 전략을 그대로 둔다.
- 결정: A
- 이유: 사용자가 말하지 않음
- 반영: plan.md 바꿀 파일·구조, 인터페이스·데이터(흐름), 검증 전략

### D012 활성 기체 변경(`vessel_change`)도 게임에서 확인한다
- 단계: plan
- 질문: D011 일부 대체(선택지 A의 "`vessel_change`는 게임에서 일으키기 어려워 단위 테스트로만 확인한다"). plan 검토 2회차 지적 1. 검토 의견: 로드된 소유 기체 둘을 MCP 호출만으로 만들고 활성 기체를 바꾸는 절차가 이 저장소에 이미 있고 실제 게임에서 수행된 것으로 기록돼 있다(`debug_switch_vessel`, docs/specs/디버그-보강/tasks.md T021·T023). 왜 문제인지: 게임에서 확인하지 못한다는 전제가 틀렸고, 활성 기체 변경 이벤트의 구독이 빠지거나 잘못 걸려도 검증을 통과한다.
- 선택지:
  - A. 게임 검증으로 바꿈: 발사대와 활주로에 기체를 하나씩 올려 로드된 소유 기체 둘을 만들고, 계측을 실행한 채 `debug_switch_vessel`로 활성 기체를 바꿔 사유 `vessel_change`를 확인한다. 사유 규칙의 단위 테스트는 그대로 둔다.
  - 고치지 않음: `vessel_change`는 단위 테스트로만 확인한다는 문장을 그대로 둔다.
- 결정: A
- 이유: 사용자가 말하지 않음
- 반영: plan.md 검증 전략

### D013 조회 응답의 오류 설명 테스트는 tasks.md에만 더하고 plan.md는 그대로 둔다
- 단계: tasks
- 질문: tasks 검토 1회차 지적 1. 검토 의견: plan.md 검증 전략은 사유 `error`를 `RecorderTests`와 조회 응답의 `error` 단위 테스트로 확인한다고 적었는데, tasks.md T013의 테스트 목록과 plan.md의 `MeasureReportTests` 목록에 조회 응답의 오류 설명이 없다. 왜 문제인지: 오류 설명은 게임에서 일으킬 수 없어 단위 테스트가 유일한 확인 수단인데, 작업 목록대로 하면 조회 응답에 오류 설명이 나가는지 어디서도 확인되지 않는다.
- 선택지:

  - B. plan.md 목록도 맞춤: A에 더해 plan.md의 `MeasureReportTests` 목록에도 더한다. plan.md는 확인받은 문서라 plan 검토와 확인을 다시 한다.
  - 고치지 않음: T013 목록을 그대로 둔다.
- 결정: A
- 이유: 사용자가 말하지 않음
- 반영: tasks.md T013
