# MCP·Mod 포트 변경 작업

형식: `- [ ] T001 [P] 설명 (파일 경로) — C번호`
`[P]`: 다른 파일을 고치고 끝나지 않은 작업에 의존하지 않아 다른 작업과 동시에 할 수 있음

## 단계 1: 포트 값 변경

- [x] T001 [P] `DefaultModPort`를 65530, `DefaultServerPort`를 65531로 바꾼다 (src/Shared/Protocol.cs) — C1
- [x] T002 [P] `port`를 65530으로 바꾼다 (src/KspBridge.Mod.Loader/settings.cfg) — C2
- [x] T003 [P] yaml 생성 값 `Port: 65531`, `ModUrl: http://127.0.0.1:65530`으로 바꾼다 (scripts/deploy.ps1) — C3
- [x] T004 [P] `ModUrl` 주석 예시를 `http://127.0.0.1:65530`으로 바꾼다 (src/KspBridge.Server/AppConfiguration.cs) — C4
- [x] T005 [P] 구성도 두 주소, settings.cfg 설명의 기본값, 클라이언트 등록 예시를 새 포트로 바꾼다 (ReadMe.md) — C4

체크포인트: T001~T005에서 바꾼 줄을 읽어 새 값(65530, 65531, `http://127.0.0.1:65530`, `http://127.0.0.1:65531/mcp`)이 정확한지 확인한다(C1~C3). bin·obj·.git을 빼고 `865[01]`를 검색해 spec C4 예외로 둔 곳만 남는다.

## 단계 2: 기준 spec

- [x] T006 기준 spec 틀대로 기준 spec을 새로 만든다. `파일:` 줄에는 T001~T005의 다섯 파일을 적는다. 요구에는 두 기본 포트와 각 값을 정하는 곳을 적고, `docs/specs/골격/`의 루프백 바인딩 요구도 옛 포트 숫자 없이 적는다. 이력에는 이번 작업 한 줄을 적고, 표에 없는 이전 변경은 "기록 없음"으로 둔다 (docs/features/bridge-connection.md) — C6

체크포인트: 파일을 읽어 요구 R번호와 이력 줄이 있다.

## 단계 3: 검증

- [x] T007 `dotnet build KspBridge.slnx`와 `dotnet test KspBridge.slnx`를 실행해 모두 통과하는지 확인한다 (KspBridge.slnx) — C5
- [x] T008 모든 변경 뒤 bin·obj·.git을 빼고 `865[01]`를 다시 검색해, 새 기준 spec을 포함해 spec C4 예외로 둔 곳만 남는지 확인한다 (workspace 전체) — C4
- [x] T009 완료 보고에 사용자가 직접 맞출 세 곳과 새 값을 적고, 동적 포트 대역에서 바인딩에 실패할 때 확인할 명령을 함께 안내한다. 실제 게임·서버를 띄운 연결은 확인하지 않았다는 사실도 적는다 (완료 보고) — C7

체크포인트: 빌드·테스트 성공, 재검색 결과가 C4 예외뿐이다, 보고에 C7 안내와 미확인 사실이 있다.

## 의존 관계

- 단계 1의 작업은 서로 다른 파일을 고쳐 동시에 할 수 있다.
- T006의 `파일:` 줄과 요구는 단계 1의 결과를 적으므로 단계 1 뒤에 한다.
- 단계 3은 모든 변경 뒤에 한다. T008은 T006이 만든 기준 spec까지 검사하므로 T006 뒤에 한다. T009는 T007·T008 결과를 보고에 함께 적으므로 마지막에 한다.
