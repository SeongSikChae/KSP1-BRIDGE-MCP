# 관측: 비행 상태 조회와 계획 진행 표시 결정

### D001 비행 상태 조회는 새 flight 모듈 쌍의 새 도구로 둔다
- 단계: spec
- 질문: 고도·속도·궤도 요소·자세·스테이지·연료·Δv·TWR을 볼 도구를 어디에 둘지 정해야 했다. 지금 `get_status`는 장면과 기체 이름·상황·고도만 준다.
- 선택지:
  - A. 새 flight 모듈: Mod와 MCP 서버에 새 모듈 쌍(`flight`)을 만들고 새 도구(`get_flight`)를 둔다. 코어는 거의 바뀌지 않고 check 모듈처럼 핫리로드로 들어간다. `get_status`는 지금처럼 간단한 요약으로 둔다.
  - B. `get_status` 확장: 코어 `get_status`의 `vessel` 항목을 크게 늘린다. 도구 수는 그대로다.
- 결정: A
- 이유: 기능을 코어 밖 모듈로 더하는 지금 구조(코어와 기능 모듈을 나누고 기능마다 따로 도구를 둠)를 따르고, 핫리로드로 반영된다. B는 코어 코드가 커지고 상태를 볼 때마다 큰 응답을 받게 되어 고르지 않았다.
- 반영: spec.md 무엇을·왜, C1, C12

### D002 계획 진행의 "목표까지 남은 양"은 단계가 직접 보고한다
- 단계: spec
- 질문: `get_plan`에 목표까지 남은 양을 어떻게 보일지 정해야 했다. 목표가 무엇인지는 단계 종류마다 다르다(지금은 `wait`뿐이라 남은 시간).
- 선택지:
  - A. 단계가 직접 보고: 코어 모듈 API에 단계가 진행 정보를 돌려주는 선택적 인터페이스를 더하고 `wait`가 구현한다. 코어 공개 API가 조금 바뀐다. 뒤 이슈(#33·#36)의 단계도 같은 방식으로 남은 양을 보일 수 있다.
  - B. 경과 시간만: 코어는 단계 경과 시간과 timeout까지 남은 시간만 보인다. 단계별 남은 양은 #33에서 정한다.
- 결정: A
- 이유: 남은 양은 단계마다 의미가 달라 그 단계만 계산할 수 있으므로, 단계가 보고하게 하면 코어가 단계 종류를 몰라도 된다. 뒤 이슈의 단계도 같은 틀을 쓴다. B는 이슈 범위의 일부("목표까지 남은 양")를 미루게 되어 고르지 않았다.
- 반영: spec.md C7·C8, C12

### D003 비행 중 Δv·연소 시간·스테이지 TWR은 게임 내장 Δv 계산기 값을 쓴다
- 단계: spec
- 질문: 비행 중 스테이지별 Δv·연소 시간·TWR을 어디서 구할지 정해야 했다.
- 선택지:
  - A. 게임 계산기: `check_ship`과 같이 게임 내장 Δv 계산기 값을 쓴다. 게임 화면의 Δv와 같고 연료 흐름 규칙을 따로 만들 필요가 없다. 계산이 끝나지 않은 순간에는 그렇다고 표시한다.
  - B. 직접 계산: 현재 질량·연료·엔진 Isp로 직접 계산한다. 언제나 즉시 나오지만 크로스피드·분리기 규칙을 다시 만들어야 하고 게임 값과 어긋날 수 있다.
- 결정: A
- 이유: 조립 점검(`check_ship`)과 같은 기준이 되어 발사 전과 비행 중 값을 비교할 수 있고, 연료 흐름 규칙을 다시 만들지 않는다. B는 규칙을 다시 만드는 비용이 크고 게임 값과 어긋날 위험이 있어 고르지 않았다.
- 반영: spec.md C2·C3·C4·C5

### D004 궤도 값 검증을 위해 debug 모듈에 궤도 설정 도구를 더한다
- 단계: spec
- 질문: 궤도 요소·속도 값이 맞는지 실제 게임에서 어떻게 확인할지 정해야 했다. 지금은 조종 단계(#32)가 없어 MCP만으로는 발사대에 서 있는 기체밖에 만들 수 없고, 발사대에서는 궤도가 땅속으로 들어가는 형태라 Ap/Pe·경사각·주기·미래 시각 값을 제대로 확인하기 어렵다.
- 선택지:
  - A. `debug_set_orbit` 추가: debug 모듈에 활성 기체를 지정 궤도로 옮기는 도구를 더한다(게임의 궤도 설정 치트와 같은 기능). 알려진 궤도와 `get_flight` 값을 대조할 수 있고 뒤의 #34·#37·#43 시험에도 쓴다. debug 모듈 코드가 바뀐다.
  - B. 발사대 + 단위 시험: 실제 게임에서는 발사대 값만 확인하고, 궤도 수치 변환은 단위 시험으로만 확인한다. 궤도 값은 실제 게임에서 확인하지 못한다.
  - C. #32 뒤로 미룸: 궤도 값의 실제 확인은 #32가 생긴 뒤에 한다. 이번 완료 조건에서 궤도 값 확인이 빠진다.
- 결정: A
- 이유: 궤도 값을 실제 게임에서 MCP 응답만으로 확인할 수 있고, 뒤 이슈의 시험 준비에도 다시 쓴다. B는 궤도 값을 실제 게임에서 확인하지 못하고, C는 이번 작업의 핵심 값 확인을 미루게 되어 고르지 않았다.
- 반영: spec.md C9·C10·C11·C12

### D005 get_flight 기본 응답은 요약이고 스테이지 표·자원 목록은 요청할 때만 준다
- 단계: spec
- 질문: Planner는 계획을 실행하는 동안 `get_flight`를 10~20초마다 부르게 된다. 스테이지별 Δv 표와 자원 목록까지 늘 받으면 호출마다 응답이 커진다. 응답 범위를 정해야 했다.
- 선택지:
  - A. 기본 요약 + 선택 항목: 기본 응답은 고도·속도·궤도·자세·현재 스테이지와 그 스테이지의 Δv·TWR·전체 Δv 합만 준다. 스테이지별 표와 자원별 연료 목록은 인자로 달라고 할 때만 준다.
  - B. 늘 전부: 인자 없이 항상 모든 항목을 준다.
- 결정: A
- 이유: 자주 부르는 호출이 가볍고, 자세한 값은 필요할 때만 받는다. B는 단순하지만 단이 많은 기체일수록 매 호출 응답이 커져 고르지 않았다.
- 반영: spec.md C2·C5·C6

### D006 스테이지는 두 번호(마지막으로 작동한·다음)로 주고, 기본 응답 Δv는 기준 스테이지로 정한다
- 단계: spec
- 질문: spec 검토 1회차 지적 2. 검토 의견: C2의 "현재 스테이지 번호"가 마지막으로 작동한 스테이지인지, 다음에 작동할 스테이지인지, 연소 중인 스테이지인지 정해지지 않았고, 발사 전 값과 검증 조건이 없다. 왜 문제인지: 게임 `currentStage`는 마지막으로 작동한 스테이지이며, 발사 전에는 스테이지 수와 같아 실제 스테이지 번호가 아니다. 그대로 쓰면 그 스테이지의 Δv를 찾을 수 없고, 모든 호출에 나오는 핵심 값이 구현마다 달라진다.
- 선택지:
  - A. 두 번호 + Δv 기준 정의: 마지막으로 작동한 스테이지(발사 전 `null`)와 다음 스테이징으로 작동할 스테이지(없으면 `null`)를 따로 둔다. 기본 응답의 Δv·연소 시간·TWR은 발사 뒤에는 마지막으로 작동한 스테이지, 발사 전에는 다음 스테이지 기준이다. C11에 발사대에서 이 값이 스테이지별 표의 같은 스테이지 값과 같다는 확인을 더한다.
  - B. `currentStage` 그대로: 게임 값을 그대로 내보내고 설명만 붙이며, Δv는 그 값 기준으로 둔다.
  - 고치지 않음: C2를 그대로 둔다.
- 결정: A
- 이유: Planner가 게임 내부 규칙을 몰라도 그대로 쓸 수 있고, 발사대에서 검증할 수 있다. B는 발사 전에 Δv 대상이 없는 스테이지 번호가 되어 Planner가 직접 해석해야 하므로 고르지 않았다. 고치지 않으면 핵심 값이 모호하게 남는다.
- 반영: spec.md 용어(마지막으로 작동한 스테이지·다음 스테이지·기준 스테이지), C2, C11

### D007 최대 TWR을 빼고 스로틀 100% TWR은 스테이지 TWR로 본다
- 단계: spec
- 질문: spec 검토 1회차 지적 3. 검토 의견: C2의 최대 TWR이 대기압 기준인지 진공 기준인지, "작동 중인 엔진"이 무엇인지, 발사 전 값이 무엇인지 정해지지 않았다. 왜 문제인지: 값의 뜻이 정해지지 않아 Planner가 판단에 쓸 수 없고 검증 기준도 없다. 한편 C2에는 이미 게임 계산기가 스로틀 100%·현재 위치 기준으로 계산하는 스테이지 TWR이 있어 뜻이 겹친다.
- 선택지:
  - A. 최대 TWR 빼기: C2 "질량·추력"에서 최대 TWR을 지운다. 현재 추력·현재 TWR은 남긴다.
  - B. 기준 정의: 최대 TWR을 "이미 작동한 엔진의 추력 제한 반영 최대 추력(현재 위치 대기압 기준) ÷ (질량 × 현재 위치 중력), 발사 전 0"으로 정의한다.
  - 고치지 않음: C2를 그대로 둔다.
- 결정: A
- 이유: 스테이지 TWR과 겹치고, 따로 정의하면 계산과 검증만 늘어난다. B는 겹치는 값을 하나 더 만들어 고르지 않았다. 고치지 않으면 뜻 없는 값이 남는다.
- 반영: spec.md C2, 용어(게임 계산기)

### D008 debug_set_orbit은 궤도 적용과 상황 변경을 확인한 뒤 응답한다
- 단계: spec
- 질문: spec 검토 1회차 지적 5. 검토 의견: C9·C10에 `debug_set_orbit`이 이동을 마친 뒤 응답하는지 접수만 하고 응답하는지, 직후 `get_flight` 값과 "옮긴 뒤" 시점이 정해지지 않았다. 왜 문제인지: 게임의 궤도 설정 함수는 즉시 실행되지만 기체 상황 값은 몇 프레임 늦게 바뀔 수 있어, 바로 부른 `get_flight`가 이전 상황을 주면 C9를 판정할 수 없다.
- 선택지:
  - A. 적용 확인 뒤 응답: 도구는 궤도가 적용되고 상황이 `ORBITING`으로 바뀐 것을 확인한 뒤 응답하며, 응답 뒤 첫 `get_flight`부터 C9를 채운다. 10초 안에 끝나지 않으면 `not_ready`와 이유를 준다. `check_ship`처럼 시작 뒤 결과를 되묻는 대기 처리가 필요하다.
  - B. 접수 뒤 `not_ready`: 접수만 응답하고, 궤도 적용이 끝날 때까지 `get_flight`는 `not_ready`를 준다. C10 `not_ready` 경우에 "궤도 이동 중"을 더한다.
  - 고치지 않음: C9·C10을 그대로 둔다.
- 결정: A
- 이유: 장면·상태 변경 직후의 실패를 재시도로 우회하지 않는다는 원칙과 맞고, 호출하는 쪽이 기다릴 필요가 없다. B는 호출하는 쪽이 다시 불러야 하고 `get_flight`가 debug 모듈 상태를 알아야 해 모듈끼리 연결이 생기므로 고르지 않았다. 고치지 않으면 C9를 판정할 수 없다.
- 반영: spec.md C9

### D009 천체 상수는 get_flight 요청 항목(천체 정보)으로 주고, 발사대 좌표는 stock 값을 고정값으로 적는다
- 단계: spec
- 질문: spec 검토 2회차 지적 1. 검토 의견: C11은 천체 반지름·자전 주기·중력 상수·발사대 좌표를 비교 기준으로 쓰는데, 이 값을 돌려주는 MCP 도구가 없다. 왜 문제인지: 저장소의 검증 원칙(MCP 응답만으로 확인)으로는 발사대 궤도 속도와 지정 궤도 확인 항목 전체를 판정할 수 없고, 바깥에서 아는 값에 기대게 된다.
- 선택지:
  - A. 천체 정보 요청 항목: `get_flight` 요청 항목(C5)에 지금 천체의 반지름·GM·자전 주기·대기 상한·영향권 반경을 더하고, C11 계산은 이 값으로 한다. 발사대 좌표는 stock 발사대 값을 spec에 고정값으로 적되, 그 값은 plan에서 게임 데이터로 확인한다.
  - B. 상수를 spec에 고정: Kerbin 반지름·GM·자전 주기·발사대 좌표를 spec에 숫자로 적는다.
  - 고치지 않음: C11을 그대로 둔다.
- 결정: A
- 이유: 판정이 MCP 응답만으로 되고, 천체 상수는 #36 원궤도화 계산 등에서 Planner도 쓴다. B는 Planner가 여전히 천체 값을 얻을 수 없고, 다른 천체로 확인할 때마다 값을 다시 적어야 하므로 고르지 않았다. 고치지 않으면 C11 세 항목을 판정할 수 없다.
- 반영: spec.md C5, C11

### D010 질량 비교는 무인 stock 기체 ComSat Lx로 한다
- 단계: spec
- 질문: spec 검토 2회차 지적 5. 검토 의견: C11의 질량 비교 기준인 에디터 `mass_t`가 비행 중 질량과 같은 항목을 더하는지 근거가 없고, 0.01 t 허용치는 승무원 한 명보다 작을 수 있다. 왜 문제인지: 디컴파일 결과 게임의 기체 질량 함수(`ShipConstruct.GetShipMass`)는 승무원 목록을 받을 때만 승무원·인벤토리 질량을 더하는데, 에디터 `mass_t`는 목록 없이 부른다. 승무원 3명을 태워 발사하는 `Kerbal X`는 기능이 맞아도 반드시 어긋난다.
- 선택지:
  - A. 무인 기체로 질량 비교: 질량 비교만 무인 stock 기체 `ComSat Lx`(프로브 코어)를 발사대에 올려, 같은 craft의 에디터 `mass_t`와 0.01 t 안에서 같은지 본다. 검증 때 발사가 한 번 는다.
  - B. 승무원 질량을 더한 기준: 기준을 "에디터 `mass_t` + 승무원 수 × 게임 승무원 질량 + 승무원 인벤토리 질량"으로 바꾼다. 승무원 수·인벤토리 질량을 MCP로 얻는 요구가 더 필요하다.
  - 고치지 않음: C11 질량 항목을 그대로 둔다.
- 결정: A
- 이유: 승무원이 없어 두 값이 같아야 하고, 지금 도구의 응답만으로 판정된다. B는 승무원 수·인벤토리 질량을 MCP로 얻을 수 없어 판정할 수 없으므로 고르지 않았다. 고치지 않으면 기능이 맞아도 C11이 실패한다.
- 반영: spec.md C11

### D011 계산기 값 비교(C4)도 무인 stock 기체 ComSat Lx로 한다
- 단계: spec

### D013 대기가 없는 천체의 Pe 하한은 게임이 쓰는 지형 최고 높이(radiusMax − radius)로 하고, 모르면 거절한다

- 결정: A
- 이유: 게임이 실제로 쓰는 값이고 stock 밖 천체에도 맞으며, 값을 모를 때는 안전하게 거절한다. B는 stock에서만 맞고 값의 출처를 따로 확인·관리해야 하므로 고르지 않았다. 고치지 않으면 지형을 뚫는 궤도를 받아들일 수 있다.
- 반영: plan.md 결정(궤도 설정 검증), 검증 전략 C9·C10

### D016 스테이징 전 판정은 상황 PRELAUNCH와 currentStage > 부품 최대 번호를 함께 본다
- 단계: plan
- 질문: plan 검토 2회차 지적 1. 검토 의견: plan은 `c > m`(`c`는 `vessel.currentStage`, `m`은 스테이지가 있는 부품의 최대 번호)이면 아직 스테이징하지 않았다고 본다. 그런데 분리 스테이지가 작동하면 `c` 이상인 부품이 떨어지고, 게임은 빈 스테이지를 지우며 `currentStage`를 줄인다(`StageManager.DeleteEmptyStages`). 그러면 분리 뒤에도 `c = m + 1` 꼴이 생긴다. 왜 문제인지: 비행 중 분리 뒤 마지막으로 작동한 스테이지가 `null`로 나오고 기준 스테이지가 다음 스테이지로 바뀌어, 확인받은 spec D006·C2를 어긴다. 발사대 확인만으로는 드러나지 않는다.
- 선택지:
  - A. 상황 `PRELAUNCH`로 판정: 아직 스테이징하지 않았는지를 게임 상황 `PRELAUNCH`로 가른다. 근거는 디컴파일로 확인해 적고, 스테이징 뒤 게임 확인은 #32로 넘긴다.
  - B. 스테이징 이벤트 기억: 모듈이 스테이징 게임 이벤트를 받아 기체별로 기억한다. 핫리로드·저장된 비행 불러오기에서 기록이 사라진다.
  - 고치지 않음: `c > m` 규칙을 둔다.
- 결정: A. 디컴파일 확인 결과에 맞춰 "`PRELAUNCH`이고 `c > m`"으로 적용한다. `Vessel.updateSituation`은 착지 상태이고 지표 속도 2.5 m/s 이하인 동안 `PRELAUNCH`를 유지한다. 그래서 발사대에서 엔진을 점화했지만 고정대가 잡고 있는 상태(이미 스테이징함, `c ≤ m`)도 `PRELAUNCH`이며, `c > m`을 함께 봐야 그 상태를 스테이징 뒤로 판정한다.
- 이유: 분리 뒤(상황이 `PRELAUNCH`가 아님)에도 맞고, 핫리로드·저장 불러오기와 상관없는 게임 상태만 쓴다. B는 기록이 사라지는 경우가 많아 고르지 않았다. 고치지 않으면 분리 뒤 값이 spec을 어긴다.
- 반영: plan.md 결정(스테이지 판정), 오류·위험(스테이징 뒤 스테이지 판정)

### D017 지형 위 고도는 게임 지형 높이 함수로 직접 계산한다
- 단계: plan

  - 고치지 않음: `radarAltitude`를 그대로 쓴다.
- 결정: A
- 이유: 고도와 상관없이 spec 정의대로 맞고 비용이 작다. B는 높은 고도 값이 틀린 채 남으므로 고르지 않았다. 고치지 않으면 C2를 채우지 못한다.
- 반영: plan.md 결정(지형 위 고도)

### D018 마지막으로 작동한 스테이지는 "부품이 남아 있는" 스테이지로 정의한다
- 단계: plan
- 질문: D016 대체, D006 일부 대체(마지막으로 작동한 스테이지·기준 스테이지의 정의). plan 검토 3회차 지적 1. 검토 의견: D016 규칙("상황 `PRELAUNCH`이고 `c > m`일 때만 스테이징 전")에서는, 스테이징 없이 `debug_set_orbit`으로 궤도에 옮긴 기체(`Aeris 3A`)의 마지막으로 작동한·기준 스테이지가 부품이 없는 번호(`m + 1`)가 되고 Δv가 빈다. `SetShipOrbit`은 `currentStage`를 바꾸지 않기 때문이다. 왜 문제인지: 게임은 분리 뒤 빈 스테이지를 지우고 `currentStage`를 줄이므로(`StageManager.DeleteEmptyStages`), "분리로 마지막 작동 스테이지의 부품이 모두 사라진 기체"와 "한 번도 스테이징하지 않은 기체"를 게임 상태로 구분할 수 없다. 그래서 확인받은 spec의 정의("발사 뒤에는 마지막으로 작동한 스테이지")는 게임 상태만으로 지킬 수 없다. spec을 고치는 의도 변경이다.
- 선택지:
  - A. spec을 "남은 스테이지" 기준으로: 마지막으로 작동한 스테이지를 "가장 최근에 작동했고 그 부품이 아직 기체에 남아 있는 스테이지, 남아 있지 않으면 없음"으로, 기준 스테이지를 "마지막으로 작동한 스테이지가 있으면 그것, 없으면 다음 스테이지"로 바꾼다. 판정은 `c ≤ m`이면 `c`, 아니면 `null`(상황은 보지 않음). 계산기에 그 번호 값이 없으면 Δv·연소 시간·TWR은 0.
  - B. 스테이징 이벤트 기억: spec을 두고 모듈이 스테이징 게임 이벤트를 받아 기체별로 마지막 작동 번호를 기억한다. 핫리로드·저장된 비행 불러오기에서 기록이 사라진다.
  - 고치지 않음: D016 규칙을 둔다.
- 결정: A
- 이유: 게임 상태만으로 언제나 판정되고, 분리 뒤 기준 스테이지가 다음에 작동할 스테이지가 되어 남은 엔진의 Δv를 보인다. B는 기록이 사라지는 경우가 남아 틀릴 수 있으므로 고르지 않았다. 고치지 않으면 스테이징 없이 옮긴 기체에서 spec 정의와 다른 값이 나온다.
- 반영: spec.md 용어(마지막으로 작동한 스테이지·다음 스테이지·기준 스테이지), plan.md 결정(스테이지 판정)·오류·위험

### D019 스테이지 판정은 currentStage 산술 대신 부품 작동 상태로 한다
- 단계: plan
- 질문: D018 일부 대체(plan 판정 규칙). plan 검토 4회차 지적 1. 검토 의견: D018의 plan 판정("`c ≤ m`이면 `c`, 아니면 `null`", `c`는 `vessel.currentStage`, `m`은 스테이지 부품의 최대 번호)은 분리 뒤 `c = m + 1`이라는 전제에 기댄다. 그런데 `StageManager` 디컴파일을 따라가면 작동한 스테이지 부품이 모두 떠난 뒤 빈 맨 위 그룹이 지워지며 `DecrementCurrentStage`가 불려 `c = m`이 될 수 있다. 왜 문제인지: 그러면 한 번도 작동하지 않은 `m`이 마지막으로 작동한 스테이지로, 다음 스테이지가 `m − 1`로 나와 spec 용어 정의·C2를 어긴다. 분리 뒤 `currentStage` 값은 디컴파일만으로 확정할 수 없고, 이번 작업에는 게임에서 스테이징할 수단이 없어 확인되지 않은 전제로 남는다. 단위 시험도 같은 전제로 입력을 만들어 드러나지 않는다.
- 선택지:
  - A. 부품 작동 상태로 판정: 마지막으로 작동한 스테이지는 스테이지 부품 가운데 상태가 `ACTIVE`·`DEACTIVATED`인 부품이 있으면 `c`, 없으면 `null`. 다음 스테이지는 상태가 `IDLE`인 스테이지 부품의 최대 번호, 없으면 `null`. 근거(`Part.activate` → `force_activate`가 `ACTIVE`로 바꿈)를 plan에 적고 시험 입력도 그 근거로 만든다. spec은 그대로.
  - B. debug 스테이징 도구 추가: 다음 스테이지를 작동하는 debug 도구를 더해 분리 뒤 값을 게임에서 확인한다. spec 범위가 바뀌는 의도 변경이다.
  - C. 미확인으로 두고 #32에서 확인: 지금 규칙을 두고 근거 문장을 "미확인"으로 고친다.
  - 고치지 않음: plan을 그대로 둔다.
- 결정: A
- 이유: `currentStage`를 줄이는 동작과 상관없이 맞고, 디컴파일로 확인한 게임 동작(작동 시 부품 상태가 `ACTIVE`가 됨, 작동한 부품이 남으면 맨 위 그룹이 지워지지 않음)에만 기댄다. B는 #32 범위(스테이징)를 당겨 오고 spec 검토부터 다시 해야 해 비용이 크므로 고르지 않았다. C는 확인하지 않은 전제로 설계하게 되어 고르지 않았다. 고치지 않으면 분리 뒤 값이 spec과 다를 수 있다.
- 반영: plan.md 결정(스테이지 판정)

### D020 "그 스테이지의 부품"은 스테이징 아이콘이 있는 부품으로 정의한다
- 단계: plan
- 질문: D018 일부 대체(스테이지 부품 정의), D019 일부 대체(근거 문장). plan 검토 5회차 지적 1. 검토 의견: 스테이지 그룹이 비었는지는 부품이 아니라 스테이지 아이콘으로 정해진다(`StageManager.DeleteEmptyStages`는 `Icons.Count == 0`인 그룹을 지움). 그런데 분리기는 분리 뒤 기체에 남아도 스스로 아이콘을 지우고 스테이징을 끈다(`ModuleDecouple.OnDecouple` → `ModuleDecouplerBase.LateUpdate` → `Part.UpdateStageability`). 그래서 분리기가 남는 기체(예: 루트가 분리기 아래쪽인 조립)에서 그 스테이지를 작동하면 plan 판정(D019, 아이콘 있는 작동 부품 기준)은 `null`을 낸다. 확인받은 spec 정의("스테이지 번호가 그 스테이지 이상인 부품이 남아 있으면 남은 것으로 봄")로는 그 스테이지 번호여야 한다. 왜 문제인지: spec 정의가 게임 스테이지 표시(아이콘)에 없는 부품까지 세므로, 그룹이 지워져 `currentStage`가 바뀐 뒤에는 그 번호를 게임 상태로 믿을 수 있게 구할 수 없다. D019의 근거("작동한 부품이 남으면 그룹이 지워지지 않음")도 이 경우 틀렸다.
- 선택지:
  - A. spec을 스테이지 표시 기준으로: spec 용어 "그 스테이지의 부품"을 "스테이지 번호가 그 스테이지 이상이고 스테이징 아이콘이 있는 부품(게임 스테이지 표시에 남는 부품). 분리를 마친 분리기처럼 아이콘이 없어진 부품은 세지 않는다"로 바꾼다(의도 변경). plan 규칙은 그대로 두고 근거를 "아이콘 있는 작동 부품이 남으면 그룹이 지워지지 않아 `c`가 그대로"로 바로잡는다.
  - B. plan 규칙을 spec대로 넓힘: 아이콘 있는 작동 부품이 있으면 `c`, 없고 아이콘 없는 작동 부품만 남으면 그 부품들의 최소 번호로 한다. spec은 그대로.
  - 고치지 않음: plan·spec을 그대로 둔다.
- 결정: A
- 이유: 게임 상태로 언제나 정확히 판정되고, Planner가 보는 값이 게임 화면의 스테이지 표시와 같다. B는 오래된 스테이지의 분리기만 남은 경우 여전히 spec과 달라지고 규칙이 복잡해지므로 고르지 않았다. 고치지 않으면 분리기가 남는 기체에서 값이 spec과 다르다.
- 반영: spec.md 용어(마지막으로 작동한 스테이지), plan.md 결정(스테이지 판정)

### D021 이슈의 "오류 코드 일관 적용"은 새·바뀌는 도구에 적용하고 기존 도구는 바꾸지 않는다

### D023 오류 코드 목록에 submit_wait·reload를 더하고 editor·check 도구는 기준 spec 규칙으로 적는다

- 결정: A. 승인 때는 D022 선택지 A 문구를 그 자리에서 맞추기로 했으나, 사용자가 고른 결정은 덧붙이기만 한다는 규칙(12회차 지적 1과 같은 이유)에 따라 D022는 원문대로 두고 이 절로 적었다.
- 이유: 목록이 서버 도구 전부(32개)를 빠짐없이 덮고, `submit_wait` 응답 변경이 의도한 것으로 드러난다. 고치지 않으면 두 도구의 처리를 구현에서 임의로 정하게 된다.
- 반영: spec.md 무엇을·왜(오류 코드 일관 적용 문단), C7

### D025 발사대 지형 위 고도는 범위 대신 두 기체의 발사대 지형 높이 일치로 확인한다
- 단계: 구현
- 질문: 실제 게임 검증(T044)에서 spec C11 발사대 항목 "지형 위 고도는 0~30 m"가 stock `Kerbal X`에서 31.17 m로 어긋났다. 기체 고도의 기준점이 루트 부품(맨 위 캡슐, craft 좌표로 기체 바닥에서 약 23.5 m)이라 값은 게임 상태대로 맞고, 두 기체의 "해발 고도 − 지형 위 고도"(발사대 지형 높이)는 `ComSat Lx` 80.985 − 16.200 = 64.785 m, `Kerbal X` 95.955 − 31.170 = 64.785 m로 같았다. 확인받은 spec의 범위 기대값이 틀린 것이라 의도 변경이다.
- 선택지:
  - A. 두 기체의 지형 높이 일치: "지형 위 고도는 0보다 크고, 발사대에 올린 두 기체(`ComSat Lx`·`Kerbal X`)의 해발 고도 − 지형 위 고도가 0.5 m 안에서 같다"로 바꾼다.
  - B. 범위를 넓힘: "0~40 m"로 바꾼다.
- 결정: A
- 이유: 기체 크기와 상관없이 지형 높이 계산이 맞는지를 확인한다. B는 기체에 따라 또 어긋날 수 있고 계산이 맞는지는 확인하지 못하므로 고르지 않았다.
- 반영: spec.md C11, docs/features/flight-observation.md R8, tasks.md T043·T044, plan.md 검증 전략 C11

### D026 자원 목록 확인은 craft 적재량(에디터 부품 설정 합계)과 대조한다
- 단계: 구현
- 질문: 실제 게임 검증(T044)에서 spec C11 발사대 항목 "자원 목록의 자원마다 현재량이 최대량과 같다"가 stock `Kerbal X`에서 어긋났다(`Ablator` 400/800). craft 파일에 `Ablator`가 `amount = 400`, `maxAmount = 800`으로 저장되어 있어 값은 게임 상태 그대로이고, 나머지 자원(LiquidFuel·Oxidizer·MonoPropellant·ElectricCharge)은 가득이었다. 확인받은 spec의 기대값이 틀린 것이라 의도 변경이다.
- 선택지:
  - A. craft 적재량 기준: "무인 stock `ComSat Lx`의 자원 목록이 같은 craft를 에디터에 불러온 `editor_get_part_settings` 자원 현재량·최대량의 자원별 합계와 같다"로 바꾸고, tasks T043에 부품마다 그 호출을 더한다.
  - B. 연료만 가득: "LiquidFuel·Oxidizer는 현재량 = 최대량, 모든 자원은 0 ≤ 현재량 ≤ 최대량"으로 바꾼다.
- 결정: A
- 이유: 기체에 실제로 실린 양과 직접 대조해 합계 계산이 맞는지 확인한다. B는 비용이 작지만 합계가 실제 적재량과 맞는지는 확인하지 못하므로 고르지 않았다.
- 반영: spec.md C11, docs/features/flight-observation.md R8, tasks.md T043, plan.md 검증 전략 C11

### D027 자원 합계 대조에 반올림 허용치를 두고 ElectricCharge 현재량은 범위로 본다
- 단계: 구현
- 질문: D026 일부 대체(자원 대조의 허용치와 ElectricCharge 처리). spec 검토 16회차 지적 1. 검토 의견: D026의 자원 합계 대조에 허용 오차가 없다. `editor_get_part_settings`는 부품마다 자원량을 소수 셋째 자리로 반올림하고(`PartSettings`·`PartCatalog.Round`), `get_flight`는 반올림하지 않은 합계를 돌려주므로 미세하게 어긋날 수 있다. 비행 장면에서는 탐사 코어가 `ElectricCharge`를 쓰고 태양 전지판이 충전해 발사 직후에도 에디터 값과 달라질 수 있다. 왜 문제인지: 정확히 같기를 요구하면 기능이 맞아도 T043에서 어긋나 의도 변경이 또 생기고, 통과 기준을 검증하는 사람이 임의로 정하게 된다.
- 선택지:
  - A. 허용치 + ElectricCharge 따로: 자원마다 최대량은 합계와 0.001 × (그 자원을 가진 부품 수) 안에서 같고, 현재량은 `ElectricCharge`를 뺀 자원이 같은 허용치 안에서 같다. `ElectricCharge` 현재량은 0 이상 최대량 이하다.
  - B. 최대량만 대조: 모든 자원을 최대량만 같은 허용치로 대조한다.
  - 고치지 않음: 허용치 없이 둔다.
- 결정: A
- 이유: 반올림과 전력 소모에 흔들리지 않으면서 현재량 합계 계산도 확인한다. B는 현재량 합계가 맞는지 확인하지 못하므로 고르지 않았다. 고치지 않으면 기능이 맞아도 어긋날 수 있다.
- 반영: spec.md C11, docs/features/flight-observation.md R8

### D028 기준 spec에는 확인받은 spec의 요구만 두고 설계 세부(롤 부호·경도 범위)는 plan에 둔다
- 단계: 구현
- 질문: spec 검토 18회차 지적 2. 검토 의견: 기준 spec(`docs/features/flight-observation.md`)의 용어 "지표 기준 자세"에 "오른쪽 날개가 내려가면 +"(롤 부호)가, R2 위치·고도에 "경도 −180~180"이 들어 있다. 둘 다 plan·tasks에서 정한 설계 세부로, 사용자가 확인한 spec 용어·C2에는 없다. 왜 문제인지: 확인받은 spec과 기준 spec의 요구가 갈라져, 기준 spec 반영이 이 작업의 변경을 옮긴 것인지 spec을 거치지 않은 요구 추가인지 판정할 수 없다. 특히 롤 부호는 plan이 "이번에는 단위 시험으로만 확인"으로 정했는데 완료 조건처럼 적혔다.
- 선택지:
  - A. 기준 spec에서 빼기: 두 내용을 기준 spec에서 빼 spec 문구와 같게 맞춘다. 설계 세부는 plan에 남는다.
  - B. spec에 더하기: spec 용어·C2에 두 내용을 더한다(의도 변경, spec 검토·확인과 뒤 단계 다시).
  - 고치지 않음: 그대로 둔다.
- 결정: A
- 이유: 확인받은 요구만 기준 spec에 남고 설계는 plan이 맡는다. B는 의도 변경 비용이 크고, 롤 부호는 이번 작업에서 게임으로 확인할 수단이 없어 완료 조건으로 두기 어려우므로 고르지 않았다. 고치지 않으면 기준 spec의 근거가 둘로 갈린다.
- 반영: docs/features/flight-observation.md 용어·R2
