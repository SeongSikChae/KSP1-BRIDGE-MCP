# Debug 보강: 활성 기체 전환과 저장·불러오기 결정

### D001 활성 기체 전환은 로드된 기체(`Vessel.loaded`, 레일 위 포함)만 받는다
- 단계: spec
- 질문: 활성 기체 전환 도구가 어느 기체까지 전환 대상으로 받을지 정해야 했다. 게임은 로드된 기체(`Vessel.loaded`, 레일 위 포함. 가까이 있는 분리된 단 등)로는 장면을 다시 불러오지 않고 바로 바꾸며, 이때 활성 기체 변경 이벤트가 나서 코어가 계획을 `vessel_change`로 끝낸다. 로드되지 않은(멀리 있는) 기체로 바꾸면 게임이 저장한 뒤 비행 장면을 다시 불러오므로 계획은 `new_flight`로 끝난다.
- 선택지:
  - A. 로드된 기체만: 지금 로드된 기체만 받고, 로드되지 않은 기체는 이유와 함께 `bad_request`로 거절한다. 장면 재로드 경로가 없다.
  - B. 모든 기체: 저장 파일에 있는 모든 기체를 받는다. 로드된 기체는 바로 바꾸고, 먼 기체는 장면을 다시 불러오며 호출하는 쪽이 `get_status`로 준비를 확인한다. 두 경로와 각각의 오류·검증이 늘어난다.
- 결정: A
- 이유: 이슈의 핵심인 `vessel_change` 중단 경로 검증과 분리된 단으로의 전환에 충분하고 구현 범위가 작다. B는 먼 기체 전환이 이번 이슈 목표에 필요하지 않은데 경로와 검증이 늘어나 고르지 않았다. 먼 기체 전환은 필요해지면 따로 더한다.
- 반영: spec.md 무엇을·왜, C2·C3

### D002 기체 목록은 별도의 읽기 전용 도구로 준다
- 단계: spec
- 질문: 전환할 기체를 고르려면 다른 기체 목록이 필요한데 지금 도구(`get_status`·`get_flight`)는 활성 기체만 보인다. 목록을 어떤 도구로 줄지 정해야 했다.
- 선택지:
  - A. 별도 목록 도구: 읽기 전용 `debug_list_vessels`를 더해 기체마다 id·이름·종류·로드 여부·활성 기체와의 거리 등을 준다. 전환 도구는 id로 대상을 받는다. 도구가 하나 늘어난다.
  - B. 전환 도구가 목록도: `debug_switch_vessel`을 대상 없이 부르면 목록을 돌려주고, 대상을 주면 전환한다. 도구 수는 그대로지만 한 도구의 동작이 인자에 따라 갈린다.
- 결정: A
- 이유: 조회와 기체를 바꾸는 동작을 나눠, 목록만 보려다 기체가 바뀌는 일이 없고 도구를 기능별로 나누는 지금 구성과 맞는다. B는 조회와 변경이 한 도구에 섞여 도구 이름만 보고 동작을 알기 어려워 고르지 않았다.
- 반영: spec.md 무엇을·왜, C1

### D003 상태 저장·불러오기는 이름 있는 저장으로 받고 이름을 생략하면 퀵세이브 파일을 쓴다
- 단계: spec
- 질문: 시험 비행을 반복하려고 상태를 저장·복원하는 방식을 정해야 했다. 게임 퀵세이브는 `quicksave` 파일 하나라 시험 지점을 여럿 두면 덮어쓴다.
- 선택지:
  - A. 이름 있는 저장: `debug_save(name)`·`debug_load(name)`가 이름을 받아 지금 세이브 폴더에 저장·불러오기한다. 이름을 생략하면 게임 퀵세이브와 같은 `quicksave` 파일이다. 없는 이름은 `bad_request`, 게임이 쓰는 `persistent` 덮어쓰기는 막는다. 이름 검사가 더해진다.
  - B. 퀵세이브 하나만: 인자 없는 `debug_quicksave`·`debug_quickload`로 게임 F5/F9와 같은 파일만 쓴다. 가장 작지만 시험 지점을 하나만 둘 수 있다.
- 결정: A
- 이유: 궤도 진입 직전·분리 직전처럼 시험 지점을 여럿 두고 반복할 수 있다. B는 다른 지점을 저장하면 앞 지점을 잃어 고르지 않았다.
- 반영: spec.md 무엇을·왜, C5·C6·C7·C8

### D004 기체 전환은 게임 규칙을 기본으로 하고 force 인자로 강제 전환을 받는다
- 단계: spec
- 질문: 게임의 일반 기체 전환은 활성 기체가 대기 안이거나 가속 중이거나 지면 위를 움직이거나 곧 추락하거나, 장면의 어느 EVA 대원이든 사다리에 있으면 거절한다(게임 화면에 메시지만 뜬다). 상승 계획이 도는 동안은 대부분 이 상태라, 이대로면 계획 실행 중 전환(`vessel_change` 검증)은 진공에서 엔진을 끈 구간에서만 된다. 게임의 강제 전환은 이 검사를 건너뛴다. 전환 도구가 이 규칙을 어떻게 다룰지 정해야 했다.
- 선택지:
  - A. force 인자: `debug_switch_vessel`에 `force`(기본 false)를 둔다. false면 게임이 전환을 막는 상태일 때 게임의 이유를 담아 `bad_request`이고 기체·계획은 그대로다. true면 그 상태에서도 전환한다.
  - B. 항상 강제 전환: 게임 검사 없이 언제나 전환한다. 대기 안·가속 중에도 알림 없이 바뀌어, 게임이 막는 이유(예: 원래 기체가 대기 안에서 물리 범위를 벗어나 사라질 수 있음)를 호출하는 쪽이 모른다.
  - C. 게임 규칙만: 강제 전환 없이 게임 규칙만 따른다. 계획 실행 중 검증이 진공·엔진 끈 구간으로 제한된다.
- 결정: A
- 이유: 기본 동작은 게임과 같아 안전하고, 상승 연소 중 `vessel_change` 검증도 `force`로 할 수 있다. B는 게임이 막는 위험을 알리지 않아, C는 계획 실행 중 검증 범위가 좁아 고르지 않았다.
- 반영: spec.md C3·C4

### D005 저장은 비행 장면에서만, 불러오기는 debug_launch와 같은 장면에서 받는다
- 단계: spec
- 질문: 저장·불러오기를 어느 장면에서 받을지 정해야 했다. 게임 퀵세이브·퀵로드는 비행 장면에서만 되고, 비행 중 저장한 파일을 불러오면 저장 때의 활성 기체로 비행 장면이 다시 열린다.
- 선택지:
  - A. 저장은 비행, 불러오기는 넓게: `debug_save`는 비행 장면에서 게임의 퀵세이브 저장 가능 검사를 통과할 때만 저장하고(아니면 게임의 이유로 `bad_request`), `debug_load`는 우주센터·비행·에디터·추적소에서 받는다.
  - B. 둘 다 비행 장면만: 게임 퀵세이브·퀵로드와 같은 범위. 비행 장면이 아니면 `not_ready`이다.
- 결정: A
- 이유: 게임을 다시 켜거나 우주센터로 나온 뒤에도 먼저 발사할 필요 없이 시험 지점으로 바로 돌아갈 수 있다. B는 우주센터에서 불러오려면 먼저 기체를 발사해 비행 장면에 들어가야 해 고르지 않았다.
- 반영: spec.md C5·C7

### D006 소유하지 않은 기체로는 force와 상관없이 전환하지 않는다
- 단계: spec
- 질문: spec 검토 1회차 지적 3. 검토 의견: 게임의 강제 전환(`ForceSetActiveVessel`)은 저장 가능 검사뿐 아니라 소유한 기체인지 검사(`DiscoveryInfo.Level == Owned`)도 건너뛰어, `force=true`면 소행성처럼 소유하지 않은 로드된 기체로도 전환된다. spec은 이를 허용하는지 막는지 정하지 않았다. 조종할 수 없는 기체가 활성 기체가 될 수 있어 문제다.
- 선택지:
  - A. 미소유는 항상 거절: 소유하지 않은 기체는 `force`와 상관없이 `bad_request`로 거절하고, 기체 목록에 소유 여부를 더한다. `force`가 건너뛰는 것은 저장 가능 검사뿐이라고 밝힌다.
  - B. force면 미소유도 허용: 게임 강제 전환을 그대로 따라 `force=true`면 소유하지 않은 기체로도 전환한다고 spec에 적는다.
- 결정: A
- 이유: 시험 도구가 조종할 수 없는 상태를 만들지 않고, 호출하는 쪽이 목록의 소유 여부로 거절될지 미리 알 수 있다. B는 시험에 쓸모없는 상태를 허용해 고르지 않았다.
- 반영: spec.md 무엇을·왜 2, 용어 "소유한 기체", C1, C3, C4

### D007 저장·불러오기는 persistent를 바꾸지 않고, 불러오기는 비행 중 저장한 파일만 받는다
- 단계: spec
- 질문: spec 검토 1회차 지적 5. 검토 의견: 게임의 퀵세이브는 설정(`AutoSaveOnQuickSave`)에 따라 `persistent`도 덮어쓰고, 퀵로드는 비행 밖에서 저장한 파일을 불러올 때 `persistent`에 덮어쓴 뒤 우주센터를 연다. D003의 "`persistent` 덮어쓰기는 막는다"와 어긋나며, 시험 중 본 게임 진행 저장이 모르는 사이에 바뀔 수 있다.
- 선택지:
  - A. persistent를 쓰는 경로를 없앰: `debug_save`는 지정한 파일만 쓰고 `persistent`는 바꾸지 않는다. `debug_load`는 비행 중 저장한 파일만 받아 저장 때의 활성 기체로 비행 장면을 열고, 그 밖의 파일은 `bad_request`로 거절한다(우주센터를 여는 경로 삭제).
  - B. 게임과 같게 두고 명시: 게임 동작처럼 `persistent`가 함께 바뀔 수 있다고 spec에 적고, D003을 대체하는 결정을 더한다.
- 결정: A
- 이유: `persistent`가 바뀌는 원인을 설계로 없애고 불러오기 경로도 하나로 줄어든다. 비행 장면에서 불러올 때 계획 종료 사유가 언제나 `new_flight`가 되어 지적 8도 함께 풀린다. B는 시험이 본 진행 저장을 바꿀 수 있어 고르지 않았다.
- 반영: spec.md 무엇을·왜 3, 범위 밖, 용어 "비행 중 저장한 파일", C5, C7, C8, C9

### D008 게임의 퀵세이브·퀵로드 허용 설정은 따르지 않는다
- 단계: spec
- 질문: spec 검토 1회차 지적 6. 검토 의견: C6은 게임 설정이 퀵세이브를 막는 경우(`CanQuickSave`)를 오류로 두었지만, C8에는 퀵로드 금지 설정(`CanQuickLoad`)이 없어 비대칭이다. 난이도 설정으로 이를 막은 게임에서만 동작이 갈린다.
- 선택지:
  - A. 두 설정 모두 무시: 시험 도구이므로 두 설정과 상관없이 저장·불러오기한다. C6의 설정 항목을 빼고 C5·C7에 그렇다고 적는다.
  - B. 두 설정 모두 따름: C8에 퀵로드 금지 설정이면 `bad_request`를 더한다.
- 결정: A
- 이유: 난이도 설정 때문에 시험이 막히지 않고, 이미 게임 치트를 쓰는 `debug_set_orbit`과 일관된다. B는 게임 규칙과 같아 자연스럽지만, 설정을 막은 게임에서는 시험 도구가 동작하지 않아 고르지 않았다.
- 반영: spec.md 무엇을·왜 3, C5, C6, C7

### D009 불러오기 가능 여부는 장면을 바꾸기 전에 모두 판정한다
- 단계: spec
- 질문: spec 검토 1회차 지적 7. 검토 의견: 게임 퀵로드는 파일 읽기 실패만 그 자리에서 판정하고, 버전·호환성 판정은 업그레이드 처리(`KSPUpgradePipeline`) 콜백이나 게임 대화상자에서 한다. 그래서 C8의 "즉시 `bad_request`, 장면 그대로"를 만족할 수 없고, 버전이 다른 시험 파일을 만들 수 없어 확인할 수도 없다. 비행 상태가 없는 파일도 빠져 있었다.
- 선택지:
  - A. 장면을 바꾸기 전 모두 판정: C8을 "장면을 바꾸기 전에 판정해 `bad_request`"로 고치고 판정 항목(파일 없음, 읽을 수 없음, 비행 중 저장 파일이 아님, 게임이 이 버전과 호환되지 않는다고 판정함)을 정한다. 실제 확인은 없는 이름과 내용이 깨진 `.sfs`로 하고, 버전 불일치의 실제 확인은 범위 밖에 적는다. plan에서 게임 흐름 대신 직접 판정하는 설계가 필요하다.
  - B. 버전 판정은 게임에 맡김: C8에서 버전 항목을 빼고 그 경우는 게임 대화상자에 맡긴다고 적는다.
- 결정: A
- 이유: MCP 응답만으로 실패를 알 수 있고 완료 조건을 확인할 수 있다. B는 MCP만으로 실패를 알 수 없고 게임 화면에 대화상자가 남을 수 있어 고르지 않았다.
- 반영: spec.md 무엇을·왜 3, 범위 밖, C8

### D010 C9의 비교 기준과 기준 spec의 결정 참조 표기를 함께 정한다
- 단계: spec
- 질문: spec 검토 1회차 지적 9. 검토 의견: C9 후반 "이름이 다른 저장 두 개를 차례로 불러오면 각자의 상태가 나온다"는 무엇을 어떤 오차로 비교하는지 없어 판정할 수 없다. 또 기준 spec `debug-tools.md` 머리말이 "괄호 안 D번호는 docs/specs/관측/decisions.md의 결정"이라고 적고 있어, 이번 D001~D005(D004가 관측 D004와 겹침)를 반영하면 어느 폴더 결정인지 잘못 읽힐 수 있다.
- 선택지:
  - A. 둘 다 고침: C9을 "서로 다른 궤도로 저장한 두 파일을 차례로 불러오면 각각 `get_flight`의 Ap·Pe가 그 저장 때 값(각 1 km 안)"으로 고치고, C11에 "기준 spec의 결정 참조는 변경 폴더 이름을 붙여 적고 머리말도 맞춘다"를 더한다.
  - B. C9만 고침: C11은 그대로 둔다.
- 결정: A
- 이유: 완료 조건을 판정할 수 있게 되고 기준 spec의 결정 출처가 분명해진다. B는 기준 spec의 D번호 혼동이 남아 고르지 않았다.
- 반영: spec.md C9, C11

### D011 비행 장면 시작 때 게임의 자동 저장은 막지 않고, 도구 자체만 persistent를 쓰지 않게 한다
- 단계: spec
- 질문: spec 검토 2회차 지적 1(D007 보완). 검토 의견: 비행 장면이 시작될 때 게임은 몇 프레임 뒤 저장 가능 검사를 통과하면 `persistent`를 덮어쓴다(`FlightDriver.PostInit`, 막는 것은 난이도 설정의 자동 저장 끄기 `CanAutoSave`뿐). 그래서 D007을 반영한 C7 "`persistent`는 바꾸지 않는다"와 C9 "`persistent.sfs` 수정 시각이 바뀌지 않는다"를 기본 설정에서 만족할 수 없다. 이 저장은 `debug_launch`·`debug_revert`·게임 퀵로드에서도 일어나는 게임 본래 동작이다.

  - B. CanAutoSave를 잠시 꺼서 막음: 불러오는 동안 난이도 설정 `CanAutoSave`를 끄고 비행 준비 뒤 되돌린다. 장면 로드 실패나 핫리로드 중단 때 설정이 바뀐 채로 남을 위험이 있다.
- 결정: A
- 이유: 게임이 비행을 시작할 때마다 하는 정상 동작이고, D007이 막으려던 도구 자체의 쓰기 경로(퀵세이브의 자동 저장, 비행 밖 파일을 불러올 때 덮어쓰기)는 그대로 막힌다. B는 막는 이득보다 게임 설정을 건드리는 위험이 커서 고르지 않았다.
- 반영: spec.md 무엇을·왜 3, C7, C9

### D013 debug_save는 게임 F5 퀵세이브의 기본 규칙을 CAN_ALWAYS_QUICKSAVE와 상관없이 따른다
- 단계: spec
- 질문: D012 대체. spec 검토 3회차 지적 1. 검토 의견: 게임 F5 퀵세이브(`QuickSaveClearToSave`)는 대기 안·가속 중에도 설정과 상관없이 저장하고, 설정 `CAN_ALWAYS_QUICKSAVE`가 꺼져 있을 때 막는 것은 사다리·지면 위 이동·곧 추락 세 가지뿐이다(켜져 있으면 모두 허용). D012대로 `ClearToSave`를 그대로 쓰면 `debug_save`는 F5보다 엄격해 대기 안·가속 중 저장을 거절한다. D012는 이 차이를 모른 채 "PC 설정에 따라 갈리는지"만 비교했고, D003이 이유로 든 "분리 직전" 같은 대기 안 상승 구간을 저장할 수 없게 된다.
- 선택지:
  - A. 퀵세이브 기본 규칙 따름: 저장 가능 검사 결과가 사다리·지면 위 이동·곧 추락일 때만 거절하고 대기 안·가속 중에는 저장한다. `CAN_ALWAYS_QUICKSAVE`는 따르지 않는다. 용어에 "퀵세이브 검사"를 정의하고 C6을 그 검사로 고친다.
  - B. ClearToSave 그대로, 엄격함 명시: 지금 규칙을 두고 F5보다 엄격해 대기 안·가속 중 저장할 수 없다고 적는다.
  - C. 게임과 완전히 같게: A에 더해 `CAN_ALWAYS_QUICKSAVE`가 켜져 있으면 세 상태도 허용한다.
- 결정: A
- 이유: 상승 중 시험 지점 저장이라는 D003의 목적을 살리고, 결과가 `CAN_ALWAYS_QUICKSAVE`와 상관없이 게임 기본 F5와 같다(각 결과의 판정 조건은 게임을 따른다). B는 상승 구간 시험 지점을 저장할 수 없어, C는 `CAN_ALWAYS_QUICKSAVE` 설정에 따라 결과가 갈려 고르지 않았다.
- 반영: spec.md 무엇을·왜 3, 용어 "저장 가능 검사"·"퀵세이브 검사", C6

### D014 저장 가능 검사는 게임 판정식을 옮겨 적지 않고 ClearToSave 결과 이름으로 정의한다
- 단계: spec
- 질문: spec 검토 5회차 지적 1. 검토 의견: 4회차에 더한 곧 추락 정의("지형 위 높이가 `QUICKSAVE_MINIMUM_ALTITUDE`(최소 0.5 m)보다 낮은 상태")에 상황 조건이 빠졌다. 게임은 활성 기체가 `FLYING`·`SUB_ORBITAL`일 때만 높이를 비교하고 높이가 `-1`(측정값 없음)이면 곧 추락으로 보지 않는다. 문구대로면 발사대·착륙 기체도 곧 추락에 걸려 `debug_save`·`debug_switch_vessel`이 지상에 멈춘 기체에서 거절된다. 3·4·5회차 지적이 모두 게임 판정식을 문장으로 옮겨 적은 부분에서 나왔다.
- 선택지:
  - A. 상황 조건을 더해 맞춤: 곧 추락 정의에 비행·준궤도 상황, 높이 측정 조건을 더한다. 다른 판정 조건에서 같은 종류의 옮겨 적기 오차가 또 나올 수 있다.
  - B. 게임 판정 결과로 정의: 저장 가능 검사는 `FlightGlobals.ClearToSave` 결과를 그대로 쓰고 `CLEAR`가 아니면 통과하지 못한다고 정의하며, 결과 이름만 나열하고 각 판정 조건은 게임을 따른다고 적는다. 퀵세이브 검사는 결과 이름 세 개로 정의한다. 4회차에 더한 고도 문장은 지운다.
- 결정: B
- 이유: 판정식을 다시 적지 않아 옮겨 적기 오차가 원인부터 사라지고, 구현도 게임 함수의 결과를 그대로 써 spec과 어긋날 곳이 없다. A는 지금 오류만 고치고 같은 종류의 오차가 남아 고르지 않았다.
- 반영: spec.md 용어 "저장 가능 검사"·"퀵세이브 검사", D013 이유 괄호

### D015 debug_load는 지금 게임 버전이 만든 파일만 받고 업그레이드 처리를 하지 않는다
- 단계: plan

- 선택지:

  - C. 업그레이드 없이 불러옴: 호환 판정만 하고 업그레이드 처리를 건너뛴다. spec은 그대로다.
- 결정: A
- 이유: 업그레이드 실패 경로(대화상자)를 설계로 없애고, 이 도구와 게임 F5가 만드는 파일은 모두 지금 버전이라 받을 파일은 모두 받는다. B는 게임 대화상자를 찾아 닫는 확인할 수 없는 UI 조작이 남아, C는 옛 파일이 고쳐지지 않은 채 불러와져 게임과 다른 상태가 될 수 있어 고르지 않았다.
- 반영: spec.md C8, 범위 밖

### D016 불러오기 판정은 activeVessel까지 보고, 그보다 깊은 값의 형식 오류는 예외를 잡아 알린다
- 단계: plan

- 결정: A
- 이유: 게임과 이 도구가 만드는 파일에서는 생기지 않는 경로이고, 예외 없이 이유와 복구 방법을 알려 준다. B는 실패하지 않는 정상 불러오기에도 늘 부수 효과를 남겨 고르지 않았다.
- 반영: plan.md 인터페이스(SaveFileCheck), 오류·위험

### D018 불러올 때 활성 기체는 번호가 아니라 저장 파일의 pid로 찾는다
- 단계: plan

- 반영: plan.md 결정(불러오기 실행 3·6단계), 인터페이스(SaveFileFacts·SaveFileCheck·LoadedGameFacts·LoadedGameCheck), 검증 전략 C8

### D019 활성 기체 pid 판정은 비행 아님 판정 뒤에 한다
- 단계: plan
- 질문: plan 검토 5회차 지적 1. 검토 의견: D018로 더한 손상 조건 "`activeVessel`이 가리키는 `VESSEL`의 `pid`가 없음"이 비행 아님 판정보다 먼저 와서, `FLIGHTSTATE` 없음·`VESSEL` 0개·`activeVessel` 범위 밖 파일(가리키는 노드가 없어 `ActivePid`가 `null`)이 모두 "손상"으로 거절된다. spec C8의 사유 구분을 어기고 plan의 단위 시험 요구와 모순되며, 기체가 없는 게임에서 저장한 파일처럼 게임이 실제로 만드는 파일에서 일어난다.
- 선택지:
  - A. pid 판정을 뒤로: 순서를 손상(값 형식) → 비행 아님(`scene`·`FLIGHTSTATE`·`VESSEL` 0개·`activeVessel` 범위) → 활성 기체 `pid` 손상(없음·GUID 아님) → 버전으로 한다. 범위 확인 뒤라 `ActivePid`가 `null`이면 노드에 `pid`가 없다는 뜻만 된다.
  - B. pid 조건에 전제 붙임: 순서는 그대로 두고 손상의 `pid` 조건을 "`activeVessel`이 범위 안일 때만"으로 한정한다.
- 결정: A
- 이유: 판정 순서만으로 가려져 각 조건이 독립적이고 읽기 쉽다. B는 결과는 같지만 조건끼리 서로 기대 고르지 않았다.
- 반영: plan.md 인터페이스(SaveFileCheck 판정 항목·순서), 검증 전략 C8(SaveFileCheckTests)
