# Debug 보강: 활성 기체 전환과 저장·불러오기

기능: debug-tools(기준 spec docs/features/debug-tools.md)
이슈: GitHub #35

## 무엇을, 왜

시험 비행을 MCP 도구만으로 반복하려면 발사·되돌리기·우주센터 이동·궤도 설정(기준 spec R1~R4)에 더해, 시험 지점을 저장·복원하고 활성 기체를 바꿀 수 있어야 한다. 활성 기체 전환은 계획이 활성 기체 변경으로 끝나는 경로(`vessel_change`, 계획 기준 spec `docs/features/flight-plan.md` R2)를 실제 게임에서 확인하는 데도 필요하다. 이 경로는 골격 작업 뒤로 실제 게임에서 재현한 적이 없다.

이슈 #35 범위 가운데 "발사할 craft 파일 지정(VAB/SPH)"은 이미 `debug_launch`(기준 spec R1)가 한다. 이번 작업은 바꾸지 않는다.

이번 작업은 debug 모듈 쌍(Mod 모듈과 MCP 서버 모듈 `debug`)에 다음 도구를 더한다.

1. 기체 목록(`debug_list_vessels`, D002): 비행 장면의 기체를 보여 주는 읽기 전용 도구.
2. 활성 기체 전환(`debug_switch_vessel`): 로드된 기체로만 바꾼다(D001). 장면을 다시 불러오지 않으므로, 실행 중인 계획은 `vessel_change`로 끝난다. 기본은 게임의 전환 규칙을 따르고, `force`로 그 가운데 저장 가능 검사만 건너뛴다(D004). 소유하지 않은 기체로는 `force`와 상관없이 바꾸지 않는다(D006).
3. 저장·불러오기(`debug_save`·`debug_load`): 이름을 받아 지금 세이브 폴더에 저장하고 불러온다. 이름을 생략하면 게임 퀵세이브와 같은 `quicksave` 파일이다(D003). 저장은 비행 장면에서, 불러오기는 `debug_launch`와 같은 장면에서 받는다(D005). 두 도구 자체는 지정한 파일만 쓰거나 읽고 게임 진행 저장(`persistent`)을 쓰지 않는다. 그래서 불러오기는 비행 중 저장한 파일만 받는다(D007). 불러온 뒤 비행 장면이 시작될 때 게임이 하는 자동 저장은 다른 발사와 같이 막지 않는다(D011). 게임 난이도 설정의 퀵세이브·퀵로드 허용은 따르지 않고(D008), 저장은 게임 F5의 기본 규칙(퀵세이브 검사)을 게임 설정 `CAN_ALWAYS_QUICKSAVE`와 상관없이 쓴다. 그래서 대기 안 상승 중에도 저장할 수 있다(D013). 불러올 수 있는지는 장면을 바꾸기 전에 모두 판정한다(D009).

범위 밖: 로드되지 않은 기체로 전환(장면 재로드), 세이브 폴더 바꾸기(다른 게임 불러오기), 저장 파일 지우기·목록 보기, 비행 밖에서 저장한 파일 불러오기, 활성 기체가 아닌 기체의 상세 상태 조회, 다른 게임 버전이 만든 저장 파일 불러오기(게임의 업그레이드 처리가 필요하므로 게임 자체 불러오기로 연다, D015), 그런 파일을 거절하는 동작의 실제 게임 확인(그런 시험 파일을 만들 수단이 없다). 기존 도구(`debug_launch`·`debug_revert`·`debug_space_center`·`debug_set_orbit`)의 동작은 바꾸지 않는다.

용어:

- 활성 기체: 비행 장면에서 게임이 조종 대상으로 잡은 기체(`get_status`의 `vessel`과 같은 기체).
- 로드된 기체: 게임이 장면에 올려 둔 기체(`Vessel.loaded`). 물리로 다루는 중이든 레일 위든 포함하며, 대체로 활성 기체 가까이 있다. 게임은 로드된 기체로는 장면을 다시 불러오지 않고 전환한다.
- 소유한 기체: 게임이 플레이어 소유로 표시한 기체(`DiscoveryInfo.Level`이 `Owned`). 발견만 한 소행성 등은 아니다.
- 기체 id: 게임이 기체마다 붙인 영구 id(`persistentId`). 저장·불러오기를 거쳐도 같은 기체는 같은 값이다.
- 저장 가능 검사: 게임이 퀵세이브와 일반 기체 전환 전에 하는 검사 `FlightGlobals.ClearToSave`의 결과를 그대로 쓴다. 결과가 `CLEAR`가 아니면 통과하지 못한다. 통과하지 못하는 결과는 대기 안(`NOT_IN_ATMOSPHERE`), 가속 중(`NOT_UNDER_ACCELERATION`), 지면 위 이동(`NOT_WHILE_MOVING_OVER_SURFACE`), 곧 추락(`NOT_WHILE_ABOUT_TO_CRASH`), 사다리(`NOT_WHILE_ON_A_LADDER`)이며, 각 결과의 판정 조건(높이 기준, 상황 조건, 게임 설정)은 게임을 따른다. 기체 전환이 이 검사를 쓴다.
- 퀵세이브 검사: 게임 F5 퀵세이브의 기본 규칙. 저장 가능 검사 결과가 `NOT_WHILE_ON_A_LADDER`·`NOT_WHILE_MOVING_OVER_SURFACE`·`NOT_WHILE_ABOUT_TO_CRASH`이면 통과하지 못하고, 그 밖의 결과(대기 안·가속 중 포함)는 통과한다. 게임은 설정 `CAN_ALWAYS_QUICKSAVE`가 켜져 있으면 세 상태도 허용하지만, 이번 도구는 이 설정과 상관없이 기본 규칙을 쓴다.
- 저장 이름: 지금 세이브 폴더 안 저장 파일(`<이름>.sfs`)의 이름.
- 비행 중 저장한 파일: 불러오면 게임이 비행 장면을 여는 저장 파일(시작 장면이 비행이고 비행 상태가 들어 있음). `debug_save`와 게임 퀵세이브가 만든 파일이 그렇다.

## 완료 조건

- C1. `debug_list_vessels`는 비행 장면의 모든 기체를 돌려준다. 기체마다 id, 이름, 종류(게임 기체 종류 이름, 예: `Ship`·`Debris`), 상황(게임 상황 이름), 천체 이름, 로드 여부, 소유 여부, 활성 기체 여부, 활성 기체와의 거리(m)가 있다. 기체를 바꾸지 않는 조회다. 비행 장면이 아니거나(지금 장면 이름을 이유에 넣음) 장면을 불러오는 중이거나 비행 장면이 준비되지 않았으면 `not_ready`이다.
- C2. `debug_switch_vessel`은 기체 id를 받아 그 기체를 활성 기체로 만든다. 장면을 다시 불러오지 않는다. 응답에 새 활성 기체의 id와 이름이 있고, 응답 뒤 `get_status`가 그 기체를 활성 기체로 보이며 짧은 시간(1초) 안에 `ready=true`가 된다. 이미 활성 기체인 id면 아무것도 바꾸지 않고 그 사실을 알리는 성공 응답이다.
- C3. `debug_switch_vessel`의 오류: 비행 장면이 아니거나 장면을 불러오는 중이거나 비행 장면이 준비되지 않았으면 `not_ready`. 없는 id, 로드되지 않은 기체(먼 기체는 받지 않는다는 이유를 넣음), 소유하지 않은 기체(`force`와 상관없음)이면 `bad_request`. `force`가 false(기본)이고 저장 가능 검사를 통과하지 못하면 게임이 전환을 막는 이유를 담아 `bad_request`이다. 게임이 그 밖의 이유로 전환을 거절해도 `bad_request`이다. 어느 오류든 활성 기체와 실행 중인 계획은 바뀌지 않고, 오류 뒤 짧은 시간(1초) 안에 `get_status`가 `ready=true`이다.
- C4. `force`가 true면 저장 가능 검사를 통과하지 못하는 상태(예: 스로틀을 올리고 대기 안에서 상승 중)에서도 로드된 소유 기체로 전환한다. `force`가 건너뛰는 것은 저장 가능 검사뿐이다. 실제 게임에서 계획이 실행 중일 때 전환하면 그 계획은 `vessel_change`로 끝나고, `get_plan`이 끝난 사유 `vessel_change`를 보인다(계획 기준 spec R2의 실제 확인). 계획이 없을 때 전환해도 오류가 없다.
- C5. `debug_save`는 비행 장면에서 지금 게임을 저장 이름으로 지금 세이브 폴더에 저장한다. 이름을 생략하면 `quicksave`이다. 같은 이름이 있으면 덮어쓴다. 지정한 파일만 쓰고 `persistent`는 쓰지 않는다. 게임 난이도 설정의 퀵세이브 허용(`CanQuickSave`)과 상관없다. 이 파일은 비행 중 저장한 파일이다. 실행 중인 계획과 기체는 바뀌지 않는다. 응답에 저장 이름이 있다.
- C6. `debug_save`의 오류: 비행 장면이 아니거나 장면을 불러오는 중이거나 비행 장면이 준비되지 않았으면 `not_ready`. 활성 기체가 파괴된 상태이거나 퀵세이브 검사를 통과하지 못하면(사다리·지면 위 이동·곧 추락, 게임 설정 `CAN_ALWAYS_QUICKSAVE`와 상관없음) 게임의 이유를 담아 `bad_request`이다. 이름이 비었거나 영문자·숫자·`-`·`_`·공백 밖의 글자가 있거나 64자를 넘거나 게임이 쓰는 이름(`persistent`, 대소문자 무시)이면 `bad_request`이다. 오류면 파일이 만들어지거나 바뀌지 않는다.
- C7. `debug_load`는 저장 이름(생략하면 `quicksave`)의 비행 중 저장한 파일을 불러와, 저장 때의 활성 기체로 비행 장면을 연다. 우주센터·비행·에디터·추적소 장면에서 받는다. 도구 자체는 `persistent`를 쓰지 않으며(불러온 뒤 비행 장면이 시작될 때 게임이 하는 자동 저장은 막지 않는다), 게임 난이도 설정의 퀵로드 허용(`CanQuickLoad`)과 상관없다. 요청을 받으면 장면을 불러오며, 호출하는 쪽이 `get_status`로 준비를 확인한다. 실행 중인 계획은 코어의 장면 추적으로 끝난다(비행 장면에서 불러오면 `new_flight`).
- C8. `debug_load`의 오류: 게임이 없거나 장면을 불러오는 중이거나 받는 장면이 아니면 `not_ready`. 다음은 장면을 바꾸기 전에 판정해 `bad_request`이다. 이름이 C6의 글자 규칙에 맞지 않음, 그 이름의 파일이 없음, 파일을 읽을 수 없음(손상. 판정에 쓰는 값인 `GAME` 노드·`version`·`scene`이 없거나 형식이 맞지 않는 경우를 포함하며, `version`은 정수 세 개를 점으로 이은 형식, `scene`은 정수), 비행 중 저장한 파일이 아님(비행 상태가 없거나 시작 장면이 비행이 아님), 저장 파일 `GAME` 노드의 `version`(주.부.수정)이 지금 게임 버전(주.부.수정)과 다름(빌드 번호·플랫폼은 보지 않음, D015). 오류면 장면·계획·`persistent`가 바뀌지 않는다. 실제 게임에서는 없는 이름과 내용이 깨진 `.sfs` 파일로 확인한다.
- C9. 실제 게임에서 MCP 응답만으로 다음 순서가 맞는다. 궤도에 올린 기체(`debug_set_orbit`)를 `debug_save`로 저장하고, 궤도를 다른 값으로 바꾼 뒤 `debug_load`로 불러오면 `get_flight`의 Ap·Pe가 저장 때 값(각 1 km 안)으로 돌아온다. 서로 다른 궤도로 저장한 두 파일을 차례로 불러오면 각각 `get_flight`의 Ap·Pe가 그 저장 때 값(각 1 km 안)이다. `debug_save` 뒤와, 판정에 실패한 `debug_load` 뒤에는 `persistent.sfs`의 수정 시각이 바뀌지 않는다.
- C10. 새 도구 네 개(`debug_list_vessels`·`debug_switch_vessel`·`debug_save`·`debug_load`)와 그 Mod 처리는 기존 debug 모듈 쌍에 더하고 코어 코드를 고치지 않는다. 새 도구는 핫리로드로 반영되고 실제 Claude Code 세션에서 `mcp__` 도구로 불린다. 게임에 예외가 남거나 도구가 멈추지 않는다.
- C11. 기준 spec `docs/features/debug-tools.md`에 이번 요구와 이력이 반영된다. 기준 spec의 결정 참조는 변경 폴더 이름을 붙여 적고(예: `디버그-보강 D004`, `관측 D004`), 머리말도 그에 맞춘다.
