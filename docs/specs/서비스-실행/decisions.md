# MCP 서버 서비스 실행과 게시 기반 배포 결정

### D001 서버 코드에 Windows 서비스 지원을 더한 뒤 서비스로 등록한다
- 단계: spec
- 질문: 게시 폴더의 서버를 서비스로 등록해 달라는 요청을 받았다. 그런데 서버(`KspBridge.Server.exe`)에는 서비스 제어 관리자(SCM)에 응답하는 코드가 없다. 그대로 `sc.exe`로 등록하면 SCM이 시작 완료 신호를 받지 못해 1053 오류로 기동이 실패한다. 어떻게 진행할지 정해야 했다.
- 선택지:
  - A. 서비스 지원 추가 후 등록: 서버에 Windows 서비스 수명 관리를 넣고 다시 게시한 뒤 서비스로 등록한다.
  - B. 작업 스케줄러로 로그온 시 실행: 코드를 바꾸지 않는다. 로그온할 때 작업 스케줄러가 서버를 숨김 실행한다. 서비스 목록에는 나타나지 않는다.
  - C. 지금 상태로 sc.exe 등록만: 코드를 바꾸지 않고 등록만 한다. 기동은 1053으로 실패한다.
- 결정: A
- 이유: 서비스 목록에서 관리하고 로그온 없이 실행하려면 서비스 수명 관리가 필요하다. B는 로그온해야만 뜨고 서비스로 관리되지 않는다. C는 기동이 실패해 쓸 수 없다.
- 반영: spec.md C1

### D002 서비스를 로그인 계정으로 실행하고 등록 경로는 절대 경로로 바꾼다
- 단계: spec
- 질문: spec 검토 1회차 지적 2. 서비스는 현재 폴더 `C:\Windows\System32`에서 시작한다. 그래서 등록 스크립트가 `--config`·`--log`에 상대 경로를 그대로 넘기면 System32 기준으로 풀려 설정 오류로 기동에 실패하거나 로그가 엉뚱한 곳에 쌓인다. 이것을 어떻게 고칠지 정해야 했다.
- 선택지:
  - A. 절대 경로로 변환: 등록 스크립트가 받은 경로를 절대 경로로 바꿔 등록한다.
  - B. 상대 경로 거부: 절대 경로가 아니면 등록하지 않고 알린다.
  - C. 고치지 않음.
- 결정: 사용자가 서비스를 로그인 계정으로 실행하겠다고 답했고, 이어서 경로는 A(절대 경로로 변환)로 정했다.
- 이유: 사용자 지정. 계정 지정은 상대 경로 문제를 풀지 않으므로 경로 처리는 따로 정했다. B는 쓰기 불편하고, C는 기동 실패가 남는다.
- 반영: D009·D012로 대체되어 지금 spec에는 남아 있지 않다.

### D003 로그인 계정 등록은 사용자가 직접 실행한다
- 단계: spec
- 질문: 로그인 계정으로 서비스를 등록하려면 그 계정의 패스워드가 필요하다. 에이전트는 패스워드를 다룰 수 없다. 등록을 누가 할지 정해야 했다.
- 선택지:
  - A. 사용자가 직접 실행: 관리자 PowerShell에서 사용자가 등록하고 패스워드는 사용자가 직접 넣는다.
  - B. LocalSystem으로 먼저 등록: 에이전트가 LocalSystem으로 등록·시작하고, 계정은 나중에 사용자가 services.msc에서 바꾼다.
- 결정: A
- 이유: 패스워드를 에이전트가 다루지 않는다. B는 처음 실행 계정이 사용자 의도와 달라진다.
- 반영: spec.md 무엇을·왜(등록은 사용자가 수동으로 함)

### D004 ContentRootPath는 무조건 절대 경로로 둔다
- 단계: spec
- 질문: spec 검토 2회차 지적 1. 설정 파일의 `ContentRootPath`도 상대 경로면 현재 폴더 기준으로 풀린다. 서비스에서는 모듈 폴더가 `C:\Windows\System32\modules`로 잡혀 모듈을 읽지 못한다. 이것을 어떻게 고칠지 정해야 했다.
- 선택지:
  - A. 설정 파일 폴더 기준: 서버가 상대 `ContentRootPath`를 설정 파일이 있는 폴더 기준으로 푼다.
  - B. 서버가 상대 경로 거부: 상대 `ContentRootPath`를 설정 오류로 처리한다.
  - C. 스크립트에서만 거부: 등록 스크립트가 설정을 읽어 상대 경로면 등록을 거부한다.
  - D. 고치지 않음.
- 결정: 사용자가 "ContentRootPath를 무조건 절대 경로로"라고 답했다(B).
- 이유: 사용자 지정. A는 기존 상대 경로의 뜻을 바꾸고, C는 콘솔 실행에서 문제가 남고, D는 서비스에서 모듈을 못 읽는다.
- 반영: D009·D010으로 대체되어 지금 spec에는 남아 있지 않다.

### D005 서버가 새 모듈 세대를 읽었는지는 시각으로 판정한다
- 단계: spec
- 질문: spec 검토 2회차 지적 2. 서버 로그의 세대 기록(`Loaded server module generation {Generation}`)의 번호는 서버 안에서 1씩 늘어나는 값이다. 그래서 manifest의 `build` 값과 대응시킬 수 없어, 어떤 로그 줄로 "그 배포 세대를 읽었다"고 판정할지 정해지지 않았다.
- 선택지:
  - A. 시각으로 판정: 게시 시각 뒤에 새 `Loaded server module generation` 줄이 생기면 읽은 것으로 본다. 코드를 바꾸지 않는다.
  - B. 로그에 build 값 추가: 서버가 세대를 읽을 때 manifest의 `build` 값을 로그에 남기도록 코드를 고치고 그 값으로 판정한다.
  - C. 고치지 않음.
- 결정: A
- 이유: 코드 변경 없이 판정할 수 있다. B는 판정 하나를 위해 코드를 바꾼다. C는 판정이 모호하게 남는다.
- 반영: spec.md C12

### D006 시작 단계 오류를 --log 폴더의 파일에도 남긴다
- 단계: spec
- 질문: spec 검토 3회차 지적 2. 설정 오류와 호스트 생성 오류는 로거를 만들기 전에 나서 stderr(`Console.Error`)로만 나간다. 서비스에는 콘솔이 없어 사용자가 기동 실패 원인을 볼 수 없다. 이것을 어떻게 고칠지 정해야 했다.
- 선택지:
  - A. --log 폴더에 기록: 시작 단계 오류를 `--log` 폴더의 파일에도 남기고, 서비스는 `Running`이 되지 않는 것으로 판정한다.
  - B. 이벤트 로그에 기록: Windows 이벤트 로그에 남긴다. 이벤트 원본 등록이 더 필요하다.
  - C. 콘솔만 확인: 서비스 쪽 요구를 빼고 콘솔 실행만 확인한다.
  - D. 고치지 않음.
- 결정: A
- 이유: 콘솔 실행과 같은 곳(로그 폴더)에서 원인을 볼 수 있다. B는 이벤트 원본 등록이 더 필요하다. C·D는 서비스 기동 실패 원인을 볼 수 없게 남긴다.
- 반영: spec.md C2

### D007 루트만·드라이브만 있는 경로는 등록을 거부한다
- 단계: spec
- 질문: spec 검토 5회차 지적 1. `\KspBridge`(현재 드라이브 루트 기준)나 `C:KspBridge`(드라이브별 현재 폴더 기준) 같은 경로는 "실행 폴더 기준으로 푼다"는 규칙으로 결과가 정해지지 않았다.
- 선택지:
  - A. 그런 경로는 거부: 루트·드라이브가 없는 상대 경로만 실행 폴더 기준으로 풀고 나머지는 등록을 거부한다.
  - B. 예시별 결과 명시: 경로 종류마다 변환 결과를 적는다.
  - C. 고치지 않음.
- 결정: A
- 이유: 결과가 하나로 정해진다. B는 규칙이 길어진다. C는 구현마다 결과가 달라진다.
- 반영: D009로 대체되어 지금 spec에는 남아 있지 않다.

### D019 배포는 게시할 때 복사한다

### D022 Mod는 어느 프로젝트를 게시하든 세트로 게시한다
