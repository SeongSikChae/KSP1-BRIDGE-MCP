# 비행안정 설계 — 2단계: 이상 상태 감시 · 최근 구간 요약

방안: [0047-비행안정-방안.md](0047-비행안정-방안.md) 결정 1의 2단계, 결정 2(기본 중단 + 조절). 이슈 [#24](https://github.com/SeongSikChae/KSP1-BRIDGE-MCP/issues/24) 문제 2와 작업 내용 "최근 구간 진동·오차 요약". 1단계 실측에서 드러난 공력 가열 파괴(0049 "실측 결과")를 감시 항목에 넣는다(사용자 합의). `gravity_turn` 프로파일 보정은 별도 이슈 [#26](https://github.com/SeongSikChae/KSP1-BRIDGE-MCP/issues/26).

## 범위

- 비행 계획이 실행 중일 때 매 틱 이상 상태를 판정해 경고 이벤트를 내거나 계획을 중단한다.
- 원격측정 변수 3개를 더해 `abort`·`until` 조건과 `get_flight`에서도 쓴다.
- `get_flight` `plan.monitor`에 최근 10 s 통계를 낸다.
- 비범위: 자세 제어기 수정(3단계), 자동 회복 동작(스로틀 자동 감소 등), `gravity_turn` 프로파일(#26).

## 현재 구조 (조사 결과)

- 원격측정 `Telemetry.NumVars`(`Telemetry.cs:16-23`)에 각속도·받음각·부품 온도가 없다. 각속도는 모드 안에서 `v.angularVelocity`를 직접 읽는다. 부품 온도는 파괴 순간(`PartLossLog.OnWillDie`)에만 기록하고 주기 조회가 없다. `part_limit`은 게임 이벤트(`onOverheat`) 구독이며 임계는 게임이 정한다.
- 틱 순서(`Coordinator.Tick`): (a) 캡처 → (b) `abort` 판정(`FirstTrue`) → `timeout` → (c)(d)(e) 명령 계산 → (f) 워프 → (g) 단계 완료. 중단은 `Abort(reason, condition, message)`.
- 계획 JSON은 알 수 없는 키를 거부한다(`Plan.UnknownKeys`). 리로드는 `Plan.Restore`가 원본 JSON을 다시 파싱하므로 새 키는 자동으로 넘어간다.
- `get_flight` `plan` 객체는 `Coordinator.Describe`(835-856)가 만든다.

## 결정

### 1. 구조: 공통 감시기 + 새 변수 (사용자 합의)

- 새 정적 클래스 `FlightMonitor`(`src/KspBridge.Logic/Flight/FlightMonitor.cs`)가 계획 실행 중 매 틱 표본을 쌓고 판정한다.
- 호출 위치: `Coordinator.Tick`의 (b) `abort` 판정 뒤, `timeout` 앞. 같은 틱의 캡처값 `_t`를 쓰고, 중단이면 명령 계산 전에 `Abort`로 끝낸다.
- Submit·단계 교체의 시험 계산(trial)에서는 부르지 않는다. 표본은 실제 틱만 쌓는다.
- 계획·단계가 바뀌면(새 계획, `NextStep`, `replace_flight_steps include_current`로 현재 단계 교체) 판정 타이머와 경고 상태를 초기화한다. 초기화할 때 경고 중이던 항목마다 `monitor_clear`를 내서 경고·해제 이벤트가 짝을 이루게 한다. 10 s 표본 창은 계획 안에서 이어진다(단계 경계에서도 요약이 끊기지 않게).
- 계획이 끝나면(완료·중단·해제) 경고 상태를 비운다(이벤트 없음, 계획 종료 이벤트가 대신한다). 표본 창은 다음 계획 시작까지 남겨 중단 직후 `get_flight`로 원인을 볼 수 있게 한다.

### 2. 새 원격측정 변수 (조건·`get_flight`에서도 사용)

| 이름 | 뜻 | 단위 | 값이 없을 때 |
|---|---|---|---|
| `angular_rate` | 기체 각속도 크기 `|v.angularVelocity|` | rad/s | packed·레일 워프 중 NaN |
| `aoa` | 기수(`ReferenceTransform.up`)와 지표 속도 사이 각 | deg | 지표 속도 1 m/s 미만·packed 중 NaN |
| `temp_ratio` | 모든 부품의 `max(temperature/maxTemp, skinTemperature/skinMaxTemp)` 최댓값 | 0~1+ | 부품 없음 NaN |

- `Telemetry.NumVars`에 이름을 더하고 `Capture`에서 채운다(조건 파서는 이 배열을 보므로 따로 고치지 않는다).
- `get_flight`의 `flight` 그룹에 `angular_rate`·`aoa`, 별도 `thermal` 그룹 없이 `flight`에 `temp_ratio`를 더한다.

### 3. 감지 항목과 기본 대응 (사용자 합의, 한계값은 초기값 — 3단계 실측으로 조정)

| 항목 | 조건 | 기본 대응 |
|---|---|---|
| 뒤집힘 `flipped` | 대기권 안, `dynamic_pressure` ≥ 5 kPa, 명령 자세가 지표 속도와 30° 안(모드가 속도 방향으로 날려 함), 그런데 `aoa` > 30° 가 2 s 이어짐 | 계획 중단 |
| 제어 상실 `control_lost` | 추력 중(`throttle` > 0 그리고 `thrust` > 0), `attitude_error` > 30° 가 5 s 이어짐 | 계획 중단 |
| 과열 `overheat` | `temp_ratio` ≥ 0.95 | 계획 중단 |
| 과열 경고 `overheat` | `temp_ratio` ≥ 0.80 | 경고 |
| 진동 `oscillation` | 최근 10 s 동안 기체 축(피치·요·롤) 중 하나의 각속도 부호가 6번 이상 바뀜(각 전환은 |ω축| ≥ 0.05 rad/s일 때만 셈). 해제는 전환 수가 그 절반(3) 미만으로 내려갈 때 | 경고 |
| 추력 낭비 `thrust_waste` | 추력 중 `attitude_error` > 10° 가 5 s 이어짐 | 경고 |

- 뒤집힘의 기준: 받음각 절댓값만 보면 착륙(`land`: 기수 위, 속도 아래)·역추진 하강·열차폐 재진입처럼 모드가 일부러 속도 반대로 향하는 경로가 걸린다. 그래서 명령 자세(`Command.Attitude`)와 지표 속도 사이 각이 `flip_aoa_deg` 이하일 때만 판정한다. 명령 자세가 없으면 판정하지 않는다.
- 제어 상실과 선회의 구분(구현 검토 R3-2-B-1 반영): 추력 중 큰 선회(예: `attitude` 단계의 `retrograde` + 추력)는 오차가 30°를 넘어도 목표로 줄어든다. 그래서 `control_lost` 타이머는 시작(또는 재시작) 때의 오차를 기준으로 두고, 오차가 그보다 5° 이상 줄면 그 값에서 다시 센다. 오차가 줄지 않거나 커지는 채로 5 s가 지나야 중단한다(초당 1° 미만으로 느리게 도는 선회는 중단될 수 있다). `thrust_waste`는 그대로 경고한다.
- 의도된 정렬 중 제외: 모드가 정렬이 끝나기 전에 일부러 추력을 내는 경우(`land` 강제 시작의 `_aligning`)에는 모드 명령의 새 표시 `ModeCommand.Aligning`을 켜고, 그동안 `control_lost`·`thrust_waste` 타이머를 멈춘다.
- 타이머 멈춤: 스테이징 진행 중(`staging` ≠ `none`), `Aligning`, `attitude_error`가 NaN(자세 목표 없음, 레일 워프)인 틱에는 해당 타이머의 누적 시간을 그대로 두고 더하지 않는다. 조건이 거짓인 틱에만 0으로 되돌린다. 누적은 틱 간격(`ut` 차이)을 더하는 방식이다.
- 수준은 항목마다 한 틱에 한 번 정한다(중단·경고·해제 중 하나). 과열은 0.95 이상이면 중단, 0.8 이상이면 경고, 그 아래면 해제다.
- 중단은 `Abort("monitor", null, message)`로 하고 `plan_aborted`의 `message`에 항목과 값(예: `flipped: aoa 47.2 deg at q 12.3 kPa for 2.0 s`)을 적는다. `reason`은 `monitor` 하나로 두고 항목은 `message` 머리말과 직전 `monitor_alert` 이벤트로 구분한다.
- 이벤트:
  - `monitor_alert {kind, level warn|abort, value, limit}`: 항목이 경고·중단 상태에 들어갈 때 한 번(중단 직전에도 한 번 낸다).
  - `monitor_clear {kind}`: 경고 상태에서 벗어날 때 한 번.
  - 같은 항목이 경고 ↔ 해제를 반복해도 이벤트는 상태가 바뀔 때만 낸다.

### 4. 계획·단계 선택 키 `monitor`

- 계획 최상위와 단계에 선택 키 `monitor`(객체)를 더한다. 단계 값이 계획 값보다 우선하고, 없는 항목은 계획 값, 그다음 기본값을 쓴다.
- 파싱은 지정한 항목만 담는 부분 설정으로 한다(계획·단계 모두). 병합은 실행할 때 `Coordinator`가 단계 → 계획 → 기본값 순서로 한다. 그래서 `replace_flight_steps`가 실행 중 계획을 모른 채 단계를 파싱해도(`FlightHandler`가 `Plan.ParseSteps`를 먼저 호출) 같은 규칙으로 병합된다.
- `temp_warn` ≤ `temp_abort` 검사는 병합 결과에 한다. 파싱 때는 한 객체 안에 둘 다 있을 때만 검사하고, 병합 결과가 어긋나면(예: 계획 `temp_abort` 0.7, 단계 `temp_warn` 0.8) 경고 수준을 중단 수준으로 낮춰 쓴다.
- 형식:

```json
"monitor": {
  "enabled": true,
  "abort": true,
  "flip_aoa_deg": 30, "flip_min_q_kpa": 5, "flip_for_s": 2,
  "lost_error_deg": 30, "lost_for_s": 5,
  "waste_error_deg": 10, "waste_for_s": 5,
  "osc_flips": 6, "osc_min_rate": 0.05,
  "temp_warn": 0.8, "temp_abort": 0.95
}
```

- `enabled: false`면 그 범위에서 판정·이벤트를 끈다(표본과 `plan.monitor` 요약은 계속 만든다).
- `abort: false`면 중단 항목도 경고(`level warn`)만 낸다.
- 알 수 없는 하위 키·범위 밖 값은 `invalid_plan`으로 거부한다(기존 `UnknownKeys`·`OptionalNumber` 재사용). 단계의 `monitor`는 모드 `Args`와 이름이 겹치지 않는다.
- 키가 없으면 기본값으로 감시한다. 기존 계획 JSON은 그대로 통과한다(하위 호환).

### 5. `get_flight` `plan.monitor` (최근 10 s 통계, 사용자 합의)

계획이 있을 때 `plan` 객체에 더한다.

```json
"monitor": {
  "window_s": 10.0,
  "samples": 500,
  "attitude_error_max": 3.2, "attitude_error_mean": 0.8,
  "angular_rate_max": 0.31,
  "sign_flips": 9,
  "aoa_max": 4.1,
  "temp_ratio_max": 0.42,
  "alerts": ["oscillation"]
}
```

- `window_s`는 실제로 쌓인 표본의 시간 폭(최대 10 s), `sign_flips`는 세 축 중 최댓값이다. 값이 하나도 없으면 null.
- `alerts`는 지금 경고·중단 상태인 항목 목록이다. 계획이 끝난 뒤에는 빈 목록이다(통계는 남은 창으로 계속 낸다).
- `sign_flips`는 마지막 틱의 병합 설정 `osc_min_rate`로 센다(`enabled: false`여도 갱신).
- 표본은 틱마다 한 개(물리 틱 약 50 Hz), 10 s 넘은 표본은 버린다. 레일 워프 중(packed)에는 쌓지 않는다.

### 6. 리로드 인계

- 표본 창·타이머·경고 상태는 넘기지 않는다. 리로드 뒤 창이 비어 다시 쌓이고, 이미 경고 중이던 항목은 조건이 이어지면 `monitor_alert`를 한 번 더 낸다(허용, 문서화).
- 설정은 계획 원본 JSON에 있으므로 리로드 뒤에도 같다.

### 7. MCP·문서 영향

- `submit_flight_plan` 설명: `monitor` 키, 감시 항목과 기본값, `plan_aborted` 사유 `monitor`, 조건 변수 목록에 `angular_rate`·`aoa`·`temp_ratio`.
- `get_flight` 설명: `flight`의 새 필드, `plan.monitor`.
- `get_flight_events` 설명: `monitor_alert`·`monitor_clear`.
- ReadMe 비행 계획 절에 감시 설명.
- 도구 이름·인자는 바뀌지 않는다.

## 검증 (2단계 완료 조건)

- Logic·App.Tools 빌드, `dotnet test tests/KspBridge.App.Tests` 통과.
- 계획 JSON: `monitor` 잘못된 키·값이 `invalid_plan`으로 거부되고, 키 없는 기존 계획이 그대로 통과함을 HTTP로 확인.
- 실측(MCP 응답·이벤트로만):
  1. 공력적으로 불안정한 기체(날개 없는 시험 기체)의 상승: `flipped` 또는 `control_lost`로 연료를 다 쓰기 전에 중단(이슈 완료 조건 2).
  2. 노즈콘 없는 기체, `gravity_turn` 기본값: `overheat` 경고(0.8) 뒤 중단(0.95)으로 파괴 전에 멈춤.
  3. `get_flight` `plan.monitor`가 상승 중 값을 내고, `angular_rate`·`aoa`·`temp_ratio`가 조건에서 동작.
  4. 착륙·역방향 하강 계획이 `flipped`로 중단되지 않음(`land` 또는 `retrograde` 자세 하강 중 감시 이벤트 없음).
  5. 진동 경고(`oscillation`): 이슈 완료 조건 "조종면 + 짐벌 기체에서 진동이 사라지거나, 감지되어 이벤트로 보고됨"은 3단계 자세 제어기 수정과 함께 판정한다. 2단계는 이 조건을 완료로 치지 않으며, 2단계 실측에서는 불안정 기체 상승 중 `plan.monitor` `sign_flips` 값이 나오는지만 본다.
