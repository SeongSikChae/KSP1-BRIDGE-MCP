# 구조정비 방안

이슈: [#29 구조 정비: Planner-Coordinator-Controller 원칙 기준 전수 조사와 핵심/보정 분리](https://github.com/SeongSikChae/KSP1-BRIDGE-MCP/issues/29)

관련: [0004-비행제어-방안.md](0004-비행제어-방안.md), [0005-비행제어-설계.md](0005-비행제어-설계.md)

## 문제

최초 방안 0004는 역할을 셋으로 나눴다.

- **Planner**(MCP 클라이언트 AI): 상태를 보고 계획을 세우고, 상황이 바뀌면 다시 계획한다.
- **Coordinator**(Mod, 게임 스레드): 계획을 단계별로 실행하고 완료·중단을 판정한다.
- **Controller**(Mod, 물리 프레임): 요청받은 단계를 실시간 제어로 수행한다.

이후 기능 추가와 실측 보정이 메인 Mode와 공용 코드 안에 쌓이면서 계층 책임이 섞였다. 한 기능을 고치면 다른 기능이 깨지고, Planner가 상황을 보고 개입할 수 없는 곳이 생겼다.

### 계기 (2026-11-17)

- 랑데뷰·도킹 실측(v0.2.63)에서 `dock` 단계가 포트 약 11.9 m부터 접촉까지 약 290 s 동안 0.03~0.04 m/s로 표류했다. 그동안 모노프로펠런트 감소는 약 0.01로, RCS를 사실상 분사하지 않았다. 결합은 됐지만 원인은 확정하지 못했다. `DockMode`의 하위 단계(Route·BackOut·Align·Advance)와 오차가 Planner에게 보이지 않기 때문이다.
- 이어서 전체 소스(약 21,000줄)를 독립 검토자 4명에게 맡겨 지적 28건을 받았다. 핵심 지적은 원본과 대조해 확인했다. 확인된 지적은 아래 "조사 사실"에 반영했다.

### 조사 사실

경로는 `src/KspBridge.Logic/Flight/` 기준이다.

1. **명령 형식이 한 기능 때문에 커졌다.**
   - `ModeCommand`(`Modes/IFlightMode.cs:30-83`) 필드는 설계 0005 당시 `Attitude`, `Throttle`, `ModeThrottle`, `WarpToUt` 4개였다. 지금은 11개다.
   - 추가된 7개 중 6개(`Aligning`, `PhysicsWarpOk`, `PhysicsWarpKeepOk`, `PhysicsWarpWhy`, `PhysicsWarpAttDeg`, `PhysicsWarpRate`)는 `LandMode`만 설정한다. 읽는 곳은 Coordinator·Warp(`Coordinator.cs:83-89`)와 FlightMonitor(`FlightMonitor.cs:61,87`)다.
2. **공용 코드에 land 특례가 들어갔다.**
   - `Coordinator.cs:65`: 자유낙하 중 과열 경고만 낸다.
   - `Coordinator.cs:83-89`: PhysicsWarp 값을 Warp로 넘긴다.
   - `Coordinator.cs:876-881`, `:925-934`: `_mode is LandMode` 분기다.
   - `FlightMonitor.cs:40,61,87,134`: 과열 특례와 `Aligning` 정지가 있다.
   - `Warp.cs:245-342`: 물리 ×2, `RailsFloor`, DIAG 최댓값을 둔다.
   - `Landing/LandingTracker.cs:333`은 `LandMode.WarpLeadS`를 거꾸로 참조한다(Landing → Mode). `Landing/ImpactPredictor.cs:33,42`는 주석에서만 LandMode 값을 언급한다.
3. **Controller가 할 실시간 제어가 Mode 안에 있다.**
   - `ApproachMode.cs:233-257`, `:328-368`: RCS 가속도 추정, 축 변환(`ToolAxes`).
   - `DockMode.cs:154-233`: 속도 법칙과 `(want - relV) / aRcs` 입력 계산.
   - `LandMode.cs:336-388`, `:869-910`: 수평 속도 루프와 기울기 제한.
   - Controller(`Control/AttitudeController.cs:228-234`)는 병진 입력에 불감대만 보정해 그대로 넘긴다.
4. **Planner가 할 예측·판단이 Mode 안에 있다.**
   - `LandMode.cs:683-845`: 착지점 예측, 연소 창, 보정 연소 결정과 중단 판정.
   - `ApproachMode.cs:83-181`: 최근접 예측, 재동기화, off_course 판정.
5. **보정을 붙일 자리가 없다.**
   - Mode 등록은 `Plan.cs:214-252`의 switch에 하드코딩돼 있다.
   - 명령을 덮어쓰는 지점은 `Coordinator.ComputeCommand`(`Coordinator.cs:241-260`)의 `AutoStager.Override` 하나뿐이다.
   - 그래서 보정은 메인 Mode나 공용 코드를 직접 고쳐서 넣어 왔다.
6. **Planner 경계 검사가 도구마다 따로 있어 빠진 곳이 있다.**
   - `submit_flight_plan`(`Handlers/FlightHandler.cs:17-22`)에는 장면 준비, 회수 대기, 전환 대기, 제어 가능 여부 검사가 없다.
   - 부품·리소스·액션 그룹·시간 가속 도구는 `Guard.ActiveVessel()`만 본다.
   - 전환 대기 검사(`VesselSwitch.RequireNotPending`)는 `switch_vessel`과 `open_tracking_station`에만 있다.
   - `open_editor`에는 회수 대기 검사가 없다(`Editor/CraftFiles.cs:299-313`).
7. **Mode가 묶은 내부 단계가 Planner에게 보이지 않는다.**
   - `dock`는 하위 단계를 노출하지 않는다.
   - `circularize`는 연소 시작·방향 고정을 로그로만 남긴다(`Modes/CircularizeMode.cs:131,145`).
   - `land`는 기어 전개와 감속 연소 시작을 이벤트로 남기지 않는다(`Modes/LandMode.cs:309-318`, `:500-503`).
8. **Planner 계약(도구 설명)이 동작과 다르다.**
   - `land`: 설명은 "no warp"인데(`src/KspBridge.App.Tools/FlightTools.cs:221`) 실제로는 자유낙하 중 워프한다(`LandMode.cs:465-482`). 목표 인자(latitude, longitude, vessel), 보정 연소, 이벤트(`landing_correction_*`, `landing_target_unreachable`), `get_flight.landing`도 설명에 없다.
   - `launch_craft`: 설명은 사전 점검 대화상자가 플레이어를 기다린다고 한다(`EditorTools.cs:168-172`). 실제로는 대화상자를 닫고 `preflight_failed`를 돌려준다(`Editor/CraftFiles.cs:251-266`).
   - 오류 코드 목록이 빠졌다: `plan_maneuver`·노드·`set_target`의 `scene_loading`, `not_controllable` 등과 `replace_flight_steps`의 `vessel_mismatch`.
   - 편집기 도구의 `ReadOnly`·`Destructive` 표기가 실제와 다르다.
9. **같은 규칙이 경로마다 다르게 적용된 결함**(검토 확인분)
   - `land`는 엔진 추력이 0이면 연소 창 판정보다 먼저 스로틀 1을 요구한다(`LandMode.cs:449-452`). 그래서 자유낙하 중에도 `no_thrust`나 다음 단 분리로 이어질 수 있다.
   - step `rcs` 켜기가 실패해도 이벤트가 남지 않는다(`Control/AttitudeController.cs:119`). 그런데 접근·도킹은 step 값으로 RCS를 쓸 수 있다고 판정한다(`ApproachMode.cs:331`).
   - reload 인계 때 계획을 현재 천체 기준으로 다시 검증한다(`Plan.cs:62,77`).
   - 시험 계산 중 스테이저 이벤트에 이전 계획의 step 번호가 붙는다(`Coordinator.cs:270-277`, `:320`).

## 목표

- 3계층 책임을 다시 세우고, 앞으로의 변경이 이를 지키게 한다.
- 다음 사용자 원칙을 구조로 보장한다.
  1. **Planner가 적절히 명령할 수 있는, 역할이 구별되는 도구를 만드는 데 주력한다.**
  2. **게임 내 로직(Coordinator·Controller·Mode)은 핵심만 구현한다.**
  3. **보정은 메인 기능을 고치지 않고 보정용 도구나 플러그인으로 붙인다.**
- 기능의 결과를 유지한다. 기능별 시나리오(발사·궤도, 기동 노드, 랑데뷰·도킹, 착륙, 장면 전환, 편집기)의 목표 달성과 핵심 지표가 유지되어야 한다. 이번 작업은 기능 추가가 아니라 구조 정비다.

  - 계획 형식: 기존 계획과의 호환을 포기한다. "계획 호환과 reload 인계" 참조.
  - Planner 도구 계약
  - "의도된 동작 변경" 표의 항목

### 계층별 책임

| 계층 | 할 일 | 하지 않을 일 |
| --- | --- | --- |
| Planner (MCP AI) | 상태·이벤트로 판단하고 step·도구를 조합한다. 정체·이상을 보면 즉시 재계획한다(중단, 교체, 수동 조작) | 프레임 단위 제어 |
| Planner 도구 (App + Logic 라우트) | 성격이 하나인 명령·조회·계산을 제공한다. 계약(설명, 오류 코드, 이벤트, 응답 필드)이 동작과 일치한다 | 한 도구에 계산과 숨은 상태 변경 섞기 |
| Coordinator | 계획 단계 실행, 완료·중단 판정, 조건 변수 매 틱 판정, 공통 규칙(추력 없음, 스테이징, 워프 요청 실행, 사건 예상 시각의 선행 시간 전 워프 종료), 보정 모듈 호출 | 특정 Mode 전용 분기 |
| 공용 계산 모듈 | 예측·계산(연소 창, 착지점, 최근접점)을 하고, 결과를 텔레메트리 조건 변수와 사건 예상 시각으로 낸다 | Mode·Coordinator 상태 변경, 판정 |
| Mode | 한 가지 단계 목표(자세, 스로틀, 원하는 상대 속도, 워프 목표 시각)를 내고 그 단계의 완료를 판정한다. 내부 상태를 Planner에게 노출한다 | 실시간 제어 루프, 예측·재계획, 측정 보정 |
| Controller | 목표를 기체 입력으로 바꾸는 실시간 제어(자세, 병진 속도) | 단계 판단 |
| 보정 모듈 | 프레임 단위로 꼭 필요한 보정을 명령 경로에 끼운다. 켜고 끌 수 있다 | 메인 Mode 수정 |

## 대안과 채택

### 1. Mode 단위

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| **핵심 단위로 분해 (채택)** | Mode가 한 가지 일만 해서 고칠 때 영향이 그 Mode에 그친다. 보정 연소·워프 같은 판단은 Planner가 step·도구로 조합해 보고 개입할 수 있다 | Planner가 조합할 step이 늘어난다. 묶음 동작은 계획 템플릿(예시 계획)으로 제공한다 |
| 묶음 유지, 내부 노출 | 기존 계획을 그대로 쓸 수 있다 | 판단이 Mode 안에 남아 보정이 계속 쌓인다 |
| 기능별로 따로 판단 | 변경량을 조절할 수 있다 | 기준이 갈린다 |

**시간에 민감한 판단의 위치 (채택: 조건 변수 + Coordinator 판정)**

0004는 AI가 느리거나 끊겨도 제출한 계획이 끝까지 실행되어야 한다고 정했다. 그래서 감속 연소 시작 시각, 낙하 중 워프 종료, 보정 연소 중단처럼 프레임 단위로 정확해야 하는 판단은 Planner가 실시간으로 내리지 않는다.

- **예측·계산**: 연소 창, 착지점, 최근접점 같은 값은 Mode 밖의 공용 계산 모듈이 한다. 결과는 텔레메트리 변수로 낸다(예: `brake_window`, 예측 착지 오차).
- **Planner**: 이 변수를 쓰는 `until`·`abort` 조건을 계획에 미리 적는다. 판단 기준은 Planner가 보고 바꿀 수 있다.
- **Coordinator**: 매 틱 조건을 판정해 단계를 전환한다. AI가 늦거나 끊겨도 계획은 계속 실행된다.
- **Mode**: 그 단계의 목표만 낸다. 예측과 재계획은 하지 않는다.
- **워프 선행**: 레일 워프 중에는 틱 사이 게임 시간이 크게 벌어진다. 그래서 조건이 참이 되기 전에 워프를 끝내야 한다. 공용 계산 모듈은 사건 예상 시각과 그 사건에 필요한 선행 시간을 함께 낸다. 그 시각보다 선행 시간만큼 앞서 워프를 끝내는 일은 Coordinator가 모든 단계에 같은 규칙으로 한다.
  - **사건 예상 시각**은 "행동을 시작해야 하는 시각"이다(예: approach의 kill 시작, 연소 모드의 연소 시작, land의 감속 시작, coast의 `until` 성립 시각). 이 시각을 구하는 계산은 공용 계산 모듈이 맡는다.
  - **현재 동작 보존 원칙**: 각 Mode의 현재 워프 종료 계산을 값과 동작 그대로 옮긴다. 대상은 식, 정렬 게이트 적용 여부, 상수다. Mode마다 다른 부분(어느 Mode가 정렬 게이트를 쓰는지, 점화 지연을 얼마나 빼는지, 선행 상수의 값 등)은 이 방안에 적지 않는다. 설계 문서의 분류표에 현재 코드 위치와 함께 Mode별로 적는다.
  - **상수의 자리**: 지금 Mode 안에 있는 선행 상수(예: `ApproachMode.KillLeadS`, `LandMode.WarpLeadS`)는 사건 시각 계산(공용 계산 모듈)과 선행 시간(사건별 값) 가운데 **한 곳에만** 둔다. 두 번 빠지지 않게 하기 위해서다. 어느 쪽에 둘지는 설계 분류표에서 상수마다 정한다.
  - 착지 예측기의 물리 스텝 정책(현재 `LandMode.WarpLeadS`를 같이 씀, #22 결정 12-2)도 공용 계산 모듈 안에서 같은 값을 쓴다.
  - Mode 전용 상수와 Landing → Mode 역참조(`LandingTracker.cs:333`)는 없앤다. 값과 동작은 바뀌지 않는다.

### 2. 보정을 붙이는 방식

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| **혼합 (채택)** | 판단·계획성 보정(보정 연소 결정, 디오빗 보정 등)은 Planner가 부르는 별도 도구·step으로 둔다. 물리 프레임마다 개입해야 하는 보정만 Mod 안의 등록형 보정 모듈(플러그인)로 Coordinator/Controller 명령 경로에 끼운다 | 보정 모듈 틀을 새로 만들어야 한다 |
| 전부 Planner 도구 | Mod가 가장 단순하다 | 프레임 단위 보정을 할 수 없다 |
| 전부 Mod 플러그인 | Planner 도구가 늘지 않는다 | 판단이 다시 Mod 안에 숨는다 |

### 3. 실시간 제어의 위치

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| **Controller로 통합: 공통 인터페이스 + 구동기별 구현 (채택)** | Mode는 "목표 상대 속도"와 구동 수단(RCS 또는 주 엔진)만 낸다. Controller는 구동기별로 구현한다. RCS 병진은 가속도 추정, 축 변환, 불감대를 맡는다(approach·dock). 주 엔진 벡터링은 기울기 제한과 수직 감속 우선을 맡는다(land). 제어 코드가 Controller 한 곳에 모인다 | 세 Mode의 제어 코드를 옮겨야 한다. 구동기가 둘이라 구현도 둘이다 |
| RCS 병진만 통합 | 변경량이 적다 | land의 수평 속도 루프가 Mode에 남는다 |
| Mode 안에 두고 공용화 | 변경량이 가장 적다 | Mode가 계속 Controller 일을 한다 |

RCS 병진을 먼저 만들어 dock·approach에 쓴다. 주 엔진 벡터링은 land를 옮길 때 만든다.

### 4. 진행 방식

| 대안 | 장점 | 단점 |
| --- | --- | --- |

- **알려진 결함**: "의도된 동작 변경" 표에 있거나 기준선에서 결함으로 표시한 항목이다. 예를 들어 dock의 접촉 전 표류가 있다. 이 항목은 개선 방향의 변화만 허용한다.
- **기준선 기록**: 시나리오마다 2회 기록한다.

### 9. 첫 이동 대상

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| **dock·approach (채택)** | 이번 실측 문제가 있고 크기가 작다(약 850줄). 병진 제어 통합, Mode 분해, 내부 상태 노출 틀을 검증하기 좋다. 랑데뷰·도킹 시나리오로 회귀를 확인한다 | land의 큰 특례는 뒤로 미뤄진다 |
| land | 가장 많이 얽힌 곳(약 2,300줄, 공용 코드 특례 다수)을 먼저 푼다 | 단위가 크고 실측이 길다 |
| 경계 검사·계약부터 | Mode를 건드리지 않아 위험이 낮다 | 핵심 문제(Mode 안 제어·판단)는 뒤로 밀린다 |

**dock·approach 분해 (채택: 우회는 approach, 결합은 dock 하나)**

- **approach**: 표적 뒤에서 앞으로 도는 경로를 맡는다. 포트 앞 지점까지 접근하는 일은 이미 approach가 하고 있다.
- **dock**: "포트 축 정렬 → 전진 → 접촉" 하나의 목표만 맡는다. 내부 상태(단계, 축 거리, 측면 오차)는 `get_flight`와 이벤트로 노출한다.
- **재시도**: dock은 스스로 판단하지 않는다. Planner가 이벤트를 보고 step을 다시 내거나, `abort` 조건으로 정한다.

### 10. 계획 호환과 reload 인계

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| **호환 포기 (채택)** | 새 형식만 받는다. 바뀐 단위부터 기존 mode 이름과 인자를 거부하고, 도구 설명을 같은 단위에서 고친다. 옛 형식을 지탱하는 코드가 남지 않는다 | 기존 계획(예: `land` 한 step 착륙)을 다시 써야 한다 |
| 기존 mode 이름을 템플릿으로 유지 | 기존 계획이 그대로 돈다 | 변환 계층이 생긴다 |
| 폐기 기간 뒤 제거 | 전환 기간이 있다 | 두 형식이 한동안 공존한다 |

- **reload 인계**: 계획 형식 버전을 함께 저장한다. 버전이 다르면 사유를 밝혀 `reload_incompatible`로 명시적으로 중단한다.
- **형식 버전 산출**: 사람이 올리지 않는다. 계약 선언에서 해시로 자동 산출한다.
  - **해시 범위**: 인계되는 계획이 실제로 쓰는 mode·인자·조건 변수의 선언만 넣는다. 선언에는 이름, 의미 설명, 인자의 형식·단위·기본값·필수 여부가 들어간다. 계획이 쓰지 않는 mode의 설명을 고치거나 새 조건 변수를 추가해도, 진행 중인 계획의 reload는 중단되지 않는다.
  - **의미 변경**: 인자의 의미만 바꿔도 선언의 설명이 바뀌므로 버전이 바뀐다.
  - **해시 입력**: 이름순으로 정렬하고 직렬화 형식을 고정한다. 같은 선언이면 항상 같은 해시가 나온다.
  - **버전 필드가 없는 인계**: 기존 인계도 불일치로 보고 중단한다.
  - **선언 삭제·이름 변경**: 계획이 쓰던 mode·인자·조건 변수가 새 코드에서 삭제되거나 이름이 바뀌어 해시를 다시 계산할 수 없으면, 불일치로 보고 `reload_incompatible`로 중단한다.
- **천체 재검증 결함**: 인계 때 현재 천체로 계획을 다시 검증하는 결함(`Plan.cs:62,77`)도 이 항목에서 고친다.

## 전수 조사 방법

- **대상**: 모든 MCP 도구, Mode, 보조 모듈(Landing, Maneuver, Warp, AutoStager, FlightMonitor 등)을 빠짐없이 다룬다.
- **분류**: 각 항목을 다음 다섯 가지로 나눈다.
  - (a) 단계 목표
  - (b) 실시간 제어
  - (c) 계획·예측
  - (d) 측정 보정·진단
  - (e) 게임 상태 직접 변경
- **분류표 내용**: 항목마다 이동할 계층(Planner 도구, Coordinator, Mode, Controller, 보정 모듈)과 이동 단위를 적는다.
  - Planner 도구는 성격, 공통 검사, 계약 일치 여부를 함께 적는다.
  - Mode는 현재 워프 종료 계산(식, 정렬 게이트 적용 여부, 상수와 그 코드 위치)과 상수마다의 자리(사건 시각 계산 또는 선행 시간 중 한 곳)를 함께 적는다. "워프 선행"의 현재 동작 보존 원칙과 상수의 자리 원칙이 이 필드로 지켜진다.
- **분류표 위치**: 분류표 전체는 설계 문서에 둔다. 이 방안의 "조사 사실"은 그 출발점이다.

## 진행 순서 (개략)

1. **기준선 기록**: 기능별 실측 시나리오를 정하고 현재 결과를 MCP 응답으로 시나리오마다 2회 기록한다. "의도된 동작 변경" 항목은 표시해 둔다.
2. **원칙 문서**: 상시 원칙 문서와 저장소 `CLAUDE.md` 연결을 만든다.
3. **틀**: 경계 검사(도구 성격별), 계약 생성·검사, 보정 모듈 등록 틀, Controller 병진 제어를 만든다.
4. **기능 이동**: dock·approach → land → 나머지 Mode 순서로 옮긴다. 마지막으로 공용 코드의 Mode 전용 특례와 `ModeCommand` 전용 필드를 제거한다.
5. **회귀 확인**: 단위마다 해당 시나리오와 App 테스트로 확인한다.

## 위험

- **실행 위치 이동**: 실시간 제어를 Mode(Coordinator 틱의 `ComputeCommand`)에서 Controller(`OnFlyByWire`)로 옮기면 갱신 순서·주기와 시험 계산(trial) 처리가 달라질 수 있다. 같은 법칙이라도 결과가 바뀔 수 있으므로 해당 단위의 시나리오 지표로 확인한다.
- **분해 뒤 Planner 부담**: step이 늘어 Planner가 조합할 일이 많아진다. 기능별 예시 계획을 문서와 도구 설명에 둔다.
- **조건 변수 의존**: 시간에 민감한 판단이 조건 변수에 달린다. 변수의 값 없음(null)과 갱신 주기를 계약에 명시한다.
