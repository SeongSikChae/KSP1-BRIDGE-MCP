# KspBridge 시간 가속 — 설계

선행: `0018-시간가속-방안.md`

## HTTP (로직, 비행 장면 + 활성 기체 필요)
### POST /api/warp/to
- 요청: `{"target": "ut"|"ap"|"pe"|"node"|"soi", "ut": 12345 (target=ut만), "lead": 30}`
- 목표 UT 계산
  | target | 목표 UT | 없으면 |
  |---|---|---|
  | ut | 요청값 | — |
  | ap | now + `orbit.timeToAp` | 탈출 궤도(e ≥ 1)면 409 `no_target` |
  | pe | now + `orbit.timeToPe` | — |
  | node | 첫 노드 `UT` | 노드 없음 409 `no_target` |
  | soi | `orbit.EndUT` (`patchEndTransition`이 ENCOUNTER·ESCAPE) | 전환 없음 409 `no_target` |
- 정지 UT = 목표 − lead. 정지 UT ≤ now + 1이면 400 `bad_request`(이미 지남/너무 가까움)
- 사전 거부(409 `warp_not_allowed`, 사유 포함): 스로틀 > 0(레일 워프 불가), 현재 고도의 최대 레일 배속(`GetMaxRateForAltitude`)이 0 = 대기권·저고도
- 실행: 진행 중 자동 워프 `CancelAutoWarp()` → `TimeWarp.fetch.WarpTo(stopUT)`(스톡 기본 max/min 시간)
- 응답: `{target, target_ut, stop_ut, now_ut, duration}`. 즉시 반환 — 도착은 `wait_until ut >= stop_ut` 또는 트리거로

### POST /api/warp
- 요청: `{"rate": 100, "physics": false}`
- rate는 해당 모드 배속표(`warpRates` 1,5,10,50,100,1000,10000,100000 / `physicsWarpRates` 1,2,3,4)의 값과 정확히 일치해야 함, 아니면 400에 허용값 목록
- 레일: 모드 HIGH → `SetRate(index, instant: false)`. 물리: 모드 LOW → `SetRate(index, false)`
  - 모드 변경은 스톡 비공개 `setMode`를 리플렉션으로 호출(배속 > 1에서 모드 바꾸면 스톡처럼 1배속을 거침)
- 스톡이 낮춘 경우(고도 한계 등) 응답 `limited: true`와 실제 배속
- rate 1 = 정지와 같음
- 응답: `{requested, rate, index, mode, limited}`

### POST /api/warp/stop
- `CancelAutoWarp()` → `SetRate(0, instant: true)`. 응답 `{rate_before, rate}`

### 상태 (GET /api/vessel에 추가)
```json
"warp": {"rate": 100, "index": 4, "mode": "rails", "stop_ut": 8123.4, "max_rails_rate_here": 100000}
```
- `stop_ut`: 이 모드가 시작한 warp_to의 정지 UT(끝났거나 취소되면 null)
- `ut`는 이미 최상위에 있음

## 트리거와 워프 (결정: 참이 되면 워프 정지)
- `TriggerManager.FixedUpdate`에서 조건이 참이 되고 `TimeWarp.CurrentRateIndex > 0`이면
  1. `CancelAutoWarp()` + `SetRate(0, instant: true)`
  2. 레일 워프였으면(기체 `packed`) 동작을 바로 실행하지 않고 상태 `pending` → 기체가 레일에서 내려온(`!v.packed`) 첫 틱에 실행. 레일 위에서 분리·스로틀을 실행하면 무시되거나 깨질 수 있기 때문
  3. 물리 워프였으면 1배속으로 내린 같은 틱에 실행
- 기록: `fired_value`는 참이 된 틱의 값(워프 때문에 목표를 넘었는지 Claude가 판단), 새 필드 `warp_stopped_from`(배속, 없으면 null)
- 반복(repeat) 트리거도 같은 규칙

## 조건 필드 추가
- `ut`(숫자): `wait_until ut >= stop_ut`, 트리거 조건에 사용

## 비범위
레일 워프 중 자세 유지, 트리거 동작으로 워프 시작(`warp` 동작 타입), 다른 장면 워프

## 구현 중 변경 (2026-11-08)
- 상태 필드: `max_rails_rate_here`(현재 고도 기준) → `max_rails_rate` + `rails_limit`. 스톡 기본 `ORBIT_WARP_MAXRATE_MODE`가 Pe 기준이라 현재 고도 함수(`GetMaxRateForAltitude`)는 50배로 잘못 표시(실제 1,000배 허용) → 스톡 판정 `getMaxOnRailsRateIdx`(리플렉션) 사용, warp_to 사전 거부도 같은 판정
- 검토 반영(0.6.2)
  - warp_to: 자동 워프 진행·대기 중이면 409 `warp_busy`(스톡 코루틴이 바로 멈추지 않아 두 개가 동시에 돌 수 있음)
  - stop_warp/set_warp: `setAutoWarp=false`도 지움(warp_to 직후 아직 시작 전인 자동 워프 취소)
  - 트리거: 워프 판정을 `v.packed || CurrentRate > 1`로(감속 중 index 0이어도 레일 위면 pending)
  - soi: 노드 뒤 패치까지 따라가 SOI 전환 탐색
  - stop_ut: 자동 워프 시작 전에 지워지지 않게
- 알려진 동작(수정 안 함)
  - set_warp는 스로틀 검사 없음(물리 워프는 분사 중 정상, 레일은 스톡 제한기가 처리)
  - SOI 임박 시 상태 조회마다 스톡 로그 1줄
  - pending 트리거는 사용자가 다시 워프를 걸면 1배속이 될 때까지 대기(워프를 다시 멈추지 않음)
  - 레일 워프 중 트리거: 조건 판정이 틱 간격만큼 늦고(1,000배속에서 약 7~19초), 레일 해제까지 추가로 약 16~19초 흐름 → 정밀 타이밍은 warp_to lead로 미리 멈춘 뒤 트리거 사용
- 게임 검증 (2026-11-08, Claude 재시작 후 MCP 도구, KB Orbiter 1 귀환)
  - warp_to ap lead 40 → 1,363초를 약 12초에 지나 time_to_ap 40.0에 정지 → 역추진(Pe 24.9km)
  - set_warp 100 → Pe가 대기권 안이라 스톡이 50배로 낮춤(`limited: true`), 72km 트리거가 50배에서 워프 정지(71.9km)
  - 71.9km(대기권 직전)에서는 warp_to pe가 허용됨 → 스톡 자동 워프가 70km 진입 시 스스로 1배속 정지. 대기권 안(69.6km)에서는 409 `warp_not_allowed (not_in_atmosphere)`
  - 물리 4배 워프로 하강, 6km 낙하산 트리거가 4배에서 워프 정지 후 같은 틱 실행(5,983m) → 착지(312m)·회수
