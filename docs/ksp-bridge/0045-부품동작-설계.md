# 부품동작 설계 (3단계: 연료 전달)

이슈: [#15](https://github.com/SeongSikChae/KSP1-BRIDGE-MCP/issues/15)
방안: [0040-부품동작-방안.md](0040-부품동작-방안.md)
2단계 설계: [0043-부품동작-설계.md](0043-부품동작-설계.md)

방안 결정 1의 3단계(연료 전달)만 다룬다. 방안 결정 4(시간에 걸친 전달, 진행 확인·취소), 7(`set_resource`는 editor 전용으로 두고 바꾸지 않음), 8(실행 중 비행 계획 허용), 9(활성 기체만), 10(실행 기록)을 따른다. 1·2단계 도구는 바꾸지 않는다(`get_flight_events` 설명에 새 이벤트 종류만 더한다).

## 게임 동작 (디컴파일, Assembly-CSharp)

### PAW Transfer In/Out (`UIPartActionResourceTransfer`)

- 자원 행마다 In·Out·Stop 버튼이 있다. 상태는 `None`·`Out`·`In`.
- 버튼은 `transferRequiresFullControl`이면 `TWEAKABLES_FULLONLY`, 아니면 `TWEAKABLES_ANYCONTROL`(0x1000) 잠금이 풀려 있어야 동작한다. `transferRequiresFullControl`은 선언만 있고 어디서도 쓰지 않으므로(전체 디컴파일 검색) 항상 `TWEAKABLES_ANYCONTROL`이다. 잠금은 버튼을 누를 때만 보고, 전달 중에는 다시 보지 않는다.
- In 버튼: 열린 다른 창의 같은 자원 행(`targets`)을 모두 Out으로 바꾸고, 그중 잔량이 0보다 큰 행 수를 `transferFraction`으로 해 자신을 In으로 둔다.
- Out 버튼: 자신을 Out으로 두고, 다른 행들 가운데 가득 차지 않은 행 수를 `transferFraction`으로 해 모두 In으로 둔다.
- 매 프레임(`UpdateItem`), In 상태인 행
  - 가득 찼거나 `transferFraction == 0`이면 멈춘다. 활성(`activeInHierarchy`)이면서 상태가 `None`이 아닌 상대 행이 하나도 없어도 멈춘다.
  - 아니면 `양 = maxAmount / 20 / transferFraction × Round(UT − lastUT, 2)`를 구하고, Out 상태인 원본마다 `min(양, 원본 잔량, 자기 빈 용량)`만큼 `TransferResource`로 옮긴다(자기 쪽 `+val`, 원본 쪽 `−val`).
  - `transferFraction`은 누른 버튼에 따라 다르다. In(대상 1개, 원본 여럿)은 잔량이 있는 원본 수라 대상은 초당 자기 용량의 1/20을 받는다. Out(원본 1개, 대상 여럿)은 가득 차지 않은 대상 수라 대상마다 초당 자기 용량의 1/20을 대상 수로 나눈 만큼 받는다. 값은 시작 때 고정된다.
- Out 상태인 행은 잔량이 0 이하가 되면 멈춘다.
- 시간 간격은 UT 차이이므로 물리 가속·on rails 시간 가속 중에도 같은 비율로 진행된다.
- 흐름 잠금(`PartResource.flowState`)은 보지 않는다.

### 전달 가능 조건

- 행이 생기는 조건(`UIPartActionWindow`): 2단계 설계의 자원 행 조건(`CanActivateResource`: `maxAmount != 0`, 활성 기체 부품, `isVisible`)에 더해, 비행 장면에서 `info.resourceTransferMode != NONE`이고 `UIPartActionController.ShowTransfers(r)`가 참이어야 한다.
- `ShowTransfers(r)`
  - 열린 창이 2개 이상이다.
  - `GameVariables.UnlockedFuelTransfer(R&D 시설 레벨)`: 정규화 레벨 `> 0.2`.
  - 열린 창의 부품마다 그 자원이 있다. `AdvancedParams.ResourceTransferObeyCrossfeed`가 켜져 있으면 `r.part.CanCrossfeed(창 부품, id)`도 참이어야 한다.
- `Part.CanCrossfeed(target, id)`: 자원 정의의 흐름 방식이 `STACK_PRIORITY_SEARCH`·`STAGE_STACK_FLOW(_BALANCE)`면 crossfeed 부품 집합에 있어야 하고, `ALL_VESSEL(_BALANCE)`·`STAGE_PRIORITY_FLOW(_BALANCE)`면 같은 기체면 되고, 그 밖(`NO_FLOW` 등)은 자기 자신뿐이다.
- `Part.TransferResource(resource, amount, other)`
  - `resource.flowMode`가 `None`이면 아무것도 하지 않는다. 넣을 때 `Out`, 뺄 때 `In`이면 아무것도 하지 않는다.
  - 넣을 때는 빈 용량, 뺄 때는 잔량에서 잘린다. 비행 중이면 다른 부품과의 온도를 섞는다.
  - 반환값은 남은 요청량 형태라 실제 이동량으로 쓰기 어렵다. 이 설계는 호출 전후 `amount` 차이로 실제 이동량을 잰다.

## 결정

| # | 항목 | 결정 |
| --- | --- | --- |
| 1 | 대상 지정 | 원본 부품 목록·대상 부품 목록(각 1개 이상). 게임에서 원본 창들을 Out, 대상 창들을 In으로 둔 것과 같다(사용자 결정) |
| 2 | 속도 | 게임 규칙: 대상마다 `대상 maxAmount / 20 / n × dt`를 원본마다 옮긴다. 원본이 1개면 Out 버튼 규칙으로 `n` = 시작 때 가득 차지 않은 대상 수, 원본이 여럿이면 In 버튼 규칙으로 `n` = 시작 때 잔량이 0보다 큰 원본 수(원본·대상이 모두 여럿이면 대상마다 In을 누른 것과 같다). `n`은 시작 때 고정. `dt = Round(UT − lastUT, 2)`(사용자 결정, 계획 검토 R1) |
| 3 | 양 | `amount`(선택, 0 초과). 대상 전체가 받은 합계가 `amount`에 이르면 끝낸다. 생략하면 원본이 모두 비거나 대상이 모두 찰 때까지 |
| 4 | 흐름 잠금 | 게임과 같게 보지 않는다. 응답의 부품 행에 `flow_enabled`를 보여 준다(사용자 결정) |
| 5 | 동시 전달 | 한 번에 하나. 진행 중 시작 요청은 409 `transfer_running`(사용자 결정) |
| 6 | 도구 | `start_resource_transfer`·`get_resource_transfer`·`stop_resource_transfer` 3개(사용자 결정) |
| 7 | 시간 가속 | 게임과 같게 UT 차이로 계속 진행한다. on rails여도 멈추지 않는다 |
| 8 | 잠금 | 시작 때만 `TWEAKABLES_ANYCONTROL`(창 포커스 잠금 제외, `PartStates.Unlocked`)을 본다. 전달 중 조종 상태가 바뀌어도 계속한다(게임과 같음) |
| 9 | flowMode | 원본은 `Out`·`Both`, 대상은 `In`·`Both`여야 시작한다. 게임은 막힌 쪽을 조용히 건너뛰어 한쪽만 바뀔 수 있으므로 시작 때 거부한다 |
| 10 | 실제 이동량 | 원본에서 먼저 뺀다: 원본 `TransferResource(−val)` 전후 차이를 뺀 양으로 보고, 그 양을 대상에 `+`로 넣어 대상 전후 차이를 받은 양으로 잰다. 받은 양이 뺀 양보다 적으면 남는 양을 원본 `amount`에 직접 더해 되돌린다(`TransferResource`는 flowMode `Out`인 원본에 넣기를 거부하므로 쓰지 않는다). 되돌린 뒤에도 원본 감소량과 대상 증가량이 다르면(1e-9 초과) `error`로 끝낸다. 자원이 새로 생기지 않게 한다 |
| 11 | 중단 | 매 Tick에 활성 기체 id가 시작 때와 다르면 `vessel_changed`, 부품이 죽었거나 활성 기체를 떠났으면 `part_lost`로 끝낸다. 장면 전환은 `FlightScene.OnScene`에서 `scene`, `reload_mod`는 `logic_stop`. 도킹으로 활성 기체 id가 유지되면 계속한다 |
| 12 | 상태 보관 | 마지막 전달(진행 중 또는 끝난 것) 하나를 보관해 조회에 돌려준다. 새 전달을 시작하면 바뀐다. `reload_mod` 뒤에는 없다 |
| 12a | 끝내기 안전 | `Stop`은 예외를 던지지 않는다(`BridgeLogic.Stop`에서 `Coordinator.Stop` 앞에 부르므로 인계가 끊기지 않게). 진행 해제·`end_reason`·`ended_ut`(마지막 Tick UT)를 먼저 정하고, 부품 다시 읽기와 끝 이벤트 기록을 각각 따로 try로 감싼다. 기록이 실패한 경우에만 끝 이벤트가 빠지고 KSP.log에 오류 줄이 남는다 |
| 13 | 취소 | 진행 중이면 `stopped`로 끝내고 그 상태를 돌려준다. 진행 중이 아니면 오류 없이 `stopped: false`와 마지막 상태를 돌려준다 |
| 14 | 기록 | 시작은 `resource_transfer_start`, 끝(완료·취소·중단)은 `resource_transfer_end` 이벤트와 같은 `[KspBridge]` KSP.log 줄(`PartStates.Log`) |
| 15 | 계획 실행 중 | 허용한다(방안 결정 8). 계획 단계 번호는 `PartStates.Log`가 붙인다 |

#### 시작 요청

```json
{ "resource": "LiquidFuel", "source_part_ids": [123, 456], "target_part_ids": [789], "amount": 50 }
```

검사 순서와 오류(앞에서 걸리면 뒤는 보지 않는다)

1. `Guard.ActiveVessel()`: 기존 `not_in_flight`·`no_active_vessel`.
2. 요청 형식: `resource`(문자열), `source_part_ids`·`target_part_ids`(숫자 목록, 각 1개 이상), `amount`(있으면 0 초과 유한 수). 목록 키가 없거나 배열이 아니면 기존 `RequestBody.GetList` 문구(`'<key>' must be an array`) 그대로 400이다. 같은 id가 목록 안이나 두 목록에 겹치면 400 `bad_request`.
3. 진행 중 전달이 있으면 409 `transfer_running`.
4. 부품이 활성 기체에 없으면 404 `part_not_found`(기존 `PartStates.PartNotFound` 문구).
5. 부품에 그 자원 행이 없으면(자원이 없거나 `maxAmount == 0` 또는 `!isVisible`) 404 `resource_not_found`(`set_resource_flow`와 같은 문구 형식).
6. 자원 정의 `resourceTransferMode == NONE`이면 409 `not_transferable`.
7. R&D 시설 레벨로 전달이 열리지 않았으면 409 `transfer_not_unlocked`.
8. `ResourceTransferObeyCrossfeed`가 켜져 있으면 목록의 모든 부품 쌍(a≠b)에 `a.CanCrossfeed(b, id)`가 참이어야 한다. 아니면 409 `no_crossfeed`(어느 부품에서 어느 부품으로 막혔는지 메시지에 적는다).
9. 원본 `flowMode`가 `Out`·`Both`가 아니거나 대상 `flowMode`가 `In`·`Both`가 아니면 409 `flow_mode_blocked`.
10. `TWEAKABLES_ANYCONTROL` 잠금(포커스 잠금 제외)이 걸려 있으면 409 `transfer_locked`.
11. 원본 잔량이 모두 0이거나 대상이 모두 가득 찼으면 409 `nothing_to_transfer`.

성공하면 전달을 시작하고 상태(아래)를 돌려준다.

#### 상태 응답 (시작·조회·취소 공통)

```json
{
  "active": true,
  "id": 3,
  "resource": "LiquidFuel",
  "requested": 50,
  "transferred": 12.5,
  "ut": 133.4,
  "started_ut": 123.4,
  "ended_ut": null,
  "end_reason": null,
  "sources": [{ "part_id": 123, "part": "fuelTank", "amount": 170.0, "max_amount": 180.0, "flow_enabled": true }],
  "targets": [{ "part_id": 789, "part": "fuelTankSmall", "amount": 52.5, "max_amount": 90.0, "flow_enabled": false }]
}
```

- `id`: 로직 기동 뒤 시작한 전달의 순번(1부터).
- `requested`: `amount`, 생략했으면 null.
- `transferred`: 대상 전체가 받은 합계.
- `error`: `end_reason`이 `error`일 때 원인 문구(그 밖에는 null). 끝 이벤트의 `error`와 같다.
- `ut`: 응답 시점 UT(비행 장면이 아니면 null). 속도를 UT 기준으로 잴 수 있게 한다.
- `end_reason`: `done`(요청량 도달) · `source_empty` · `target_full` · `stopped` · `vessel_changed` · `part_lost` · `scene` · `logic_stop` · `error`.
- 부품 행의 `amount`·`flow_enabled`는 응답 시점 값이다. 끝난 전달에서 부품을 찾을 수 없으면 마지막으로 읽은 값을 그대로 둔다.
- 전달한 적이 없으면 같은 키에 `active: false`, `id: null`, 나머지는 null·빈 목록으로 돌려준다.
- 조회·취소는 비행 장면이 아니어도 동작한다(마지막 상태를 돌려줄 뿐 기체를 건드리지 않는다).
- 취소 응답: 상태에 `stopped`(이번 요청으로 끝냈으면 true)를 더한다.

### 매 Tick (`BridgeLogic.FixedUpdate` → `ResourceTransfer.Tick()`, 예외를 던지지 않음)

1. 진행 중이 아니면 끝.
2. 활성 기체 id 비교 → `vessel_changed`. 부품 확인 → `part_lost`.
3. `dt = Round(UT − lastUT, 2)`, `lastUT = UT`.
4. 대상마다(가득 차지 않은 것) `rate = max / 20 / n × dt`, 원본마다(잔량 > 0) `val = min(rate, 원본 잔량, 대상 빈 용량, 남은 요청량)`을 원본에서 빼서 대상에 넣는다(결정 10).
5. 남은 요청량이 0 → `done`, 원본이 모두 비면 `source_empty`, 대상이 모두 차면 `target_full`.
6. 예외는 잡아 `error`로 끝내고 KSP.log에 남긴다.

## 비범위

- 비행 계획 단계에서 전달.
- 다른 기체(도킹되지 않은 기체) 사이 전달.
- 비행 중 자원량 직접 설정(`set_resource`는 editor 전용 유지).
- 여러 전달 동시 진행.
