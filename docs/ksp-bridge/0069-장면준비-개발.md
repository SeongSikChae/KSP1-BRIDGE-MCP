# 장면준비 개발 (바로 구현)

게임이 장면 초기화 일부를 코루틴으로 몇 프레임 뒤로 미루는데, 모드가 그 완료를 확인하지 않고 명령을 실행해 생긴 버그 두 개를 고친다. 대기 시간을 어림하지 않고, 게임이 미룬 초기화가 끝났는지를 직접 확인한다.

## 원인 (2026-11-16 실측·디컴파일)

1. 편집기: `open_editor`(기체 지정) 직후 `launch_craft`가 `internal: NullReferenceException`.
   - `EditorLogic.Start` 코루틴: `SetupFSM` → `StartEditor` → `fsm.StartFSM` → `yield return null` → `InitAnalytics()`(`timeInMode` 생성) → `availableCargoParts` 대입(코루틴 마지막).
   - 모드의 `EditorScene.Ready`는 `FSMStarted`에서 참이 되어 `yield` 다음 프레임을 기다리지 않는다. 그 사이 `launchVessel` → `FinalizeAnalytics`가 null `timeInMode`에서 예외(Player.log `POST /api/editor/launch failed ... at EditorLogic.FinalizeAnalytics`).
2. 비행: 발사 직후 `on_start: ["stage"]`가 엔진을 켜지 못하고 `no_thrust`로 중단(`U5d 재진입 시험`, `회귀 호퍼`).
   - `StageManager.ResumeFlight`는 현재 스테이지 설정과 `canSeparate = true`를 즉시 하고, 스테이지 목록은 `SortIcons(instant: false)` 코루틴(2프레임 이상 뒤)으로 만든다.
   - `ActivateStage`는 번호를 `0..stages.Count − 1`로 자르므로 목록이 비면 −1이 되어, 스테이지 없는 부품(−1)만 작동시키고 현재 스테이지를 −1로 둔다. 로그 `stage request sent: stage -1`, `confirmed: stage 3 -> -1`.
   - 모드의 `StageRequest`는 `StageManager.CanSeparate`만 확인해 그 창에 요청을 보냈다. 발사 때 게임이 쓴 기체 사본(`자동 저장된 기체.craft`)의 `istg`는 정상이라 편집기 쪽 문제는 아니다.

### 확장 원인 (같은 날 실측, 사용자 지적)
- 앱 툴바 버튼이 네 묶음으로 중복됐다. `CraftFiles.RequireOpenableScene`는 `HighLogic.LoadedScene`만 봐서, `leave_flight` 직후 우주 센터 장면이 초기화 중일 때 `open_editor`가 들어갔다(Player.log 비행→우주 센터→편집기 연속 전환, UI 앱 생성·파괴가 뒤섞이며 `GenericAppFrame.Reposition`·`ActionGroupsApp` NRE). `leave_flight`·`revert_flight`·`recover_vessel`은 이미 `FlightReset.RequireSceneReady()`를 쓰는데 편집기 도구만 빠져 있다. 이미 생긴 중복은 장면을 넘어 유지되는 `ApplicationLauncher`에 남아 KSP 재시작 전에는 되돌리지 못한다.
- `clear_site` 없이 발사대가 차 있는 채 `launch_craft` → 게임 `PreFlightCheck`의 `LaunchSiteClear` 실패 → "TestWarning" 대화 상자(에이전트가 닫을 수 없음). 그 위에서 `open_editor`로 편집기를 다시 불러오자 대화 상자가 `persistAcrossScenes: false`로 `OnDismiss` 없이 파괴돼 `EditorLogic_launchSequence` 잠금이 고아로 남았고, 이후 `launch_craft`가 계속 `launch_locked`.
- 디컴파일: `launchVessel`은 `Lock(..., "EditorLogic_launchSequence")` → `GetStockPreFlightCheck(site).RunTests()`. 전부 통과하면 `proceedWithVesselLaunch` → `goForLaunch` → 1프레임 뒤 `Unlock` + `FlightDriver.StartWithNewLaunch`. 실패하면 `PopupDialog`("TestWarning", 이름 `"TestWarning dialog handler"`의 GameObject), 응답·닫힘(`OnDismiss`)에서 `abortLaunch` → 1프레임 뒤 `Unlock`.

## S4. 사전 점검 실패를 게임 대화 상자에서 읽어 409로

**대상**: `CraftFiles.Launch`

점검을 흉내 내지 않는다. 게임은 `launchVessel` 안에서 잠금 → 기체 저장 → 승무원 목록(`ShipConstruction.ShipManifest`) 설정 → `RunTests` 순으로 점검하고(`NoControlSources`는 그 승무원 목록을 쓴다), 실패하면 같은 호출 안에서 동기로 "TestWarning" 대화 상자를 띄운다(디컴파일 `PreFlightCheck.runNextTest`). 그래서 `launchVessel`을 그대로 부르고, 돌아온 직후 그 대화 상자가 있으면 내용(`MultiOptionDialog`의 공개 필드 `title`·`message`)을 읽어 409로 돌려주고 게임이 Esc로 닫는 것과 같은 순서(`OnDismiss` → `Dismiss`)로 닫는다. `OnDismiss = Abort` → `abortLaunch` → 1프레임 뒤 `Unlock`이 게임 자신의 중단 경로라 잠금이 남지 않는다. 공개 함수 `PopupDialog.DismissPopup`·`Dismiss`는 `OnDismiss`를 부르지 않으므로 쓰지 않는다(계획 재검토 지적, 디컴파일 확인).

```csharp
EditorLogic.fetch.launchVessel(site);
// A failed pre-flight test opens its dialog synchronously inside launchVessel (PreFlightCheck.runNextTest, decompile checked).
// A tool cannot answer it, and a scene change would destroy it without OnDismiss and orphan the launch lock: read it and
// dismiss it through the game, whose OnDismiss is the game's own abort (abortLaunch unlocks a frame later).
GameObject handler = GameObject.Find("TestWarning dialog handler");
if (handler != null)
{
    PopupDialog popup = handler.GetComponent<PopupDialog>();   // SpawnPopupDialog adds it to this handler object (always set)
    // MultiOptionDialog(name, msg, windowTitle): title = the test's GetWarningTitle, message = GetWarningDescription
    string why = popup.dialogToDisplay != null
        ? popup.dialogToDisplay.title + ": " + popup.dialogToDisplay.message : "a pre-flight check failed";
    // The game's own way to close it (PopupDialog Update on Esc): OnDismiss, then Dismiss. Dismiss alone only destroys it and
    // would never call Abort, leaving the launch lock behind (decompile checked).
    popup.OnDismiss?.Invoke();
    popup.Dismiss();
    throw new ApiException(409, "preflight_failed", why + " (the game's pre-flight check; nothing launched. " +
        "A vessel on the site: clear_site true recovers it)");
}
```
- 판정과 입력은 게임 것 그대로다(승무원 목록 포함). 실패 사유 문구는 게임 대화 상자의 제목·본문(현지화 문구)이다.
- 게임은 "그래도 진행" 선택지가 있는 경고도 대화 상자로 띄운다. 도구는 응답할 수 없으므로 이것도 409로 돌려주고 발사하지 않는다(지금은 대화 상자에 막혀 멈추는 것보다 낫다. 진행 선택지 지원은 범위 밖).
- `Mission` 계열 게임은 기존대로 `not_supported`(바뀌지 않음).

## S5. 진행 중인 발사 동안 편집기 재로드 거부, 고아 잠금 해제

**대상**: `EditorScene` 새 `Tick()`(매 물리 틱), `BridgeLogic.FixedUpdate`에서 호출, `CraftFiles.Open`·`New`

잠금의 주인을 어림하지 않고, 게임 흐름이 이 잠금을 쥐는 조건(디컴파일)으로 판정한다. `launchVessel`은 같은 호출 안에서 잠금을 걸고 점검을 끝낸다. 그 뒤 잠금이 정당하게 남는 경우는 다음뿐이다.
- 사전 점검 대화 상자("TestWarning")가 떠 있음: 응답·닫힘에서 `Abort`(→ 1프레임 뒤 `Unlock`) 또는 다음 점검.
- 회수 대화 상자가 떠 있음: `goForLaunch`는 편집기의 `missionDialogs`(`List<MissionRecoveryDialog>`)가 비어 있지 않으면 잠금을 쥔 채 돌아가고, 모두 닫히면(`onMissionDialogDismiss`) 다시 `goForLaunch`.
- 그 밖에는 1프레임: 통과 `goForLaunch`의 `DelayedCallback(1, Unlock + StartWithNewLaunch)`, 중단 `DelayedAbort`의 `yield return null` → `Unlock`.

이 잠금은 편집기(`EditorLogic`)만 걸고 풀 수 있다. 그러니 편집기가 아닌 장면에서 로딩이 끝났는데 남아 있는 잠금도 주인이 없는 고아다(장면과 함께 파괴된 대화 상자). 모드는 매 틱 관찰해 스스로 푼다. 도구 호출 시점에 의존하지 않는다.

```csharp
const string LaunchLock = "EditorLogic_launchSequence";
static readonly FieldInfo MissionDialogs =
    typeof(EditorLogic).GetField("missionDialogs", BindingFlags.Instance | BindingFlags.NonPublic);
static int _lockFreeSince = -1;   // Time.frameCount when the lock was first seen with nothing holding it

// EditorScene.Tick (BridgeLogic.FixedUpdate, never throws)
public static void Tick()
{
    if (!Flight.FlightReset.SceneReady || !InputLockManager.lockStack.ContainsKey(LaunchLock)) { _lockFreeSince = -1; return; }
    if (HighLogic.LoadedScene != GameScenes.EDITOR)
    {
        Orphan("outside the editor, which alone can release it");   // no EditorLogic: nothing will ever unlock it
        return;
    }
    if (MissionDialogs == null) { _lockFreeSince = -1; return; }   // cannot see recovery dialogs: never guess inside the editor
    if (GameObject.Find("TestWarning dialog handler") != null || MissionDialogsOpen()) { _lockFreeSince = -1; return; }
    if (_lockFreeSince < 0) { _lockFreeSince = Time.frameCount; return; }
    if (Time.frameCount - _lockFreeSince < 2) return;   // the game's own hold without a dialog is one frame
    Orphan("no pre-flight or recovery dialog for 2+ frames");
}
static bool MissionDialogsOpen() =>
    EditorLogic.fetch != null && MissionDialogs != null && MissionDialogs.GetValue(EditorLogic.fetch) is ICollection c && c.Count > 0;
static void Orphan(string why)
{
    InputLockManager.RemoveControlLock(LaunchLock);
    _lockFreeSince = -1;
    Debug.LogWarning("[KspBridge] orphaned " + LaunchLock + " lock removed (" + why + ")");
}

// CraftFiles.Open / New, after RequireSceneReady, only in the editor scene (outside it Tick has already released any such lock):
if (HighLogic.LoadedScene == GameScenes.EDITOR && InputLockManager.lockStack.ContainsKey(LaunchLock))
    throw new ApiException(409, "launch_locked", "a launch is in progress in the editor; poll get_status input_locks");
// Launch: unchanged, the existing launchLocks check refuses it
```
- 플레이어 발사와 모드 발사를 같은 기준으로 다룬다. 사전 점검·회수 대화 상자가 떠 있는 동안(플레이어가 응답할 수 있음)은 풀지 않는다.
- `FixedUpdate`는 물리 틱마다 불리고 `Time.frameCount`로 프레임을 센다. 2프레임 기준은 게임 코드의 1프레임 대기에서 나온 것이지 어림값이 아니다.
- `missionDialogs` 필드를 못 찾으면(게임 버전 차이) 회수 대화 상자 대기를 알 수 없으므로, 그때는 편집기 안 2프레임 해제를 하지 않고 편집기 밖 해제만 한다(오판으로 정상 발사의 잠금을 풀지 않는 쪽).

## S6. 앱 툴바의 주인 없는 버튼·중복 버튼과 콜백 정리 (사용자 요청 "이 UI/UX 이상현상 좀 해결해봐")

**원인**(Player.log·디컴파일)
- 각 `UIApp`은 `Awake`에서 `onGUIApplicationLauncherReady`를 구독하고, 이벤트마다 `AddToAppLauncher`(5프레임 뒤 `AddApplication`, `AddOnHide/Show/RepositionCallback`)로 버튼과 콜백을 더한다. 버튼 참조는 `appLauncherButton` 하나에 덮어쓴다. `OnDestroy`는 그 마지막 버튼 하나와 콜백 한 벌만 지운다.
- 모드가 `leave_flight` 직후 `open_editor`를 보내 우주 센터·편집기 로딩이 겹쳤을 때(48906·50314·51389행), 편집기 앱이 준비 이벤트를 `scene SPACECENTER`·`scene EDITOR`로 두 번 받아 버튼·콜백을 두 벌 만들었다. 남은 한 벌은 앱이 파괴돼도 `ApplicationLauncher`(`DontDestroyOnLoad`)에 남는다. 그래서 툴바 버튼이 여러 묶음으로 쌓였고, 파괴된 앱의 재배치 콜백이 불릴 때 `GenericAppFrame.Reposition` NRE가 났다.
- 비행 툴바에 묶음이 4번 보인 경로(Player.log 51732~51910): 편집기 앱(`AlarmClock`, `ActionGroupsApp`, `Missions App`, `EngineersReport`, `DeltaVApp`, `KSPedia`)이 겹친 로딩마다 `Adding … to Application Launcher`를 두 번 찍었다. 겹친 로딩이 세 번이었으므로 주인 없는 묶음 3벌과 정상 1벌이 남는다. 주인 없는 버튼은 만든 앱의 `GetAppScenes()`를 `VisibleInScenes`로 가지므로 비행 장면에서도 보이는 앱(알람 시계, KSPedia 등)은 비행 툴바에 쌓인다. 이 버튼들의 `onTrue`는 모두 `UIApp.Show`(인스턴스 메서드, `Target`이 그 앱)다(디컴파일 `AddToAppLauncher`: `Callback onTrue = Show`). 순정이지만 `UIApp`이 아닌 버튼이 묶음에 섞여 있는지는 정리 전 로그(아래 "로그")로 실측해 판정한다.
- 비행 장면의 `ResourceDisplay` 두 번 등록(53661·53664행)은 원인이 아니다. 둘째 인스턴스는 등록을 마친 뒤 "already exist, destroying this instance"로 파괴되고(53676·53679행), 그 `OnDestroy`가 자기 버튼과 콜백을 직접 지운다. 버그 이전 비행 로드(16513~16531행 등)에서도 매번 같은 순서이며 중복을 남기지 않는다. 그래서 `before`에 `ResourceDisplay` 중복이 없는 것이 정상이다.
- 재발 방지는 S3(로딩 완료 전 `open_editor` 거부)이다. S6은 이미 쌓인 것을 지운다.
- 새 파일인 이유: 툴바 정리는 편집기 상태(`EditorScene`)와 무관하게 모든 장면에서 돈다. 사용자 요청으로 태스크를 확장할 때 `allowed_paths`에 이 파일을 넣었다.

**대상**: `src/KspBridge.Logic/Editor/AppLauncherRepair.cs`(새 정적 클래스), `BridgeLogic.FixedUpdate`에서 `Tick()` 호출

```csharp
// Stock buttons, shown and hidden (ApplicationLauncher.appList / appListHidden, private; SetHidden moves a button between them,
// RemoveApplication removes it from both and from the layout list): a UIApp's button calls the app's own Show (onTrue = Show,
// a public Callback field of ApplicationLauncherButton).
foreach (ApplicationLauncherButton b in appList.Concat(appListHidden).ToArray())
{
    if (!(b.onTrue?.Target is UIApp app)) continue;            // not a UIApp button (other stock or mod buttons): leave it
    if (app == null || !ReferenceEquals(app.appLauncherButton, b))   // owner destroyed, or a second button of a live app
        ApplicationLauncher.Instance.RemoveApplication(b);     // the game's own removal (lists, layout item, mutual exclusion)
}
// onHide / onShow / onReposition (private multicast delegates, read by reflection): each invocation entry whose target is a
// destroyed UIApp, and copies of the same (target, method) beyond the first for a live UIApp, are removed through the public
// RemoveOnHideCallback / RemoveOnShowCallback / RemoveOnRepositionCallback (no reflection write).
```
- 판정은 게임 상태(주인 앱의 생존과 그 앱이 기억하는 버튼)로만 한다. 시간이나 개수를 어림하지 않는다.
- 구현에서 바로잡음(실측): 버튼의 `onTrue`는 버튼이 만든 빈 람다에 `Setup`이 앱의 `Show`를 `Delegate.Combine`한 다중 델리게이트다. `onTrue.Target`만 보면 앱이 나오지 않아 첫 실행에서 버튼 27개가 모두 `other`로 분류됐다(콜백 56개만 정리). 그래서 주인은 `GetInvocationList()`의 항목 가운데 대상이 `UIApp`인 것으로 찾는다(`Owner`).
- `apps with !=1 button`은 버튼이 1개 이상 남은 살아 있는 앱만 센다(버튼 0개인 앱은 세지 않음, R2-1-B-3 남은 위험).
- `AddToAppLauncher`는 `AddApplication` 반환값을 같은 문장에서 `appLauncherButton`에 넣는다. 그래서 정상 등록 중인 버튼을 중복으로 오판하지 않는다.
- **언제 도는가**: `BridgeLogic.FixedUpdate`에서 `Tick()`을 부르되, 장면 로딩이 끝났을 때(`FlightReset.SceneReady`)만 본다. 매 틱에는 두 목록의 개수와 세 델리게이트의 참조만 읽는다(할당 없음). 델리게이트는 불변이라 `Add/Remove…Callback`마다 새 인스턴스가 되므로, 지난 검사 때와 개수·참조가 모두 같으면 아무것도 하지 않는다. 바뀌었을 때만 전체를 훑는다. 앱이 파괴되면 그 `OnDestroy`가 콜백을 지워 참조가 바뀌므로 그 뒤 첫 틱에 다시 훑는다.
- **예외를 던지지 않는다**: 전체를 `try/catch`로 감싼다. 예외가 나면 `Debug.LogError` 1회 뒤 이 로직 인스턴스에서는 정리를 멈춘다(같은 예외의 매 틱 반복과 로그 폭주를 막는다. `reload_mod`로 다시 시작된다). 뒤 순서의 Tick에는 영향이 없다.
- 리플렉션 필드(`appList`, `appListHidden`, `onHide`·`onShow`·`onReposition`)를 하나라도 못 찾으면 아무것도 하지 않는다(정리 생략, 기존 동작).
- **로그**(지울 것이 있을 때만, 화면 없이 판정하는 근거)
  - 정리 전: `[KspBridge] app launcher before: <형식이름>×<개수>, …`(`UIApp` 버튼은 `onTrue.Target`의 형식 이름과 생존 여부, 그 밖의 버튼은 `other`로 묶음)
  - 정리: `[KspBridge] app launcher repaired: buttons removed N (orphan a, duplicate b), callbacks removed c`
  - 정리 뒤 상태: `[KspBridge] app launcher after: live UIApp buttons <n> for <m> apps, apps with !=1 button <k>, dead-target callbacks <d>, other buttons <before>-><after>`

**검증(S6)**
- 빌드·테스트.
- 실측: `reload_mod` 뒤 Player.log
  - `before`에 같은 형식의 `UIApp` 버튼 여러 개(주인 없는 것 포함)가 보이고, `repaired`의 제거 수가 0보다 크다.
  - `after`에서 `apps with !=1 button 0`, `dead-target callbacks 0`, `other buttons`의 앞뒤 수가 같다(정상·다른 버튼을 지우지 않았다).
  - 이후 장면 전환(비행 → 우주 센터 → 편집기, S3로 로딩 완료 뒤에만)에서 `GenericAppFrame.Reposition` NRE가 새로 없다. 전환 뒤 `repaired`가 나오면 `before` 내용으로 새 중복인지(같은 살아 있는 앱의 버튼 2개) 판정한다. 장면마다 앱이 새로 생기고 파괴되는 정상 교체는 `OnDestroy`가 직접 지우므로 `repaired`를 내지 않는다.
- 툴바 모양은 화면으로 확인하지 않으므로 사용자에게 한 번 봐 달라고 부탁한다(판정 근거는 위 로그).

**실측 결과(S6, 비행 장면 `reload_mod`)**
- 1차(주인 판정 수정 전): `before: other×27`, `callbacks removed 56`, `after: dead-target callbacks 0, other buttons 27->27`. 파괴된 앱의 콜백만 지워졌다.

**남은 위험(S6)**
- 지우는 중복 버튼이 켜진 상태(앱 창이 열림)이면 `RemoveApplication`은 `onFalse`를 부르지 않는다. 창이 열린 채 남을 수 있다(사용자가 다시 버튼을 누르면 닫힘). 낮음.
- `UIApp`을 상속한 모드가 `AddApplication`을 직접 불러 반환값을 `appLauncherButton`이 아닌 곳에 두면 그 버튼을 중복으로 지운다. 해당 여부는 정리 전 로그의 형식 이름으로 확인한다. 낮음.

## S1. 스테이지 목록이 준비된 뒤에만 작동

**대상**: `src/KspBridge.Logic/Flight/StageRequest.cs` `Tick`, 새 private 도우미 `StagesReady`

**코드 초안**

```csharp
// StageManager.ResumeFlight sets canSeparate at once but builds the stage list in a SortIcons coroutine 2+ frames later;
// ActivateStage clamps to stages.Count − 1, so an empty list activates stage −1 and drops currentStage to −1 (decompile
// checked, measured: stage 3 -> -1 with no engine lit). Send only once the sort is done and the list exists.
private static readonly FieldInfo SortRoutine =
    typeof(StageManager).GetField("sortRoutine", BindingFlags.Instance | BindingFlags.NonPublic);

private static bool StagesReady()
{
    StageManager sm = StageManager.Instance;
    return sm != null && sm.Stages.Count > 0 && (SortRoutine == null || SortRoutine.GetValue(sm) == null);
}

// Tick:
if (due && StageManager.CanSeparate)
{
    if (!StagesReady())
    {
        if (!_heldLogged)   // once per request: proof the race window was hit and held (not saved: diagnostics only)
        {
            _heldLogged = true;
            UnityEngine.Debug.Log("[KspBridge] stage request held: stage list not ready (stages " + ... + ", sort pending " + ... + ") ut " + ut);
        }
        return Result.Waiting;
    }
    StageManager.ActivateNextStage();
    ...
}
```

- 필드를 못 찾으면(게임 버전 차이) 정렬 대기는 건너뛰고 `Stages.Count > 0`만 본다.

## S2. 편집기 Start 코루틴 완료 뒤 준비

**대상**: `src/KspBridge.Logic/Editor/EditorScene.cs` `Ready`

**코드 초안**

```csharp
// EditorLogic.Start: ... fsm.StartFSM -> yield return null -> InitAnalytics (timeInMode) -> availableCargoParts (its last
// statement). FSMStarted is true one frame before that tail; launchVessel then throws in FinalizeAnalytics (measured).
private static readonly FieldInfo CargoParts = typeof(EditorLogic).GetField("availableCargoParts", Private);

bool started = ... existing conditions ...;
bool ready = started && (CargoParts == null || CargoParts.GetValue(editor) != null);
if (started && !ready && !ReferenceEquals(editor, _tailLoggedFor))   // once per EditorLogic: proof this condition held a call
{
    _tailLoggedFor = editor;
    UnityEngine.Debug.Log("[KspBridge] editor ready held: EditorLogic.Start tail pending");

```

- `get_status` `editor.ready`와 `Require()`(→ `editor_not_ready` 409)가 같은 판정이라 둘 다 바로잡힌다.

**검증**
- 빌드·테스트(`dotnet build`, `dotnet test tests/KspBridge.App.Tests`).
- 실측(MCP 응답, 판정 근거 기록만 Player.log): `leave_flight` → `open_editor`(기체 지정) → 곧바로 `launch_craft` → 곧바로 `submit_flight_plan`(`U5d 재진입 시험`, `auto_stage: true`, `gravity_turn` 76000 `on_start: ["stage"]` → `circularize`).
  - 편집기: `launch_craft`가 `internal` 오류 없이 `editor_not_ready`로 거부되거나 발사된다. 거부되면 `get_status` `editor.ready`가 참이 된 뒤 다시 보낸다.
  - 비행: 첫 `staged` 이벤트가 엔진이 있는 스테이지(이 기체는 `stage 2`)이고 `no_thrust` 중단이 없다. Player.log `stage request sent`가 −1이 아닌 번호다.
  - 경쟁 창 통과 증거(비행·편집기 따로 판정): 수정이 실제로 막았다는 증거는 Player.log 보류 기록이다. 비행은 `stage request held`(정렬 대기 3프레임 이상이라 잡히기 쉬움), 편집기는 `editor ready held`(Start 꼬리 1프레임이라 드묾)다. `editor_not_ready` 응답만으로는 장면 로딩 중의 기존 거부와 구분되지 않으므로 증거로 쓰지 않는다. 한 번의 발사에서 관찰되지 않은 쪽은 같은 순서로 최대 3회까지 다시 한다.
  - 3회 안에 관찰되지 않은 쪽은 그 항목만 "경쟁 창 미재현(수정 효과 미확인)"으로 보고하고 사용자 판단을 받는다. 그 경우 편집기 쪽은 수정 전 재현 기록(같은 순서에서 `FinalizeAnalytics` NRE)과 디컴파일 근거만 남는다는 점을 함께 적는다. 다른 항목(정상 발사·점화·회귀)의 판정은 따로 한다.
  - 회귀(같은 비행): 상승 중 자동 분리(`staged stage 1 separate`)와 점화(`staged stage 0 ignite`)가 이어지고, `circularize`까지 궤도 투입된다.
  - 회귀(리로드): 1단 연소 중 `reload_mod`를 한 번 하고(`logic_reloaded resumed: true`), 그 뒤 자동 분리·점화가 정상이다. 리로드 뒤 `ResumeFlight`는 부르지 않으므로 정렬 대기는 없을 수 있다(기록만).
  - 범위 밖으로 남김: 발사 클램프 기체(`ClampHold`), 스테이징 부품이 없는 기체의 `Failed`, 기체 전환 직후 요청. 이 기체·계획으로는 지나지 않는다.

**선행 단위**: 없음
