# KspBridge 부품 테스트 — 설계

선행: `0020-부품테스트-방안.md`

## 연결 규칙 (스톡과 같음)
- 활성 계약 `ContractSystem.Instance.GetCurrentActiveContracts<Contracts.Templates.PartTest>()` 중 `PartName == part.partInfo.title`인 계약을 그 부품의 테스트 계약으로 본다(ModuleTestSubject.delayedStart와 같은 비교)
- 계약 안의 `Contracts.Parameters.PartTest` 파라미터(직계 자식)를 찾는다 → `hauled`, 하위 조건(`GetParameter(i)` 제목·상태)
- `ready` = 파라미터 상태가 Incomplete이고 `AllChildParametersComplete()`
- 테스트 방식: 모듈 `useEvent` → `event`, 아니고 `useStaging` → `staging`, 계약이 운반이면 `haul`

## HTTP (로직, 비행 장면 + 활성 기체, 커리어)
### GET /api/part-tests
```json
{"tests": [
  {"part_id": 4012345678, "part": "HeatShield1", "title": "방열판 (1.25m)", "method": "event",
   "contract_id": 693185070711, "contract": "방열판 (1.25m)(을)를 커빈 비행 중 테스트.",
   "state": "Incomplete", "ready": false, "event_active": true, "armed": false,
   "conditions": [{"title": "커빈", "state": "Complete"}, {"title": "고도: 36,000m 에서 45,000m", "state": "Incomplete"}]}
]}
```
- 활성 기체의 부품 중 `ModuleTestSubject`가 있고 연결 계약이 있는 것만. 같은 부품이 여러 개면 각각 한 줄(`part_id` = `part.flightID`)
- 이미 완료된 계약 파라미터는 `state: Complete`, `ready: false`

### POST /api/part-tests/run
- 요청: `{"part": "HeatShield1" | 4012345678, "force": false}` — 이름(부품 name 또는 title)이 여러 개에 맞으면 400(part_id로 지정하라는 메시지)
- 거부: 연결 계약 없음 404 `no_test`, 이미 완료 409 `already_done`, 운반 계약 409 `haul_only`(실행할 것 없음), `ready`가 아니고 force 아님 409 `not_ready`(미충족 조건 제목 목록)
- 실행: `event`면 `ModuleTestSubject.RunTestEvent()`(스톡 "테스트 실행"과 같음, 단계 아이콘 부품은 함께 활성화), `staging`이면 `part.force_activate()`(OnActive → RunTest)
- 응답: `{part_id, part, method, ready_before, state_after}` — state_after는 실행 직후 계약 파라미터 상태

### POST /api/part-tests/arm
- 요청: `{"part": ...}`. 검사는 run과 같되 `not_ready`는 거부하지 않음
- 트리거로 등록: 조건 `part_test_ready`(그 부품, 내부 판정), 동작 `part_test`(force=false로 run과 같은 실행). 단발
- 응답: 트리거 Describe(기존 형식, `when: {"field": "part_test_ready", "part_id": ...}`)
- 트리거와 같은 규칙: list_triggers에 보임, remove_trigger로 취소, 기체·장면 바뀌면 삭제, 워프 중이면 워프 정지 후 실행(레일이면 off-rails 후)
- 실행 시 이미 완료됐으면(다른 경로로 완료) 동작은 아무것도 안 함

## 트리거 변경 (TriggerManager)
- Trigger에 내부 조건 함수(`Func<Vessel, object>`)를 둘 수 있게 함 — 없으면 기존처럼 FlightFields.Read
- 동작 타입 `part_test`는 arm 경로에서만 생성(add_trigger 공개 동작 목록에는 넣지 않음)

## MCP 도구 (새 PartTestTools 또는 CareerTools에 추가)
| 도구 | HTTP | 비고 |
|---|---|---|
| `list_part_tests()` | GET /api/part-tests | ReadOnly |
| `run_part_test(part, force=false)` | POST /api/part-tests/run | Destructive(부품 소모 가능) |
| `arm_part_test(part)` | POST /api/part-tests/arm | |
- part 인자는 문자열(name/title) 또는 숫자(part_id) — JsonElement로 받아 그대로 전달

## 구현 중 변경 (2026-11-08)
- 검토 반영(로직 0.7.1)
  - staging 방식(낙하산·디커플러·엔진, 스톡 cfg `useStaging=True, useEvent=False`): 부품의 staging이 꺼져 있으면 `OnActive`가 테스트를 부르지 않음 → 이 경우 `RunTest()`를 직접 호출한 뒤 `force_activate`
  - 무장 실행 직전 `ready` 재확인: 워프 정지 사이에 구간을 벗어났으면 실행하지 않고 다시 armed(발동 횟수에 넣지 않음) — 내부 동작은 `Func<Vessel,bool>`(false = 계속 무장)
  - 한 부품에 계약 여러 개: 부품 기준 한 줄로 묶음, `ready` = 어느 계약이든 ready, 대표 계약은 ready → 미완료 → 첫 번째 순, 나머지는 `other_contracts`. 응답에 `staging_on` 추가
- 알려진 동작(수정 안 함): 무장 중에는 매 물리 틱 계약 목록·부품 모듈을 훑음(성능 비용만)
- 게임 검증 (2026-11-08, Claude 재시작 후 MCP 도구)
  - Mk16 낙하산 계약 수락 → KB Test Flea는 정점 13~16km라 조건(4~7km, 30~120m/s) 불가 판단, 발사대에서 회수
  - 새 기체 KB Chute Hopper(Mk1 사령선, Mk16, FL-T100×2, LV-T45, 핀 3; 8부품 3.5t, Δv 825m/s ASL)
  - 발사대에서 list_part_tests: parachuteSingle method staging, staging_on true, 조건 "커빈" Complete. arm_part_test → 트리거 id 1(part_test_ready)
  - Ap ≥ 6,000(값 `6000.0` — 378.0 수정 확인) 엔진 차단 → 정점 5,024m 부근 MET 22.7초에 무장 테스트 자동 실행 → 계약 Completed(조건 4개 Complete), list_part_tests 빈 목록
  - 착지: 지면 40m 감속(스로틀 0.3) → 속도 +3.7m/s로 튀어 오른 뒤 정지·전복(다리 없음), 손상 없음, 회수
- 방열판 비행 (2026-11-08, KB Orbiter 1H = Orbiter 1 + 사령선 아래 HeatShield1 + 분리단 HeatShield0) — **비행으로서는 실패**(사용자 판정)
  - 결과: 0.625m 운반(상승 중 25km·1,119m/s 전에 완료), 1.25m 테스트(무장 → MET 465 자동 실행) 계약은 완료. 자금 155,010 → 213,567
  - 실패 1 — 궤도 진입 실패: 상단(끝 질량 ~1.3t) 위에 방열판·어블레이터 ~0.38t를 얹어 Δv가 크게 줄었는데 발사 전 `get_stages` 실측을 보지 않음(build_craft 추정은 상단 연료 과다 계산) → 원궤도화 중 연료 고갈, Pe −85km 준궤도로 낙하. 테스트 구간 통과는 우연
  - 실패 2 — 재진입 자세: 분리 직후 SAS retrograde를 걸었으나 이후 stability_assist로 바뀌어 사령선 앞쪽이 진행 방향을 향한 채(방열판이 뒤쪽) 테스트 구간을 지남. 사용자 지적 후 24km에서 다시 retrograde. 모드가 바뀐 원인 미확인
  - 발견 — accept_contract(id) 정수 인자: 19자리 id(192925036314244835)가 2^53을 넘어 MCP 경유 시 …830으로 바뀜 → HTTP 직접 호출로 수락. 이후 수정: accept/decline_contract의 id를 문자열 인자로 받아 그대로 URL에 전달(App, 테스트 ContractIdKeepsAllDigits)
  - HeatShield0/1은 디커플러 부품이지만 staging_on=false라 테스트 실행 시 분리되지 않음, 착수 시 10m/s→6m/s 바다 착수·회수
