# KspBridge 핫 리로드 — 방안

## 문제
- 모드 로직(조립, 트리거, 자세 제어, 핸들러)을 고칠 때마다 KSP 재시작이 필요하다. KSP 재시작은 느리다(로딩 수 분).
- 원인: KSP(Unity 2019 Mono, .NET Framework)는 시작 시 `GameData`의 플러그인을 한 번 로드하고, 로드한 어셈블리는 내릴 수 없다.

## 후보
| 방안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. 로더 + 교체 가능한 로직 DLL | 작은 로더(`KspBridge.dll`, KSPAddon)가 HTTP 서버·디스패처·FixedUpdate 호출만 유지. 로직은 `KspBridge.Logic.dll`을 `Assembly.Load(byte[])`로 로드, `/api/reload`로 새 버전 로드 후 교체 | 대부분의 수정이 재시작 없이 반영 | 구 버전 어셈블리는 메모리에 남음(재시작 전까지 누적), 로직의 정적 상태·이벤트 구독을 교체 전에 정리해야 함 |
| B. 계산 로직을 MCP 서버로 이동 | 모드는 게임 데이터 조회·실행만, 배치·추정 등 계산은 .NET 10 서버 | 서버는 Claude 앱 재시작으로 갱신, 테스트 쉬움 | 매 물리 갱신 로직(트리거, 자세, 예측)은 이동 불가, 데이터 전송 API 추가 필요 |
| C. A + B | 둘 다 | 재시작 최소 | 작업량 최대 |

## 추천: A
- 이번 대화의 재시작 원인은 대부분 모드 로직(조향 부호, SAS 방식, 배치, 트리거, 스로틀 고정)이었다 → A가 모두 해결
- 로더는 거의 바뀌지 않는 최소 코드로 유지

## A의 고려 사항(설계에서 결정)
- 로더↔로직 계약: 로더가 정의한 인터페이스(`IBridgeLogic`: Start(context), BuildRoutes, Update, FixedUpdate, Stop)만 공유. 로직 어셈블리는 `[KSPAddon]`을 쓰지 않음(KSP가 시작 시에만 스캔)
- 교체 순서: 새 DLL 로드·초기화 성공 → 구 로직 Stop(트리거·스로틀 고정·자세 제어 해제, GameEvents 구독 해제, OnFlyByWire 제거) → 라우트 교체. 실패 시 구 로직 유지
- 비행 중 교체 시 진행 중인 트리거·자세 유지는 해제됨(명시)
- 로직 DLL 위치: `GameData/KspBridge/Logic/`(KSP가 자동 로드하지 않도록 `.dll`이 아닌 확장자 또는 PluginData 폴더 사용)
- 빌드 후 복사는 로직 DLL만 → `/api/reload`(MCP 도구 `reload_mod`) 호출
- `/api/status`에 로더 버전·로직 버전·로드 횟수 표시
