# 비행제어 방안

이슈: [#2 비행제어: Planner/Coordinator/Controller 3계층 비행체 제어](https://github.com/SeongSikChae/KSP1-BRIDGE-MCP/issues/2)

관련: [0001-기체설계-방안.md](0001-기체설계-방안.md) (기체 설계·발사 도구)

## 문제

KspBridge는 VAB/SPH에서 기체를 설계하고 발사대로 보내는 데(`launch_craft`)까지만 다룬다.
발사 뒤 기체를 MCP 클라이언트(AI)가 목표(예: 궤도 진입)까지 비행시킬 수단이 없다.

AI가 조종 입력을 직접 보내는 방식은 맞지 않는다.

- 자세·스로틀 제어는 물리 프레임(약 50Hz)마다 해야 하는데, AI 도구 호출은 수 초 단위다.
- 분리·점화 같은 단계 전환은 프레임 단위로 정확해야 한다. AI 응답이 늦거나 끊기면 기체를 잃는다.

## 목표

- 역할을 셋으로 나눈다.
  - **Planner**: 기체 상태와 주변 정보를 보고 목표까지의 계획을 세운다. 상황이 바뀌면 다시 계획한다.
  - **Coordinator**: 계획을 받아 단계별로 Controller에 제어를 요청하고, 단계 완료·중단을 판정한다.
  - **Controller**: 실시간으로 기체 상태를 읽어 요청받은 단계를 수행하도록 기체를 제어한다.
- AI가 느리거나 연결이 끊겨도 제출한 계획은 끝까지(또는 중단 조건까지) 실행된다.
- 사용자는 같은 비행을 게임 화면에서 그대로 본다.

## 구조 개요

```
Planner (MCP 클라이언트 AI)
   │  계획 제출·교체              ▲ 상태·이벤트 조회
   ▼  (MCP 도구 → HTTP)           │
Coordinator (Mod, 게임 스레드) ── 현재 단계의 모드·목표 ──▶ Controller (Mod, 물리 프레임)
   ▲  완료·중단 조건 판정 ◀──────── 기체 상태 ────────────────┘
```

## 대안과 채택

### 1. 계층 배치

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| **Coordinator·Controller 모두 Mod (채택)** | 단계 전환이 프레임 단위로 정확함. AI·App이 늦거나 끊겨도 계획이 계속 실행됨. `reload_mod`로 반영 | Mod(Logic) 코드가 늘어남 |
| Coordinator는 App, Controller는 Mod | Mod 코드가 줄어듦 | HTTP 폴링 때문에 전환이 늦어짐. App이 끝나면 제어 공백이 생김 |

Planner는 MCP 클라이언트 AI 자신이다. KspBridge는 Planner가 쓸 MCP 도구(계획 제출, 상태·이벤트 조회)를 제공한다.

### 2. 계획 형태 (Planner → Coordinator)

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| **단계 목록 + 조건 (채택)** | 단계마다 제어 모드·목표값·완료 조건·중단 조건을 둔다. Coordinator가 조건을 판정해 다음 단계로 자동 전환한다. Planner는 언제든 계획 전체나 남은 단계를 바꿀 수 있다(재계획) | 계획 형식과 조건 표현을 정의해야 함 |
| 한 단계씩 지시 | 단순함 | 단계 경계마다 AI 왕복 지연. 분리·점화 타이밍에 취약 |

### 3. Controller 저수준 제어

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| **자체 제어기, 제어 중 스톡 SAS 끔 (채택)** | `OnFlyByWire`로 자세·스로틀을 직접 계산한다(PID 등). 모든 자세를 한 경로로 제어해 SAS와 입력이 충돌하지 않는다. 계획이 끝나면 SAS를 원래 상태로 되돌린다. 외부 모드에 의존하지 않음 | 제어기 구현·튜닝 필요 |
| 자체 제어기 + 스톡 SAS 보조 | prograde 등 SAS가 지원하는 방향은 SAS에 맡겨 구현이 줄어듦 | 파일럿 레벨에 따라 SAS 모드가 없을 수 있어 경로가 둘로 갈림 |
| MechJeb 등 외부 모드 연동 | 검증된 오토파일럿 재사용 | 해당 모드 설치가 필수가 되고 버전에 의존함 |

### 4. Planner 피드백

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| **상태 조회 + 이벤트 로그 (채택)** | 비행 상태(궤도·고도·속도·Δv·현재 단계) 조회와 cursor 기반 이벤트 로그(단계 완료·스테이징·중단 등). 이벤트를 놓치거나 중복으로 받지 않음. 모든 MCP 클라이언트에서 동작 | AI가 조회하지 않으면 이벤트를 늦게 앎 |
| 조회 + 로그 + 대기 도구 | 반복 조회가 줄어듦 | 호출이 오래 걸리고 클라이언트 타임아웃 위험 |
| 대기 도구만 | 단순함 | 현재 상태를 바로 볼 수 없음 |

### 5. 안전·시간 가속

- **중단 조건 → 제어 해제 (채택)**: 단계마다 중단 조건(예: 자세 오차 지속, 상승 중 하강, 목표 미달 상태의 연료 고갈)을 둔다. 조건이 충족되면 계획을 멈추고, 스로틀을 0으로 내리고, 제어 입력을 해제한 뒤 이벤트로 알린다.
- **시간 가속 (채택)**: 코스팅 구간(예: 원지점까지 대기)에서 Coordinator가 시간 가속을 걸고, 점화 전에 해제한다.
- **사용자 조종 시 자동 양보 (비채택)**: 1차 범위에서 뺀다. 사용자는 계획 중단 도구나 중단 조건으로 제어를 되찾는다.
- **reload_mod 때 계획 이어받기 (채택)**: 비행 중에 제어기를 고치며 시험할 수 있도록, `reload_mod` 때 계획·진행 상태를 새 Logic에 넘겨 계속 실행한다. Mod에 인계 통로가 필요해 KSP 재시작이 1회 필요하다. 씬 전환·활성 기체 변경·기체 파괴는 중단한다.

### 6. 실제 발사체식 스테이징·엔진 반영 (채택)

- 연소 종료(연료 고갈) → 잔여 추력 소멸 대기 → 분리 → 이격 대기 → 점화 순서로 스테이징한다(콜드 스테이징). 분리 뒤에도 켜진 엔진이 남는 병렬 부스터 분리는 코어 추력을 유지한다.
- 엔진 추력이 스로틀을 바로 따라오지 않는 경우(점화 지연·차단 후 잔여 추력)를 연소 시작·차단 시점 계산에 반영한다.
- 고체 부스터(스로틀로 끌 수 없는 엔진)는 남은 연료로 연소 종료 시각과 남은 Δv를 예측해 부스터 분리 시점과 예측 원지점에 반영한다. 추력 곡선이 있는 부품(모드)은 곡선을 따르고, 곡선이 없는 스톡 SRB는 연료가 떨어질 때까지 유량이 일정하다고 본다. 스톡 SRB는 연료가 떨어지면 추력이 즉시 0이 된다.
- 연소 종료 뒤에도 남은 상승 속도로 목표 원지점에 닿으면 다음 단을 점화하지 않고 관성으로 올라간다(분리는 한다).

## 1차 범위

- **VAB 발사체 발사 → 궤도 진입**: 수직 상승, 중력 선회, 연소 종료에 따른 스테이징, 원지점 도달 대기(시간 가속), 원궤도화 연소
- Planner용 MCP 도구: 계획 제출·교체·중단, 비행 상태 조회, 이벤트 조회

## 추후 대상

1차에서는 하지 않지만 이후 단계에서 다룬다. 1차 구조(계획 형식, Controller 제어 모드, 기체 식별)는 이 대상을 모드·조건 추가로 받아들일 수 있게 둔다.

- SPH 항공기 비행(이륙·순항·착륙)
- 착륙(로켓 동력 착륙, 항공기 착륙)
- 궤도 기동 일반(임의 기동 노드 실행, 궤도 전이·랑데부)
- 여러 기체 동시 제어(1차는 활성 기체 하나만 다룸)
- 실제 핫 스테이징(분리 전에 다음 단 점화)
- 기체 회수: 발사대·활주로 등에 이미 있는 기체를 회수해 자리를 비움(게임의 Recover Vessel)
- 비행 리셋: 비행 중인 기체를 되돌려 발사대·활주로에서 다시 발사하거나(Revert to Launch) 조립동(VAB/SPH)으로 돌아감(Revert to Editor)

## 비범위

- 사용자 조종 입력 감지와 자동 양보
- 완료를 기다리는 대기 도구
- 외부 오토파일럿 모드 연동
