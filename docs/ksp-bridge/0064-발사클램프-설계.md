# 발사클램프 설계

방안: `0063-발사클램프-방안.md`. 스테이징 구조: `0005-비행제어-설계.md` "스테이징 시퀀스", `AutoStager`·`StageRequest`.

## 구조

`on_start: ["stage"]` 요청(`AutoStager._onStart`)을 처리하기 전에 발사 클램프 배치를 본다. 대상이면 `StageRequest` 대신 새 클래스 `ClampHold`가 그 요청을 맡는다. `ClampHold`는 엔진 점화 → 추력 대기 → 클램프 해제 순서로 진행하고, 해제는 기존 `StageRequest`로 한다(요청 + 확인, 재요청 1회).

```
AutoStager.Update
  └ _onStart 처리
      ├ ClampHold.Detect(v) == null → 지금과 같음(StageRequest)
      └ ClampHold
          ├ Ignite    : 같은 스테이지형 = 대상 엔진 직접 Activate / 나뉜 스테이지형 = 엔진 스테이지 StageRequest
          ├ Wait      : 추력 비율 ≥ 0.9 → Release, 제한 시간 초과·작동 엔진 0 → Fail
          ├ Release   : 클램프 스테이지 StageRequest → 확인되면 끝(staged reason on_start), Failed → Fail
          └ Fail      : 점화한 엔진 Shutdown → ModeAbortException("clamp_hold_failed")
```

## 결정

### 1. 대상 판정 (`ClampHold.Detect`)

`n = v.currentStage − 1`(다음에 작동할 스테이지). 아직 붙어 있는 `LaunchClamp` 부품의 `inverseStage`로 판정한다.

| 배치 | 조건 | 처리 |
| --- | --- | --- |
| 같은 스테이지형 | 클램프가 `n`에 있고, `n`에 끌 수 있는 액체 엔진(아래 "대상 엔진")이 1개 이상 | 대상 엔진 직접 점화 → 대기 → 스테이지 `n` 작동(클램프 해제, SRB 등 나머지 부품 작동) |
| 나뉜 스테이지형 | 클램프가 `n − 1`에만 있고 `n`에 엔진이 1개 이상 | 스테이지 `n` 작동(엔진 점화) → 대기 → 스테이지 `n − 1` 작동(클램프 해제) |
| 그 밖 | 클램프 없음, 클램프가 다른 스테이지에 흩어짐, 같은 스테이지형인데 대상 엔진 없음(SRB만) | 지금과 같다(`StageRequest` 한 번) |

- 대상 엔진: `inverseStage == n`이고 `isEnabled`가 참이며(다중 모드 엔진의 비활성 모드 모듈 제외: `MultiModeEngine`이 그 모듈의 `isEnabled`를 거짓으로 둔다, 디컴파일 확인) `allowShutdown`이 참이고 `throttleLocked`가 거짓(고체 부스터 제외)이며 추진제가 있는 `ModuleEngines`. SRB는 스테이지 작동 때 클램프 해제와 함께 점화된다(사용자 결정).
- 나뉜 스테이지형은 지금은 `on_start` 한 번으로 클램프가 풀리지 않아 기체가 묶인 채 남는다. 이 설계로 함께 해결된다. 이 배치에서 스테이지 `n`에 SRB가 있으면 대기 동안 SRB가 발사대에서 타며, 실패 시 끌 수 없다(기체 설계 책임, 이벤트 데이터에 `solid` 개수를 남긴다).
- 판정은 `on_start` 요청을 처음 처리하는 틱에 한 번 한다(`StageRequest`가 `_stageBefore`를 처음 틱에 잡는 방식과 같다).

### 2. 추력 조건

```
ratio = EngineModel.ThrustSum(v) / (EngineModel.MaxThrustSum(v, p, T, ρ) × v.ctrlState.mainThrottle)
조건: mainThrottle > 0.01 이고 ratio ≥ 0.9
```

- `MaxThrustSum`은 작동 중인 엔진의 현재 대기 최대 추력(추력 제한 반영)이다. 해면에서 Skipper도 1.0 근처가 나온다.
- 스로틀은 Mode가 원하는 값이 이미 반영된 `mainThrottle`을 쓴다. Mode 스로틀이 0이면 조건을 채우지 못해 제한 시간에 실패한다(이륙 계획에서 스로틀 0은 잘못된 계획이다).
- 비율 상한 비교만 하고 스로틀을 대신 올리지 않는다.

### 3. 제한 시간

```
limit_s = EngineModel.SpoolUpS(v) + staging_options.clamp_hold_s (기본 5)
```

- 점화 확인 시각(같은 스테이지형: `Activate` 틱, 나뉜 스테이지형: 엔진 스테이지 확인 틱)부터 잰다. `SpoolUpS`는 매 틱 다시 계산한다(점화 직후 0이어도 다음 틱에 반영).
- `staging_options.clamp_hold_s`(0~600) 새 선택 키. 계획 인자 추가 없이 쓰는 원칙(방안 결정 1)은 유지하고, 기본값 조정용으로만 둔다.

### 4. 실패 처리

- 실패는 세 경우다. 모두 클램프 스테이지를 작동하지 않은(또는 작동하지 못한) 채 같은 처리로 끝낸다.
  - `timeout`: 제한 시간을 넘김.
  - `engine_out`: 대기 중 작동 엔진이 0이 됨(점화 실패, 추진제 없음). 제한 시간까지 기다리지 않는다.
  - `release_failed`: 해제 단계의 `StageRequest`가 `Failed`(스테이징 잠금 등으로 `StageManager.CanSeparate`가 거짓, 재요청 뒤에도 미확인). 직접 점화한 엔진은 스테이징 잠금과 무관하게 켜져 있으므로, 기존 `on_start` 실패처럼 `stage_failed`만 남기고 계속하면 묶인 채 연료를 태운다(검토 R1-1-B-1).
- 처리: `ClampHold`가 점화한(같은 스테이지형) 또는 엔진 스테이지에서 켜진(나뉜 스테이지형) 엔진 중 `allowShutdown`인 엔진을 `Shutdown()`하고, `clamp_hold_failed {reason}` 이벤트를 남긴 뒤 `ModeAbortException("clamp_hold_failed", "<reason>: thrust X% of available after Y s")`를 던진다. Coordinator의 기존 경로로 `plan_aborted {reason:"clamp_hold_failed"}`이 된다. 세부 사유는 이벤트의 `reason`으로 구분한다(검토 R1-1-B-7).
- 나뉜 스테이지형의 엔진 스테이지 작동이 `Failed`면 아직 점화한 엔진이 없으므로 지금의 `on_start` 실패와 같다(`stage_failed`, 계획 계속, 엔진이 없으면 `no_thrust`).

### 5. 다른 판정과의 관계

- `AutoStager.Pending`: 대기 중 참. 점화 전 틱의 `no_thrust` 오판을 막는다(지금 `_onStart`와 같다).
- `AutoStager.BlocksWarp`: 대기 중 참(지금 `_onStart`와 같다).
- `AutoStager.KeepsThrottle`·`Override`: 바꾸지 않는다. 대기 중 엔진이 켜져 있으므로 Mode 스로틀이 그대로 나간다.
- `auto_stage` 시퀀스: 지금처럼 `on_start`가 끝날 때까지 기다린다.
- `AutoStager.RequestOnStart`: 지금은 `_onStart.Sent`일 때만 새 요청을 대기열에 넣고, 아니면 덮어쓴다. 대기가 엔진을 점화했거나(같은 스테이지형) 엔진 스테이지 요청을 보낸 뒤(나뉜 스테이지형)에는 스테이지 작동이 이미 시작된 것이므로 보낸 요청과 같이 대기열에 넣는다(`ClampHold.HasStarted`). 그러지 않으면 다음 단계나 교체 계획의 `on_start`가 클램프 해제에 흡수되어 한 번 사라진다(검토 R1-1-B-3).

### 6. 시험 실행·인계

- `submit_flight_plan`의 시험 실행(`send == false`)에서는 판정만 하고 점화·스테이지 작동·이벤트가 없다.
- 리로드 인계: `AutoStager.Save`에 `clamp_hold` 사전(단계, 배치, 엔진 스테이지 번호, 점화 시각, 대상 엔진 `persistentId` 목록, 진행 중 `StageRequest`)을 더한다. 없으면 `null`. `Load`는 그대로 복원한다.
- `AutoStager.Reset`(계획 완료·중단·실패): `ClampHold`를 버린다. 이미 점화한 엔진은 끄지 않는다(실패 경로에서만 끈다).

### 7. 이벤트·응답

| 이벤트 | 데이터 |
| --- | --- |
| `clamp_hold_started` | `stage`(클램프 스테이지), `layout`(`same`/`split`), `engines`(대기 대상 엔진 수), `solid`(나뉜 스테이지형에서 함께 켜진 SRB 수) |
| `clamp_released` | `stage`, `thrust_ratio`, `hold_s` |
| `clamp_hold_failed` | `stage`, `thrust_ratio`, `hold_s`, `reason`(`timeout`/`engine_out`/`release_failed`) |

- 해제 스테이지 작동은 기존처럼 `staged {reason:"on_start"}`도 남긴다.
- 조건 변수·`get_flight`의 `staging`: 대기 중 `clamp_hold`(새 값). 그 밖의 값은 바뀌지 않는다.
- `submit_flight_plan` 도구 설명과 `staging_options` 설명에 위 동작과 `clamp_hold_s`를 더한다.
- `get_flight_events` 도구 설명의 이벤트 목록에 위 세 이벤트와 필드, `plan_aborted` 사유 `clamp_hold_failed`를 더한다(검토 R1-1-B-6).

## 검증

- 같은 스테이지형 클램프 기체: `clamp_hold_started` → `clamp_released`(`thrust_ratio` ≥ 0.9) → 이륙. 대기 중 `get_flight`의 `staging`이 `clamp_hold`, 고도 변화 없음.
- 실패 경로: 같은 기체의 액체 엔진 추력 제한(`thrustPercentage`)을 VAB에서 0으로 둔 변형으로 발사 → 비율 0 → `clamp_hold_failed {reason:"timeout"}` → `plan_aborted {reason:"clamp_hold_failed"}`, 클램프 유지, 엔진 꺼짐. 디버그 스로틀 고정은 계획 제출 뒤에만 걸 수 있고 `currentThrottle`만 덮어써 쓸 수 없다(검토 R1-1-B-2).
- 클램프 없는 기체(PL22 Orbit): 지금과 같은 `staged {reason:"on_start"}` 한 번.
