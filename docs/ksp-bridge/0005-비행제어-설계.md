# 비행제어 설계

이슈: [#2 비행제어: Planner/Coordinator/Controller 3계층 비행체 제어](https://github.com/SeongSikChae/KSP1-BRIDGE-MCP/issues/2)

선행: [0004-비행제어-방안.md](0004-비행제어-방안.md)

## 구조

```
Planner (MCP 클라이언트 AI)
  │ submit_flight_plan / replace_flight_steps / abort_flight / get_flight / get_flight_events
  ▼
App.Tools/FlightTools ──HTTP──▶ Mod HttpServer ──▶ Logic Handlers/FlightHandler
                                                    │
        ILogic.FixedUpdate() ──▶ Flight/Coordinator ─┼─ Conditions (until·abort 판정)
                                    │                ├─ AutoStager (자동 스테이징)
                                    │                ├─ Warp (coast 시간 가속)
                                    │                └─ FlightEvents (이벤트 로그)
                                    ▼ 현재 단계의 Mode
                             Flight/Modes/* ──명령(자세 목표·스로틀)──▶ Flight/Control/AttitudeController
                                                                         │ vessel.OnFlyByWire
                                                                         ▼
                                                                    FlightCtrlState
```

- **Coordinator**는 `ILogic.FixedUpdate()`(물리 틱)에서 실행한다. 텔레메트리를 한 번 수집하고, 중단 조건을 판정하고, 스테이징 상태를 갱신한 뒤 현재 Mode로 명령을 계산하고, 완료 조건을 판정해 단계를 전환한다(아래 "Coordinator 틱").
- **Controller**는 `vessel.OnFlyByWire` 콜백에서 Coordinator가 정한 명령(자세 목표·스로틀)을 `FlightCtrlState`로 바꾼다.

## 공통 규칙

- **대상 기체**: 1차는 활성 기체 하나. 계획에 기체 `persistentId`와 **조종 기준 부품**(`vessel.GetReferenceTransformPart()`)의 `persistentId`를 기록한다. 추후 여러 기체 제어 때 이 id로 계획을 기체별로 나눈다.
  - 분리하면 원래 `Vessel`(같은 `persistentId`)은 루트 부품 쪽에 남는다. 조종 기준 부품이 떨어져 나간 쪽에 있으면 KSP가 한 프레임 뒤 그쪽을 활성 기체로 바꾼다(`ModuleDecouple.WaitAndSwitchFocus`, 디컴파일 확인).
  - **제출 시 검사**: `auto_stage: true` 계획은 분리 후 활성 기체가 바뀔 구성이면 400 `invalid_plan`으로 거부한다. 즉 이후 어느 스테이지 `N`에서든 조종 기준 부품이 루트와 끊기는 쪽 `D_N`(아래 "분리 부품 집합 계산", 버리는 쪽 `J_N`과 같음)에 있는 구성이다. 루트가 하단인 구성은 조종 기준 부품이 상단 쪽 `D_N`에 들어가므로 이 조건으로 거부된다. message는 `auto_stage: control part leaves the root vessel at stage N (control_part_jettisoned)` 형식이다(아래 "오류").
  - **비행 중 활성 기체 변경은 항상 중단**: `onVesselChange`가 오면 이유와 상관없이 `vessel_changed`로 중단한다. 대상 기체를 바꿔 이어가지 않는다(`dock` 결합만 예외, 아래 "씬·기체 변경").
- **단위·좌표**: 거리 m, 속도 m/s, 각도 deg, 시간 s. 고도는 해수면 기준. pitch는 지평선 기준(90 = 천정), heading은 북쪽 0·동쪽 90.
- **스레드**: HTTP 처리는 기존처럼 `MainThreadDispatcher`에서 동기로 실행한다. Coordinator·Controller도 메인 스레드라 따로 잠그지 않는다.
- **계획은 하나**: 기체마다 실행 중인 계획은 하나다. `submit_flight_plan`은 실행 중인 계획을 교체한다(이전 계획은 `plan_replaced` 이벤트를 남기고 끝남).
- **교체 시 이어가는 것**: 실행 중에 계획을 교체(`submit_flight_plan`, `replace_flight_steps`)하면 Controller는 다시 연결하지 않고(SAS 원래 상태 유지), 진행 중인 스테이징 시퀀스는 끝까지 마친다. 새 계획이 `auto_stage: false`여도 현재 시퀀스는 마치고, 그 뒤로 새 시퀀스를 시작하지 않는다. 계획이 완료·중단되면 시퀀스도 버린다.
- **단계 완료 규칙**: 단계는 `until`이 참이 되거나, `until`이 없을 때 Mode가 완료를 알리면 끝난다. 완료를 알리지 않는 Mode(`attitude`, `coast`)는 `until`이 필수다(제출 시 검증).
- **중단 처리**: 중단되면 스로틀 0 → 시간 가속 해제 → SAS 복원 → `OnFlyByWire` 해제 → `plan_aborted` 이벤트 순으로 처리한다. reload 인계만 예외다(아래 "reload 인계").
  - 이벤트 앞의 해제 단계(스로틀 0, 가속 해제, SAS 복원, `OnFlyByWire` 해제, `Command`를 Idle로)는 공통 `Release()` 하나로 둔다. `Abort`·`Complete`·`Submit` 실패 경로·reload 이어받기 실패가 모두 이것을 부른다.
  - `Abort`는 계획 상태와 무관하게 `Release()`를 부른다. `Aborted` 전환과 `plan_aborted` 이벤트만 계획이 `Running`일 때 한다(교체 도중 `Running` 전환 전에 실패해도 Controller가 연결된 채 남지 않게).
  - Controller의 `Fly`는 계획이 `Running`이 아니면 입력을 넣지 않는다.
  - 스로틀 0은 `FlightInputHandler.state.mainThrottle = 0`과 대상 기체 `ctrlState.mainThrottle = 0`을 둘 다 넣는다. 활성 기체가 바뀐 경우 이전 기체에 스로틀이 남지 않게 한다.
  - SAS 복원은 `OnFlyByWire` 해제(대상 기체 참조를 비움)보다 먼저 한다.
- **예외 처리**:
  - `Coordinator.Tick`과 Controller의 `Fly` 콜백은 try/catch로 감싼다. 예외가 나면 `Abort("error")`로 보내고 예외 메시지를 이벤트 `data.message`에 남긴다. 예외 로그가 매 프레임 쌓이거나 마지막 스로틀이 유지되는 일이 없게 한다.
  - `Tick`은 `ComputeCommand`가 던지는 `NoThrustException`(아래 "추력 없음 판정")을 일반 catch보다 먼저 잡아 `Abort("no_thrust")`로 보낸다.
  - `Submit`·`ReplaceSteps`: 계획 검증과 첫 명령 계산(`ComputeCommand`)을 Controller 연결·SAS 변경·`Running` 전환 **전에** 한다. 여기서 실패하면 아무것도 바꾸지 않고 400 `invalid_plan`(검증 실패) 또는 409(`no_thrust` 등 상태 오류)로 돌려준다. 연결 뒤 단계에서 난 예외는 `Tick`과 같은 catch(`NoThrustException` → `Abort("no_thrust")`, 그 밖 → `Abort("error")`)로 감싼다. `ReplaceSteps`는 이 catch에서 `Abort` 뒤 바로 409 `plan_aborted`(message에 예외 이유)로 반환하고 `steps_replaced`를 남기지 않는다.
- **추력 없음 판정**: 모든 Mode에 공통이다. Coordinator가 `ComputeCommand`에서 한 번에 판정하고, 각 Mode에 흩지 않는다. Mode 명령 스로틀 > 0인데 `Operational` 엔진이 0개이고 `StagingPending`이 거짓이면 `NoThrustException`을 던진다. `StagingPending`이 참이면 스로틀만 0으로 두고 자세 목표는 그대로 기다린다. Mode는 추력 유무를 따로 처리하지 않고 원하는 스로틀을 낸다(`circularize`는 연소 시간이 무한대이거나 최대 가속도가 0이면 스로틀 1을 낸다).
  - `Abort`, `Release`, `Coordinator.Stop`은 절대 예외를 던지지 않는다. 각 해제 단계를 따로 try/catch로 감싸고, null 상태(계획 없음, 기체 없음)를 먼저 확인한다. `LogicHost.Reload`가 `Stop()`을 try 없이 부르기 때문이다.
- **매 틱 할당 없음**: 매 물리 틱 경로(Telemetry 수집, `ComputeCommand`, `AutoStager.Update`, `EngineModel` 판정, `Warp.Request`)는 LINQ(`Sum`, `Where`, `Any`, `ToList` 등)와 새 컬렉션 할당을 쓰지 않고, 캐시한 엔진·부품 배열을 `for`로 순회한다. 캐시 키는 기체 `persistentId`, `currentStage`, 부품 수(필요하면 엔진 상태 수)를 함께 쓴다(다른 기체의 캐시를 재사용하지 않게). 엔진 배열 키가 바뀔 때마다 SRB 예측 캐시(`_srbCache`)도 비운다. 캐시 접근자는 호출될 때마다 키를 스스로 확인한다. 할당은 캐시 재계산, 제출 시 검증, 스테이지 작동 요청처럼 드문 시점에만 한다.
- **기존 코드 재사용**: 씬 가드는 `Guard.ActiveVessel()`, Δv 준비 여부는 `PerformanceCheck`의 `UpToDate` 판정을 `internal`로 열어 함께 쓴다.
- **오류**: 기존 `ApiException` 형식. 추가 코드:
  - 400: `invalid_plan`. Mod 응답 형식은 바꾸지 않고 message 문자열 규약으로 위치와 이유를 준다.
    - message는 오류 경로로 시작한다: `<경로>: <이유>`. 예: `steps[2].until: unknown variable foo`, `steps[0].turn_end_altitude: must be greater than turn_start_altitude`.
    - 분리 후 조종 기준 부품이 루트 쪽 기체에 남지 않는 계획은 message 끝에 `(control_part_jettisoned)`를 붙인다.
  - 409: `not_in_flight`, `no_active_vessel`, `no_plan`, `vessel_mismatch`, `no_thrust`(제출·교체 시 첫 명령 계산에서 추력 없음 판정. 계획은 시작·교체되지 않음), `plan_aborted`(`replace_flight_steps`의 교체 적용 단계에서 예외가 나 계획이 중단됨. message에 이유), 첫 단계 trial의 Mode 중단 사유(`no_node`, `node_missed`, `no_target`, `target_too_far`, `port_incompatible`, `dock_failed`, #18)
  - 기존 코드 `bad_request`, `timeout`도 쓴다.

## 인터페이스

### MCP 도구 ↔ HTTP 라우트

| 도구 | 라우트 | 동작 |
| --- | --- | --- |
| `submit_flight_plan` | `POST /api/flight/plan` | 계획을 검증하고 즉시 시작한다. 실행 중인 계획이 있으면 교체. 응답: `{plan_id, steps, event_seq, epoch}`(`epoch`는 이벤트 세션 id, 아래 "이벤트") |
| `replace_flight_steps` | `POST /api/flight/steps` | 실행 중인 계획에서 현재 단계 다음부터 교체한다. `include_current: true`면 현재 단계부터 교체(새 첫 단계를 즉시 시작하고 `step_started`를 남김). 빈 `steps`는 `include_current: false`면 남은 단계 삭제로 허용하고, `include_current: true`면 400 `invalid_plan`. 오류 경로 인덱스는 새 `steps` 배열 기준(`steps[i]...`). 응답은 `submit`과 같음 |
| `abort_flight` | `POST /api/flight/abort` | 계획을 중단하고 제어를 해제한다. 계획이 없거나 이미 `Completed`·`Aborted`면 409 `no_plan` |
| `get_flight` | `GET /api/flight` | 기체·궤도·추진·계획 상태 |
| `get_flight_events` | `GET /api/flight/events?since={seq}&limit={n}` | `since`보다 큰 seq의 이벤트. 응답: `{events, next, truncated, epoch}`(아래 "이벤트"의 cursor 규칙) |

### `get_status` 확장

`BridgeLogic.Status()`에 `flight: {active_vessel, plan_state, step}`을 더한다(비행 씬 밖이면 null).

## 데이터

### 계획

```json
{
  "auto_stage": true,
  "abort": [{ "var": "attitude_error", "op": ">", "value": 20, "for_s": 3 }],
  "steps": [
    { "name": "수직 상승", "mode": "attitude", "pitch": 90, "heading": 90, "throttle": 1,
      "on_start": ["stage"], "until": { "var": "altitude", "op": ">=", "value": 1000 } },
    { "name": "중력 선회", "mode": "gravity_turn", "heading": 90, "target_apoapsis": 80000 },
    { "name": "원궤도화", "mode": "circularize", "timeout_s": 900 }
  ]
}
```

| 필드 | 설명 |
| --- | --- |
| `auto_stage` | 기본 false. 아래 "스테이징 시퀀스" |
| `staging_options` | 선택. 스테이징 시퀀스 설정(`tailoff_ratio`, `max_tailoff_s`, `settle_distance`, `max_settle_s`, `max_separate_q`, `max_separate_q_wait_s`, `max_flameout_pause_s`). 조건 변수 `staging`과 이름이 겹치지 않게 따로 둔다 |
| `abort` | 계획 전체 중단 조건(모든 단계에 적용) |
| `steps[].name` | 선택. 이벤트·상태 표시용 |
| `steps[].mode` | `attitude`, `gravity_turn`, `coast`, `circularize`, `land`(#17, 0029-동력착륙-설계.md), `execute_node`, `approach`, `dock`(#18, 0032-궤도기동-설계.md) |
| `steps[].on_start` | 단계 시작 시 실행할 동작 목록. 1차는 `stage`만 지원 |
| `steps[].until` | 완료 조건 |
| `steps[].abort` | 이 단계에만 적용하는 중단 조건 |
| `steps[].timeout_s` | 선택. 넘으면 중단(`reason: timeout`) |

### 조건

- **잎**: `{var, op, value, for_s?}`. `op`는 `<`, `<=`, `>`, `>=`, `==`, `!=`. `for_s`가 있으면 그 시간 동안 계속 참이어야 참이 된다(게임 시간 기준).
- **묶음**: `{all: [...]}`, `{any: [...]}`. 배열만 주면 `all`로 본다. 중첩할 수 있다.
- 모르는 변수·연산자, 문자열 변수에 대소 비교를 쓰면 제출 시 `invalid_plan`으로 거부한다(message는 조건 경로로 시작, 예: `steps[2].until: unknown variable foo`).
- **평가 규칙**: 매 틱 모든 잎을 먼저 평가해 `for_s` 타이머를 갱신한 뒤 `all`/`any`를 조합한다. 단락 평가로 건너뛴 잎의 타이머가 초기화되지 않아 조기에 발동하는 일을 막는다. 계획 `abort`와 단계 `abort`도 둘 다 매 틱 평가한다.
- **값 없음**: 값을 아직 알 수 없는 변수(Δv 계산이 끝나지 않음, 자세 목표 없음 등)는 "값 없음"이다. 값 없음인 잎은 거짓이고 `for_s` 타이머를 초기화한다. `get_flight`에서는 null로 준다.
  - 기체가 `packed`이거나 레일 가속 중(`TimeWarp.WarpMode == TimeWarp.Modes.HIGH && TimeWarp.CurrentRateIndex > 0`)이면 `attitude_error`는 값 없음이다. 그래서 `attitude_error`를 쓰는 `for_s` 타이머는 이 규칙으로 자연히 초기화된다. Controller는 같은 조건에서 입력을 넣지 않고 적분값을 0으로 초기화한다. 물리 가속(`Modes.LOW`) 중에는 정상 제어하고 `attitude_error`도 값이 있다.

Telemetry에는 조건 변수가 아닌 Mode용 필드 `StagingPending`(bool)도 둔다. 틱 순서 (c)의 AutoStager 갱신 뒤에 채운다(아래 "Coordinator 틱"). 참이면 스테이징이 진행 중이라 곧 엔진이 생길 수 있다: `staging != none`이거나, `on_start: ["stage"]` 작동 요청이 확인을 기다리는 중. `auto_stage`가 켜져 있고 래치가 없으면, 직전 틱 Mode 원래 스로틀(`PrevModeThrottle`)이 0보다 크고 점화된 엔진이 없고 다음 스테이지에 엔진이 있는 상태는 같은 틱의 AutoStager 갱신에서 `ignite`로 들어가므로(아래 "스테이징 시퀀스") 이 정의로 덮인다. 남은 스테이지에 엔진이 있다는 것만으로는 참이 아니다. 그래서 직전 Mode 스로틀이 0이던 상태(발사대 제출, 스로틀 0 단계 뒤)에서 점화된 엔진 없이 스로틀을 원하면 `no_thrust`가 된다(첫 점화는 `on_start: ["stage"]`). `auto_stage`가 꺼져 있으면 남은 스테이지 엔진만으로 기다리지 않고 `no_thrust`가 된다. `get_flight`·조건에는 노출하지 않는다.

`PrevModeThrottle`은 직전 틱에 Mode `Update`가 낸 원래 스로틀이다. 추력 없음 대기(스로틀 0)와 `AutoStager.Override`로 덮어쓰기 **전** 값이다. 그래서 `on_start` 작동 요청을 기다리는 동안 명령 스로틀이 0으로 덮여도, 그 요청(예: 페어링 분리)이 확인된 다음 틱에 Mode가 스로틀을 원하면 `none → ignite`로 들어가 다음 스테이지 엔진을 작동한다. 덮어쓴 최종 스로틀은 `PrevCommandThrottle`로 따로 두고 `circularize` 종료 게이트만 쓴다. 둘 다 `get_flight`·조건에는 노출하지 않는다.

**연료 있는 엔진**: `Propellant.totalResourceAvailable`은 점화된 엔진에서만 갱신되므로(`ModuleEngines.FixedUpdate`: `if (EngineIgnited) UpdatePropellantStatus()`, 디컴파일 확인) 쓰지 않는다. 엔진의 추진제 정의(`propellants`의 resource id와 flow mode)로 부품 자원을 직접 조회해, 모든 추진제(`ignoreForIsp` 제외)의 남은 양에서 `minResToLeave`를 뺀 값이 `ratio × 최대 스로틀 한 틱 필요량(max(1, flowMultiplier) 포함) × ignitionThreshold` 이상이고 0보다 크면 연료가 있다고 본다(KSP `CheckDeprived` 기준, `part.GetConnectedResourceTotals`). thrustCurve 엔진은 남은 비율의 곡선 값이 `flameoutBar` 이상이어야 한다. 근거는 0023-소진판정-설계.md(#13). `ignitable_engines`가 이 판정을 쓴다. 부품 자원 조회가 무거우므로 `ignitable_engines` 결과는 기체 `persistentId`·`currentStage`·부품 수·flameout된 `Ignited` 엔진 수·`Ignited` 엔진 수 중 하나가 바뀔 때만 다시 계산해 캐시한다(점화된 엔진의 연료 고갈은 flameout으로, 재점화할 수 없는 엔진의 연료 고갈은 `Ignited` 이탈로 드러나므로 키에 넣는다. 아래 "엔진 집합"). 매 틱 LINQ 할당을 만들지 않는다("공통 규칙"의 매 틱 할당 없음). 엔진별 연료 있음 결과(`HasPropellantCached`)도 같은 키로 캐시한다. 캐시 접근자(`ignitable_engines`의 `Ignitable`, `HasPropellantCached` 등)는 호출될 때마다 키를 스스로 확인해 바뀌었으면 다시 계산한다(다른 접근자가 먼저 불렸는지에 기대지 않음).

### Mode

공통 인터페이스:

```csharp
interface IFlightMode
{
    void Begin(Vessel v, Telemetry t);
    ModeCommand Update(Vessel v, Telemetry t);   // 틱마다: 자세 목표, 스로틀, 가속 목표 UT(WarpToUt, 선택)
    bool Done { get; }                            // 완료를 알리는 Mode만 true가 됨
    Dictionary<string, object> Save();            // reload 인계용 내부 상태 (Dictionary·List·숫자·문자열만)
    void Load(Vessel v, Dictionary<string, object> state);   // Begin 대신 호출
    void End(Vessel v);                           // 단계·계획이 끝날 때 1회 (#18)
}
```

- `ModeCommand`는 `Attitude`(자세 목표, 없으면 null), `Throttle`, `ModeThrottle`(Mode가 낸 원래 스로틀, Coordinator가 채움), `WarpToUt`(선택, 없으면 null)를 가진 struct다. 기본값이 스로틀 0·자세 없음(`ModeCommand.Idle`)이라 첫 `Submit` 전에 Controller가 읽어도 null 참조가 나지 않는다.
- Mode는 `Warp`를 직접 부르지 않는다. 가속이 필요하면 `WarpToUt`를 채우고, Coordinator가 틱 순서 (f)에서 `Warp`를 호출한다.
- 추력이 없을 때의 처리(대기 또는 `no_thrust`)는 Mode가 하지 않고 Coordinator가 `ComputeCommand`에서 한다("공통 규칙"의 추력 없음 판정).

Mode 인자는 제출 시 검증한다(필수 인자 누락, 범위 밖 값, `turn_end_altitude <= turn_start_altitude` 등 → `invalid_plan`). `gravity_turn`은 대기가 있는 천체(제출 시 기체의 `mainBody`)에서 `target_apoapsis <= atmosphereDepth`면 `invalid_plan`이다(대기권 밖 완료 조건을 만족할 수 없는 원지점).

추후 Mode(항공기 등)를 추가해도 계획 형식은 그대로다. Mode 이름만 늘어난다. 착륙은 `land`로 추가했다(#17). 궤도 기동은 `execute_node`·`approach`·`dock`으로 추가했다(#18).

- **Mode 중단 사유**(#18): Mode는 `ModeAbortException(reason, message)`로 계획을 중단할 수 있다. 첫 단계의 제출·교체 trial에서 나면 아무것도 바꾸지 않고 같은 코드의 409로 거부하고, 실행 중이면 `plan_aborted {reason}`이다.
- **`End(Vessel)`**(#18): 단계가 끝나거나 계획이 끝날 때(완료·중단·교체) 한 번 부른다. `dock`의 조종 기준 부품 복원처럼 Mode가 바꾼 기체 상태를 되돌린다. 다른 Mode는 비어 있다.

## 동작

### Coordinator 틱 (`FixedUpdate`)

전체를 try/catch로 감싼다. `NoThrustException`은 `Abort("no_thrust")`, 그 밖의 예외는 `Abort("error")`. 계획이 `running`이 아니면 바로 끝낸다. 계획이 `running`인데 비행 씬이 아니면 `Abort("scene")`, 활성 기체가 없거나 계획 대상과 다르면 `Abort("vessel_changed")`로 중단한다(씬·기체 훅을 놓친 경우 대비, 조용히 넘기지 않음). 매 틱 순서는 아래와 같다("AutoStager 먼저 + 단일 경로").

| 순서 | 처리 |
| --- | --- |
| (a) | `Telemetry` 수집. 현재 자세 목표(직전 `Command.Attitude`)를 넘겨 `attitude_error`를 채운다. 직전 틱의 최종 명령 스로틀(`Command.Throttle`)과 Mode 원래 스로틀(`Command.ModeThrottle`)도 Mode용 필드 `PrevCommandThrottle`·`PrevModeThrottle`로 넣는다 |
| (b) | 계획 `abort` → 단계 `abort` → `timeout_s` 판정. 하나라도 참이면 중단하고 끝 |
| (c) | `AutoStager.Update`: `on_start` 작동 요청 처리, 연소 종료 감지·상태 전이·스테이지 작동 요청·확인. 뒤이어 `t.Str["staging"]`과 `t.StagingPending`을 갱신된 상태로 다시 채운다 |
| (d) | 현재 Mode `Update` → `ModeCommand`. Mode가 낸 스로틀을 `ModeThrottle`에 그대로 남긴다(이후 덮어쓰기와 무관). 이어서 추력 없음 판정("공통 규칙"): Mode 스로틀 > 0이고 `Operational` 엔진이 0개면 `StagingPending`이 참일 때 스로틀 0으로 기다리고, 거짓이면 `NoThrustException` |
| (e) | `AutoStager.Override(cmd)`: 직렬 분리의 `separate`·`settle`이면 스로틀을 0으로 덮어쓴다. 자세 목표는 그대로 둔다. 결과가 `Command`(Controller가 읽음) |
| (f) | `Warp`: `cmd.WarpToUt`가 있으면 `Warp.Request`(사용자 취소 래치가 걸려 있으면 요청하지 않음. 허용 조건이 아니면 우리가 건 가속만 해제), 없는데 우리가 건 가속이 있으면 `Warp.Stop`. 이어서 `Warp.Sync()`로 실제 상태와 맞춘다 |
| (g) | 단계 완료 판정(`until` 또는 `Done`). 완료되면 `Warp.Stop`·래치 해제 후 다음 단계의 `Begin`과 `on_start`(작동 요청 등록)를 실행하고, 같은 틱에 다시 수집해 `Command = ComputeCommand(v, ut)`로 새 단계의 첫 명령을 계산한다. 완료된 단계는 `step_completed`를 먼저 남긴다. 마지막 단계였으면 이어서 `Complete()`: `Completed` 전환, `Release()`, `plan_completed` |

**명령 계산은 한 함수**: (c)~(e)를 `ComputeCommand(v, ut)` 하나로 둔다(실제 인자는 계획·Mode·작동 요청 전송 여부를 더 받는다. `Submit`·`ReplaceSteps`의 첫 계산용). 호출 전에 (a) 수집은 호출자가 한다.

| `Tick` | (a)·(b) 뒤 `Command = ComputeCommand(v, ut)`, 그다음 (f)·(g) |
| `NextStep` | (g)에서 새 단계 `Begin`·`on_start` 뒤 같은 틱에 수집하고 `Command = ComputeCommand(v, ut)`. 단계 전환 틱에 이전 단계 명령이 남지 않게 한다 |
| `Submit`·`ReplaceSteps(include_current)` | 계획 검증 → 새 단계 `Begin`·`on_start` → 수집 → `ComputeCommand`로 첫 명령 계산까지 Controller 연결·SAS 변경·`Running` 전환 **전에** 한다. 실패하면 아무것도 바꾸지 않고 400/409로 돌려준다("공통 규칙"의 예외 처리). 이 첫 계산은 새 계획·Mode를 인자로 받아 실행 중인 계획을 건드리지 않고, `ActivateNextStage`를 보내지 않는다(작동 요청 등록·상태 전이만, 실제 요청은 연결 뒤 첫 `Tick`). 이 시험 계산에서 생기는 이벤트(`stage_burnout`, `staged`, `out_of_stages` 등)는 임시 버퍼에 모은다. 실패하면 임시 버퍼를 버리고 `AutoStager` 상태를 계산 전 값(`AutoStager.Save`)으로 되돌린다(되돌린 상태에서 다음 `Tick`이 같은 이벤트를 다시 남기므로 중복을 막음). 성공하면 `Command`에 넣고 연결한 뒤 임시 버퍼를 `seq`를 매겨 커밋한다. 교체 직후 1틱 동안 스로틀 0이 들어가는 일을 막는다. `Submit`(전체 교체)과 `include_current: true` 교체는 `NextStep`처럼 `Warp.Stop`·`Warp.ClearLatch`도 한다. `Submit`의 `Warp.Stop`은 우리가 요청한 가속(`Warp.Requested`)이 있을 때만 부른다(사용자가 건 가속 유지) |
| `Resume` | 계획 재검증·Mode `Load` → `AutoStager.Load`·`Running` 전환 → 인계받은 직전 명령으로 `Command` 복원("reload 인계"의 `command`) → 수집 → `Command = ComputeCommand(v, ut)` → 훅 연결 순서. 첫 `OnFlyByWire`가 빈 명령(스로틀 0)을 넣지 않게 한다 |

- 같은 물리 틱에 `ComputeCommand`가 두 번 불려도(예: `Submit` 직후 `Tick`, `NextStep`) AutoStager의 틱 수 대기(`separate`)는 `ut`가 늘었을 때만 센다. 스테이지 작동 요청도 한 틱에 한 번만 보낸다.
- `Abort`·완료 때 `Command`를 스로틀 0·자세 없음으로 초기화한다(`Release()`).
- 이 순서로 두 가지 실패가 구조적으로 사라진다. `circularize`는 (c)가 (d)보다 먼저라 연소 종료를 감지한 같은 틱에 `StagingPending`을 보므로 스테이징 시작 전에 `no_thrust`로 중단하지 않는다. `Resume`은 `Tick`과 같은 `ComputeCommand`를 쓰므로 reload 직후 첫 명령이 평소 경로와 같다.

### Controller (토크 정규화 PID)

**축과 부호** (KSP 1.12 디컴파일 확인):

- `vessel.angularVelocity`(rad/s)와 `vessel.MOI`(대각 성분)는 `vessel.ReferenceTransform` 로컬 좌표이고, 축 순서는 x = pitch, y = roll, z = yaw다.
- `FlightCtrlState`의 **양의** pitch/roll/yaw 입력은 로컬 −x/−y/−z 토크를 만든다(`ModuleReactionWheel`: `AddTorque(rotation * -input)`). 즉 양의 입력은 해당 `angularVelocity` 성분을 음수 쪽으로 바꾼다.
- `GetPotentialTorque(out pos, out neg)`도 같은 축 순서다. 모듈마다 neg의 부호가 일관되지 않으므로(조종면은 음수일 수 있음) 축별로 `(|pos| + |neg|) / 2`를 합산해 쓴다.
- 입력은 `OnFlyByWire`에서만 넣는다. 활성 기체의 `ctrlState`는 매 틱 `FlightInputHandler.state`로 덮어써지기 때문이다.

**제어 법칙**:

- 축(pitch·roll·yaw)마다 목표 자세와의 오차각 `e`를 로컬 좌표로 구한다(목표 방향으로 돌려면 그 축 `angularVelocity`가 `sign(e)` 방향이어야 하도록 부호를 정의).
- 최대 각가속도 `α = τ / I`(축별, 하한 1e-3).
- 목표 각속도 `ω* = sign(e)·min(√(2·α·|e|)·k_stop, ω_max)` (정지 거리 안에서 멈추도록).
- 필요한 각가속도 `a = Kp·(ω* − ω) + Ki·∫(ω* − ω)`를 구하고, 입력은 부호를 뒤집어 `input = clamp(−a / α, −1, 1)`로 넣는다.
- 축별 부호는 개발 단위 4 검증에서 계단 응답(입력 +0.2를 0.5초 넣었을 때 해당 `angularVelocity` 성분이 감소하는지)으로 다시 확인한다.
- 기본 게인은 정규화 기준이라 기체마다 따로 조정하지 않는다. 게인은 상수로 두고 설정으로 노출하지 않는다.
- `roll`을 지정하지 않으면 roll 입력을 0으로 두지 않고, roll 축은 목표 각속도 `ω* = 0`으로 감쇠한다(회전만 멈추고 각도는 유지하지 않음).
- 자세 제어를 멈추는 조건은 둘뿐이다: 레일 가속 중(`TimeWarp.WarpMode == TimeWarp.Modes.HIGH && TimeWarp.CurrentRateIndex > 0`)이거나 `vessel.packed`. 이때 입력을 넣지 않고 적분값을 0으로 초기화한다(`attitude_error` 값 없음). 물리 가속 중에는 정상 제어한다.
- 제어 중에는 스톡 SAS를 끈다. 계획 실행 중에는 매 틱 SAS가 켜져 있으면 다시 끈다(사용자가 T키로 켜도 입력이 충돌하지 않게). 계획 종료·중단 시 시작 전 SAS 상태로 되돌린다.
- 연결은 `AttitudeController.Attach(Vessel v, bool? sasBefore = null)` 하나로 한다.
  - 처음 연결: 현재 SAS 상태를 `sas_before`로 기록하고 SAS를 끈다.
  - reload 이어받기(`Resume`): 인계받은 `sas_before`를 넘겨 그 값을 그대로 쓴다(이미 꺼진 SAS를 원래 상태로 잘못 기록하지 않게).

### 스테이징 시퀀스 (`auto_stage`)

실제 발사체처럼 연소 종료 → 잔여 추력 소멸 → 분리 → 이격 → 점화를 나눠 처리한다. `AutoStager`가 상태 기계로 실행하며, 단계(step) 진행과는 별개로 돈다.

```
none ─(연소 종료 감지)─▶ tailoff ─(잔여 추력 소멸)─▶ separate ─(분리 작동)─▶ settle ─(이격 완료)─▶ ignite ─▶ none
none ─(작동 엔진 없음 + 연료 남은 flameout)─▶ paused ─(재점화 / 엔진 이탈 / 상한)─▶ none
```

| 상태 | 동작 | 다음으로 가는 조건 |
| --- | --- | --- |
| `none` | 감시 | 연소 종료 감지(아래) → `tailoff`. 또는 `Operational` 엔진이 0개이고 연료가 남은 점화 상태의 flameout 엔진이 있으면 → `paused`(#13, 아래 점화 진입보다 먼저). 또는 직전 틱 Mode 원래 스로틀(`PrevModeThrottle`, 추력 없음 대기·`Override` 덮어쓰기 전) > 0이고 `Operational` 엔진이 0개이고 다음 스테이지에 엔진이 있고 래치가 없으면 → `ignite`(점화 주체 보장: 점화된 엔진 없이 다음 스테이지 엔진을 두고 기다리기만 하는 상태가 없게. 스로틀 0 대기 중에는 첫 스테이지를 작동하지 않음) |
| `tailoff` | 자세 유지, 스로틀 명령 유지. 스톡 액체 엔진은 flameout과 동시에 추력이 0이므로 이 상태는 실질적으로 SRB와 응답형 엔진(`EngineModel`의 `Responsive`)의 잔여 추력 대기다 | 다 쓴 엔진들(`Ignited` 중 flameout)의 현재 추력 합이 그 엔진들 최대 추력의 `tailoff_ratio` 미만, 또는 `max_tailoff_s` 경과. 병렬 부스터: 같은 분리 단의 SRB 중 아직 타는 것이 있고 그 `burnout_s`가 `max_tailoff_s` 안이면 모두 꺼질 때까지 기다린다(SRB는 꺼지는 순간 추력이 0이라 잔여 추력 대기는 없음) |
| `separate` | 둘 다 참일 때만 작동한다(작동 요청 전에만 판정): 다음 스테이지에 다 쓴 엔진을 떼어내는 디커플러가 있음(`NextStageDecouplesFlamedOutEngine`), 분리 뒤 남는 쪽 `K_next`에 쓸 엔진이 있음(`KeptHasEngine`: `K_next`에 있는 병렬 분리의 코어 엔진이거나 `K_next`에 있는 이후 스테이지의 연료 있는 미점화 엔진. 버리는 쪽의 sepratron 같은 엔진은 세지 않음). 하나라도 거짓이면 분리하지 않고 `out_of_stages` 이벤트를 남기고 시퀀스를 끝낸다(`none`으로, 래치, 이후는 추력 없음 규칙). 마지막 상단을 다 쓴 뒤 캡슐 디커플러를 작동해 포드를 떼고 낙하산까지 이어지는 되돌릴 수 없는 작동을 막는다. 요청을 만든 뒤에는 `StageRequest` 결과로만 전이한다. 직렬 분리면 먼저 스로틀 0을 적용하고, **최소 2틱이 지나고** `vessel.ctrlState.mainThrottle`과 `FlightInputHandler.state.mainThrottle`이 0이고 점화된 엔진(다 쓴 쪽 `J` 제외)의 `currentThrottle`이 모두 0.01 미만이 된 뒤에 다음 스테이지(디커플러) 작동을 요청한다(엔진이 스로틀을 읽는 시점과 입력 처리 순서가 보장되지 않고, 분리된 기체가 `ctrlState`를 복사하기 때문). 스로틀 0 적용 뒤 2초가 지나도 조건이 맞지 않으면 기다리지 않고 그대로 요청한다. 병렬 분리면 스로틀을 유지한 채 요청하되, 동압(`dynamicPressurekPa`)이 `max_separate_q`보다 높으면 요청을 미루고(`separation_held {stage, q_kpa}` 1회) 동압이 내려가거나 대기 시작 뒤 `max_separate_q_wait_s`가 지나면(`separation_forced {stage, q_kpa}`) 요청한다. 기다리는 동안 매 틱 병렬 여부를 다시 구해 코어가 다 타면 그 틱부터 직렬 경로(스로틀 0, 2초 대기는 그때부터)로 간다(#16, 0026). 작동은 아래 "스테이지 작동 요청·확인"을 따른다 | 작동 확인(`staged`). 확인 실패면 `stage_failed`로 시퀀스 끝(래치) |
| `settle` | 직렬: 스로틀 0, 자세 유지, 분리된 부품과의 거리 측정. 병렬: 건너뜀 | 분리된 기체와의 **최소 부품 간 거리** ≥ `settle_distance` 이고 상대속도가 벌어지는 중, 또는 `max_settle_s` 경과. 분리된 기체 후보 = 분리 뒤 새로 생긴 기체(대상 기체는 바뀌지 않음: 활성 기체가 바뀌면 중단). 후보가 비어 있으면 참으로 보지 않고 `max_settle_s`까지 기다린다 |
| `ignite` | 아직 `Operational` 엔진이 없으면: 다음 스테이지에 엔진이 있을 때(`inverseStage == currentStage − 1`인 부품에 `ModuleEngines`, 작동 요청 전에만 판정) 그 스테이지 작동을 요청하고, 확인되면 `staging_completed`. 쿨다운 중이면 이 상태에서 기다린다. 다음 스테이지에 엔진이 없으면(페어링·낙하산 등) 작동하지 않고 `ignite_blocked {stage}`를 1회 남기고 시퀀스를 끝낸다(래치, 이후는 추력 없음 규칙). `Operational` 엔진이 있으면(병렬 분리 뒤 코어 등) 작동 없이 `staging_completed`. Mode의 스로틀 명령을 다시 적용 | 작동 확인 또는 작동 불필요. 확인 실패면 `stage_failed`로 시퀀스 끝(래치) |
| `paused` | 스로틀은 Mode 값 그대로(0으로 누르지 않음), 자세 유지. 작동 엔진이 없고 연료가 남은 점화 상태의 flameout 엔진이 있을 때 `none`에서 들어온다(`BurnedOut` 판정 뒤, 점화 진입 앞). KSP가 다시 켜길 기다린다(#13, 0023). `Pending`이 참이지만 계획 워프는 막지 않는다(스로틀 0 대기, 단 `on_start` 요청이 진행 중이면 막음). 이미 진행 중인 시퀀스에서도 일시 정지 엔진은 작동 엔진으로 본다: 병렬 판정(`IsParallel`)에 들고, `ignite`는 다음 스테이지를 작동하지 않고 끝내(`staging_completed {ignited: false}`) `none` → `paused`로 넘긴다. 작동 엔진이 없을 때 스로틀을 0으로 누르지 않는 조건은 `paused`이거나 시퀀스 진행 중 일시 정지 엔진이 있음이다(`on_start` 요청만 진행 중이면 0) | 작동 엔진이 생기면 `flameout_resumed` → `none`. 일시 정지 엔진이 없어지면(종료·소진·소실) 같은 틱에 `none` 판정을 다시 함(`auto_stage` 거짓이면 하지 않음). 직전 틱 Mode 스로틀이 0이면 대기 시간을 다시 시작. 스로틀 > 0이 `max_flameout_pause_s` 이어지면 `flameout_timeout`(래치) |

**엔진 집합**: KSP의 `isOperational`은 flameout이면 false다(디컴파일 확인). 그래서 둘로 나눈다.

| 집합 | 정의 | 쓰는 곳 |
| --- | --- | --- |
| `Ignited(v)` | `EngineIgnited` (flameout 포함) | 연소 종료 판정, `SpentThrust`(다 쓴 엔진의 잔여 추력) |
| `Operational(v)` | `EngineIgnited && isOperational` | 추력·`twr`·Δv·`BurnTime`·`MaxAccel` |
| `Spent(e)` (다 쓴 엔진) | `(flameout && (!EngineIgnited \|\| !HasPropellant)) \|\| (staged && !EngineIgnited && !HasPropellant)`. 연료가 남은 점화 상태의 flameout은 소진이 아니라 일시 정지(`paused`, #13). `staged`는 이미 작동한 스테이지의 엔진(`inverseStage >= currentStage`) | 연소 종료 판정(`BurnedOut`, `NextStageDecouplesFlamedOutEngine`) |

`allowRestart = false`인 엔진(모드 부품)은 연료가 떨어지면 `Flameout`이 `flameout = true`로 둔 뒤 `Shutdown`을 불러 `EngineIgnited`가 false가 되고(`ModuleEngines` 디컴파일 확인) `Ignited`에서 빠진다. `Shutdown`은 `flameout` 플래그를 내리지 않고 이 엔진은 다시 켜지지 않으므로 `Spent`의 첫 항(`flameout && !EngineIgnited`)으로 잡힌다. 점화 상태로 남은 flameout 엔진은 연료가 없을 때만 첫 항(`flameout && !HasPropellant`)으로 잡히고, 연료가 남았으면 KSP가 스로틀 > 0 틱에 스스로 다시 켜므로 소진이 아니라 `paused`의 일시 정지 엔진이다(#13). 두 번째 항(`staged && !EngineIgnited && !HasPropellant`)은 flameout 플래그 없이 꺼진 채 연료가 없는 엔진을 위한 보조다. `allowShutdown = false`인 엔진(SRB)은 `Shutdown`이 바로 반환하므로 flameout 뒤에도 `EngineIgnited`가 참으로 남아 `Ignited`에서 빠지지 않는다(연료가 있으면 일시 정지). 스톡에는 `allowRestart = false` 엔진이 없다. `HasPropellant`는 무거우므로 `HasPropellantCached`(`ignitable_engines`와 같은 키, 접근자가 키를 스스로 확인)를 쓴다.

**연소 종료 감지**(`BurnedOut`): 둘 중 하나. 스로틀 값과 무관하게 연료 고갈로만 판정한다(스로틀 0·발사 전·점화 직후 오판 방지).

- `Spent` 엔진이 1개 이상이고, flameout이 아닌 `Ignited` 엔진이 없음(평소에는 "`Ignited` 엔진이 모두 flameout")
- 다음 스테이지의 버리는 쪽 `J`에 `Spent` 엔진이 있음(부스터, `NextStageDecouplesFlamedOutEngine`)

켜진 엔진이 없으면(발사 전, 관성 상승 중 엔진을 끈 상태) 연소 종료로 보지 않는다.

**`out_of_stages`·`ignite_blocked`·`stage_failed`·`flameout_timeout` 래치**: 이 넷 중 하나로 시퀀스를 끝내면 그 종류와 그때의 `currentStage`, `Ignited` 엔진 집합을 기록한다. 스테이지나 엔진 집합이 바뀔 때까지 `BurnedOut`과 `none`의 점화 진입을 다시 감지하지 않는다. 그래서 네 이벤트는 같은 상태에서 1회만 나온다(매 틱 `stage_burnout`·`out_of_stages`가 반복되지 않게). 래치가 있는 동안 AutoStager는 `none`에 머물러 `StagingPending`이 거짓이다. 그래서 래치가 걸린 틱에 Mode가 스로틀 > 0을 원하면 추력 없음 규칙으로 즉시 `plan_aborted {reason: no_thrust}`가 된다. 스로틀 0을 명령하는 단계(`coast` 등)에서는 계획이 계속되고, 래치는 그 동안 유지된다.

**래치 뒤 재계획**: `out_of_stages`·`ignite_blocked`·`stage_failed` 래치로 `no_thrust` 중단된 뒤 다시 출발하려면 새 계획에 `on_start: ["stage"]`가 반드시 있어야 한다. `flameout_timeout` 뒤에는 필요 없다: 중단 시 `Reset`이 래치를 풀고, 엔진이 연료를 가진 점화 상태로 남아 새 계획의 첫 틱에 `paused`로 들어가 스로틀 > 0 틱에 KSP가 다시 켠다(#13). 중단 뒤 `Command`가 Idle이라 `PrevModeThrottle`이 0이므로 `auto_stage: true`만으로는 `none → ignite`에 들어가지 못하고, 스로틀 > 0 단계는 `ignite_blocked` 뒤라면 제출 시 409 `no_thrust`가 된다. `out_of_stages`·`stage_failed` 뒤라면 `Reset`으로 래치가 풀리고 다 쓴 엔진이 flameout으로 남아 있어 연소 종료가 다시 감지되므로 제출은 성공하고, `out_of_stages`면 같은 이벤트 뒤 다시 `no_thrust`로 중단, `stage_failed`면 작동을 다시 시도한다(되돌릴 수 없는 분리는 `KeptHasEngine`이 막음). 같은 틱 진입이 필요하다: 확인을 다음 틱으로 미루면 그 틱에 `Pending`이 거짓이라 `no_thrust`가 된다.

- `on_start`는 스테이지를 하나만 작동한다. 엔진 스테이지 앞에 엔진 없는 스테이지(페어링 등)가 여러 개면 그 수만큼 `on_start` 단계를 넣는다(또는 단계마다 `on_start`). 앞쪽 `on_start` 단계는 스로틀 0으로 둔다. 스로틀 > 0 단계에서 `on_start` 확인 뒤 다음 스테이지에 엔진이 없으면 `StagingPending`이 거짓이 되어 추력 없음 규칙으로 중단되기 때문이다.
- `auto_stage: true`면 마지막 엔진 스테이지 점화는 자동이다. 엔진 스테이지 바로 앞 스테이지를 작동하는 `on_start` 단계를 스로틀 > 0으로 두면, 그 요청을 확인한 같은 `Update`(같은 틱)에서 `PrevModeThrottle`(덮어쓰기 전 Mode 스로틀)이 0보다 커서 `none → ignite`가 엔진 스테이지를 작동한다.
- `auto_stage: false`면 엔진 스테이지까지 `on_start`로 작동한다(엔진 없는 스테이지 수 + 1).

**직렬·병렬 분리**(`IsParallel`): 다음 스테이지 작동 뒤 남는 쪽(`J`의 나머지)에 `Operational` 엔진이 있으면 병렬 분리, 없으면 직렬 분리다.

- **직렬**(콜드 스테이징): `tailoff` → 스로틀 0 → 분리 → `settle` → 점화. 디커플러와 다음 엔진이 같은 스테이지에 있어도 스로틀 0으로 작동하면 엔진은 켜지지만 추력이 없으므로, `settle` 뒤에 스로틀을 올리는 방식으로 분리 후 점화가 된다.
- **병렬**(방사 부스터): `tailoff` → 분리. 코어 엔진 추력을 유지하고 `settle`을 건너뛴다.
- 실제 핫 스테이징(분리 전 다음 단 점화)은 1차 범위가 아니다(방안 "추후 대상").

**점화는 필요할 때만** (관성 상승): `ignite`에서 다시 적용하는 스로틀은 현재 Mode의 명령이다. Mode가 0을 명령하고 있으면(예: `gravity_turn`에서 예측 원지점이 이미 목표에 도달) 엔진은 켜진 상태로 추력 없이 관성으로 올라간다. 공기 저항으로 원지점이 목표 아래로 떨어지면 Mode가 스로틀을 다시 올린다. 분리는 점화 필요 여부와 상관없이 해서 다 쓴 단의 질량을 버린다.

스테이징 중(`tailoff`~`ignite`)에도 단계의 `until`·`abort` 판정은 계속한다. 단계가 바뀌거나 계획이 교체돼도 진행 중인 시퀀스는 끝까지 간다("공통 규칙"의 교체 규칙).

`on_start: ["stage"]`는 시퀀스를 거치지 않고 단계 시작 직후 스테이지를 한 번 작동한다(발사대 클램프 해제·첫 점화). 단계 시작 때 작동 요청을 등록하고, 같은 "스테이지 작동 요청·확인"으로 처리한다. 쿨다운 중이면 기다렸다가 작동한다. 이미 보낸(확인 전) `on_start` 요청이 있으면 그 요청을 결과(확인 또는 `stage_failed`)가 나올 때까지 유지하고, 새 요청은 그 뒤에 등록한다(`NextStep`·`Submit`·`ReplaceSteps` 공통). 아직 보내지 않은 요청이면 새 요청으로 바꾼다. 같은 작동 요청이 두 번 겹쳐 스테이지가 의도보다 많이 줄거나 확인이 엉키지 않게 한다. 요청이 확인을 기다리는 동안 `StagingPending`이 참이고, 진행 중인 시퀀스는 그 요청이 끝날 때까지 상태 전이를 멈춘다(두 요청이 겹치지 않게). `auto_stage`가 꺼져 있어도 동작한다.

**스테이지 작동 요청·확인**: AutoStager의 `separate`·`ignite`와 `on_start`의 모든 스테이지 작동은 공통 헬퍼 `StageRequest` 하나로 한다.

- `StageManager.CanSeparate`(public static)가 참일 때만 `StageManager.ActivateNextStage()`를 요청하고, 요청 전 `currentStage`를 기록한다. 거짓이면(쿨다운 중) 요청하지 않고 그 상태에서 기다린다.
- 이후 틱에서 `currentStage`가 기록한 값보다 줄었음을 확인한 뒤에만 `staged` 이벤트를 남기고 다음 상태로 전이한다.
- 확인 시간 제한은 쿨다운 + 1초(`PhysicsGlobals.StagingCooldownTimer + 1`)다. 첫 시도부터 이 시간 안에 확인이 안 되면 다시 요청하고, 다시 요청한 뒤에도 같은 시간 안에 확인이 안 되면 `stage_failed {stage}`를 남기고 끝낸다(시퀀스는 래치, `on_start`는 단계 계속).
- 근거(디컴파일 확인): `StageManager.ActivateStage`는 `CanSeparate`가 거짓이면 아무것도 하지 않고 돌아간다. 성공하면 `canSeparate = false`로 두고 `PhysicsGlobals.StagingCooldownTimer`(Physics.cfg `stagingCooldownTimer` = 0.5625초) 동안 쿨다운한다. 그래서 직전 스테이징 0.56초 안의 작동 요청은 조용히 무시된다.
- **보낸 요청의 기록 보존**: AutoStager 상태를 비우는 `Reset`(`Release` 경로: 완료·중단·연결 뒤 실패)과 `Clear`(`Coordinator.Stop`, reload Incompatible)는 비우기 전에, 이미 보낸 요청(시퀀스의 `_request`, `on_start`의 `_onStart`)이 있으면 대상 기체의 `currentStage < stage_before`인지 확인한다. 그렇다면 확인 틱을 기다리지 않고 그 자리에서 `staged`(`reason`은 요청 종류: `separate`·`ignite`·`on_start`)를 남긴 뒤 비운다. 작동은 됐는데 확인 틱 전에 계획이 끝나 `staged`가 빠지는 일을 막는다. 대상 기체가 없거나(활성 기체가 계획 기체와 다름) 아직 보내지 않은 요청이면 이벤트 없이 비운다.
- 작동하면 `ActivateStage → SetCurrentStage`가 같은 호출 안에서 `ActiveVessel.currentStage`를 바로 줄이고 분리도 즉시 일어난다(디컴파일 확인). 그래서 "다음 스테이지"(`currentStage − 1`)를 보는 판정(`NextStageDecouplesFlamedOutEngine`, 다음 스테이지 엔진 유무)은 요청 전에만 한다. 요청이 진행 중이면 `StageRequest` 결과(`Done`·`Waiting`·`Failed`)로만 전이한다. 그렇지 않으면 작동 직후 줄어든 `currentStage` 기준으로 다시 판정해 성공한 분리를 `out_of_stages`·`ignite_blocked`로 오인한다.

계획 필드:

```json
"auto_stage": true,
"staging_options": { "tailoff_ratio": 0.05, "max_tailoff_s": 5, "settle_distance": 2, "max_settle_s": 3, "max_separate_q": 25, "max_separate_q_wait_s": 30, "max_flameout_pause_s": 3 }
```

`separate`의 스로틀 감쇠 대기 시간 제한(2초)은 상수이고 `staging_options`에 넣지 않는다.

### 분리 부품 집합 계산

스테이지 `N`을 작동했을 때 버려지는 부품 집합 `J_N`을 계산한다. 연소 종료 판정, 병렬 판정, 조종 부품 검사, `out_of_stages` 판정이 모두 이 집합을 쓴다.

1. 스테이지 `N`에서 작동하는 디커플러(`inverseStage == N`인 부품의 `ModuleDecouple`·`ModuleAnchoredDecoupler`)마다 루트와 끊기는 쪽 `D`를 구한다.
   - `ModuleDecouple`이고 `isOmniDecoupler`가 아니면: `explosiveNodeID`가 가리키는 부착 노드의 상대 부품 쪽이다. `explosiveNodeID == "srf"`면 `part.srfAttachNode`, 아니면 `part.FindAttachNode(explosiveNodeID)`를 쓴다(`ModuleDecouplerBase.OnStart`, 디컴파일 확인). 상대 부품이 디커플러의 자식이면 그 자식의 하위 트리, 부모면 디커플러 자신과 그 하위 트리다.
   - `ModuleAnchoredDecoupler`(방사): `ModuleDecouple`과 같은 규칙이다. `explosiveNodeID`의 부착 노드(`srf`면 `part.srfAttachNode`)의 상대 부품이 디커플러의 부모면 디커플러 자신과 그 하위 트리, 아니면 상대 부품의 하위 트리다(`ModuleAnchoredDecoupler` 디컴파일 확인).
   - `isOmniDecoupler`(`ModuleDecouplerBase` 필드라 두 모듈 공통으로 `m.isOmniDecoupler`로 판정): 디커플러 자신과 자식 전부(하위 트리).
2. 끊기는 쪽 합집합 `D_N`과 나머지(루트 쪽) `R_N`을 나눈다.
3. 버리는 쪽 `J_N = D_N`이다. 분리하면 루트 쪽이 원래 `Vessel`로 남고 끊긴 쪽이 새 기체가 되므로(디컴파일 확인), 엔진·연료 배치와 상관없이 끊긴 쪽을 버린다.
4. 남는 쪽 `K_N = R_N`이다.

**캐시**: `D`·`J`·`K`는 부품 트리와 스테이지 번호로만 정해지므로 기체 `persistentId`, `currentStage`, 부품 수 중 하나가 바뀔 때만 다시 계산해 캐시한다. 매 틱 판정(`IsParallel`, `NextStageDecouplesFlamedOutEngine`, `KeptHasEngine`, 직렬 분리 대기 대상, 다음 스테이지 엔진 유무)은 캐시한 집합을 순회해 엔진 상태만 본다. 매 틱 LINQ 할당을 만들지 않는다(캐시 재계산 때만 할당).

| 이름 | 정의 |
| --- | --- |
| `IsParallel` | `K_{next}`에 `Operational` 엔진이 있음 |
| `NextStageDecouplesFlamedOutEngine` | `J_{next}`에 `Spent` 엔진이 있음 |
| `KeptHasEngine` | `K_{next}`의 엔진만 본다. 그중 `Operational` 엔진(병렬 분리의 코어)이 있거나, 아직 작동하지 않은 스테이지(`inverseStage < currentStage`)의 점화되지 않은 엔진 중 연료 있는 것(`HasPropellant`)이 있음. 버리는 쪽 `J_{next}`에 있는 나중 스테이지 엔진(sepratron 등)은 세지 않는다 |
| 직렬 분리 대기 대상 | `J_{next}`에 없는 `Ignited` 엔진(다 쓴 쪽 제외) |
| 조종 부품 검사 | 제출 시 `auto_stage` 계획에서 현재 이후 어느 스테이지 `N`이든 `D_N`에 조종 기준 부품이 있으면 400 `invalid_plan`(message 끝 `(control_part_jettisoned)`) |
| `out_of_stages` | 연소 종료를 감지했는데 `NextStageDecouplesFlamedOutEngine`이 거짓이거나 `KeptHasEngine`이 거짓(분리하지 않음) |

`next`는 `currentStage − 1`이다. `ModuleDecouple`·`ModuleAnchoredDecoupler` 디컴파일로 확인한 사실:

- `explosiveNode`의 상대 부품이 디커플러의 부모면 디커플러 쪽(디커플러와 그 하위 트리)이 떨어진다. 아니면 상대 부품 쪽(그 하위 트리)이 떨어진다. 두 모듈이 같다.
- 떨어진 쪽이 새 기체가 되고, 루트 쪽이 원래 `Vessel`로 남는다.
- `isOmniDecoupler`(`ModuleDecouplerBase` 필드)면 자식 전부와 디커플러 자신이 떨어진다(루트 쪽 부모와 끊김).
- 조종 기준 부품이 떨어진 쪽에 있으면 `WaitAndSwitchFocus`가 1프레임 뒤 `Update`에서 그쪽으로 활성 기체를 바꾼다.

실제 부품 배치에서 위 판정이 맞는지는 개발 단위 8에서 시험 기체 B·D로 실측한다.

### 엔진 추력 변화 반영 (`Flight/EngineModel.cs`)

스톡 `ModuleEngines`의 스로틀 추종 (KSP 1.12 디컴파일 확인, `UpdateThrottle`):

- `useEngineResponseTime`이 켜져 있으면 매 틱 `currentThrottle = Lerp(current, requested, k·dt)`로 **지수형**으로 따라간다. 증가 때 `k = engineAccelerationSpeed`, 감소 때 `k = engineDecelerationSpeed`.
- `throttleUseAlternate`면 다른 비선형 경로를 쓰지만, 요청이 0이 되면 `throttleInstantShutdown`(기본 true) 때문에 즉시 0이 된다.
- 둘 다 아니면 즉시 반영된다(대부분의 스톡 액체 로켓 엔진).
- 추력은 `currentThrottle`에 비례한다(`maxFuelFlow · currentThrottle · Isp · g · 추진제 충족 비율`). `throttleMin`이 있으면 요청값이 `Lerp(throttleMin, 1, req)`로 바뀐다.
- 고체 부스터(`throttleLocked`): 스로틀로 끌 수 없다. 스톡 SRB 8종 cfg에는 `useEngineResponseTime = True`, `engineAccelerationSpeed = 10`이 있지만, 스톡 전체에 `thrustCurve`·`useThrustCurve`는 없다.
  - 곡선이 없으면(스톡) 연소 종료 직전까지 유량이 일정하다(추력은 고도별 Isp로만 변함). 연료가 떨어지면 추력이 **즉시** 0이 된다(`Flameout()` → `currentThrottle = 0`).
  - `useThrustCurve`가 있으면(모드 부품) `thrustCurve`의 입력은 남은 연료 비율(추진제별 `totalResourceAvailable / totalResourceCapacity`의 최솟값)이다. 곡선대로 줄다가 `flowMultiplier < flameoutBar`(기본 0.07)이거나 남은 연료가 요구량의 `ignitionThreshold`(0.1)배 미만이 되면 즉시 꺼진다.

`EngineModel`은 `Operational` 엔진으로 다음을 예측한다.

- **고체 엔진**(`Solid`): `throttleLocked`인 엔진. `useThrustCurve`가 있으면 곡선을 적분하고, 없으면 유량 일정의 닫힌식(남은 연료 / 유량)으로 계산한다. SRB 예측 결과는 틱당 한 번 계산해 캐시한다(같은 틱의 `AutoStager`·`gravity_turn`이 다시 계산하지 않게). 엔진 배열 키(기체 `persistentId`·`currentStage`·부품 수)가 바뀔 때마다 이 캐시(`_srbCache`)를 비운다(떨어져 나간 엔진이나 다른 기체 엔진 참조가 남지 않게).
- **응답형 엔진**(`Responsive`): `useEngineResponseTime && !throttleUseAlternate && !throttleLocked`인 엔진만 넣고, 나머지는 0으로 본다. 고체 엔진은 스로틀 0 명령으로 끌 수 없으므로 `tailoff_dv`·`spool_up_s`에 넣지 않는다(남은 연소는 `srb_remaining_dv`로 따로 더함).

| 값 | 식 | 쓰는 곳 |
| --- | --- | --- |
| `spool_up_s` | 엔진별 `ln(10) / engineAccelerationSpeed`(0→90%) 중 최댓값. 연속 지수 근사라 틱마다 `Lerp`하는 실제 이산 경로와 약 10% 차이가 있다 | `circularize`는 연소 시작 시각을 `spool_up_s / 2`만큼 앞당긴다 |
| `tailoff_dv` | `Σ finalThrust / engineDecelerationSpeed / totalMass` (지금 스로틀을 0으로 내렸을 때 지수 감쇠로 더해지는 Δv, kN/t = m/s²) | `circularize`는 남은 Δv가 `tailoff_dv + tolerance` 이하가 되면 스로틀을 0으로 내린다. `gravity_turn`은 이 Δv로 생기는 원지점 상승분(`ApRise`)을 예측 원지점에 더한다 |
| `burn_time(dv)` | `m0·(1 − e^(−dv/(Isp·g0))) / ṁ`, `ṁ = F / (Isp·g0)` (`Operational` 엔진 합, Isp는 추력 가중 평균). 엔진별 `F`는 현재 기압 기준 `maxFuelFlow · Isp(p) · g0 · thrustPercentage/100`(진공 정격 `maxThrust`를 쓰지 않음). `MaxAccel`도 같은 `F`의 합 / 질량 | `circularize` 연소 시작 시각, 스로틀 감쇠 |
| `burnout_s` (SRB별) | 곡선이 없으면(스톡) 닫힌식: 남은 연료 질량 / 유량(`maxFuelFlow · thrustPercentage/100`). `useThrustCurve`면 남은 연료 비율 `f`에서 `ṁ(f) = maxFuelFlow · thrustCurve(f) · thrustPercentage/100`로 `f`를 작은 시간 간격으로 줄여 가며, `thrustCurve(f) < flameoutBar` 또는 연료 < 요구량 × `ignitionThreshold`가 될 때까지의 시간(적분 상한 600초: 넘으면 600초로 본다) | 병렬 부스터 `tailoff` 대기·분리 시점 |
| `srb_remaining_dv` | 꺼질 때까지의 SRB 임펄스 합 `Σ ∫F dt`를 현재 질량으로 나눈 값(근사). 곡선이 없으면 `ṁ · Isp · g0 · burnout_s`, 곡선이 있으면 같은 적분에서 구한다 | `srb_net_dv` |
| `srb_net_dv` | `max(0, srb_remaining_dv − g·sin(γ)·burnout_s)`. `g = μ / r²`, `γ`는 비행경로각(`asin(vertical_speed / orbital_speed)`), `burnout_s`는 타는 SRB 중 최댓값. SRB가 타는 동안의 중력 손실을 뺀 값 | `gravity_turn` 예측 원지점(스로틀 0으로도 SRB는 계속 타므로 더함) |
| `ApRise(v, dv)` | 현재 궤도 상태 `(r, v_orb)`에 순방향 `dv`를 더한 `v' = v_orb + v̂_orb·dv`의 원지점에서 현재 원지점을 뺀 값. vis-viva로 계산: `ε = |v'|²/2 − μ/|r|`, `a = −μ/(2ε)`, `h = |r × v'|`, `e = √(1 + 2εh²/μ²)`, `r_ap = a(1 + e)`. `ε ≥ 0`(탈출)이면 무한대로 본다 | `gravity_turn` 예측 원지점 = 현재 원지점 + `ApRise(v, tailoff_dv + srb_net_dv)` |

스톡 SRB는 응답 시간 설정이 있지만 `throttleLocked`라 응답형에서 빠진다. 그래서 `tailoff_dv`·`spool_up_s`는 응답 시간이 켜진 액체(비고체) 엔진에만 해당한다. 스톡에서 응답 시간이 켜진 비고체 엔진은 제트 엔진과 RAPIER뿐이라(cfg 확인) 스톡 액체 로켓 엔진만 쓰는 시험 기체 A·B에서는 0이다. 고체 부스터 값(`burnout_s`, `srb_remaining_dv`)은 시험 기체 B(방사 SRB, 스톡이라 유량 일정 경로)로 확인한다. 곡선 경로는 스톡 부품이 없어 식(코드 리뷰)으로만 확인한다.

### 시간 가속

- `coast` Mode, 그리고 `circularize`의 대기 구간에서만 건다. Mode는 `ModeCommand.WarpToUt`로 목표 시각만 알리고, `Warp` 호출은 Coordinator가 틱 순서 (f)에서 한다.
- `coast`는 `until`에 아래 표의 시간 조건 잎이 있을 때만 가속한다. 시간이 지나면 줄어드는 변수는 `<=`·`<`, 늘어나는 변수는 `>=`·`>`일 때만 가속 대상이다(반대 방향 비교는 시간이 지나도 참이 되지 않으므로 가속하지 않음). 목표 UT(`WarpToUt`)는 변수별로 아래 식으로 구한다(`X`는 잎의 `value`, `ut`는 현재 UT). 잎이 여럿이면 `until`의 묶음 구조대로 조합한다.
  - 목표 UT가 현재 UT 이하인 잎(이미 참이거나 목표가 지남)은 조합에서 뺀다. 가속 대상이 아닌 잎(위 방향 규칙에 맞지 않거나 시간 변수가 아닌 잎)도 뺀다.
  - `all`은 남은 잎 목표의 최댓값(모든 잎이 참이 되는 시각), `any`는 최솟값(먼저 참이 되는 시각)이다. 중첩된 묶음은 안쪽부터 같은 규칙으로 구한다. 남은 잎이 없는 묶음은 목표 없음이다.
  - 최상위 결과가 목표 없음이면 가속하지 않는다.

| 변수 | 방향 | 가속 대상 `op` | 목표 UT |
| --- | --- | --- | --- |
| `time_to_apoapsis` | 감소 | `<=`, `<` | `ut + time_to_apoapsis − X` |
| `time_to_periapsis` | 감소 | `<=`, `<` | `ut + time_to_periapsis − X` |
| `met` | 증가 | `>=`, `>` | `ut + (X − met)` |
| `step_time` | 증가 | `>=`, `>` | `stepStartUt + X`(= `ut + (X − step_time)`) |
- 대기권 밖이고 스로틀이 0이고 추력을 내는 엔진이 없고 스테이징이 진행 중이 아닐 때(`!AutoStager.Pending`: 시퀀스가 `none`이 아니거나 `on_start` 작동 요청이 확인을 기다리면 거짓) `TimeWarp.fetch.WarpTo(target_ut - 10)`으로 궤도 가속한다. 스테이징 중 가속하면 분리·이격·점화가 레일 가속에 걸려 틱 단위 판정이 깨지므로 허용 조건에 넣는다(허용 조건이 아니면 아래 규칙대로 우리가 건 가속만 해제). 레일 가속은 레일 가속 한도(가속도 `geeForce > TimeWarp.GThreshold`, 대기권 안, 고도 한도)로 막히므로(`TimeWarp` 디컴파일 확인) 이 조건을 먼저 확인한다. 대기권 안이면 가속하지 않는다.
- **해제 시점**: `Warp.Request`는 목표까지 남은 시간이 15초 미만이면 새로 요청하지 않고, 우리가 건 가속이 있으면 `Warp.Stop`으로 해제한다. `WarpTo(target_ut - 10)`은 이 15초 경계를 놓친 경우(레일 배율이 커서 한 틱에 경계를 넘음)의 하한이다. 그래서 실제 해제는 남은 시간이 15초 아래로 처음 내려간 틱(우리 `Stop`, 래치 없음)이고, 늦어도 목표 10초 전(`WarpTo` 자체 정지, 사용자 취소와 같게 래치)이다. `warp_stopped`는 목표 15초 전과 10초 전 사이에 나온다. 남은 시간이 15초 미만이므로 같은 단계에서 다시 요청하지 않는다.
- 단계 전환·중단·reload 때 `Warp.Stop`으로 레일 가속과 대기 중인 `WarpTo`를 해제한다. 사용자가 건 물리 가속(`Modes.LOW`)은 끄지 않는다. reload(`Coordinator.Stop`)와 전체 교체(`Submit`)는 우리가 요청한 가속(`Warp.Requested`)이 있을 때만 `Warp.Stop`을 부른다. 계획 없이 reload하거나 사용자가 직접 건 레일 가속은 그대로 둔다. 해제 순서: `TimeWarp.fetch.setAutoWarp = false`(public 필드) → `TimeWarp.fetch.CancelAutoWarp()` → (레일 가속이면) `TimeWarp.SetRate(0, true)`. 우리가 가속을 요청한 적이 있으면(`Warp.Requested`) `On`·`Pending` 값과 무관하게 이 순서를 모두 실행한다. 요청한 적이 없으면 `On`이거나 `Pending`일 때만 실행한다. `WarpTo`는 `setAutoWarp`만 켜고 다음 `Update`에 autoWarp를 시작하므로, 그 전에 취소해도 시작되지 않게 `setAutoWarp`를 먼저 내린다. `WarpTo`는 autoWarp 코루틴과 입력 잠금을 걸기 때문에 `SetRate`만으로는 풀리지 않는다.
- 가속 중인지(`Warp.On`)는 내부 요청 플래그가 아니라 실제 레일 가속 값(`TimeWarp.WarpMode == TimeWarp.Modes.HIGH && TimeWarp.CurrentRateIndex > 0`)으로 판단하고 매 틱 동기화한다. 물리 가속은 세지 않는다. `Pending`은 `WarpTo`가 시작 전이거나 진행 중인 상태다: `setAutoWarp`가 켜져 있거나, autoWarp가 진행 중(private `autoWarpEngaged` 리플렉션, 또는 `WARPTO_LOCK` 입력 잠금 존재. 방법은 개발 단위 9에서 확인). `On`·`Pending` 판정(`Sync`)도 이 값을 쓴다. autoWarp가 레일 배율을 올리기 전 틱에 `On`이 거짓이어도 가속 중으로 본다. 사용자가 가속을 취소하면 그대로 반영된다(`warp_stopped` 이벤트, `get_flight`의 `plan.warp` false).
  - **구현 확인(단위 9, 이슈 #5)**: 진행 판정은 `autoWarpEngaged` 리플렉션이다(`WARPTO_LOCK`은 사용자 취소 때 1프레임 늦게 풀려 쓰지 않음). `get_flight.plan.warp`는 `Warp.Active = On || Pending`이다: autoWarp가 목표 근처에서 감속하면 배율 단계는 0인데 실제 배율이 아직 높은 구간이 있어(실측: 단계 0, 30배) `On`만으로는 먼저 false가 된다. `Stop`은 이 감속 구간(레일 모드, 배율 > 1)에서도 `SetRate(0, true)`를 부른다. 리플렉션 필드가 없으면 가속하지 않고 `warp_unavailable not_supported`를 낸다.
  - **사용자 가속과의 관계(구현 확인)**: `coast` 단계에서 사용자 가속(레일 배율, 물리 배율, 진행 중인 warp-to)이 이미 걸려 있으면 계획은 가속을 요청하지 않고 사용자 가속을 그대로 둔다(`warp_unavailable player_warp`). `WarpTo`는 현재 모드로 가속하므로(실측: 물리 모드에서 물리 4배로 걸림), 물리 모드에 배율 0이면 `setMode(HIGH)`로 레일로 바꾼 뒤 요청한다(게임도 배율 0이면 레일로 되돌림). 사용자 가속은 단계 전환·중단 때만 레일 가속이 해제되고, 물리 가속은 해제하지 않는다. reload(`Coordinator.Stop`)는 우리가 요청한 가속만 해제한다.
- **허용 조건이 아닐 때**: `Warp.Request`는 우리가 요청한 가속(`_requested`)이 있을 때만 해제한다. 사용자가 직접 건 가속은 건드리지 않는다.
- **사용자 취소 래치**: 우리가 요청한 가속이 우리 `Stop` 없이 꺼진 것을 `Sync`가 감지하면(사용자 취소) 래치를 건다. 래치가 있으면 그 단계 안에서는 `WarpToUt`가 와도 다시 요청하지 않는다. 단계가 바뀌면 래치를 푼다. reload 때 인계한다(`warp_cancelled`). `WarpTo`가 목표(`target_ut - 10`)에 닿아 스스로 끝난 경우도 같게 본다(남은 시간이 15초 미만이라 다시 걸 일이 없음).

### reload 인계

**인계 내용**: `{format: 1, epoch, events, seq, plan?}`. 이벤트 버퍼와 `seq`, `epoch`(이벤트 세션 id, "이벤트")는 계획이 없어도 **항상** 넘긴다(Planner의 cursor가 끊기지 않게). `plan`은 계획이 실행 중일 때만 넣는다.

```
plan: { plan_id, vessel_id, raw(계획 JSON, replace 반영), step, step_start_ut,
        timers(조건 잎별 trueSince, NaN은 null), mode_state(IFlightMode.Save()),
        staging: { state, start_ut, before[](분리 전 기체 id 목록), parallel(_parallel),
                   ticks(separate 대기 틱 수), last_ut,
                   latch({kind: out_of_stages|ignite_blocked|stage_failed, stage, ignited[]} 또는 null),
                   request({stage_before, first_ut, last_send_ut, tries} 또는 null: 시퀀스의 작동 요청),
                   on_start_request(같은 형식 또는 null), on_start_queued(bool: 보낸 요청 뒤에 등록된 요청) },
        command: { attitude(직전 `Command.Attitude`의 월드 방향 숫자 3개 또는 null), throttle, mode_throttle },
        sas_before, controller_integral[3],
        warp_cancelled(사용자 취소 가속 래치 `_cancelled`) }
```

- `mode_state`에는 Mode 내부 상태가 모두 들어간다. `circularize`는 `burning`, `locked_dir`(고정 방향, 없으면 null, 있으면 숫자 3개), `prev_dv`(직전 Δv 크기), `prev_ecc`(직전 이심률), `ecc_flat`(이심률 개선 없음 틱 수)를 넣는다. `gravity_turn`은 `reached`.
- **직전 명령 인계**(`command`): reload 직후 첫 계산 전에 `Command`를 인계받은 직전 명령으로 되돌린다. 자세 목표는 방향 벡터 목표(`AttitudeTarget.Vector`)로 복원한다(`Stop`과 `Start`는 같은 프레임 안에서 이어지므로 월드 방향이 그대로 맞음). 그래서 첫 수집 (a)에서 `attitude_error`가 값을 갖고, `PrevCommandThrottle`·`PrevModeThrottle`도 reload 전 값이다. `circularize` 자세 게이트(값 없음이면 스로틀 0)와 판정 카운터 초기화가 reload 첫 틱에 스로틀을 0으로 떨어뜨리지 않는다.
- 계획(`plan`) 아래 키 이름은 개발 문서의 `Handover.Capture` 초안과 같다.

- `Handover`는 `Dictionary<string, object>`·`List<object>`·숫자·문자열·bool로만 만든다. 기존 `Json.Serialize`는 알 수 없는 객체를 `ToString()`으로, NaN·Infinity를 null로 쓰기 때문이다.
- **Load 공통 규칙**: 인계를 복원하는 모든 `Load`(Coordinator, Mode, `AutoStager`, `StageRequest`)는 double 필드의 null을 그 필드의 기본값으로 되돌린다. 기본값은 따로 정한 필드(`circularize`의 `prev_dv`·`prev_ecc`: +∞)를 빼고 NaN이다. 타이머 `trueSince`, `staging.start_ut`·`last_ut`, `StageRequest`의 `first_ut`·`last_send_ut`가 모두 여기에 해당한다. 공통 헬퍼 하나로 읽어 필드마다 규칙이 갈리지 않게 한다.
- 계획은 파싱된 객체가 아니라 JSON을 넘기고, 새 Logic이 다시 파싱한다(새 Logic의 검증 규칙이 바뀌었으면 여기서 `reload_incompatible`).
- `raw`는 라우트 핸들러가 받은 요청 본문을 파싱한 `Dictionary`를 `Json.Serialize`로 다시 쓴 것이다(핸들러는 `RequestBody`만 받음). `replace_flight_steps` 때는 단계 목록을 바꾼 `Dictionary`로 `raw`도 다시 만든다.

**순서** (`LogicHost.Reload`는 이전 Logic `Stop()` → 새 Logic `Start()`, 실패하면 이전 Logic `Start()`를 다시 부른다):

1. `Stop()`: 우리가 요청한 가속(`Warp.Requested`)이 있으면 먼저 해제한다(`Warp.Stop`. 스로틀·SAS는 유지). 그래서 `warp_stopped` 이벤트가 인계 이벤트에 들어간다. 우리가 요청하지 않은 가속(계획 없이 reload, 사용자가 건 가속)은 건드리지 않는다. 그다음 위 내용을 `context.Handover`에 넣고, `OnFlyByWire`·이벤트 구독을 해제한다. 스로틀은 0으로 내리지 않는다(이어받기 때문). SAS도 되돌리지 않는다. 마지막으로 Coordinator·AutoStager·FlightEvents의 static 상태를 비운다(이전 Logic이 다시 `Start()`될 때 남은 상태로 `Tick`이 돌지 않게). `Stop()`은 예외를 던지지 않는다.
   - 인계 내용 직렬화(`Handover.Capture`)가 실패하면 이어받을 수 없으므로 `Abort("error", null, 예외 메시지)` 경로(스로틀 0·SAS 복원)로 처리한다. 그 뒤 `plan` 없이 `{format, epoch, events, seq}`를 다시 직렬화해 넘기고(`plan_aborted` 이벤트 포함), 이것도 실패하면 최소 `{format, epoch, seq}`를 넘긴다. 어느 경우든 `seq`와 `epoch`가 이어진다. 그다음 나머지 해제를 계속한다.
2. `Start()`: 맨 앞에서 `LogicHost.LoaderVersion`을 확인해(const라 Logic 빌드 때 값이 박히므로 리플렉션으로 실제 로더 값을 읽는다) 0.0.3 미만이면 분명한 메시지(예: `loader 0.0.3 required; restart KSP`)로 예외를 던진다(→ `reload_failed`, `Handover` 필드가 없는 로더에서 인계가 조용히 사라지지 않게). `context.Handover`를 참조하는 코드는 버전 확인 뒤에 부르는 별도 메서드(`[MethodImpl(MethodImplOptions.NoInlining)]`)로 분리한다. 같은 메서드에 있으면 0.0.2 로더에서 JIT 때 `MissingFieldException`이 버전 확인보다 먼저 나기 때문이다. 실패할 수 있는 작업(`Settings.Reload`, `Routes.Build`)을 **먼저** 하고, 성공한 뒤에 GameEvents 훅을 연결하고 `Resume`(이어받기, `OnFlyByWire` 연결 포함)을 한 다음 마지막에 `context.Handover`를 비운다. 훅 연결 중 예외가 나면 이미 연결한 훅을 되돌리고 `context.Handover`를 원래 값으로 둔 채 예외를 다시 던진다. 그래야 이전 Logic의 `Start()`가 같은 `Handover`로 이어받는다.
   - `format`이 같고, 비행 씬이고, 활성 기체가 계획의 기체이고, 계획 재검증과 Mode `Load`가 성공하면 이어서 실행하고 `logic_reloaded {resumed: true}`를 남긴다. 계획 재검증·Mode `Load`를 `AutoStager.Load`·사용자 취소 가속 래치 복원·`Running` 전환보다 먼저 한다(실패하면 static 상태를 바꾸지 않음). 훅 연결 전에 인계받은 직전 명령으로 `Command`를 되돌리고 수집한 뒤, `Tick`과 같은 `ComputeCommand`로 첫 명령을 채운다("Coordinator 틱").
   - 계획이 없었으면 `logic_reloaded {resumed: false}`만 남긴다.
   - 계획이 있었는데 이어받을 수 없으면(Incompatible) `_plan`·`_mode`를 null로, `AutoStager.Clear()`를 한다(비우기 전에 보낸 요청이 작동했으면 `staged`를 남김, "스테이지 작동 요청·확인"). 재검증이나 Mode `Load`가 `AutoStager.Load` 전에 실패해 인계 요청이 메모리에 없으면, 인계 `staging`의 `request`·`on_start_request`(`stage_before`, 보냄 여부)만 따로 읽어 같은 판정으로 `staged`를 남긴다. 활성 기체의 `persistentId`가 인계 `vessel_id`와 같을 때만 그 기체를 복원 대상으로 두고(`Adopt`) `Release()`(스로틀 0, SAS를 `sas_before`로 복원, `OnFlyByWire` 해제)를 한다. 다르면(활성 기체 없음 포함) 다른 기체의 SAS·`ctrlState`·가속을 건드리지 않고 `Command`만 Idle로 둔다. 단, 인계 `command.throttle > 0`이면 전역 `FlightInputHandler.state.mainThrottle`만 0으로 내린다(이전 Logic이 넣던 스로틀 입력이 다른 기체에 남지 않게). 어느 경우든 `logic_reloaded {resumed: false}`, `plan_aborted {reason: reload_incompatible}`을 남긴다. `Handover` 파싱, 계획 재검증, Mode `Load`의 실패도 여기에 속한다. 이 실패는 예외로 reload를 막지 않는다(`Start()`는 성공하고 계획만 중단).
   - 계획을 이어받는 중 첫 `ComputeCommand`가 `NoThrustException`을 던지면 Incompatible이 아니다(계획은 맞게 이어받았고 추력만 없음). 복원 대상을 두고(`Adopt`) `logic_reloaded {resumed: false}`를 남긴 뒤 `Abort("no_thrust")`(스로틀 0·SAS 복원, `plan_aborted {reason: no_thrust}`)로 처리한다.
   - `Resume`은 밖으로 예외를 던지지 않는다. 각 단계를 try로 감싸고 실패는 위 Incompatible 경로(추력 없음은 바로 위 경로)로 처리한다. `Start()`의 catch로 나가면 이전 Logic이 같은 `Handover`로 다시 이어받으므로, 이미 보낸 스테이지 작동 같은 되돌릴 수 없는 부작용이 겹친다.
3. 새 Logic `Start()`가 실패해 이전 Logic `Start()`를 다시 부르는 경우도 2와 같은 경로로 이어받는다.
4. 이전 Logic 재시작까지 실패했는데 `_context.Handover`가 남아 있으면(아무도 이어받지 못함) `LogicHost.Reload`가 인계 JSON을 최소 파싱해 `plan` 키가 있을 때만 `FlightInputHandler.state.mainThrottle = 0`으로 두고 `plan.sas_before` 값이 있으면 활성 기체 SAS를 그 값으로 되돌린다. 그다음 `Handover`를 비운다(Mod 변경). `plan` 키가 없거나 파싱에 실패하면 스로틀·SAS를 건드리지 않는다(계획이 없던 상태에서 사용자의 수동 스로틀을 0으로 만들지 않음). 실행 중 계획이 있었으면 마지막 스로틀이 남은 채 제어가 사라지지 않게 한다.
5. `Reload`가 성공한 뒤에도 `_context.Handover`가 남아 있으면(새 Logic이 소비하지 않음, 예: 인계를 모르는 Logic) 4와 같이 스로틀 0·SAS 복원 후 `Handover`를 비운다(Mod 변경).

`Handover`는 메모리에만 있다. KSP를 끄면 사라진다.

### 씬·기체 변경

`onGameSceneLoadRequested`(씬 전환), `onVesselChange`(활성 기체 변경), 대상 기체 파괴(`onVesselDestroy`)가 일어나면 중단 처리한다. reason은 각각 `scene`, `vessel_changed`, `vessel_lost`다. 활성 기체 변경은 분리 때문이어도 예외 없이 중단한다. 분리로 활성 기체가 바뀔 구성은 제출 시 거부하므로(`auto_stage` 계획) 정상 계획에서는 일어나지 않는다. 이벤트를 놓쳐도 `Tick`이 매 틱 씬과 활성 기체를 확인해 `scene`·`vessel_changed`로 중단한다("Coordinator 틱").

예외는 `dock` 단계의 결합 하나다(#18). `dock`이 감시하는 자기 포트가 결합(`onPartCouple`)된 뒤에는, 그 포트를 가진 새 활성 기체를 계획 기체로 바꿔 이어가고(`TryAdoptDocked`), 흡수돼 사라지는 계획 기체의 파괴는 `vessel_lost`로 보지 않는다. 감시 포트와 결합 여부는 reload 인계 확정 단계에서 복원한다.
