# 부품동작 설계 (1단계: 상태 조회 + 범용 event 실행)

이슈: [#15](https://github.com/SeongSikChae/KSP1-BRIDGE-MCP/issues/15)
방안: [0040-부품동작-방안.md](0040-부품동작-방안.md)

방안 결정 1의 1단계(상태 조회 + 범용 event 실행)만 다룬다. 부속 제어·action group(2단계)과 연료 전달(3단계)은 별도 설계 문서로 다룬다.

## 게임 동작 (디컴파일, Assembly-CSharp)

### PAW 표시 규칙 (`UIPartActionWindow`)

- 비활성 모듈(`!PartModule.isEnabled`)의 field·event는 PAW에 넣지 않는다. 부품 수준(`Part.Fields`, `Part.Events`)도 같은 창에 들어간다.
- field (`CanActivateField`)
  1. `!GameSettings.ADVANCED_TWEAKABLES && fld.advancedTweakable`이면 표시하지 않는다.
  2. 활성 기체 부품: `fld.guiActive`.
- event (`CanActivateEvent`)
  1. `!GameSettings.ADVANCED_TWEAKABLES && evt.advancedTweakable`이면 표시하지 않는다.
  2. 활성 기체 부품: `evt.guiActive && evt.active && !evt.EventIsDisabledByVariant`가 아니면 표시하지 않는다.
  3. 다음을 모두 만족하면 표시한다: `ControlTypes.ACTIONS_SHIP` 입력 잠금이 풀려 있음(숫자 입력 포커스 예외 제외), `part.vessel.IsControllable`, `requireFullControl`이면 `ControlTypes.TWEAKABLES_FULLONLY` 잠금이 풀려 있음.
  4. 3을 만족하지 못하면 `evt.guiActiveUncommand`일 때만 표시한다.
  5. 활성 기체가 아닌 부품은 `guiActiveUnfocused`·거리 규칙을 쓴다(이 설계는 활성 기체 부품만 다룬다).
- 창 포커스 잠금: `FlightDriver.OnApplicationFocus(false)`는 `flightDriver_ApplicationFocus`(모든 ControlTypes)를 걸고, 포커스가 돌아오면 푼다. 게임 창이 백그라운드일 때 플레이어 키 입력을 막는 잠금이며 기체 조작 가능 여부와는 관계없다. 에이전트는 보통 게임 창이 백그라운드인 상태에서 호출하므로, 규칙 3의 입력 잠금 판정에서 이 잠금은 세지 않는다(`launch_craft`가 `EditorDriver_AppFocus`를 세지 않는 것과 같다). 구현 실측 중 사용자 지적으로 추가했다.

### PAW 버튼 클릭 (`UIPartActionButton.OnClick`, 비행 장면)

- 모듈 event(`isModule`)
  1. 대칭 부품의 PAW가 함께 열려 있지 않으면(`ItemListContainsCounterparts`가 false), `part.symmetryCounterparts[i].Events.Send(evt.id)`를 부른다.
  2. `evt.Invoke()`.
- 부품 수준 event: `evt.Invoke()`만 부른다. 대칭 부품에 보내지 않는다.
- `Part.Events`는 부품 수준 event 목록(`new BaseEventList(this, null)`)이다. `BaseEventList.Send(id)`는 그 목록에서 `active`이고 id가 같은 event 하나를 실행한다. 따라서 모듈 event의 1은 대칭 부품의 **부품 수준** event에만 닿는다. 모듈 event(예: 안테나 `Extend`)의 대칭 적용은 각 모듈의 event 코드가 스스로 하는 만큼만 일어난다(예: `ModuleDeployablePart.eventsInSymmwtryAlways`).
- MCP 요청에는 열린 PAW가 없으므로 모듈 event는 항상 1을 실행한다.

### 상태 멤버 (PAW field가 아님)

- `ModuleDeployablePart`(안테나·태양광 패널·라디에이터 계열의 기반): `deployState`(`DeployState`: RETRACTED, EXTENDED, RETRACTING, EXTENDING, BROKEN). PAW의 `status` field는 현지화된 문자열이다.
- `ModuleDockingNode`: `state`(string, 예: `Ready`), `otherNode`(결합 상대 `ModuleDockingNode`).

### CommNet

- `vessel.connection`(`CommNetVessel`): `IsConnected`, `IsConnectedHome`, `ControlState`, `SignalStrength`, `Signal`, `SignalDelay`, `ControlPath`(`CommPath`), `Comm`(`CommNode`).
- `CommNode.antennaTransmit.power`, `antennaRelay.power`(결합 반영된 값), `isHome`, `displayName`.
- `CommNode`는 `Node<...> : Dictionary<CommNode, CommLink>`이며, 이웃 노드를 키로 원본 네트워크 링크를 담는다. `bestLink`·`bestLinkNode`는 경로 탐색 임시값으로, 어느 기체든 경로를 계산할 때마다(`CreateShortestPathTree`) 모든 노드에서 초기화되므로 조회 시점에 쓰지 않는다.
- 네트워크 링크(`CommNetwork.TryConnect`): relay×relay, a.relay×b.transmit, b.relay×a.transmit의 세 조합을 **각각 독립으로** 계산해 `strengthRR`·`strengthAR`·`strengthBR`에 저장하고 `bothRelay`·`aCanRelay`·`bCanRelay`를 남긴다. 우선순위는 없다.
- 경로 링크(`CommNetwork.FindPath`): 경로마다 `new CommLink()`를 만들고 `Set(a = 시작 쪽 노드, b = 다음 노드, cost, bestLink.GetSignalStrength(start))`로 채운다. 경로 링크에는 relay 플래그와 `strengthRR/AR/BR`가 **복사되지 않는다**. 경로 링크의 `a`가 `from`, `b`가 `to`이며 원본 네트워크 링크는 `from[to]`(Dictionary 조회)로 찾는다.
- 실제로 쓰인 조합은 `CommLink.GetSignalStrength(aMustRelay, bMustRelay)`가 경로 위치(시작 노드가 아니면 relay 필수)와 세기 비교로 고른다.
- 링크 최대 거리: `CommNetScenario.RangeModel.GetMaximumRange(aPower, bPower)`.
- `FindHome`에 실패하면 `FindClosestControlSource`로 가장 가까운 제어원(유인 기체 등)까지의 경로를 쓴다. 이때 경로 끝은 home이 아니다.
- CommNet 사용 여부: `HighLogic.CurrentGame.Parameters.Difficulty.EnableCommNet`.

## 결정 (사용자 합의)

### 1. 조회 도구: `get_vessel_parts` 하나

- 부품별 모듈 상태, 자원, event를 한 응답에 담는다.
- `part_id`·`module` 필터 인자로 응답을 줄일 수 있게 한다.
- 실행은 별도 도구 하나로 둔다. 조회 1개 + 실행 1개다.

### 2. 모듈 상태: 비행 PAW field 전부 + 주요 상태 보강 (검토 뒤 변경, 사용자 재합의)

- 모듈 종류를 가리지 않고 PAW 표시 규칙의 field(`guiActive`, advanced tweakable 규칙 포함)를 읽는다. 모드 모듈도 같은 규칙으로 나온다.
- PAW field에 없는 주요 상태를 모듈의 `state` 항목으로 보강한다. 1단계 대상은 `ModuleDeployablePart` 계열 `deployState`와 `ModuleDockingNode`의 `state`·결합 상대 부품 id다. 언어와 관계없이 판정할 수 있는 값이다. 2단계에서 대상 모듈을 늘릴 수 있다.
- 처음 결정(PAW field만)은 검토에서 도킹 포트 상태가 PAW field가 아님을 확인해 바꿨다.

### 3. event 목록과 실행 허용 (검토 뒤 변경, 사용자 재합의)

- 목록: PAW 표시 규칙 1·2(advanced tweakable, `guiActive`·`active`·variant)를 통과한 event를 모두 넣고, 규칙 3·4 결과를 `available`(bool)과 `reason`(`input_locked`·`no_control`, 부품이 활성 기체에 없으면 `not_active_vessel`, 가능하면 null)으로 붙인다. 이슈의 "현재 실행 가능 여부" 요구에 맞춘다.
- 실행: `available`인 event만 실행한다. 사람이 게임 PAW에서 누를 수 있는 버튼과 같다. 아니면 409로 거부한다.
- 처음 결정(실행 가능한 event만 목록에 넣음)은 검토에서 이슈 요구와 어긋남을 확인해 바꿨다.

### 4. 실행 응답: 즉시

- event를 호출한 직후 그 모듈의 상태를 담아 응답한다.
- 애니메이션 등 시간이 걸리는 변화의 완료는 `get_vessel_parts`로 확인한다.

### 5. 같은 이름 모듈: `module_index`

- 조회 응답의 모듈마다 부품 안 모듈 순번(`index`, `part.Modules` 순서)을 넣는다.
- 실행은 `module` + `event`로 지정한다. 그 부품에 같은 이름의 **활성** 모듈이 여럿이면 `module_index`를 요구하고, 없으면 409 `ambiguous_module`로 거부한다.
- `module_index`를 주면 그 순번의 모듈 이름이 `module`과 같아야 한다.

### 6. event 지정: 내부 이름

- `BaseEvent.name`(예: `Extend`, `Undock`)으로 지정한다. 게임 언어·상태와 관계없이 고정된 이름이다.
- 조회 응답에는 표시 이름(`guiName`)도 같이 넣는다.

### 7. CommNet 조회: `get_commnet`, 구간별 상세

- 연결 여부, 신호 세기, 제어 상태, 기체 안테나 출력(송신·중계, 결합 반영)을 넣는다.
- 제어 경로의 구간마다 양끝(기체 id·이름 또는 지상국 이름), 거리, 범위, 구간 신호 세기, 양끝이 쓴 안테나 종류(송신·중계)를 넣는다. 중계 여부는 양끝 안테나 종류로 나타낸다(재검토에서 "중계 여부" 단일 값은 거의 항상 true라 정보가 없음을 확인해 바꿨다).

### 8. CommNet 꺼짐: 200 `enabled: false`

- 난이도 설정에서 CommNet이 꺼져 있으면 오류 없이 `enabled: false`와 안테나 출력만 응답한다. 연결·경로 항목은 null이다.

### 9. 대칭 부품: PAW 버튼과 같게 (방안 결정 5 회귀 반영)

- 모듈 event: 대칭 부품마다 `Events.Send(evt.id)`, 그다음 `evt.Invoke()`. 응답의 `counterparts`에 `{part_id, sent}`(`Send`의 bool)를 넣는다. 보통 `sent: false`다(부품 수준 목록에 같은 id가 없음).
- 부품 수준 event(`module: "Part"`): `evt.Invoke()`만 한다. `counterparts`는 빈 배열이다.

## 도구·API

| MCP 도구 | HTTP | 비고 |
|---|---|---|
| `get_vessel_parts(part_id?, module?)` | `GET api/flight/parts?part_id=&module=` | 신규, 읽기 전용 |
| `invoke_part_event(part_id, module, event, module_index?)` | `POST api/flight/part_event` 본문 `{part_id, module, event, module_index}` | 신규 |
| `get_commnet()` | `GET api/flight/commnet` | 신규, 읽기 전용 |

모두 `Guard.ActiveVessel()`을 먼저 통과해야 한다(409 `not_in_flight`·`no_active_vessel`). 비행 계획 실행 여부는 검사하지 않는다(방안 결정 8).

### 입력 규칙

- `part_id`: 0..uint.MaxValue 정수(`DebugHandler.PartId`와 같은 규칙, 같은 400 문구). 0은 형식상 허용하고 없는 부품이면 404다.
- 쿼리 값이 빈 문자열이면 인자가 없는 것으로 본다(`EditorHandler`의 `Empty(q[...])`와 같다).
- `module_index`: null이면 없는 것으로 본다(`RequestBody.Has`). 있으면 0 이상 정수.

### `get_vessel_parts` 응답

```json
{
  "vessel": "Relay-1", "id": 123,
  "parts": [{
    "id": 456, "name": "HighGainAntenna5.v2", "title": "HG-5 High Gain Antenna",
    "modules": [{
      "index": 2, "module": "ModuleDeployableAntenna",
      "fields": [{"field": "status", "title": "Status", "value": "Retracted", "units": ""}],
      "events": [{"event": "Extend", "title": "Extend Antenna", "available": true, "reason": null}],
      "state": {"deploy_state": "RETRACTED"}
    }],
    "resources": [{"resource": "ElectricCharge", "amount": 10.0, "max": 10.0, "flow_enabled": true}]
  }]
}
```

- 부품 순서는 `vessel.parts` 순서다.
- 모듈은 `isEnabled`인 것만 넣는다. 부품 수준 field·event는 `module: "Part"`, `index: null`인 항목 하나로 넣는다(있을 때만).
- fields·events가 모두 비고 `state`도 없는 모듈은 넣지 않는다.
- field `value`: 숫자·bool·string은 그대로, enum은 이름 문자열, 그 밖의 타입은 `ToString()`. 값을 읽다가 예외가 나면 그 field만 `value: null`, `error: "<예외 이름>: <메시지>"`로 넣고 나머지는 계속한다.
- `state`: 보강 대상 모듈에만 넣는다. `ModuleDeployablePart` 계열 `{deploy_state}`(enum 이름), `ModuleDockingNode` `{state, docked_part_id}`(`otherNode?.part?.persistentId`, 없으면 null).
- `part_id` 필터: 그 부품 하나. 없으면 404 `part_not_found`.
- `module` 필터: 그 이름의 모듈만 남기고, 남는 모듈이 없는 부품은 뺀다. `resources`는 `module` 필터와 관계없이 넣는다.
- 자원은 `part.Resources`의 `resourceName`, `amount`, `maxAmount`, `flowState`.

### `invoke_part_event` 처리

1. `Guard.ActiveVessel()`
2. 인자 검사(입력 규칙). `module`·`event`는 비어 있지 않은 문자열. 아니면 400 `bad_request`.
3. 활성 기체 `parts`에서 `persistentId`로 부품을 찾는다. 없으면 404 `part_not_found`.
4. 모듈 결정
   - `module == "Part"`: 부품 수준 `Part.Events`. `module_index`를 주면 400.
   - `module_index`가 있으면 `part.Modules[module_index]`. 범위 밖이거나 `moduleName != module`이면 404 `module_not_found`.
   - 없으면 이름이 `module`인 모듈. 0개면 404 `module_not_found`(메시지에 부품의 모듈 이름 목록). 그중 활성 모듈이 2개 이상이면 409 `ambiguous_module`(메시지에 index 목록), 1개면 그것, 0개면 첫 모듈.
   - 고른 모듈이 `!isEnabled`면 409 `event_unavailable`(`module disabled`).
5. `Events[event]`(이름 일치)가 없으면 404 `event_not_found`(메시지에 그 모듈의 event 이름 목록).
6. PAW 표시 규칙 1·2를 통과하지 못하면 409 `event_unavailable`(`inactive`), 3·4로 `available`이 아니면 409 `event_unavailable`(`input_locked` 또는 `no_control`).
7. 실행 전 `before = vessel.persistentId`. 모듈 event면 대칭 부품 `Send`, 그다음 `evt.Invoke()`. 예외는 500 `event_failed`(예외 이름: 메시지)로 응답하고 이벤트를 남긴다.
8. 실행 뒤 상태
   - `vessel_changed`: `FlightGlobals.ActiveVessel?.persistentId != before`
   - `part_vessel_id`: 실행 뒤 `p.vessel?.persistentId`(부품이 사라졌으면 null). `separated`: `p.vessel != v`(Undock 등으로 부품이 다른 기체로 갔거나 사라짐).
   - `module_state`: 그 모듈만 `get_vessel_parts`와 같은 형식으로 읽는다. 부품이 활성 기체에 없으면 event의 `available`은 false, `reason`은 `not_active_vessel`로 둔다. 읽다가 예외가 나면(부품 파괴 등) `module_state: null`, `state_error`에 예외를 넣는다. event는 이미 실행됐으므로 응답은 200이다.
9. 응답: `{part_id, part, module, index, event, title, counterparts, vessel_changed, part_vessel_id, separated, module_state, state_error}`.

비행 계획이 실행 중일 때 실행한 event로 활성 기체 id가 바뀌면, 다음 Tick에 기존 `Coordinator` 처리대로 계획이 `vessel_changed`로 중단된다(결합 기체 예외 `TryAdoptDocked` 포함). 이 동작은 바꾸지 않고 도구 설명에 적는다.

### `get_commnet` 응답

```json
{
  "enabled": true,
  "vessel": "Relay-1", "id": 123,
  "antenna": {"transmit_power": 5.0e9, "relay_power": 0.0},
  "connected": true, "connected_home": true,
  "control_state": "Full", "signal_strength": 0.82, "signal": "Green", "signal_delay": 0.0,
  "path": [{
    "from": {"name": "Relay-1", "vessel_id": 123, "home": false},
    "to": {"name": "Kerbin: KSC", "vessel_id": null, "home": true},
    "distance": 2.9e6, "max_range": 1.0e10, "signal_strength": 0.95, "from_antenna": "transmit", "to_antenna": "relay"
  }]
}
```

- `enabled: false`이거나 기체에 `CommNetVessel` 또는 그 `CommNode`(`Comm`)가 없으면 `antenna`만 채우고(`CommNode`가 없으면 null) `connected`·`connected_home`·`control_state`·`signal_*`·`path`는 null이다. 연결 정보를 읽을 원본이 없기 때문이다(`CommNode`가 없는 경우는 완료 전 검토 R1-3-B-2로 추가).
- 노드 `name`은 `Localizer.Format(displayName)`이다. 지상국 `displayName`은 `#autoLOC_...` 키라서 현지화한다(실측 중 추가, 예: `커빈: 우주 센터`).
- `path`는 `ControlPath`의 링크 순서(활성 기체 → 제어원)다. 각 구간 `from = link.a`, `to = link.b`. 노드가 기체면 `vessel_id`(persistentId), 아니면 null. 마지막 `to`는 home이 아닐 수 있다(유인 제어원 기체로 연결된 경우).
- `signal_strength`: 경로 링크의 `signalStrength`(게임이 그 구간에 쓴 값).
- `max_range`·`from_antenna`·`to_antenna`: 원본 링크 `o = from[to]`에서 `strengthRR`·`strengthAR`·`strengthBR` 가운데 경로 링크 `signalStrength`와 같은 조합을 고른다(같은 값이 여럿이면 RR, AR, BR 순). 조합의 power 쌍(RR: `o.a.relay`×`o.b.relay`, AR: `o.a.relay`×`o.b.transmit`, BR: `o.b.relay`×`o.a.transmit`)으로 `GetMaximumRange`를 계산하고, 그 조합에서 `from`·`to`가 쓴 안테나를 `"relay"`·`"transmit"`으로 적는다. `o`가 없거나 맞는 조합이 없으면 세 값은 null이다.
- `distance`는 양끝 `precisePosition` 사이 거리다.
- 연결이 없으면 `path`는 빈 배열이다.

## 구조

### `PartStates` (신규, `src/KspBridge.Logic/Flight/PartStates.cs`)

메인 스레드 전용 정적 클래스.

- `List(Vessel v, string partId, string module)`: `get_vessel_parts`
- `Invoke(Vessel v, RequestBody b)`: `invoke_part_event`
- `internal static bool Listed(BaseEvent e)`, `internal static string Unavailable(BaseEvent e, Part p)`: PAW 표시 규칙. 조회와 실행이 같이 쓴다.
- `internal static Dictionary<string, object> DescribeModule(...)`: 조회와 실행 응답 `module_state`가 같이 쓴다.

### `CommNetState` (신규, `src/KspBridge.Logic/Flight/CommNetState.cs`)

- `Describe(Vessel v)`: `get_commnet`

### 라우트 (`FlightHandler.Routes`)

```csharp
yield return new Route("GET", "/api/flight/parts", (m, b, q) => PartStates.List(Guard.ActiveVessel(), Empty(q["part_id"]), Empty(q["module"])));
yield return new Route("POST", "/api/flight/part_event", (m, b, q) => PartStates.Invoke(Guard.ActiveVessel(), b));
yield return new Route("GET", "/api/flight/commnet", (m, b, q) => CommNetState.Describe(Guard.ActiveVessel()));
```

### App 도구 (`src/KspBridge.App.Tools/FlightTools.cs`)

- `get_vessel_parts`(ReadOnly), `invoke_part_event`(Destructive), `get_commnet`(ReadOnly). 설명에 응답 형식, 오류 코드, 대칭 동작(모듈 event는 대칭 부품에 전파되지 않을 수 있음), 계획 실행 중 기체가 나뉘면 계획이 중단될 수 있음을 적는다.
- `get_flight_events` 설명에 `part_event`와 data 형식을 추가한다.

### 실행 기록 (방안 결정 10)

- `invoke_part_event` 실행 단계마다(성공·`event_failed`) `FlightEvents.Add("part_event", Coordinator.Running ? Coordinator.StepIndex : -1, {part_id, part, module, index, event, counterparts, vessel_changed, separated, error})`. 사전 검사 실패(4xx)는 남기지 않는다.
- 같은 내용을 `Debug.Log("[KspBridge] part_event ...")`로 KSP.log에 남긴다.

### 이슈 완료 조건과 단계 대응

| 완료 조건 | 단계 |
|---|---|
| 방안·설계·개발 문서 합의 및 독립 검토 | 단계마다 |
| HG-5 펼침과 상태 조회 반영 | 1단계 |
| CommNet 펼침 전후 비교 | 1단계 |
| Clamp-O-Tron Jr. Undock | 1단계 |
| 부속 제어 실행·상태 반영 | 2단계(1단계 범용 event로 실행 자체는 가능하지만, 상위 도구 대상과 함께 2단계에서 실측) |
| 연료 전달 | 3단계 |
| App 테스트 | 단계마다 |

- 1단계 Undock 실측에는 비행 중에 도킹한 기체(기존 비행 계획 dock 단계로 도킹했거나 도킹된 채 저장된 기체)를 쓴다. editor에서 결합한 포트는 `Undock` 대신 `Decouple Node`가 나오므로 이 실측에 쓰지 않는다. 그런 기체가 없으면 실측 전에 사용자와 준비 방법을 정한다.
- 탱크 흐름 잠금(flow enable)은 KSPEvent도 PAW field도 아닌 자원 행 토글이므로 2단계 설계에서 상위 도구 대상으로 따로 다룬다.
