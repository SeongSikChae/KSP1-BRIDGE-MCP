# KspBridge 비행 안전 하네스 설계 — 묶음 A (분리 부품·기체 분석)

선행: [0035-비행안전하네스-방안.md](0035-비행안전하네스-방안.md)

이 문서는 방안 2번(스테이지별 분리 부품)과 1번(기체 분석)만 다룹니다. 3~8번은 다음 묶음 설계 문서에서 다룹니다.

## 구조
새 도구 없이 기존 도구 세 개의 응답을 늘립니다.

### 입력 정규화
설계 시와 비행 중 계산을 한 번만 쓰려고, `CraftAnalysis`는 아래 형태로 받습니다.

```
AnalysisPart { Part prefabOrLive; Vector3 pos; Quaternion rot; double mass; AnalysisPart parent; List<AnalysisPart> children; int istg; bool surface; }
```

- 설계 시: `BuiltPart`의 `Prefab`, `Pos`, `Rot`, `CraftEstimator.Mass` 계산값
- 비행 중: `Part`, 루트 부품 기준 좌표(`vessel.rootPart.transform`의 역변환), `part.mass + part.GetResourceMass()`
- 축: 기체 위쪽 = 루트 기준 `Vector3.up` (VAB에서 세운 방향)

## 인터페이스

### 단별 필드 (`build_craft` dry run의 `stages[]`, `get_stages`의 `staging[]`)
- `get_stages`의 기존 `stages`는 `VesselDeltaV.OperatingStageInfo`를 돌아 Δv가 있는 단만 담습니다. 분리만 하는 단(서비스 모듈·부스터 분리)이 빠지므로, 현재 단 − 1부터 0단까지 **모든 단**을 담는 최상위 `staging` 배열을 따로 둡니다. 기존 `stages` 행은 바꾸지 않습니다(검토 회귀, 2026-11-08).
- `build_craft`의 `stages`는 원래 엔진 없는 단도 행을 만들므로 그 행에 넣습니다.

```json
{
  "stage": 2,
  "drops": ["TD-12 Decoupler", "RT-10 \"Hammer\"", "Heat Shield (1.25m)"],
  "control": {
    "gimbal_engines": 0, "gimbal_range_deg": 0.0,
    "reaction_wheel_torque": 5.0,
    "control_surfaces": 0, "rcs_thrusters": 0,
    "steerable": true
  }
}
```
- `drops`: 이 단이 발동될 때 기체에서 떨어지는 모든 부품(분리기 자신 포함). 비면 `[]`.
- `control`: 이 단이 발동된 **뒤** 남은 기체가 이 단의 엔진으로 날 때의 조향 수단.
  - `gimbal_*`: 점화 중인 엔진 가운데 `ModuleGimbal`이 있는 수와 최대 `gimbalRange`
  - `reaction_wheel_torque`: 남은 부품의 `ModuleReactionWheel` 피치 토크 합(kN·m)
  - `control_surfaces`: `ModuleControlSurface` 수
  - `rcs_thrusters`: `ModuleRCS`/`ModuleRCSFX` 수
  - `steerable`: 넷 중 하나라도 있으면 true

### 기체 분석 (`build_craft` dry run의 `analysis`, `get_stages`의 `analysis`)
```json
{
  "com": [0.0, 4.12, 0.0],
  "col": [0.0, 2.80, 0.0],
  "col_minus_com": -1.32,
  "stable": true,
  "lowest_part": "Basic Fin",
  "lowest_y": -0.62,
  "lowest_engine_y": -0.45
}
```
- 좌표는 루트 기준(m). `col_minus_com`은 위쪽 축 성분 차이(음수면 양력중심이 뒤 → 안정).
- 양력 부품이 없으면 `col`, `col_minus_com`, `stable`은 `null`.
- `get_stages`의 `analysis`는 **현재 기체 전체** 기준입니다(발사대에서 쓰는 용도).

### 경고 (기존 `warnings` 문자열 배열에 추가, 저장은 막지 않음)
| 조건 | 문구 예 |
|---|---|
| 엔진이 있는 단인데 `steerable` false | `stage 3: no steering (no gimbal, reaction wheel, control surface or RCS)` |
| `drops`에 보호 부품(`ModuleAblator`, `ModuleParachute`, `ModuleCommand`) | `stage 2 drops protected part: Heat Shield (1.25m)` |
| `col_minus_com` > 0 | `center of lift is 0.35 m ahead of center of mass (unstable in atmosphere)` |
| 가장 낮은 엔진 하단보다 0.05 m 넘게 아래로 나온 비엔진 부품 | `Basic Fin sits 0.17 m below the lowest engine (may hit the pad)` |

`get_stages`는 지금까지 `warnings`가 없었으므로 새 필드로 추가합니다.

## 처리

### 분리 부품 계산
- **설계 시**: 기존 `Stages`의 분리 규칙과 같게 합니다. 단 `s`에서 `Istg == s`인 분리기의 `Subtree()` 합집합 중 아직 붙어 있던 부품.
- **비행 중**: 단 `s`에서 `inverseStage == s`인 분리기마다 끊길 연결을 정하고, 루트 부품과 이어지지 않게 되는 쪽 전체를 모읍니다.
  - `ModuleDecouple`(스택): `explosiveNodeID`의 부착 노드에 붙은 부품과의 연결을 끊습니다. `isOmniDecoupler`면 모든 연결을 끊습니다.
  - `ModuleAnchoredDecoupler`(방사형): 부모와의 연결을 끊습니다.
  - 이전 단에서 이미 떨어진 부품은 제외합니다(높은 단부터 차례로 누적).
- 두 계산 모두 엔진 단 순서는 `inverseStage`/`Istg` 내림차순입니다.

### 조향 능력
- 단 `s` 발동 뒤 남은 부품 집합에서 계산합니다. 점화 엔진 집합은 기존 `Stages`의 `ignited ∩ attached` 규칙을 씁니다(비행 중은 `inverseStage >= s`이고 남은 엔진).

### 무게중심
- `Σ(pos × mass) / Σ mass`. 설계 시 질량은 연료 포함 `CraftEstimator.Mass` 규칙.

### 양력중심 (게임 공력 계산 호출)
- VAB `EditorMarker_CoL`과 같은 방식: 부품의 `ILiftProvider` 모듈마다 `OnCenterOfLiftQuery(CenterOfLiftQuery q)`를 호출하고 `Σ(q.pos × q.lift) / Σ q.lift`.
- 질의 조건: `refVector` = 기체 위쪽 방향(정면 비행), `refAltitude` 0, `refStaticPressure`·`refAirDensity`는 Kerbin 해면값, 속도 기준은 VAB 마커와 같게 합니다.
- **설계 시**: 실제 Part 인스턴스가 없으므로 프리팹에 질의한 뒤 결과 `pos`를 프리팹 원점 기준으로 바꾸고 `rot`, `pos`로 옮깁니다. 프리팹 모듈이 질의에 응답하지 않으면(결과 lift 0) 그 부품은 빼고, 모두 빠지면 `null`.
- **비행 중**: 실제 Part에 질의하고 결과를 루트 기준으로 바꿉니다.

### 접지점
- 부품마다 콜라이더 경계(`Collider.bounds`가 아닌 로컬 `BoxCollider`/`MeshCollider.sharedMesh.bounds`의 8개 꼭짓점)를 `rot`, `pos`로 옮겨 위쪽 축 최솟값을 구합니다.
- 1단(가장 먼저 점화되는) 엔진의 최솟값과 비엔진 부품 최솟값을 비교합니다. 발사 클램프(`LaunchClamp`)는 제외합니다.

## 결정 (2026-11-08 사용자)
- 범위: 묶음 A(방안 2·1번)부터 설계합니다
- 무게중심·양력중심·접지점: `build_craft`와 `get_stages` 모두에 넣습니다
- 양력중심: 게임 공력 계산(`ILiftProvider.OnCenterOfLiftQuery`)을 호출합니다
- 경고만 하고 저장·발사는 막지 않습니다
- (검토 회귀) `get_stages`는 기존 `stages`를 두고 모든 단을 담는 `staging` 배열을 따로 추가합니다
- (검토 회귀) 단별 경고는 단을 도는 자리에서 `warnings` 목록에 바로 더합니다
- (구현 회귀) 설계 시 분리 부품과 Δv 추정 질량도 폭발 노드 기준으로 계산합니다. 접지점은 메시 경계로 계산합니다
- `list_parts`의 부품 상세에도 부품 하나의 `control`(짐벌 범위, 토크, 조종면, RCS)을 넣습니다

## 검증 계획
- `dotnet build`(솔루션), `dotnet test`
- 인게임(`reload_mod`):
  1. 열차폐 사고 기체를 `build_craft` dry run → 해당 단 `drops`에 열차폐가 있고 보호 부품 경고가 나오는지
  2. 같은 기체를 발사대에 올려 `get_stages` → `drops`가 dry run과 같은지
  3. 짐벌 없는 1단 기체 → `steerable: false`와 경고
  4. 꼬리 날개 높이 오류 기체 → 접지점 경고
  5. 무게중심·양력중심을 VAB 마커 화면과 비교(위쪽 축 차이 0.1 m 이내)

## 위험
- 프리팹의 `OnCenterOfLiftQuery`가 초기화 전이라 값을 못 줄 수 있습니다. 이 경우 설계 시 양력중심은 `null`로 두고 비행 중 값만 씁니다(설계 시 실측 후 결정).
- 콜라이더가 없는 부품은 접지점에서 빠집니다.
