# 비행안정 설계 — 3단계-1: 자세 제어기 진단 도구

방안: [0052-비행안정-방안.md](0052-비행안정-방안.md) 결정 1(측정 먼저, MCP 진단 도구)·결정 3의 1번. 이 설계는 측정 도구만 다룬다. 보정은 실측 뒤 별도 설계.

## 범위

- 자세 제어기(`AttitudeController.Steer`)가 실제로 계산·출력한 값을 틱마다 기록하고, 새 읽기 전용 MCP 도구로 축별 요약과 솎은 시계열을 돌려준다.
- 제어기 출력은 바꾸지 않는다(관찰만). 가용 토크 합산을 종류별로 나눠 기록하지만 합계는 지금과 같다.
- 비범위: 제어기 보정, 감시기(2단계) 변경, Player.log 기록.

## 결정

### 1. 도구 형태 (사용자 합의)

- 상시 읽기 도구 `get_controller_trace`(MCP, `ReadOnly = true`). `debug.cfg`와 무관하게 동작한다.
- HTTP: `GET /api/flight/controller_trace?seconds=<1..20>&step=<1..50>`. App 도구 인자 `seconds`(기본 10), `step`(생략 시 시계열 없음).
- 비행 장면이 아니면 기존 조회 도구처럼 `not_in_flight`. 표본이 없으면 `{samples: 0}`.

### 2. 기록 (`Flight/Control/ControllerTrace.cs`, 새 정적 클래스)

- `Steer`가 입력을 정한 직후 한 번 `ControllerTrace.Record(...)`를 부른다. 자세 제어가 실제로 도는 틱만 기록한다(계획 없음·자세 목표 없음·`Suspended`면 기록 없음).
- 표본(축 3개: pitch·roll·yaw, `Steer`의 축 순서 x·y·z):
  - `ut`, 축별 `err`(rad), `omega`(rad/s), `want`(rad/s), `input`(±1, 부호는 `Steer` 그대로), `alpha`(모델, rad/s²)
  - 축별 가용 토크 종류별 합: `wheel`(`ModuleReactionWheel`), `gimbal`(`ModuleGimbal`), `surface`(`ModuleControlSurface` 계열), `rcs`(`ModuleRCS` 계열), `other`
  - `moi`(축별), `throttle`(`ModeCommand.Throttle`), `q`(`dynamicPressurekPa`)
- 링 버퍼 1000표본(물리 틱 약 50 Hz × 20 s). 오래된 표본부터 덮어쓴다. 리로드 뒤에는 비어 있다(인계 없음).
- 버퍼는 기록한 기체의 `persistentId`를 함께 가진다. 다음 때 비운다.
  - 새 계획 시작(`FlightMonitor.Reset`과 같은 자리).
  - 장면 로드 요청(`FlightScene`의 `onGameSceneLoadRequested`). 우주센터 왕복과 revert가 여기에 든다.
  - `Record`에 들어온 기체가 버퍼의 기체와 다를 때.
- 요청 때 활성 기체가 버퍼의 기체와 다르면 `{samples: 0}`을 돌려준다(다른 기체의 표본을 요약하지 않음). 같은 기체면 계획이 끝난 뒤에도 남아 원인 조사에 쓴다.
- `AvailableTorque`는 제공자 배열을 다시 만드는 같은 블록에서 종류 배열도 다시 만든다(단 분리 때 길이 불일치 방지). 종류별 합을 낸 뒤 그 합계를 지금처럼 `alpha`에 쓴다(값 동일).
- 기록은 관찰만 한다. `Record` 호출을 따로 try/catch로 감싸, 기록 실패가 `Fly`의 catch(계획 중단 `error`)로 가지 않게 한다. 실패는 한 번만 로그에 남긴다.

### 3. 요약 (요청 때 계산)

`seconds` 창 안의 표본으로 축마다 낸다. 연속 표본 간격이 물리 틱의 1.5배를 넘으면 끊긴 구간으로 보고 차분·상관에서 그 쌍을 뺀다.

| 필드 | 뜻 | 가릴 원인 후보(0052) |
|---|---|---|
| `err_rms_deg`, `err_max_deg` | 오차 크기 | — |
| `osc_hz`, `osc_amp_deg`, `osc_peak_ratio`, `err_offset_deg` | 스펙트럼으로 잰다. `\|want\| ≥ OmegaMax`인 표본(큰 선회 중)과 끊긴 쌍(간격이 물리 틱의 1.5배 초과)에서 표본열을 나누고, 그 가운데 가장 긴 연속 구간 하나만 쓴다(빠진 구간을 이어 붙이지 않음). 그 구간의 오차에서 최소제곱 직선을 뺀 뒤, 구간의 실제 길이(`t_last − t_first`)를 분모로 Hann 창을 씌운다. 표본 시각 그대로 0.2~5 Hz를 0.05 Hz 간격으로 이산 푸리에 변환해 가장 큰 봉우리의 주파수를 `osc_hz`, 그 진폭(`2·\|X\|/Σw`, 창 보정)을 `osc_amp_deg`로 낸다. `osc_peak_ratio`는 봉우리 크기 / 전 주파수 크기의 중앙값이다(진동 판정 문턱은 정하지 않는다). 0을 지나지 않는 치우친 진동, 느린 목표 이동(직선 제거와 0.2 Hz 하한), 롤 목표 없는 롤 축(`want` 0, 포화 없음)에도 같은 정의가 통한다. `err_offset_deg`는 쓴 구간의 오차 평균(진동 중심). 쓴 구간이 5 s 미만(0.2 Hz 한 주기)이거나 오차에 NaN이 있으면 네 값 모두 null. 봉우리 크기가 0(오차가 평탄, 예: 롤 목표 없는 롤 축은 오차가 늘 0)이면 `osc_hz`·`osc_peak_ratio` null, `osc_amp_deg` 0, `err_offset_deg`는 값을 낸다 | 1 |

진동 요약의 한계(실측으로 보정, 3단계-1 단위 4와 원인 판정 실측):

- 자세 오차는 저주파로 치우친 신호라, 진동이 없어도 `osc_peak_ratio`가 클 수 있다. 진동 여부의 문턱은 실측 `series`와 대조해 정한다.
- 포화가 풀린 뒤의 감속 과도(최대 약 `(OmegaMax/KStop)²/(2·alpha)` rad)가 구간에 남으면 0.2~0.5 Hz 봉우리로 보일 수 있다.
- 진폭이 커서 봉우리마다 `want`가 포화하면 구간이 짧게 끊겨 값이 null이 되거나 진폭이 작게 나올 수 있다. 이때는 `input_sat_ratio`가 높다.
- 0.2 Hz 하한과 5 s 최소 길이 때문에 주기 5 s 이상의 진동은 보이지 않고, 0.2~0.6 Hz의 주파수 분해가 거칠다.
- 요약 값이 의심스러우면 `series`(원시 오차·각속도·목표 각속도·입력)로 판정한다.
| `input_sat_ratio` | `|input| ≥ 0.99` 표본 비율 | 1·2 |
| `alpha_model` | 기록된 `alpha` 평균(참고값) | 2 |
| `alpha_gain`, `alpha_r2`, `accel_bias` | 각가속도 `Δomega/Δt`를 `k`틱 앞 표본의 예측 가속 `−input·alpha`(틱마다의 `alpha`)에 절편을 넣어 최소제곱 회귀한 기울기·결정계수·절편(rad/s²). 기울기 1이면 모델과 실제가 같고, 1보다 작으면 모델이 토크를 과대평가한다. 절편은 창 안의 평균 교란 가속(공력·추력 중심 어긋남)이라, 제어기가 일정한 교란을 상쇄하려고 입력을 유지해도 기울기가 끌려가지 않는다. `k`는 아래 `lag_ticks`의 것 | 2 |
| `lag_ticks`, `lag_r2` | 위 회귀를 `k` = 1~10마다 같은 쌍 집합(`i−10..i`가 모두 연속인 `i`)으로 해서 결정계수가 가장 큰 `k`를 고르고 `k − 1`을 낸다(`Δomega[i]`의 원인은 `input[i−1]`이므로 0이 지연 없음). `lag_r2`는 `k` = 1~10의 결정계수 10개 배열(곡선이 평평하면 지연을 가려낼 수 없다는 뜻) | 3 |
| `want_slope_at_amp` | 진동 동작점 `e = max(|err_offset|, amp)`에서 `want` 곡선의 해석 기울기 `KStop·sqrt(alpha_model / (2·e))`(1/s). 그 동작점에서 `want`가 `OmegaMax`에 걸리면 0. `osc_amp_deg`가 null이면 null | 1 |
| `torque` | 종류별 가용 토크 평균 | 2 |

- 다음이면 `alpha_gain`·`alpha_r2`·`accel_bias`·`lag_ticks`·`lag_r2`는 null:
  - 회귀에 쓰는 쌍이 10개 미만.
  - 예측 가속의 분산이 0에 가깝다(표준편차가 평균 크기의 1% 미만).
  - 회귀 쌍의 포화 비율(`|input| ≥ 0.99`)이 0.9 이상이고 입력 부호가 한 번도 바뀌지 않는다(한쪽 포화에서는 `x`의 변동이 `alpha` 변화뿐이라 동압을 따라 변하는 교란과 섞임). 포화하지 않고 치우친 입력으로 진동하는 정상 추종은 값을 낸다(절편이 일정한 교란을 흡수).
- 포화 표본도 회귀에 넣는다. 포화 중에도 입력 부호와 `alpha`는 변하므로 예측 가속의 분산이 남는다.

공통: `window_s`, `samples`, `tick_s`(연속 표본 간격의 중앙값), `throttle_mean`, `q_mean`.

### 4. 시계열 (`step` 지정 때)

- `series`: `step` 틱마다 하나, `{t(창 시작 기준 s), throttle, q, pitch/roll/yaw: {err_deg, omega, want, input}}`. 20 s·`step` 1이면 약 1000개라 응답이 크므로 도구 설명에 권장값(`step` 5, 10 Hz)을 적는다.

### 5. MCP·문서 영향

- `FlightTools`에 `get_controller_trace` 추가(설명: 기록 조건, 인자, 필드 뜻, 크기 주의). 기존 도구 이름·인자는 바뀌지 않는다.
- ReadMe 도구 목록·비행 계획 절에 한 줄.
- `Routes.Version` 올림.

## 검증

- Logic·App.Tools 빌드, `dotnet test tests/KspBridge.App.Tests` 통과.
- 실측(MCP 응답으로만):
  1. 리로드 직후 계획 시작 전 → `{samples: 0}`, 비행 장면 밖 → `not_in_flight`. 계획 뒤 다른 기체로 전환 → `{samples: 0}`.
  2. StabT 궤도에서 `attitude` 단계 → 요약 값이 나오고 `alpha_gain`이 1과 같은 차수(0.3~3), `torque.wheel` > 0, `gimbal`은 추력 0일 때 0 근처.
  3. `step` 5 시계열이 10 Hz로 나오고 `seconds`·`step` 범위 밖은 400, `seconds` 소수(예: 10.5)는 허용.
  4. 제어 출력 불변: diff에서 `Steer`의 계산식과 `s.pitch/roll/yaw` 대입이 바뀌지 않았고, `AvailableTorque`의 `sum` 누적은 지금 식 `(Abs(pos) + Abs(neg)) * 0.5f`를 지역 변수 `t`로 옮긴 것 말고는 같고, 종류별 합은 같은 `t`를 따로 더하기만 한다(반환값 `sum`의 계산 경로 불변). 보조로 같은 계획의 `plan.monitor`(오차·부호 전환)가 같은 수준.
