# KspBridge 승무원·SAS 상태 감시 — 설계

선행: `0022-승무원SAS감시-방안.md`

## 구성 (로직 DLL만, `reload_mod`)
- 새 `Flight/SasMonitor.cs`: 요청 모드 보관·매 물리 틱 감시·자동 유지·이벤트 기록. `BridgeLogic.FixedUpdate`에서 호출, `Stop`에서 Clear, 기체·장면 바뀌면 해제(트리거와 같은 규칙)
- `VesselHandler`: 응답에 `g_force`, `crew`, `sas` 블록 추가(기존 `control.sas`, `control.sas_mode`는 유지)
- `FlightFields`: `g_force`, `g_load_max`
- `ControlHandler`: set_sas_mode → SasMonitor에 요청 등록(hold), set_sas(false) → 해제. `AttitudeController`가 SAS를 직접 바꿀 때(set_attitude own/sas)도 해제

## 응답 (GET /api/vessel 추가분)
```json
"g_force": 5.7,
"crew": [{"name": "발렌티나 커맨", "trait": "Pilot", "level": 1, "conscious": true,
          "inactive_for": null, "g_load": 0.42, "out_due_to_g": false}],
"sas": {"on": true, "requested": "retrograde", "actual": "retrograde", "hold": true,
        "autopilot_enabled": true, "steering": true,
        "available_modes": ["stability_assist", "prograde", "retrograde"],
        "events": [{"ut": 20101.4, "met": 246.4, "event": "mode_lost", "from": "retrograde", "to": "stability_assist",
                    "reason": "vessel_modified", "detail": "staged 0.04 s before"},
                   {"ut": 20101.5, "met": 246.5, "event": "reapplied", "mode": "retrograde"}]}
```
- `g_force` = `vessel.geeForce`. 승무원 = `vessel.GetVesselCrew()`: `conscious` = `!inactive`, `inactive_for` = `inactiveTimeEnd − now`(기절 중만), `g_load` = `GExperiencedNormalized`(1 이상이면 기절), `out_due_to_g`
- `steering` = SAS가 실제로 조종 신호를 넣는지(`VesselSAS.FBWconnected`, 비공개 → 리플렉션, 못 읽으면 null)
- `available_modes` = 모든 모드 중 `CanSetMode` 참
- `events`: 최근 10개, 새 기체·장면이면 비움

## 감시·자동 유지 (SasMonitor.FixedUpdate)
- 요청 상태: `requested`(모드), 기체 id, `hold`(기본 true). set_sas_mode 성공 시 등록
- 매 틱 관찰: SAS 그룹, `Autopilot.Mode`, `Autopilot.Enabled`, steering
- **이상 판정**: 요청이 있고 (SAS OFF | 모드 ≠ 요청 | steering false) → 처음 그렇게 된 틱에 이벤트 `mode_lost` 또는 `steering_lost`
  - 사유 추정 순서: 직전 0.5초 안에 `onVesselWasModified`(분리 등) → `vessel_modified` / 조종사 전원 의식 없음 → `crew_unconscious` / `CanSetMode(요청)` 거짓 → `mode_unavailable` / 그 밖 → `unknown`
- **자동 유지(hold)**: 이상 상태이고 `CanSetMode(요청)`이면 SAS ON + `SetMode(요청)`(steering만 끊겼으면 같은 모드로 SetMode 재호출) → 이벤트 `reapplied`. 재시도는 0.5초에 한 번
  - 다시 걸 수 없으면 기다렸다가 가능해지는 틱에 다시 건다(기절 후 회복)
- **해제**: set_sas(false), 다른 set_sas_mode(새 요청으로 교체), set_attitude(own은 SAS를 끄고 sas는 SAS를 직접 씀), 기체·장면 변경, reload. 게임 화면에서 사람이 모드를 바꾸면 요청과 다르므로 되돌린다(문서화 — 사람이 조종할 때는 set_sas false로 해제)

## 조건 필드 (트리거·wait_until)
- `g_force`(숫자), `g_load_max`(승무원 중 최대 `g_load`, 승무원 없으면 null)

## MCP (App)
- 새 도구 없음. 설명 갱신: `get_vessel_state`(g_force·crew·sas), `set_sas_mode`(요청 모드를 모드가 유지, 해제 방법), 필드 목록(`TriggerTools.Fields`)에 `g_force`, `g_load_max`

## 구현 중 변경 (2026-11-08)
- set_sas_mode는 자세 유지(set_attitude)를 먼저 해제 — sas 방식 자세 유지가 매 틱 stability_assist를 걸어 모드 유지와 서로 뒤집는 것을 막음
- 첫 reload 실패(NullReferenceException, 이전 로직 유지): KSP `EventData.Add`가 델리게이트 `Target`을 읽는데 정적 메서드 그룹을 넘김 → 람다로 감쌈(0.8.0, load 15)
- 독립 검토 반영(0.8.1)
  - [Medium, 원래 버그의 유력 원인] SAS가 꺼진 상태에서 set_sas_mode → SAS ON + SetMode는 모드만 저장, 다음 프레임 `VesselAutopilot.Update`의 `Enable()`(= Enable(StabilityAssist))이 덮어씀. 지난 재진입은 own 자세 제어가 SAS를 꺼 둔 뒤 release_attitude → set_sas_mode 순서였음 → `SasMonitor.Apply`: 자동조종이 꺼져 있으면 `Enable(mode)`, 켜져 있으면 `SetMode(mode)`. set_sas_mode와 자동 재적용이 함께 사용
  - 재적용: 기체가 조종 불가(승무원 기절 등)·packed면 기다림(스톡과 같음), `reapplied`는 실제로 그 모드로 켜졌을 때만 기록
  - 이상 판정 3틱 유예(분리 직후 non-locked 모드가 다음 렌더 Update에서 다시 연결되기 전 가짜 steering_lost 방지)
  - 알려진 동작(수정 안 함): 사람이 T 키·UI로 바꾼 모드도 되돌림(set_sas false로 해제), 저속에서 retrograde가 속도 벡터 무효로 풀리면 이벤트 쌍 반복 가능

## 게임 결과 (2026-11-08, KB Hopper 2S, 발렌티나 Lv1)
- 발사대: crew(level·conscious·g_load)·sas·g_force 응답 확인. Lv0 조종사는 available_modes가 stability_assist뿐 → 검증은 Lv1 조종사로
- 원래 버그 조건(own 자세 제어로 SAS OFF → release_attitude → set_sas_mode prograde, 1.5 km 상승 중): actual prograde, steering true, events 없음 — stability_assist로 덮이지 않음
- Hammer 분리(activate_next_stage) 직후: prograde 유지, steering true, events 없음(3틱 유예로 가짜 이벤트 없음)
- SAS ON 상태 retrograde 전환: 실제 자세 pitch 66.9°·heading 270°, 속도 벡터 역방향 계산(약 66°, 서쪽)과 일치
- g_force 조회값 정상(상승 2.67). 미확인: g_force 조건 트리거, mode_lost 사유·reapplied 경로(모드가 한 번도 풀리지 않음)
- 비행 자체는 착지 감속 부족(burn_margin 60 m 시작, 해상 착수 66 m/s)으로 실패 → revert_to_launch. SAS 모니터와 무관
- 재비행(수직 도약): g_force 조건 트리거 확인(MET 0.36 s, 값 2.01 → light on). 정점에서 수평 속도 약 20 m/s가 남아 retrograde가 풀리지 않음(스톡 조건: 지면 기준 속도 1 m/s 미만) → mode_lost·reapplied 여전히 미확인. 엔진 착지 중 retrograde가 수평 흐름 쪽으로 기울어 다리 없는 기체가 넘어짐 → revert_to_launch. 착지는 낙하산으로 해야 함(사용자 지적)
- 0025 비행 기록 확인 비행(2026-11-08)에서 mode_lost(mode_unavailable)와 reapplied 경로가 실제로 기록됐습니다. 그런데 착지 후 다시 걸린 retrograde가 넘어지는 기체의 속도 방향을 따라 조향해, 기울기가 7°에서 73°로 커지고 연료통이 부서졌습니다.
- 수정(0.9.2, 사용자 "지금 고치기"): 착지·착수(`v.Landed || v.Splashed`) 상태에서 요청 모드가 prograde/retrograde이면 유지를 해제하고 `released` 이벤트(mode, reason landed/splashed)를 남깁니다. 스톡 SAS 모드 자체는 바꾸지 않습니다. MCP `set_sas_mode` 설명에는 아직 반영하지 않았습니다(App 변경 없음).
- 완료 처리(사용자 결정): mode_lost 사유·reapplied 경로는 미확인으로 남김. 확인 방법: 낙하산 착지 후 정지(지면 속도 1 m/s 미만) 순간 retrograde 해제 이벤트 확인
