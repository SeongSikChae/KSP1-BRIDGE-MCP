# 디버그도구 개발

방안 [0018](0018-디버그도구-방안.md), 설계 [0019](0019-디버그도구-설계.md).

## 공통

- 단위마다 구현 → 검증 → 커밋 확인. 단위 커밋마다 Logic `Routes.Version`을 하나 올린다(0.2.26부터).
- App 도구를 추가하는 단위는 `tests/KspBridge.App.Tests/ExpectedTools.cs`의 도구 목록을 함께 고치고, 배포는 `reload_app`(App.Tools)·`reload_mod`(Logic)로 한다. 새 도구가 목록에 안 보이면 클라이언트를 재시작한다(0006 공통 규칙). 로더는 바꾸지 않는다.
- 모든 디버그 라우트는 `POST /api/debug/<이름>`이고 메인 스레드에서 실행한다(`onHttpThread` false). 플래그가 꺼져 있으면 409 `debug_disabled`.
- 상태 응답의 중첩 값은 `Dictionary<string, object>`로 만든다(로더 Json은 익명 객체를 `ToString()` 문자열로 쓴다).
- ReadMe에 "디버그 도구" 절을 두고 단위마다 해당 도구 행을 추가한다.
- 검증은 MCP 응답·KSP.log로만 한다. 플래그 파일 `GameData/KspBridge/debug.cfg`는 사용자 확인 뒤 KSP 폴더에 만든다(빌드가 배포·덮어쓰지 않음, 저장소에 두지 않음).

```csharp
// Debugging/DebugState.cs
public static class DebugState
{
    public const string LockId = "kspbridge_debug";
    public static volatile bool Enabled;   // GameData/KspBridge/debug.cfg KSPBRIDGE_DEBUG { enabled = true }

    public static void LoadFlag()
    {
        Enabled = false;
        try
        {
            string path = KSPUtil.ApplicationRootPath + "GameData/KspBridge/debug.cfg";
            ConfigNode n = File.Exists(path) ? ConfigNode.Load(path)?.GetNode("KSPBRIDGE_DEBUG") : null;
            Enabled = n != null && bool.TryParse(n.GetValue("enabled"), out bool on) && on;
        }
        catch (Exception e) { UnityEngine.Debug.LogWarning("[KspBridge] debug.cfg not read: " + e.Message); }
        if (Enabled) UnityEngine.Debug.Log("[KspBridge] debug tools enabled");
    }

    public static void Require()
    {
        if (!Enabled) throw new ApiException(409, "debug_disabled", "create GameData/KspBridge/debug.cfg with KSPBRIDGE_DEBUG { enabled = true } and reload_mod");
    }

    // KSP's EvtDelegate reads evt.Target.GetType(), which throws for static methods: an instance handler like FlightScene.
    private sealed class SceneHook { public void OnScene(GameScenes s) => Clear(); }
    private static SceneHook _hooked;

    /// <summary>Only when enabled: with the flag off the start path is unchanged.</summary>
    public static void Hook()
    {
        if (!Enabled || _hooked != null) return;
        _hooked = new SceneHook();
        GameEvents.onGameSceneLoadRequested.Add(_hooked.OnScene);
    }
    public static void Unhook()
    {
        if (_hooked != null) { GameEvents.onGameSceneLoadRequested.Remove(_hooked.OnScene); _hooked = null; }
        Clear();
    }

    /// <summary>Releases every debug state, the reload faults included (later units add their fields here).</summary>
    public static void Clear() { /* ... unit 2..6 fields ... */ }

    public static Dictionary<string, object> Status() => !Enabled ? null : new Dictionary<string, object>
    {
        // ... unit 2..6 fields ...
    };
}

// Handlers/DebugHandler.cs
public static IEnumerable<Route> Routes()
{
    yield return Post("clear", b => { DebugState.Clear(); return DebugState.Status(); });
    // ... unit 2..6 ...
}
private static Route Post(string name, Func<RequestBody, object> f)
    => new Route("POST", "/api/debug/" + name, (m, b, q) => { DebugState.Require(); return f(b); });

// Routes.Build
routes.AddRange(DebugHandler.Routes());

// BridgeLogic.StartCore: after Settings.Reload()
DebugState.LoadFlag();
// ... in the hook try: FlightScene.Hook(); FlightReset.Hook(); DebugState.Hook();  (the catch also calls DebugState.Unhook())

// BridgeLogic.Stop: after Coordinator.Stop (unit 6 makes the reload faults independent of this order anyway)
try { DebugState.Unhook(); } catch (Exception e) { UnityEngine.Debug.LogError("[KspBridge] debug unhook failed: " + e); }

// BridgeLogic.Status: before return
try { status["debug"] = DebugState.Status(); }
catch (Exception e) { status["debug"] = null; status["debug_error"] = e.GetType().Name + ": " + e.Message; }
```

## 단위 2: 입력 잠금

- **대상**: `DebugState`(InputLockMask, InputLocksError), `DebugHandler`, `InputLocks.Describe`, `DebugTools`(`debug_input_lock`, `debug_input_locks_error`), ExpectedTools, ReadMe.
- **코드 초안**:

```csharp
// DebugState
public static ulong? InputLockMask;
public static volatile bool InputLocksError;
public static void SetInputLock(ulong? mask)
{
    InputLockManager.RemoveControlLock(LockId);
    InputLockMask = mask;
    if (mask.HasValue) InputLockManager.SetControlLock((ControlTypes)mask.Value, LockId);
}
// Clear(): SetInputLock(null); InputLocksError = false;
// Status(): ["input_lock"] = InputLockMask.HasValue
//               ? new Dictionary<string, object> { ["id"] = LockId, ["mask"] = "0x" + InputLockMask.Value.ToString("X") } : null,
//           ["input_locks_error"] = InputLocksError

// DebugHandler: mask is a hex string: JSON numbers are double and lose bits above 2^53
yield return Post("input_lock", b => { DebugState.SetInputLock(b.Has("mask") ? ParseMask(b.GetString("mask")) : (ulong?)null); return DebugState.Status(); });
yield return Post("input_locks_error", b => { DebugState.InputLocksError = b.GetBool("on"); return DebugState.Status(); });

private static ulong ParseMask(string s)
{
    string hex = s.StartsWith("0x", StringComparison.OrdinalIgnoreCase) ? s.Substring(2) : s;
    if (!ulong.TryParse(hex, NumberStyles.HexNumber, CultureInfo.InvariantCulture, out ulong m))
        throw ApiException.BadRequest("mask must be a hex string like 0x8");
    return m;   // 0 allowed: a lock with no controls (0008 controls: [])
}

// InputLocks.Describe(): first line
if (DebugState.InputLocksError) throw new InvalidOperationException("debug: injected input lock listing failure");
```

- **검증**:
  - 시험 mask는 `ControlTypes`에서 계산해 고른다: 이름 있는 단일 비트 하나, 별칭으로 겹치는 비트 하나, 정의되지 않은 최상위 비트 하나(구현 때 `Enum.GetValues`로 확인해 이 문서에 기록).
    - 구현 때 확인(KSP 1.12 Assembly-CSharp): 64비트 중 이름 없는 비트는 `0x2` 하나이고, 최상위 비트 `0x8000000000000000`은 `EDITOR_CREW`다. 같은 단일 비트를 두 이름이 쓰는 별칭은 없어 `A|B` 출력은 이 KSP에서 나오지 않는다(시험 생략).
    - 시험 mask: `0x8`(→ `["YAW"]`), `0x800000000000000A`(2^53 초과 비트 포함 → `["YAW","EDITOR_CREW","0x2"]`), `0x0`(→ `[]`), 잘못된 `"zz"`(→ 400 `bad_request`).
  - 각 mask로 `debug_input_lock` → `get_status.input_locks`의 `kspbridge_debug` 항목에 이름·`A|B`·hex 출력 → `debug_input_lock {mask null}`로 사라짐.
  - mask `"0x0"` → `kspbridge_debug` 항목의 `controls: []`(0008).
  - `debug_input_locks_error {on true}` → `input_locks` null·`input_locks_error` 문자열, `editor`·`flight`는 그대로.
  - 잠금을 건 채 씬 전환 → 잠금 해제, `reload_mod` → 잠금 해제.
- **선행 단위**: 1

## 단위 4: 스테이지 확인 지연

- **대상**: `DebugState.StageDelayS`, `DebugHandler`, `StageRequest.Tick`, `DebugTools`(`debug_stage_delay`), ExpectedTools, ReadMe.
- **코드 초안**:

```csharp
// DebugState: main thread only (volatile double does not compile)
public static double StageDelayS;

// StageRequest: first send time
private double _firstSendUt = double.NaN;
// ... where it sends: if (double.IsNaN(_firstSendUt)) _firstSendUt = ut;

// StageRequest.Tick
double hold = DebugState.StageDelayS;   // 0 normally
if (v.currentStage < _stageBefore)
{
    if (hold > 0 && !double.IsNaN(_firstSendUt) && ut - _firstSendUt < hold)
    {
        return Result.Waiting;           // debug: confirmation held; never re-request a stage that already fired
    }
    // ... existing confirmed log, return Result.Done ...
}
// ... existing !send ...
bool expired = _tries >= MaxTries
    ? ut - _lastSendUt > ConfirmS + hold
    : ut - _firstUt > ConfirmS * MaxTries + hold;
```

- `_firstSendUt`는 디버그 전용 판정이라 `Save`·`Load`(핸드오버)에 넣지 않는다. 핸드오버 뒤 새 로직은 지연이 0이라 바로 확인한다(의도).
- 한계: `Submit` 시험 실패 때의 `AutoStager.Load(stagerBefore)` 뒤에는 `_firstSendUt`가 없어 보류가 조용히 사라진다. 만료 기한의 `+ hold`는 실제 실패 판정만 늦춘다(0006 임시 훅과 같음).
- **검증**(0006 기대값과 맞춤, `debug_stage_delay {seconds 5}`):
  - `on_start` 요청 확인 대기 중 `on_start:["stage"]`가 있는 계획으로 `submit_flight_plan` 재제출 → `staged {reason: on_start}` 2회, 스테이지 2개 감소, `stage_failed` 없음(0006:574)
  - `on_start` 요청 확인 대기 중 `abort_flight` → `staged {reason: on_start}` 1회가 `plan_aborted {reason: user}` 앞에(0006:1162). `ignite` 요청 송신 직후 `abort_flight`도 같은 확인. KSP.log `stage request sent ... try 1`이 abort보다 앞인지 함께 기록
  - `on_start`·`ignite` 요청 확인 대기 중 `reload_mod` → 새 로직이 확인, `staged` 1회, 재요청 없음, 스테이지 1개만 감소(0006:1497)
  - 구현 때 확인한 시험 조건: `on_start`는 TestD(3단: 하단 엔진 → 디커플러 → 상단 Terrier)를 발사대에서 `attitude throttle 0`으로. `ignite`는 TestD 하단 긴 탱크 2개의 LF·Ox를 에디터 `set_resource 0.15`로 줄이고 `auto_stage:true, throttle 1`로 띄워, Player.log의 세 번째 `stage request sent` 직후 HTTP로 `abort`·`reload`를 보낸다. 1%는 발사대 위에서 분리돼 상단이 폭발하므로(실측) 쓰지 않는다.
- **선행 단위**: 1

## 단위 5: 엔진 정지·스로틀 고정

- **대상**: `DebugState`(ThrottleHold), `DebugHandler`, `BridgeLogic.FixedUpdate`, `DebugTools`(`debug_engine_stop`, `debug_throttle_hold`), ExpectedTools, ReadMe.
- **코드 초안**:

```csharp
// DebugHandler
yield return Post("engine_stop", b =>
{
    ModuleEngines e = DebugState.Engine(Guard.ActiveVessel(), (uint)b.GetDouble("part_id"));
    string mode = b.GetString("mode");
    if (mode == "shutdown") e.Shutdown();
    else if (mode == "flameout") e.Flameout("debug");
    else throw ApiException.BadRequest("mode must be shutdown or flameout");
    return new Dictionary<string, object> { ["part_id"] = (double)e.part.persistentId, ["ignited"] = e.EngineIgnited, ["flameout"] = e.flameout };

yield return Post("throttle_hold", b =>
{
    if (!b.Has("throttle")) { DebugState.ThrottleHold = null; return DebugState.Status(); }
    uint id = (uint)b.GetDouble("part_id");
    DebugState.Engine(Guard.ActiveVessel(), id);   // validate now
    DebugState.ThrottleHold = new ThrottleHold(id, Mathf.Clamp01((float)b.GetDouble("throttle")));
    return DebugState.Status();
});

// DebugState: the first ModuleEngines of the part (multi-mode engines: first mode only)
/// <summary>Null when the part is not on the vessel or has no engine. A plain loop: Tick calls it every physics tick.</summary>
public static ModuleEngines FindEngine(Vessel v, uint partId)
{
    List<Part> parts = v.parts;
    for (int i = 0; i < parts.Count; i++)
    {
        if (parts[i].persistentId == partId) return parts[i].FindModuleImplementing<ModuleEngines>();
    }
    return null;
}
/// <summary>For the routes: 404 instead of null.</summary>
public static ModuleEngines Engine(Vessel v, uint partId)
    => FindEngine(v, partId) ?? throw ApiException.NotFound("engine part " + partId + " not found on the active vessel");
public static void Tick()   // never throws
{
    ThrottleHold h = ThrottleHold;
    if (h == null || !FlightGlobals.ready || FlightGlobals.ActiveVessel == null) return;   // no vessel this tick: keep holding
    try
    {
        ModuleEngines e = FindEngine(FlightGlobals.ActiveVessel, h.PartId);   // loop without LINQ, null when not found
        if (e == null)
        {
            ThrottleHold = null;
            UnityEngine.Debug.Log("[KspBridge] debug throttle hold released: engine part " + h.PartId + " not on the active vessel");
            return;
        }
        e.currentThrottle = h.Throttle;
    }
    catch (Exception ex)
    {
        ThrottleHold = null;
        UnityEngine.Debug.LogError("[KspBridge] debug throttle hold released: " + ex);
    }
}

// BridgeLogic.FixedUpdate: first line, before Coordinator.Tick reads currentThrottle (AutoStager.KeptThrottleDown) in the same call
Debugging.DebugState.Tick();   // never throws
Coordinator.Tick();
// ...
```

- **검증**:
  - 스로틀 고정: 남는 쪽에 두 엔진이 있는 직렬 기체가 필요하다.
    - 엔진 B(고정 대상): 발사 스테이지에서 점화되지만 자기 탱크 연료가 0이라 곧 flameout(점화 상태 유지). 작동 가능한 남은 엔진이 있으면 `IsParallel`이 true라 2초 대기를 건너뛰므로 B는 작동 불가여야 하고, `KeptThrottleDown`은 점화된 엔진만 보므로 B는 점화 상태여야 한다.
    - 엔진 C: 뒤 스테이지의 미점화 연료 엔진(별도 탱크). 없으면 `KeptHasEngine`이 false라 Separate 전에 `out_of_stages`로 끝난다.
    - 버리는 쪽 엔진 A: 발사 스테이지에서 연소, 분리 대상.
    - 기체는 에디터에서 만든다. B 탱크의 연료 0은 `set_resource`(에디터 전용 경로 `/api/editor/parts/<id>/resource`)로 두고 저장·발사한다.
    - B는 다른 탱크에서 연료를 받을 길이 없어야 한다. B가 C·A 쪽 탱크 연료를 끌어오면 flameout이 아니라 작동 가능이 되어 `IsParallel`이 true(2초 대기 생략)가 된다. 예: B 탱크와 C 사이, B와 A 사이에 crossfeed가 꺼진 디커플러를 둔다.
    - 판정 전에 분리 시점에 B가 점화 상태이면서 flameout인지(`debug_engine_stop` 응답 형식의 `ignited`·`flameout` 또는 KSP.log staging sets 로그) 확인하고 기록한다. 아니면 시험 무효로 하고 기체를 고친다.
    - `auto_stage` 계획에서 B에 `debug_throttle_hold {throttle 1}` → 같은 기체로 고정 없이 대조 시험을 한 번 더 한다. 판정: 두 시험의 (`stage_burnout` → `staged {reason: separate}`) ut 차의 차이가 2초 ± 0.5초. 대조로 Tailoff·StageRequest 확인 시간을 상쇄한다(2초 상한은 Separate 진입 `_since` 기준).
  - 엔진 정지 `shutdown`: 점화 엔진, 다음 단에 엔진 있음 → `staged {reason: ignite}`.
  - `ignite_blocked`: 0006 D′ 기체(페어링 스테이지가 2단 엔진 앞). 계획 1단 `throttle 1, until ignitable_engines <= 1`(`ignitable_engines`는 미점화 연료 엔진도 센다. D′의 2단 엔진 수가 1이므로 1단 소진 뒤 1이 된다. 엔진 수가 다르면 그 수로 둔다) → `throttle 0` 단계. 분리 뒤 `ignite_blocked` 1회가 스로틀 0 단계에서 나오고 이후 다시 나오지 않음(래치). 스로틀 > 0이면 같은 틱에 `no_thrust` 중단(0006:1145). 1단 소진은 필요하면 `debug_engine_stop {flameout}`으로 앞당긴다.
  - `flameout`: `stage_burnout` → 분리 경로, 결과(이벤트 순서, flameout이 풀리는지) 기록.
  - 구현 때 확인한 시험 조건과 결과(2026-11-13, 기체는 저장하지 않음):
    - 2초 상한 기체 TestHold(위에서부터): 포드 → FL-T200(C 탱크) → Terrier C → TD-12 D2 → FL-T200(B 탱크, LF·Ox 0) → Swivel B → TD-12 D1 → FL-T400(A 탱크, 50%) → Swivel A. 스테이지 3 = A+B, 2 = D1, 1 = C, 0 = D2. TD-12의 crossfeed는 편집 필드에 없어 기본값을 쓴다. `get_flight`에 엔진별 상태가 없어 B의 상태는 측정과 독립된 두 관찰로 확인한다.

- **구현 완료 전 검토(4회차) 반영**:
  - `debug_throttle_hold`는 실행 중인 계획이 있을 때만 건다(없으면 409 `no_plan`). `DebugState.Tick`은 계획이 끝나거나 중단되면(`Coordinator.Running` false) 고정을 풀고 `debug throttle hold released: the flight plan ended`를 남긴다. 계획 종료 뒤 추력이 남는 경로를 막는다. 재검토(5회차) 반영: `Tick`은 쓰기 전 값을 기억하고, `Coordinator.Tick` 바로 뒤의 `DebugState.AfterTick`이 그 틱에 계획이 끝났으면 기억한 값으로 되돌린 뒤 푼다(종료 틱에도 고정값이 남지 않음). 틱 사이(HTTP `abort_flight` 등)에 끝났으면 다음 `Tick`이 쓰지 않고 푼다. `Unhook`은 `Remove`가 성공한 뒤에만 참조를 지운다(실패하면 다음 `Unhook`이 다시 시도).
  - `part_id`는 0..uint.MaxValue 정수만 받는다(소수·음수·범위 밖은 400, 다른 id로 잘리지 않게). `debug_stage_delay`의 `seconds`는 0..60(기한이 그만큼 늘어나므로 상한).
  - `DebugState.Unhook`은 핸들러 제거가 예외를 내도 `finally`에서 `Clear`한다. `Clear`는 일반 필드를 먼저 풀고, 잠금이 걸려 있을 때만 `RemoveControlLock`을 부른다(플래그가 꺼져 있으면 게임 호출 없음). `StartCore`의 시작 실패 정리는 세 Unhook을 각각 따로 실행한다.
  - `StartCore`는 `LoadFlag`를 먼저 하고 `ConsumeStartFault`는 플래그가 꺼져 있으면 아무것도 하지 않는다(주입 뒤 debug.cfg를 끄고 reload해도 시작 불변, 남은 `debug_fault` 키는 `Handover.Parse`가 무시).
- **선행 단위**: 1

## 단위 6: reload 실패 주입

- **대상**: `DebugState`(ReloadFault), `DebugHandler`, `Coordinator.Stop` 직렬화 3단계, `BridgeLogic.StartCore`, `DebugTools`(`debug_reload_fault`), ExpectedTools, ReadMe.
- **코드 초안**:

```csharp
// DebugState: set by debug_reload_fault, spent by the next Coordinator.Stop, released by Clear
public static int StartFailures, HandoverFailures;

/// <summary>Coordinator.Stop, first thing: read and reset at once, so neither the Stop order nor the restarted previous
/// logic (same assembly, same statics) can see them again.</summary>
public static (int start, int handover) TakeReloadFault()
{
    (int, int) f = (StartFailures, HandoverFailures);
    StartFailures = HandoverFailures = 0;
    return f;
}
public static Dictionary<string, object> Tag(Dictionary<string, object> h, int startFailures)
{
    if (startFailures > 0) h["debug_fault"] = new Dictionary<string, object> { ["start_failures"] = (double)startFailures };
    return h;
}

/// <summary>StartCore, first thing: a handed-over start failure is spent here. Never throws on a bad handover
/// (Handover.Parse handles that as Incompatible); throws only when a debug_fault asks for it.</summary>
public static void ConsumeStartFault(LogicContext context)
{
    if (string.IsNullOrEmpty(context.Handover)) return;
    Dictionary<string, object> h;
    try { h = Json.Json.Parse(context.Handover) as Dictionary<string, object>; }
    catch { return; }
    if (h == null || !(h.TryGetValue("debug_fault", out object f) && f is Dictionary<string, object> fault)
        || !(fault.TryGetValue("start_failures", out object n) && n is double left && left >= 1)) return;
    if (left > 1) fault["start_failures"] = left - 1; else h.Remove("debug_fault");
    context.Handover = Json.Json.Serialize(h);   // the loader restarts the previous logic with this string
    throw new InvalidOperationException("debug: logic start failure injected (" + (left - 1) + " left)");
}

// Coordinator.Stop
(int startFail, int handoverFail) = DebugState.TakeReloadFault();
// stage 1
if (handoverFail >= 1) throw new InvalidOperationException("debug: handover stage 1 failure injected");
context.Handover = Json.Json.Serialize(DebugState.Tag(Handover.Capture(), startFail));
// ... catch: stage 2
    if (handoverFail >= 2) throw new InvalidOperationException("debug: handover stage 2 failure injected");
    context.Handover = Json.Json.Serialize(DebugState.Tag(Handover.CaptureEvents(), startFail));
// ... catch: stage 3
    Safe(() =>
    {
        if (handoverFail >= 3) throw new InvalidOperationException("debug: handover stage 3 failure injected");
        context.Handover = Json.Json.Serialize(DebugState.Tag(new Dictionary<string, object> { /* format, epoch, seq */ }, startFail));
    });

// BridgeLogic.StartCore: first line, before Stopped = false (a logic that refuses to start stays Stopped)
Debugging.DebugState.ConsumeStartFault(context);
```

- `debug_reload_fault {start_failures, handover_failures}`: 0~2, 0~3 범위 검사(벗어나면 `bad_request`). `start_failures ≥ 1`과 `handover_failures 3`의 조합은 시작 실패가 전달되지 않으므로 `bad_request`로 거부한다.
- **검증**:
  - `start_failures 1`: `reload_mod` → `reload_failed ... (previous logic restarted)`, 계획 유지, `get_status.debug.reload_fault` 0·0, 이어서 `reload_mod` 성공(재발 없음)
  - `start_failures 2`(`rcs` 단계 키가 있는 계획 중, 로더 RCS 복원은 `rcs_touched`일 때만): `reload_mod` → `previous logic could not be restarted`, KSP.log `handover dropped: ...` note가 계획 기체 기준(0016), `get_status.logic_error`. 이어서 `reload_mod` → 성공, `logic_reloaded` 없음·epoch 변경(0017)
  - `handover_failures 1·2·3`(계획 중): `reload_mod` → `aborted (handover failed)`. 1: 이벤트 유지·`logic_reloaded {resumed:false}`, 2: 이전 이벤트는 없고 `logic_reloaded {resumed:false}` 1건만, seq는 `LastSeq` 다음부터 이어지고 epoch 유지(최소 핸드오버도 `Present`, 0017), 3: epoch 변경·`logic_reloaded` 없음, KSP.log에 주입 로그 `flight release step failed ... handover stage 3`
  - 주입 뒤 `debug_clear` 또는 씬 전환 → `reload_fault` 0·0, `reload_mod` 정상
  - 로딩 화면 중 reload: 씬 로딩 중(`reset.loading_seconds` 있음) `reload_mod` → 판정 구간: `reload_mod` 호출 직전 KSP.log 줄 수를 기록하고, 응답(성공 또는 `reload_failed`) 뒤 2초까지 새로 붙은 줄. 합격 기준: 그 구간에 `debug: handover stage 3 failure injected`가 아닌 `flight release step failed`가 없음. 있으면 별도 이슈로 낸다
  - 구현 때 확인(2026-11-13): 판정 로그는 KSP.log 대신 즉시 기록되는 Player.log로 본다(단위 3 기록, R3-1-B-3 해소). 시험 기체는 TestD 발사대, 계획은 `attitude throttle 0, on_start:["stage"]`(T2만 `rcs:true`). HTTP `POST /api/reload`로 보내 응답과 로그 줄 수를 같은 스크립트에서 잰다.
  - 결과: start 1 → `reload_failed ... (previous logic restarted)`, 계획 계속(`logic_reloaded resumed:true`), 주입 0·0, 다음 reload 성공. start 2(`rcs:true`) → `previous logic could not be restarted`, `logic_error`, 로더 `handover dropped: throttle 0, sas False, rcs False`(계획 전 RCS 꺼짐으로 복원), 다음 reload `version_before null` 성공·이벤트 없음·epoch 변경. handover 1 → 이벤트 유지·`plan_aborted error`·`logic_reloaded resumed:false`, 2 → 이전 이벤트 없이 `logic_reloaded`만(잃은 `plan_aborted` seq 다음), epoch 유지, 3 → 이벤트 없음·epoch 변경·`flight release step failed ... handover stage 3 failure injected`. `debug_clear`·revert 뒤 0·0. 로딩 2.04초째 reload → 2초 구간에 `flight release step failed`·예외 없음. 잘못된 인수(start 1 + handover 3, start 3, handover 1.5)는 400 `bad_request`.
- **선행 단위**: 1
