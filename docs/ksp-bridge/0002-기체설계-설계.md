## 구조

```
MCP 클라이언트 ──▶ App.Tools/EditorTools (17개 도구) ──HTTP──▶ Mod HttpServer ──▶ Logic Handlers/EditorHandler
                                                                    │                 ├─ Editor/*   (에디터 상태·편집·파일)
                                                                    │                 ├─ Catalog/*  (부품 목록)

                                                                    │                 └─ Render/*   (PNG)

```

## 공통 규칙

- **부품 식별**: `Part.persistentId`(uint). 저장·불러오기 후에도 유지된다. `add_part`는 새 부품과 대칭 사본의 id를 모두 돌려준다.
- **좌표계**: 루트 부품 로컬 좌표. +Y = 로켓 위·비행기 기수. VAB·SPH 동일. 단위 m, 각도 deg.
- **원자성**: 편집 도구 한 번은 전부 성공하거나 아무것도 바꾸지 않는다(대칭 사본 포함). 실패 전에 되돌릴 수 없는 단계가 남지 않게, 검사를 먼저 끝내고 변경은 마지막에 한다. 앞선 호출의 결과는 유지한다. 성공한 호출마다 에디터 Undo 1단계를 등록한다.
- **스레드**: 편집·검사·렌더는 모두 `MainThreadDispatcher`에서 동기 실행한다.
- **비동기 작업**(`open_editor`, 불러오기가 있는 `open_editor`, `launch_craft`): 요청만 걸고 `{accepted:true}`를 즉시 반환한다. 완료는 `get_status`의 `editor.ready`·`scene`으로 확인한다.
- **오류**: 기존 `ApiException` 형식. 추가 코드 `not_in_editor`(409), `editor_not_ready`(409), `part_not_found`(404), `part_locked`(409), `attach_failed`(409), `name_exists`(409).

## 인터페이스

### MCP 도구 ↔ HTTP 라우트

| 분류 | 도구 | 라우트 | 인자 | 응답 |
| --- | --- | --- | --- | --- |
| 에디터 | `open_editor` | `POST api/editor/open` | `facility` VAB\|SPH, `craft?`(불러올 이름) | `{accepted}` |
| 에디터 | `new_craft` | `POST api/editor/new` | `name?` | 에디터 상태 |
| 에디터 | `save_craft` | `POST api/editor/save` | `name`, `overwrite?`=false | 저장 경로, 구조 경고 |
| 조회 | `list_parts` | `GET api/parts` | `category?`, `q?`, `unlocked?`=true | 부품 요약 목록 |
| 조회 | `get_part` | `GET api/parts/{name}` | | 부품 상세 |
| 조회 | `list_crafts` | `GET api/editor/crafts` | `facility?` | 이름·부품 수·수정 시각 |
| 조회 | `get_craft` | `GET api/editor/craft` | | 에디터 상태 + 부품 트리 + 스테이지 |
| 편집 | `add_part` | `POST api/editor/parts` | `part`, `parent?`, `node?{parent, child}` 또는 `surface?{azimuth, height, angle}`, `symmetry?{mode radial\|mirror, count}` | 변경 결과 |
| 편집 | `remove_part` | `DELETE api/editor/parts/{id}` | | 변경 결과(하위·대칭 포함) |
| 편집 | `offset_part` | `POST api/editor/parts/{id}/offset` | `x`, `y`, `z` | 변경 결과 |
| 편집 | `rotate_part` | `POST api/editor/parts/{id}/rotate` | `axis` x\|y\|z, `degrees` | 변경 결과 |
| 편집 | `set_part_field` | `POST api/editor/parts/{id}/field` | `module`, `field`, `value` | 변경 결과 |
| 편집 | `set_resource` | `POST api/editor/parts/{id}/resource` | `resource`, `fraction` 0..1 | 변경 결과 |
| 스테이징 | `set_stage` | `POST api/editor/parts/{id}/stage` | `stage` 또는 `new_stage_at` | 스테이지 목록 |
| 검증 | `check_craft` | `GET api/editor/check` | `body?`=Kerbin, `altitude?`=0, `vacuum?`=false | 구조 + 성능 |
| 검증 | `render_craft` | `POST api/editor/render` | `views?`, `resolution?`=512, `markers?`=false | `images[]` |
| 발사 | `launch_craft` | `POST api/editor/launch` | `site?`(기본: VAB=LaunchPad, SPH=Runway) | `{accepted}` |

- `add_part`: 루트가 없으면 `parent` 없이 루트로 놓는다. 루트가 있으면 `parent`와 `node`/`surface` 중 하나가 필요하다. `node.child`를 생략하면 부모 노드의 반대편 노드(top↔bottom)를 고른다.
- `surface`: `azimuth` 0..360(부모 +Y 축 기준, 0 = 부모 +Z), `height` = 부모 높이 방향 0..1(0 = 아래 끝, 1 = 위 끝), `angle` = 바깥 법선 축 회전. 부모 표면 위치는 부모 콜라이더에 레이를 쏴서 구한다.
- `symmetry.mode`: VAB 기본 radial, SPH 기본 mirror. `count` 1..8(mirror는 2).
- `remove_part`는 루트를 지울 수 없다(`new_craft` 사용).
- `set_stage`: 스테이징 대상 부품(엔진·분리기·낙하산 등)만. `new_stage_at`이면 그 위치에 새 스테이지를 만들고 옮긴다.

### Mod `get_status` 확장

```csharp
public interface ILogic
{
    // ... existing ...
    /// <summary>Main thread. Extra fields merged into /api/status (null = none).</summary>
    IDictionary<string, object> Status();
}
```

`LogicHost.Status()`는 기존 필드에 `_logic?.Status()` 결과를 합친다. Logic은 `editor = {facility, ready, craft, part_count}`를 넣는다(에디터 밖이면 `editor = null`). 인터페이스가 바뀌므로 `LoaderVersion`을 올리고 Mod·Logic을 함께 배포한다.

## 데이터

### 부품 요약 (`get_craft.parts[]`, 편집 응답)

```json
{ "id": 123456789, "part": "fuelTank", "title": "FL-T400", "parent": 987654321,
  "attach": { "kind": "node", "parent_node": "bottom", "child_node": "top" },
  "symmetry": { "mode": "radial", "group": [123456789, 223456789] },
  "stage": 1, "position": [0, -1.9, 0], "rotation": [0, 0, 0] }
```

`attach.kind`는 `node`|`surface`|`root`. `rotation`은 루트 기준 오일러(deg).

### 편집 응답

```json
{ "added": [...부품 요약], "changed": [...], "removed": [ids],
  "warnings": [{ "code": "overlap", "parts": [a, b], "depth": 0.12 }] }
```

경고는 이번에 바뀐 부품이 관련된 것만 넣는다.

### `check_craft`

```json
{ "structure": { "ok": false, "issues": [
    { "severity": "error|warning", "code": "locked_part|bad_node|orphan|overlap|no_root", "parts": [...], "message": "..." } ] },
  "performance": { "ready": true, "situation": { "body": "Kerbin", "altitude": 0, "vacuum": false },
    "stages": [ { "stage": 1, "mass_start": 0, "mass_end": 0, "thrust": 0, "twr": 0, "isp": 0, "delta_v": 0, "burn_time": 0 } ],
    "total_delta_v": 0, "com": [0,0,0], "cot": [0,0,0], "col": [0,0,0],
    "warnings": [ "twr_below_1", "col_ahead_of_com", "no_control" ] } }
```

- 성능은 에디터의 `VesselDeltaV`(스테이지 앱과 같은 값)를 쓴다. 상황(천체·고도·진공)을 지정해 계산하고, 결과가 아직 계산 중이면 `ready=false`로 돌려준다.
- CoM은 부품 질량 가중 평균, CoT·CoL은 게임의 `CenterOfThrustQuery`·`CenterOfLiftQuery`(`IThrustProvider`, `ILiftProvider`)를 쓴다.
- 겹침은 서로 충돌할 부품 쌍(분리 지점 너머라 분리 후 다른 기체가 되는 쌍, 또는 두 부품 모두 `sameVesselCollision`)의 콜라이더를 `Physics.ComputePenetration`으로 계산해 깊이가 0보다 크면 경고로 보고한다. 같은 기체 부품끼리는 게임이 충돌을 무시하므로 기준값을 두지 않는다(개발 U10에서 정정).

### `render_craft`

- `views`: 문자열 배열. 이름 `front`|`side`|`top`|`iso` 또는 `"azimuth,elevation"`(deg, 예: `"45,30"`). 기본 `[side, front, iso]`, 최대 4개. (검토 R5: 도구 스키마를 단순하게 하려고 객체 대신 문자열로 통일)
- 기체 경계에 맞춰 거리를 정하고, 단색 배경, 기체 레이어만 찍는다. `markers=true`면 CoM/CoT/CoL 표시를 함께 그린다.
- `resolution`: 기본 512, 최대 1024.
- Logic 응답: `{ images: [{ view, width, height, png: <base64> }] }`. Tools가 각 이미지를 MCP `ImageContentBlock`(`image/png`)으로 바꾸고, 뷰 이름은 텍스트 블록으로 붙인다.

## 의존성

- KSP API: `EditorLogic`, `EditorDriver.StartEditor`, `ShipConstruct`, `ShipConstruction`, `PartLoader`, `AvailablePart`, `ResearchAndDevelopment.PartTechAvailable`, `VesselDeltaV`, `DeltaVStageInfo`, `CenterOfLiftQuery`, `CenterOfThrustQuery`, `EditorLogic.LoadShipFromFile`, `EditorLogic.fetch.launchVessel`.

- MCP SDK 2.4.0: `ImageContentBlock`, `TextContentBlock`(Tools만 사용, Core 변경 없음).
- 정확한 API 시그니처와 동작(SetBackup, 대칭 API, DeltaV 상황 설정)은 개발 단계에서 게임 DLL로 확인한다.
