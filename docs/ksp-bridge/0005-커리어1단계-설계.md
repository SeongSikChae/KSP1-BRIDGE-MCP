# KspBridge 커리어 1단계 — 설계

선행: `0004-커리어1단계-방안.md`. 기존 계약(`0002-비행제어-설계.md`)의 공통 규칙(응답 형식, 오류 코드, 단위, 메인 스레드 디스패처)을 그대로 따른다.

## 결정 목록
| # | 항목 | 결정 |
|---|---|---|
| E1 | 조향 | **두 방식 모두** 구현, 요청마다 `mode`로 선택: `own`(자체 컨트롤러, OnFlyByWire) / `sas`(스톡 SAS 안정 유지 + `LockRotation`) |
| E2 | 승무원 | 발사 시 **이름 지정** 가능, 미지정이면 게임 기본 배정 |
| E3 | 권한 | 계약 **수락·거절**, 과학 데이터 **폐기**, 발사 **되돌리기(Revert)** 허용 |
| E4 | 대기 | `wait_until` 한 번 최대 **120초**, 길면 Claude가 나눠 호출 |
| E5 | 장면 전환 | 발사·회수·되돌리기는 요청을 받아들이면 즉시 응답(`accepted`)하고 장면이 바뀐다. 완료 확인은 `get_status`로 한다. 전환 중(`LOADING` 등)에는 기존 409 오류가 나간다 |
| E6 | 긴 요청 | `wait_until`은 HTTP 스레드에서 0.1초마다 메인 스레드 조건 검사를 반복한다(메인 스레드를 막지 않음). App은 요청별 타임아웃을 쓴다(일반 `TimeoutSeconds`, 대기는 요청 시간+10초) |
| E7 | 커리어 아님 | 계약·자금 등 커리어 전용 기능은 커리어가 아니면 409 `not_career` |

추가 오류 코드: `not_career`(409), `scene_not_allowed`(409, 이 장면에서 불가한 요청), `not_recoverable`(409), `cannot_revert`(409)

## A. 커리어 상태·계약 (모든 장면, 게임 로드 후)
| 경로 | 동작 |
|---|---|
| `GET /api/career` | `{mode, funds, science, reputation, facilities:{launch_pad, runway, vab, sph, tracking_station, mission_control, rnd, astronaut_complex, administration: {level, max_level}}}` — level은 0부터, `GetFacilityLevel`(0~1) × (단계 수−1) |
| `GET /api/contracts?state=offered\|active\|completed` | 계약 목록 `{id, title, state, prestige, deadline_ut, rewards:{funds_advance, funds_completion, science, reputation}, parameters:[{title, state, optional, parameters:[...]}]}` (state 생략 시 offered+active) |
| `POST /api/contracts/{id}/accept` | `Contract.Accept()` — 제안 상태가 아니면 400 |
| `POST /api/contracts/{id}/decline` | `Contract.Decline()` — 제안 상태가 아니면 400 |

`id`는 계약 고유 ID(개발 단계에서 `ContractID`/`ContractGuid` 중 확정).

## B. 과학 실험 (비행 장면)
| 경로 | 동작 |
|---|---|
| `GET /api/science` | `{situation, biome, experiments:[{id, part, experiment_id, title, deployed, inoperable, rerunnable, can_run_now, expected_science, data:[{title, amount, subject_id, science_value}]}]}` |
| `POST /api/science/run` `{id}` | `ModuleScienceExperiment.DeployExperiment()`. 결과는 부품에 보관(게임 결과 창이 뜰 수 있음 — 개발 단계에서 처리 방식 확인) |
| `POST /api/science/discard` `{id}` | 보관 데이터 `DumpData` 후 `ResetExperiment` (되돌릴 수 없음) |

`id`는 `{part persistentId}:{모듈 순번}` 문자열.

## C. 발사·회수
| 경로 | 장면 | 동작 |
|---|---|---|
| `GET /api/craft?facility=VAB\|SPH` | 모두 | 저장 기체 목록 `{name, facility, path, stock}` (세이브 `Ships/{VAB,SPH}` + 게임 기본 `Ships`) |
| `GET /api/crew` | 모두 | `{name, trait, level, status}` — 배정 가능 여부 포함 |
| `POST /api/launch` `{craft, facility, site:"LaunchPad"\|"Runway", crew:[이름]}` | KSC·에디터·비행 | 검증(기체 존재, 발사장 비어 있음, 자금 ≥ 비용, 승무원 가용·좌석 수) 후 `FlightDriver.StartWithNewLaunch`. 응답 `{accepted:true}` |
| `POST /api/recover` | 비행 | 착륙/착수 + `IsRecoverable`이면 `GameEvents.OnVesselRecoveryRequested.Fire(v)`, 아니면 409 `not_recoverable` |
| `POST /api/revert` | 비행 | `FlightDriver.CanRevertToPrelaunch`이면 `RevertToLaunch()`, 아니면 409 `cannot_revert` |

확인 필요(개발 단계): `StartWithNewLaunch`가 커리어 자금 차감·부품 해금·시설 한계(부품 수·질량)를 처리하는지. 처리하지 않으면 모드가 같은 검증·차감을 한다.

## D. 상승 제어 (비행 장면)
| 경로 | 동작 |
|---|---|
| `POST /api/attitude` `{mode:"own"\|"sas", pitch, heading, roll?}` | 목표 자세 설정·유지. roll 생략 시 롤 자유. 같은 기체에 하나만 활성 |
| `POST /api/attitude/off` | 해제(조종 입력 반환, `sas` 모드면 SAS는 켜진 채 안정 유지) |
| `POST /api/wait` `{field, op, value, timeout}` | 조건 충족 또는 timeout(≤120s)까지 대기. 응답 `{met, elapsed, value, vessel:{situation, altitude_asl, apoapsis, time_to_ap, speed_vertical, stage}}` |
| `GET /api/stages` | `VesselDeltaV.OperatingStageInfo` → 스테이지별 `{stage, dv_vac, dv_asl, dv_actual, twr_vac, twr_asl, twr_actual, burn_time, start_mass, end_mass, parts:[제목]}` (parts = 그 스테이지에서 작동하는 부품) |

`/api/vessel` 응답에 `autopilot:{active, mode, pitch, heading, roll, error_deg}` 추가.

`wait` 조건
- `field`: `altitude_asl, altitude_terrain, apoapsis, periapsis, time_to_ap, speed_surface, speed_vertical, met, situation, stage_flameout`
- `op`: `>=, <=, ==` (`situation`은 `==`만, `stage_flameout`은 bool)
- 기체가 바뀌거나 비행 장면을 벗어나면 즉시 `met:false`, `reason` 포함해 반환

조향 방식
- `own`: `Vessel.OnFlyByWire`에 콜백 등록. 목표 회전과 현재 회전의 오차각(기체 좌표계 pitch/yaw/roll)과 각속도로 PD 제어 → `FlightCtrlState.pitch/yaw/roll`(−1~1). 게인은 `settings.cfg`의 `ATTITUDE { kp, kd }`로 조정
- `sas`: SAS 켜기 + 모드 `StabilityAssist` + 매 물리 틱 `Autopilot.SAS.LockRotation(목표 회전)`. SAS 불가(조종사·프로브 없음) → 400
- 목표 회전: 지표 기준 pitch/heading/roll → 상태 조회의 MechJeb 방식 역변환
- 장면 전환·기체 파괴·기체 변경 시 자동 해제

## G. 비행체 조립 (모든 장면, 게임 로드 후)
| 경로 | 동작 |
|---|---|
| `GET /api/parts?category=&unlocked=true` | 부품 카탈로그 `{name, title, category, cost, mass, size, tech, unlocked, nodes:[id], crew, resources:[{name,max}], engine:{thrust_vac, thrust_asl, isp_vac, isp_asl}, decoupler}` |
| `POST /api/craft/build` `{name, facility, overwrite, dry_run, root}` | 설계도 검증 → (dry_run 아니면) `.craft` 저장. 응답 `{saved, path, cost, mass, part_count, limits:{max_parts, max_mass}, stages:[{stage, parts, dv_asl, dv_vac, twr_asl}], errors:[], warnings:[]}`. 오류가 하나라도 있으면 저장하지 않음 |

설계도 형식 (스택은 위→아래로 자식이 매달리는 트리)
```json
{ "part": "mk1pod.v2",
  "children": [
    { "node": "bottom", "part": "fuelTankSmallFlat",
      "children": [ { "node": "bottom", "part": "liquidEngine2" } ],
      "radial": [ { "part": "radialDecoupler", "symmetry": 3,
                    "children": [ { "node": "srf", "part": "solidBooster.v2" } ] } ] } ],
  "stage": null }
```
- `node`: 부모의 부착 노드 id(`bottom`, `top` 등). 자식은 자신의 반대 노드(`top`↔`bottom`)로 붙는다
- `radial`: 부모 표면에 `symmetry`개를 원형 대칭으로 부착(선택 `angle`, `height` 오프셋). 부착 반지름은 부모 부품 크기에서 계산
- `stage`: 생략 시 자동 스테이징 — 맨 아래 엔진부터 점화, 디커플러는 그 위 스테이지, 낙하산은 마지막. 숫자를 주면 그 부품의 `istg`를 직접 지정

검증
- 오류(저장 안 함): 없는 부품, 커리어에서 미해금 부품(`PartModelPurchased`), 없는 노드, 시설 한계 초과(`GameVariables.GetPartCountLimit/GetCraftMassLimit`, 해당 시설 레벨), 같은 이름 존재 + `overwrite` 아님
- 경고: 노드 크기 불일치, 자금 < 비용, 첫 스테이지 TWR(ASL) < 1.2, 명령 부품 없음
- 예상 Δv·TWR은 모드 자체 계산(치올콥스키, 엔진 `atmosphereCurve` 기준). 발사 후 실제 값은 `get_stages`

생성 방식: 부품 프리팹의 부착 노드 위치로 각 부품의 위치·회전을 계산해 `.craft` ConfigNode(PART, attN/srfN, istg/dstg, 모듈 기본값)를 만든다. 개발 단계에서 텍스트 생성과 메모리 `ShipConstruct` 생성 중 하나를 시험해 고른다.

추가(2026-11-08, 로직 0.9.3): 엔진 추력 제한 `thrust_limit` 0~100(%)
- 엔진이 아닌 부품에 지정하면 오류입니다.
- craft 파일에는 그 엔진의 MODULE 노드 하나만 씁니다(`name`, `isEnabled`, `thrustPercentage`). 로더는 모듈을 이름으로 찾습니다(인덱스가 맞지 않는다는 경고 로그는 무해).
- 추정치: 추력만 줄이고 Isp는 그대로 둡니다. 그래서 Δv는 같고 TWR만 낮아집니다.
- 배경: 플리 시험에서 붙인 채 다 태울 때 G를 낮추려고(100%면 5~7 g, 40%면 2~2.8 g) 넣었습니다.
- 추가(로직 0.9.5): 부품 연료량 `resources: {자원: 0~1}`(maxAmount 대비 비율)
  - 그 부품에 없는 자원을 지정하면 오류입니다.
  - craft의 RESOURCE `amount`와 추정 질량·Δv가 같은 계산(`BuiltPart.Amount`)을 씁니다.
  - 배경: 해머 궤도 테스트에서 해머를 연료 8%·추력 20%로 달아, 시험 겸 약 200 m/s 궤도 이탈 분사로 쓰려고 넣었습니다.
- 추가(로직 0.9.7, 문 근접 통과 계약):
  - 기동 노드 응답(`add`/`list`)에 `patches`(노드 뒤 궤적 패치: 천체, 시작·끝 UT, 끝 방식 encounter/escape/maneuver/final, 근지점·원지점)와 `transfers`(현재 천체의 위성별 위상각, 호만 위상각, 창까지 시간, 호만 Δv, 천이 시간)를 넣었습니다. 조우 패치의 근지점이 근접 거리입니다.
  - 조건 필드 `any_flameout`(점화된 엔진 중 하나라도 꺼짐)을 추가했습니다. `stage_flameout`은 전부 꺼졌을 때만 참이라 코어 엔진이 타는 동안 고체 부스터 분리에 쓸 수 없습니다.
  - `warp_to`는 스로틀이 0보다 크거나 레일 가속이 막혀 있으면(대기권 등) 거부하지 않고 예약합니다. 매 물리 틱에 둘 다 풀리면 목표 시각을 다시 계산해 시작합니다. 응답은 `scheduled: true, waiting_for`이고, `get_vessel_state`의 `warp.scheduled`에 보이며 `stop_warp`·`set_warp`로 취소됩니다.
- 수정(로직 0.9.6): 단계를 받은 분리 부품의 분리 모듈(`ModuleDecouplerBase`)이 기본으로 스테이징이 꺼져 있으면(예: 방열판 `HeatShield1`), craft에 그 MODULE 노드(`name`, `isEnabled`, `stagingEnabled = True`)를 씁니다. 이전에는 게임이 그 단계를 빈 단계로 없애고 위 단계 번호를 당겨, 방열판을 분리할 수 없었고 비행 기록의 Δv 대조도 어긋났습니다.
- App: 일부 클라이언트가 `design`을 JSON 문자열로 넘겨 "'root' must be an object"가 나던 결함도 함께 고쳤습니다. 문자열이면 파싱해서 보냅니다.

## E. MCP 도구 (App)
| 묶음 | 도구 |
|---|---|
| A | `get_career`, `list_contracts(state?)`, `accept_contract(id)`, `decline_contract(id)` |
| B | `get_science`, `run_experiment(id)`, `discard_science(id)` |
| C | `list_craft(facility?)`, `list_crew`, `launch_craft(craft, facility, site, crew?)`, `recover_vessel`, `revert_to_launch` |
| D | `set_attitude(mode, pitch, heading, roll?)`, `release_attitude`, `wait_until(field, op, value, timeout)`, `get_stages` |
| G | `list_parts(category?, unlockedOnly?)`, `build_craft(name, facility, design, dryRun, overwrite)` — `design`은 위 설계도 JSON 객체 |

- 되돌릴 수 없는 도구(`decline_contract`, `discard_science`, `launch_craft`, `recover_vessel`, `revert_to_launch`)는 `Destructive = true`
- `KspBridgeClient.SendAsync`에 요청별 타임아웃 인자 추가, `HttpClient.Timeout`은 무한으로 두고 요청마다 `CancellationTokenSource`
