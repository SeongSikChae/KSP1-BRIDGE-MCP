# KspBridge 비행 기록·예측 대조 — 설계

방안: [0024-비행기록-방안.md](0024-비행기록-방안.md)

## 구성
- 로직 DLL에 `Flight/FlightRecorder.cs`(기록·대조)와 `Handlers/FlightLogHandler.cs`(조회)를 새로 만듭니다. 배포는 `reload_mod`로 합니다. 로더는 바꾸지 않습니다.
- App에 `FlightLogTools.cs`(`list_flights`, `get_flight_log`)를 새로 만들고 `Program.cs`에 등록합니다. 적용하려면 Claude를 재시작해야 합니다.
- 기존 코드에서 고칠 곳:
  - `BridgeLogic`: Start에서 Hook, FixedUpdate에서 호출, Stop에서 닫기
  - `TriggerManager.Run`: 트리거 실행 이벤트
  - `SasMonitor.Record`: SAS 이벤트 전달
  - `LaunchHandler` revert: 결과 `reverted`
  - `Routes`: 라우트 2개 추가, 버전 0.9.0

## 파일
- 경로: `saves/<세이브>/KspBridge/flights/<id>.jsonl`.
  - `<id>` = `<발사 UT 정수>-<vessel.persistentId>`. 같은 기체의 같은 비행이면 이어서 씁니다(reload, 씬 재진입).
  - 기체 이름은 파일 이름에 넣지 않습니다. 한글과 특수문자 경로 문제를 피하기 위해서입니다.
- 줄 형식은 JSON 한 줄씩이며 `t` 필드로 종류를 구분합니다. JSON 쓰기는 기존 로더 `Json`을 씁니다.
  - `{"t":"start","reason":"launch|resume","ut","met","vessel","craft","crew":[{name,trait,level}],"site","stages":[{stage,dv_actual,dv_vac,twr_actual}],"logic":"0.9.0"}`
  - `{"t":"s", ...샘플}`: 필드 이름은 짧게 씁니다(아래 표).
  - `{"t":"e","ut","met","type", ...}`: 이벤트입니다.
  - `{"t":"end","ut","met","reason", ...요약}`: 비행 끝에 한 번 씁니다. reload 또는 씬 이탈 뒤 이어 쓰면 `end`가 여러 개일 수 있고, 조회는 마지막 `end`를 씁니다.
- 쓰기:
  - `StreamWriter`(UTF-8, 이어 쓰기)를 씁니다.
  - 버퍼는 2초마다 비웁니다. 이벤트와 `end`는 즉시 비웁니다.
  - 쓰기 실패는 한 번만 로그를 남기고 기록을 끕니다. 비행 제어에는 영향을 주지 않습니다.

## 샘플 (`t:"s"`)
| 키 | 내용 |
|---|---|
| ut, met | 시간 |
| alt, agl | 고도 ASL, 지면 기준(바다 위는 해수면 기준, Prediction과 같은 기준) |
| vz, vh, vs | 수직, 수평, 지면 기준 속도 |
| pitch, hdg, roll, tilt | 자세, tilt = 기체 축과 지면 법선 사이 각도 |
| m | 질량 t |
| thr | 스로틀 |
| f, f_pred | 실제 추력 합(`finalThrust`), 예측 추력(`ThrustKn` × 스로틀) kN |
| acc | 측정 가속도(`v.perturbation` 크기) |
| stop, margin | 예측 `stop_distance`, `burn_margin`(하강 중일 때만) |
| sas | 실제 SAS 모드(꺼짐이면 null), steer = steering |
| g | g_force |
| stage | 현재 단계 |

- 간격: 기본 0.5초. 스로틀이 0보다 크고 `agl` < 1,000 m이면 0.1초.
- 레일 워프 중(packed)에는 10초마다 기록하고 추력·예측 필드는 뺍니다.

## 이벤트 (`t:"e"`, type)
| type | 시점, 내용 |
|---|---|
| stage | 단계 변경(`onStageActivate`): 새 단계 번호 |
| trigger | 트리거 실행: id, name, field, value, actions |
| control | 스로틀(0.05 이상 변화), SAS 모드·on/off, 자세 유지 시작·해제. 매 틱 상태를 비교해 감지합니다. 사람 조작도 같이 잡힙니다 |
| sas | SasMonitor 이벤트(mode_lost/steering_lost/reapplied)를 그대로 전달 |
| situation | 상황 변화(`onVesselSituationChange`): from, to. LANDED·SPLASHED가 되면 그 틱의 vz·vh·tilt를 함께 기록 |
| impact | `onCrash`, `onCrashSplashdown`, 부품 파괴(`onPartDie`, 이 기체): 부품 이름, 그 틱의 vz·vh·tilt |
| crew | 승무원 기절·회복(`inactive` 변화), 사망(`onCrewKilled`) |
| warp | 워프 배율 변경 |

## 요약 (`t:"end"`)
- `reason`: recovered, destroyed(활성 기체 파괴, `onVesselWillDestroy`), reverted, switched(기체 전환), scene_exit, reload, unknown
- 비행 요약:
  - `max_alt`, `max_g`, `max_vs`
  - `parts_lost`(개수), `crew_lost`(이름)
  - `touchdown`: 마지막 LANDED·SPLASHED 또는 impact 시점의 vz, vh, tilt, 결과
- `dv_used`: 단계별로 실제 사용한 Δv입니다. 엔진이 켜진 매 물리 틱마다 ∫ f/m dt를 누적합니다. `start.stages`의 `dv_actual`과 나란히 둡니다.
- `checks[]`: 예측 대조(아래)

## 예측 대조
1. **감속 (`brake`)**
   - 시작: 하강 중(vz < −1)에 스로틀이 0.05 미만에서 0.5 이상으로 오를 때입니다. 그 틱의 `stop`(예측 거리), `agl`, `vz`, `f_pred`를 기록합니다.
   - 끝은 다음 중 먼저 오는 것입니다.
     - vz ≥ 0
     - 스로틀 < 0.05
     - LANDED, SPLASHED, impact
     - 60초 경과
   - 결과 항목:
     - `pred_dist`, `actual_dist`(시작 agl − 끝 agl), `ratio`(실제/예측)
     - `end_vz`(끝 속도. 0 미만이면 지면까지 다 못 멈춘 것)
     - `mean_tilt`, `mean_f_ratio`(실제/예측 추력 평균), `mean_thr`
   - 스로틀이 1보다 작으면 예측(전 추력)과 조건이 달라집니다. 이때는 `mean_thr`로 구분할 수 있게 남깁니다.
2. **추력 (`thrust`)**: 엔진이 켜진 샘플에서 f/f_pred 비율의 평균, 최솟값, 최댓값, 샘플 수를 기록합니다.
3. **Δv (`dv`)**: 다 쓴(연소가 끝난) 단계마다 dv_used와 dv_actual의 비율을 기록합니다.

## API
- `GET /api/flights?vessel=<이름 일부>&limit=20`: 최신 순서입니다.
  - 각 항목: `id`, `vessel`, `craft`, `start_ut`, `recording`(지금 기록 중), `reason`, `max_alt`, `touchdown`, `checks`, 샘플 수, 파일 크기
  - `end`가 없으면 `reason: "incomplete"`입니다.
- `GET /api/flights/<id>/log?from_met=&to_met=&around=<이벤트 type>&window=10&step=&types=s,e`
  - `around`가 있으면 그 type 이벤트마다 ±window초 구간을 줍니다(구간 여러 개).
  - `step`(초)은 샘플 간격을 줄입니다. 이벤트는 항상 다 줍니다.
  - 샘플이 400개를 넘으면 step을 자동으로 키우고 응답에 `downsampled_step`을 넣습니다.
  - start와 end 줄은 항상 포함합니다.
- 파일 읽기는 메인 스레드 디스패처 안에서 합니다. 크기가 수 MB 이하라 문제없다고 봅니다.

## MCP (App)
- `list_flights(vessel?, limit=20)` → GET /api/flights
- `get_flight_log(id, from_met?, to_met?, around?, window=10, step?, types?)` → GET /api/flights/{id}/log
- 설명에 필드 표의 키 이름을 짧게 넣습니다(s/e/start/end, vz·vh·tilt·stop·margin 등).

## 수명 주기
- 시작: 비행 씬에서 활성 기체가 정해질 때입니다(Start, `onVesselChange`, `onFlightReady`).
  - PRELAUNCH이고 MET 0이면 `launch`, 그 밖에는 `resume`입니다. 같은 id 파일이 있으면 이어 씁니다.
  - EVA 커벌은 기록하지 않습니다. 탐사선(무인)은 기록합니다.
- 닫기: 회수(`onVesselRecovered`), 파괴, revert, 기체 전환, 씬 이탈(`onGameSceneLoadRequested`), Stop(reload)일 때 `end`를 씁니다.
- revert: 우리 `revert_to_launch`에서 먼저 `reverted`로 닫습니다. 화면 메뉴로 되돌린 경우를 잡는 스톡 이벤트 이름은 개발 단계에서 디컴파일로 확인합니다. 못 잡으면 `scene_exit`로 남깁니다.
- 되돌린 뒤의 새 비행은 발사 UT가 달라 새 파일이 됩니다. 실패 비행 기록이 남습니다.

## 저장소 스킬 반영 (구현 후, 사용자 확인 뒤 등록)
`ksp-flight-preflight`에 단계 하나를 추가합니다: 같은 기체로 비행한 기록이 있으면 `list_flights(vessel)`의 `checks.brake.ratio`, `touchdown`, `dv`를 보고 감속 시작 여유와 Δv 여유를 정합니다.

## 개발 (작업 단위)
1. S1 기록기: 파일, start/s/end, 간격, 수명 주기, 이벤트 감지(상태 비교와 GameEvents)
2. S2 대조: brake, thrust, dv 계산과 요약
3. S3 조회 API와 라우트(버전 0.9.0)
4. S4 App 도구와 단위 테스트(요청 변환)
5. S5 게임 확인: 짧은 비행(낙하산 착지) → list_flights, get_flight_log(around=situation), checks 확인

## 구현 중 변경 (2026-11-08)
- 시작 이유에 `attach`를 추가했습니다(PRELAUNCH가 아닌 기체를 새로 기록할 때). 발사 시점 Δv가 아직 계산되지 않았으면 start의 `stages`는 null이고, 계산되면 `stages` 이벤트로 남깁니다.
- 화면 메뉴로 되돌리기: `GameEvents.OnRevertToLaunchFlightState` / `OnRevertToPrelaunchFlightState`(FlightDriver 디컴파일로 확인) → `reverted`. 화면 버튼 회수: `OnVesselRecoveryRequested` → `recovered`. 비행 장면이 닫힌 뒤 `onVesselRecovered`가 오면 마지막 파일에 `recovered` end를 덧붙입니다.
- 파괴 뒤 남은 잔해(Debris)와 EVA는 새로 기록하지 않습니다.
- 독립 검토 반영(0.9.0)
  - [High] 되돌리면 UT와 persistentId가 복원되어 새 비행이 옛 파일에 덧붙던 문제를 고쳤습니다. 새 파일 id가 이미 있으면 UT 키를 1씩 올립니다.
  - [Medium] 기록 중 어떤 예외가 나도 기록을 끕니다(매 틱 로그 폭주 방지).
  - [Medium] 잘린 줄(KSP 크래시)은 건너뜁니다. 조회 응답에 `skipped_lines`를 넣었고, 마지막 end 찾기도 계속 거슬러 올라갑니다.
  - [Low] 예측은 샘플을 쓰는 틱과 감속 판정에만 계산합니다. 감속 시작 조건은 "스로틀이 꺼졌다가(< 0.05) 처음 0.5 이상"으로 바꿨습니다(서서히 올려도 잡힘). 시작 스로틀 `start_thr`도 남깁니다(예측은 전 추력·수직 가정).
  - 알려진 제약(수정 안 함): 로그 조회는 파일 전체를 메인 스레드에서 읽습니다. 긴 비행에서는 조회 순간 프레임이 끊길 수 있습니다.
- 게임 데이터로 발견해 수정(0.9.1):
  - Δv를 현재 단계 번호 대신 **엔진이 속한 단계**(`part.inverseStage`)로 집계합니다. 낙하산 단계 이후에도 Swivel이 타면 단계 0으로 잡히던 문제입니다. dv 대조는 비행 끝에 단계별로 한 번 계산하며 `done` 필드는 없앴습니다.
  - 스로틀이 바뀐 뒤 5틱 동안은 추력 비율과 감속의 평균 추력 비율에서 뺍니다(추력이 한 틱 늦게 따라와 비율 0이 섞임).
- 수정(0.9.4): 0.9.1의 엔진 단계 집계도 틀렸습니다. KSP는 분리 뒤 남은 부품의 `inverseStage`를 다시 매깁니다. 그래서 비행 `24769-1422278655`에서 스위블 Δv가 단계 3·1·0으로 나뉘었습니다(합 약 1,336 m/s). 이제는 엔진마다(`flightID`) 기록을 시작할 때, 또는 처음 본 때의 단계 번호를 고정해 씁니다. 이 번호는 발사대 `get_stages`와 같습니다. 제약: 분리 뒤 reload나 장면 재진입으로 resume하면 그때의 번호를 다시 씁니다.
- 게임 확인(2026-11-08, 비행 `23167-1065206691`):
  - 기록 흐름: start(launch) → end(reload) → start(resume) → end(recovered)
  - 착지 contact: vz −4.95, vh 0.4, tilt 7.1
  - SAS 이벤트: mode_lost(mode_unavailable), reapplied
  - checks.brake(전 추력, 수직): 예측 1,825 m / 실제 1,756 m, 비율 0.96, mean_f_ratio 1.0
  - 부분 스로틀(0.6) 구간은 비율 4.3입니다. 예측이 전 추력을 가정하므로 `start_thr`로 걸러 읽어야 합니다.
- 수정(0.9.6): 게임은 비행 시작 직후, Δv 첫 계산 전에 빈 단계를 없애며 단계 번호를 당길 수 있습니다. 비행 `25915-1377496221`에서는 스테이징이 꺼진 방열판 단계 때문에 엔진 단계가 기록기는 6·4·2, 게임 Δv 표는 5·3·1이었습니다. 그래서 스위블 2,331 m/s가 릴라이언트 잔여 150 m/s와 대조됐습니다. 이제 Δv 표를 처음 받을 때 아직 분사 기록이 없으면 엔진 단계를 그 시점 번호로 다시 고정합니다.
- 확인: reload 두 번 → 첫 파일에 `start(launch)` → `end(reload)` → `start(resume)` 순서로 이어 씀(HTTP 조회)
