# 가속 허용 조건 개발 계획

이슈 #2(비행제어) 단위 9 `Warp`의 결함 수정. 단위 10 `circularize` 실측에서 발견했다. 사용자 지시("고치고 나서 B D")로 방안·설계를 건너뛰고 개발 계획부터 잡는다.

## 증상

동력 단계(`gravity_turn`, 스로틀 1 `attitude`)가 끝난 직후 첫 틱에 `circularize` 대기가 `WarpToUt`를 내면 다음 순서로 진행된다.

1. `Warp.Request`가 `WarpTo`를 호출한다.
2. KSP가 `Warping to UT:…. Max Rate Allowed: 1.0x.`를 찍고, 0.03초 뒤 `Real-time resumed … (Undershot)`로 끝낸다.
3. `Warp.Sync`가 이것을 "우리 Stop 없이 끝남"으로 보고 사용자 취소로 래치한다. 그래서 그 단계 동안 가속을 다시 요청하지 않는다.

2026-11-12 기체 A에서 두 번 재현했다.

| 단계 시작 ut | 고도 | `TgtUT Error`(남은 시간) |
| --- | --- | --- |
| 167 | 70 km | −36.0초 |
| 300 | 80 km | −1140.6초 |

## 원인 (디컴파일, Assembly-CSharp `TimeWarp`·`Vessel`)

- `TimeWarp.Update`: `setAutoWarp`이면 `getMaxWarpRateForTravel(warpToUT − now, warpToMaxWarping(8), warpToMinWarping(2.5), out rateIdx)` → `setRate(min(current + 1, rateIdx))` → `autoWarpTo` 코루틴을 시작한다. 로그의 "Max Rate Allowed"는 그 시점의 `tgt_rate`다(첫 단계라 최대 5x, 올리지 못하면 1x).
- `autoWarpTo`: `WaitForFixedUpdate` 뒤 `current_rate_index < rateIdx`이면 `getMaxOnRailsRateIdx(rateIdx, lookAhead: true)`로 한 번 더 올려 본다. 그래도 `current_rate_index`가 0이면 루프를 빠져나가 끝난다.
- 그래서 다음 두 판정 중 하나라도 0이면 `WarpTo`는 즉시 끝난다.
  1. **레일 판정** `getMaxOnRailsRateIdx`: 다음 경우 0을 돌려준다(이유는 `ClearToSaveStatus`).
     - 대기 안(`NOT_IN_ATMOSPHERE`)
     - 가속 중 `activeVessel.geeForce > GThreshold(0.1)`(`NOT_UNDER_ACCELERATION`). 비착지일 때만 본다.
     - 고도 제한(`NOT_WHILE_ABOUT_TO_CRASH`). lookAhead로 대기 진입이나 저고도 Pe를 예측했을 때도 같은 사유로 0이 된다.
     - 지표 이동(`NOT_WHILE_MOVING_OVER_SURFACE`)
     - 사다리 위 EVA
     - 궤도 전이 임박(`ORBIT_EVENT_IMMINENT`)은 배율을 3으로 제한할 뿐 0으로 만들지 않는다.
  2. **이동 시간 판정** `getMaxWarpRateForTravel(Δ, 8, 2.5)`: 기본 배율(1, 5, 10, …)에서 Δ가 약 12.5초 이하이면 `rateIdx` = 0이다.
- `Vessel.geeForce`는 최근 20 물리 틱 가속도 평균에서 중력 가속도를 뺀 크기(g)다. 엔진을 끈 뒤 최대 20틱(0.4초) 동안 0.1 g를 넘는다. 이번 두 재현은 남은 시간이 길었으므로(표) 이동 시간 판정이 아니라 레일 판정(가속 중)이다.
- 우리 `Request`의 허용 조건(대기권 밖, 스로틀 0, 추력 0, 스테이징 대기 아님)과 15초 경계는 두 판정을 모두 막지 못한다.
  - 엔진을 끈 직후 틱에서 요청한다(가속 중).
  - 남은 시간이 15~22.5초인 틱에서 첫 요청이 나간다(`WarpTo(target − 10)`의 Δ가 5~12.5초).
  - 그래서 KSP가 받지 않을 `WarpTo`를 보내고, KSP가 스스로 끝낸 것을 사용자 취소로 잘못 읽는다.

## 방안

KSP 조건을 복제하지 않고, `WarpTo`가 쓰는 **KSP 판정 두 개를 리플렉션으로 직접 호출**한다. 둘 다 0보다 클 때만 요청한다. 기존 `SetMode`(`setMode`) 리플렉션과 같은 방식이다. 조건을 복제하면 착지 상태(KSP는 비착지일 때만 `geeForce`를 본다)나 고도 제한처럼 새는 곳이 계속 생긴다.

- 판정은 요청 전(`_requested`가 거짓)에만 한다. 거부되면 요청하지 않고 다음 틱에 다시 판정한다. 가속 중·이동 시간 부족은 시간이 지나면 풀리고, 고도 제한처럼 계속되는 거부는 가속 없이 대기한다. 어느 쪽이든 요청 시점의 오래치는 없다.
- 이동 시간 판정은 1초 여유를 두고 `targetUt − 10 − 1`로 한다. 우리 판정(물리 틱)과 KSP 판정(다음 `Update`) 사이에 Δ가 12.5초 경계를 넘어가는 경합을 막기 위해서다.
- 판정은 player_warp 검사 뒤에 둔다. 이 등가성은 `current_rate_index == 0`일 때만 성립하고, 그 조건을 player_warp 검사가 보장한다. 그래야 `getMaxOnRailsRateIdx(1, true)` > 0이 `WarpTo`의 첫 `setRate(1)` 성공과 같아진다.
- 거부 사유는 바뀔 때만 `Debug.Log`로 남긴다. 이벤트·도구 설명(`warp_unavailable` reason 목록)은 바꾸지 않는다.
- 메서드를 찾지 못하면 기존 사유 `not_supported`로 `Unavailable`을 낸다.
- 래치(`Sync`)는 바꾸지 않는다. 이 수정으로 **요청 직후** KSP가 스스로 끝내는 경우는 없어진다.
- **범위 밖**: 가속이 이미 걸린 **도중**에 KSP가 배율을 0으로 내려 스스로 끝내는 경우(고도 제한, lookAhead의 대기·저고도 Pe 예측)는 남는다. 이때도 래치가 걸린다. 근거는 `FixedUpdate`가 매 틱 `setRate(current, instantIfLower)`를 하는 것이다. 이 경로는 이번 변경 전부터 있었고 원궤도화·상승 시나리오에는 해당하지 않는다. 필요하면 별도 과제로 다룬다.
- 기존 허용 조건(대기권, 스로틀, 추력, 스테이징)과 15초·`target − 10` 경계는 그대로 둔다.

## 작업 단위

### 1. `Warp.Request`에 KSP 판정 호출

- **대상**: `src/KspBridge.Logic/Flight/Warp.cs`(`Request`, 새 private `KspRefusal`), `src/KspBridge.Logic/Routes.cs`(Version 0.2.12)
- **코드 초안**:

```csharp
// TimeWarp private judges WarpTo uses (looked up by parameter types, null checked at use)
private static readonly MethodInfo RailsRateMethod = typeof(TimeWarp).GetMethod("getMaxOnRailsRateIdx",
    BindingFlags.Instance | BindingFlags.NonPublic, null,
    new[] { typeof(int), typeof(bool), typeof(ClearToSaveStatus).MakeByRefType() }, null);
private static readonly MethodInfo TravelRateMethod = typeof(TimeWarp).GetMethod("getMaxWarpRateForTravel",
    BindingFlags.Instance | BindingFlags.NonPublic, null,
    new[] { typeof(double), typeof(double), typeof(double), typeof(int).MakeByRefType() }, null);

/// <summary>Why KSP would end a WarpTo(warpUt) at once (rate index stays 0), or null when it would warp.</summary>
private static string KspRefusal(TimeWarp w, double warpUt)
{
    object[] travel = { warpUt - Planetarium.GetUniversalTime() - 1, 8.0, 2.5, 0 };   // as TimeWarp.Update passes WarpTo's defaults; 1 s margin
    TravelRateMethod.Invoke(w, travel);
    if ((int)travel[3] <= 0) return "too_close";
    object[] rails = { 1, true, ClearToSaveStatus.CLEAR };
    if ((int)RailsRateMethod.Invoke(w, rails) <= 0) return rails[2].ToString();
    return null;
}

// Request: after the existing allowed / 15 s check and the player-warp check
if (RailsRateMethod == null || TravelRateMethod == null || AutoWarpEngagedField == null) { Unavailable("not_supported"); return; }
string refusal = KspRefusal(TimeWarp.fetch, targetUt - 10);
if (refusal != _refusal) { _refusal = refusal; if (refusal != null) Debug.Log("[KspBridge] warp waits: KSP refuses (" + refusal + ")"); }
if (refusal != null) return;                     // nothing requested yet (the _requested path returned above)
// ... existing SetMode + WarpTo(targetUt - 10)
```

- 거부 판정은 요청 전(`_requested`가 거짓)에만 한다. 우리 가속이 걸린 뒤에는 KSP가 자체로 배율을 관리하므로 다시 판정하지 않는다. 레일 위에서는 `geeForce`가 0으로 고정된다(`packed`이면 매 틱 0을 씀). 레일에서 내려온 첫 틱의 튐은 KSP의 `ignoreGeeforceFrames`가 막는다.
- `_refusal`은 로그 중복 방지용이다. `ClearLatch`(단계 변경·새 계획)에서 null로 되돌린다.
- **검증**:
  - 빌드 성공, App 테스트 통과(도구 변화 없음).
  - 게임(기체 A 재발사): `gravity_turn` → `circularize`
    - 핵심 판정: `warp_started` 이후 `warp ended without our Stop`이 없다.
    - 단계 시작 직후 `warp waits: KSP refuses (NOT_UNDER_ACCELERATION)` 로그가 남을 수 있다. 엔진을 끈 지 20틱이 넘은 뒤 단계가 바뀌면 남지 않는다. 남으면 기록한다.
    - `get_flight` `time_warp.rate` > 1이 관찰된다.
    - 목표 15~10초 전에 우리 `Stop`으로 `warp_stopped`가 나고, 이어서 연소해 `plan_completed`.
    - 첫 요청까지의 지연(이벤트 `ut` − 단계 시작 `ut`)을 기록한다. 기대값은 정하지 않는다.
  - 이동 시간 판정: 남은 시간이 15~23.5초(1초 여유 포함)인 틱에서 요청하지 않음(`too_close` 로그). `coast`를 `until step_time >= 20`으로 제출해 확인한다(원궤도에서는 `time_to_apoapsis`가 불안정).
