# 디버그도구 설계

방안: [0018-디버그도구-방안](0018-디버그도구-방안.md)

## 구조

- **Logic**(`KspBridge.Logic`)에 디버그 상태와 주입 훅, HTTP 라우트를 둔다. 로더(`KspBridge.Mod`)는 바꾸지 않는다(방안 비범위).
- **App.Tools**(`KspBridge.App.Tools`)에 기능별 MCP 도구를 둔다. 기존 도구처럼 `[McpServerToolType]` 클래스의 `[McpServerTool]` 메서드가 `KspBridgeClient.SendAsync`로 Logic 라우트를 부른다. 도구 목록은 `ToolHost.CreateTools`가 리플렉션으로 찾으므로 별도 등록은 없다.
- 오류는 기존 `ApiException(status, code, message)` → `{"ok":false,"error":{code,message}}` → 도구 결과 `error: code: message` 경로를 그대로 쓴다.

## 결정 (사용자 합의)

### 1. 설정: Logic이 별도 `debug.cfg`를 직접 읽음

- 로더 `Settings`(`KspBridge.Mod/Settings.cs`)는 로더 DLL에 있어 키를 추가하면 로더 변경이 된다. 또 빌드(`KspBridge.Mod.csproj` `DeployToKsp`)가 `settings.cfg`를 매번 덮어쓴다.
- 그래서 Logic이 `BridgeLogic.StartCore`에서 빌드가 배포하지 않는 `GameData/KspBridge/debug.cfg`를 `ConfigNode`로 읽는다.

```
KSPBRIDGE_DEBUG
{
	enabled = true
}
```

- `enabled`가 `true`일 때만 켜짐이다. 파일·노드·키가 없거나 해석할 수 없으면 꺼짐이다. 저장소에는 이 파일을 두지 않는다.
- 파일을 만들거나 지운 뒤 `reload_mod`로 반영된다. KSP 재시작은 필요 없다.

### 2. 도구 목록

| 도구 | 인수 | 동작 |
|---|---|---|
| `debug_stage_delay` | `seconds` (0 = 해제) | 스테이지 작동 확인을 N초 미룬다 |
| `debug_engine_stop` | `part_id` | 지정한 엔진을 비행 중 정지·flameout 상태로 만든다 |
| `debug_throttle_hold` | `part_id`, `throttle` (null = 해제) | 지정한 엔진의 `currentThrottle`을 매 물리 틱 고정한다 |
| `debug_add_part_timeout` | `on` | `add_part`의 Finish 단계를 504 timeout으로 만든다(결정 3) |
| `debug_input_lock` | `mask` (null = 해제) | 디버그 전용 id로 임의 mask 입력 잠금을 건다 |
| `debug_input_locks_error` | `on` | 입력 잠금 조회에 예외를 주입한다 |
| `debug_reload_fault` | `start_failures` 0~2, `handover_failures` 0~3 | 다음 `reload_mod` 한 번에 쓰이는 실패를 주입한다(방안 결정 3) |
| `debug_clear` | 없음 | 모든 디버그 상태를 해제한다 |

- 기능마다 설정과 해제를 같은 도구로 한다. 현재 상태는 `get_status.debug`로 본다.
- 플래그가 꺼져 있으면 모든 디버그 라우트는 `debug_disabled` 오류를 돌려준다.

### 3. `add_part` 504: Finish 대기 시간 단축

- 실제 경로는 부품을 만드는 Begin이 성공하고, 그 뒤 메인 스레드 호출이 기한(5초) 안에 선택되지 않아 `MainThreadDispatcher`가 504 `timeout`을 던지는 경우다(`PartPlacer.Add` → `catch (ApiException e) when (e.Code == "timeout")` → `DiscardLater`).
- `debug_add_part_timeout`이 켜져 있으면 `PartPlacer`가 Finish를 부를 때 `dispatcher.Invoke`의 대기 시간을 0으로 준다. Begin으로 부품은 생기고 Finish는 실행 전에 취소되어 실제 504 → `DiscardLater` 경로를 탄다.
- 루트 배치는 Begin이 `Pending`을 돌려주지 않아 Finish 단계가 없다. 부모에 붙이는 `add_part`에만 적용된다.
- `Enqueue`와 취소 사이에 메인 스레드가 작업을 먼저 집으면 Finish가 정상 실행된다(드묾, `MainThreadDispatcher.Invoke`). 그때는 다시 시도한다.
- 504로 남은 부품은 ship에 붙지 않아 `part_count`에 원래 포함되지 않는다. 정리 여부를 판정할 수 있게 `DiscardLater`가 정리 성공 때도 로그를 남긴다.
- 기각: 메인 스레드를 지정 시간 멈추는 방식은 더 실제에 가깝지만 `add_part` 호출과 타이밍을 맞춰야 하고 게임 전체가 멈춘다.

### 4. 엔진 정지·스로틀 고정

- `debug_engine_stop`에 `mode` 인수(`shutdown` | `flameout`)를 둔다. 도구 호출 때 한 번 적용한다.
  - `shutdown`: 엔진을 끈다(`EngineIgnited` false, 연료 있음). `AutoStager`의 "점화 엔진 소멸 → `ignite`" 경로(`PrevModeThrottle > 0 && !AnyOperational && NextStageHasEngine`)를 만든다.
  - `flameout`: 연료 고갈처럼 꺼진 상태로 만든다. `Spent`가 `flameout`만으로 참이라 연소 종료(`stage_burnout`) → 분리 경로를 탄다. 연료가 남은 엔진은 스스로 flameout을 풀 수 있어 결과가 흔들릴 수 있다.
  - 대상 모듈은 부품의 첫 `ModuleEngines`다. 다중 모드 엔진은 첫 모드만 다룬다.
- `debug_throttle_hold`는 엔진의 `currentThrottle` 값을 직접 고정한다. `KeptThrottleDown`이 `Coordinator.Tick` 안에서 값을 읽으므로 `BridgeLogic.FixedUpdate`의 `Coordinator.Tick` 앞에서 쓴다. 쓰기와 읽기가 같은 호출 안에서 연달아 일어나 엔진 모듈이 끼어들 수 없으므로 읽기는 항상 고정 값을 본다(읽기 지점 주입 대안은 두지 않는다).
- 2초 상한 경로의 조건: `IsParallel`은 남는 쪽 엔진 중 작동 가능(`IsOperational`)한 것이 하나라도 있으면 병렬로 보고 2초 대기를 건너뛴다(`AutoStager.cs` `IsParallel`, `if (!_parallel)`). `KeptThrottleDown`은 남는 쪽 엔진 중 점화된 것만 본다. 따라서 대상은 **남는 쪽에서 점화됐지만 작동 불가(flameout)인 엔진**이다(0006의 "다 쓴 쪽 제외, Ignited" 경우). 또 Separate 전에 `KeptHasEngine`(작동 가능한 엔진 또는 아직 쓰지 않은 스테이지의 미점화 연료 엔진)이 참이어야 하므로, 남는 쪽에 뒤 스테이지의 미점화 연료 엔진이 따로 있어야 한다. 없으면 `out_of_stages`로 끝난다.
- 그 엔진의 `currentThrottle`을 쓰면 다음 엔진 `FixedUpdate`의 응답 보간 시작값이 되어 실제 추력이 날 수 있으나, 대상이 flameout 엔진이라 추력은 나지 않는다.
- 고정 대상 부품이 사라지면 고정을 풀고 로그를 남긴다. 활성 기체가 잠깐 없는 틱은 건너뛰고 고정을 유지하며, 로그로 두 경우를 구분한다.

### 5. 상태와 훅 위치

- 상태: Logic에 정적 `DebugState` 클래스 하나를 둔다. 새 Logic 어셈블리는 새 정적 상태로 시작한다.
- 씬 전환 훅: KSP의 `EvtDelegate`는 `evt.Target.GetType()`을 읽어 정적 메서드면 예외를 던진다(`FlightScene.cs` 주석, 디컴파일 확인). 그래서 `FlightScene`·`FlightReset`처럼 인스턴스 핸들러 객체를 두고 정적 필드(`_hooked`)에 보관한다. 플래그가 켜져 있을 때만 Hook해 플래그 꺼짐 상태의 시작 경로를 바꾸지 않는다.

| 도구 | 훅 위치 |
|---|---|
| `debug_stage_delay` | `StageRequest`의 확인 판정(`v.currentStage < _stageBefore`)을 첫 송신 뒤 N초가 지날 때까지 보류하고(보류 중에는 재요청하지 않음), 만료 기한도 N초 늘린다 |
| `debug_engine_stop` | 도구 호출 때 지정 엔진에 한 번 Shutdown 또는 Flameout |
| `debug_throttle_hold` | `BridgeLogic.FixedUpdate`의 `Coordinator.Tick` 앞에서 매 틱 지정 엔진의 `currentThrottle`을 씀 |
| `debug_add_part_timeout` | `PartPlacer.Add`의 Finish `dispatcher.Invoke` 대기 시간을 0으로 |
| `debug_input_lock` | `InputLockManager.SetControlLock((ControlTypes)mask, "kspbridge_debug")`, 해제는 `RemoveControlLock("kspbridge_debug")`. mask 0도 허용한다(값 0인 잠금의 `controls: []` 출력 확인용, 0008). 해제는 `null` |
| `debug_input_locks_error` | `InputLocks.Describe` 첫 줄에서 예외 |
| `debug_reload_fault` | `Coordinator.Stop` 직렬화 단계와 `BridgeLogic.StartCore`(아래 6) |

### 6. 핸드오버 실패 주입(`debug_reload_fault`)

- `handover_failures`는 `Coordinator.Stop`의 직렬화를 차례로 실패시킨다.
  - 1: 전체 직렬화(`Handover.Capture`) 실패 → 이벤트만 담은 핸드오버(`CaptureEvents`)
  - 2: 이벤트 직렬화도 실패 → 최소 핸드오버(`{format, epoch, seq}`)
  - 3: 최소 핸드오버도 실패 → 핸드오버 null(핸드오버 없는 시작, 0017)
- `start_failures`는 남는 핸드오버(1·2단계 결과 포함)에 키 `debug_fault: {start_failures}`로 넣는다. `handover_failures`가 3이면 핸드오버가 없어 전달되지 않으므로, 라우트는 `start_failures ≥ 1`과 `handover_failures 3`의 조합을 `bad_request`로 거부한다.
- `handover_failures` 3단계 주입은 `Coordinator.Safe` 안에서 던지므로 KSP.log에 `flight release step failed`가 남는다(의도된 주입 로그).
- 소비형: `Coordinator.Stop`은 시작할 때 `StartFailures`·`HandoverFailures`를 지역 변수로 읽고 곧바로 0으로 되돌린다. 그래서 `BridgeLogic.Stop`의 해제 순서와 무관하고, 재시작된 이전 로직(같은 어셈블리, 같은 정적 상태)에 값이 남지 않는다.
- `BridgeLogic.StartCore`는 맨 앞(`Stopped = false` 전)에서 `debug_fault.start_failures`가 1 이상이면 1 줄인 값으로 `context.Handover`를 고쳐 쓴 뒤 예외를 던진다. 로더는 같은 문자열로 이전 로직을 재시작하므로 2면 이전 로직도 실패해 `DropHandover` 이중 실패 경로가 실행된다.
- Hook 전에 던지므로 Unhook 정리 경로는 타지 않는다. 고쳐 쓴 핸드오버는 이전 로직이 그대로 이어받는다.
- 핸드오버 파싱 예외는 잡고 그냥 돌아간다. 깨진 핸드오버는 지금처럼 `Handover.Parse`가 Incompatible로 다룬다(플래그 꺼짐 동작 보호). 이 확인은 플래그와 무관하게 하지만 `debug_fault` 키가 없으면 아무것도 하지 않는다.

### 7. 초기화와 표시

- 초기화 지점
  - `debug_clear`: 모든 상태를 해제한다.
  - Logic `Stop`: 디버그 입력 잠금을 해제한다. 새 Logic은 새 정적 상태로 시작하므로 나머지는 자연히 초기화된다(`reload_mod`).
  - 씬 전환(`GameEvents.onGameSceneLoadRequested`): reload 실패 주입을 포함해 모든 상태를 해제한다.
  - 엔진 정지는 게임 상태라 되돌리지 않는다.
- `get_status.debug`
  - 플래그가 꺼져 있으면 `null`.
  - 켜져 있으면 `{stage_delay_s, throttle_hold: {part_id, throttle} | null, add_part_timeout, input_lock: {id, mask} | null, input_locks_error, reload_fault: {start_failures, handover_failures}}`.
  - 중첩 값은 `Dictionary<string, object>`로 만든다(로더 Json은 익명 객체를 `ToString()` 문자열로 쓴다).
  - `BridgeLogic.Status`의 다른 필드처럼 try/catch로 격리한다.
- 새 도구는 `reload_app` 뒤에도 클라이언트를 재시작해야 목록에 나타날 수 있다(0006 개발 문서 공통 규칙).
