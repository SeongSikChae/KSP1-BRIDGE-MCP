# 궤도기동 방안

## 문제

비행 계획이 다루는 궤도 기동은 발사 뒤 원지점 원궤도화(`circularize`, src/KspBridge.Logic/Flight/Modes/CircularizeMode.cs)뿐이다. `set_sas`의 `maneuver` 모드로 기동 노드 방향을 잡을 수는 있지만, 기동 노드를 만들거나 실행하는 도구와 목표(target)를 지정하는 도구는 없다. 0004-비행제어-방안.md "추후 대상"에 궤도 기동 일반(임의 기동 노드 실행, 궤도 전이·랑데부)이 들어 있다.

## 목표

- 궤도에 있는 기체에서 MCP 도구만으로 기동 노드를 만들고 실행한다.
- 원지점·근지점·경사 변경, Hohmann 전이, Mun 전이를 기동 노드로 계산해 실행한다.
- 같은 궤도 계열의 두 기체를 랑데부시키고 도킹해 한 기체로 결합한다.
- 실행 Δv, 연소 시간, 결과 궤도, 최근접 거리, 도킹 결과를 MCP 응답(`get_flight`, `get_flight_events`)으로 확인할 수 있다.

## 결정 (사용자 합의)

### 1. 진행: 방안 하나, 단계별 구현

- #18의 방안·설계·개발 문서는 하나씩 둔다.
- 개발 단위는 기동 노드 → 궤도 변경·전이 → 랑데부 → 도킹 순으로 나누고, 단계마다 실측한 뒤 다음 단계로 간다.
- 기각
  - 하위 이슈·별도 방안 문서로 분할: 기동 노드 실행과 노드 계산이 모든 단계의 공통 기반이라 문서가 서로를 계속 참조한다.
  - 기동 노드만 먼저: 이후 단계의 요구(랑데부 보정, 도킹 접근)가 노드 실행 설계에 반영되지 않는다.

### 2. 기동 노드 실행: 비행 계획 Mode

- 기동 노드 실행은 비행 계획 step의 새 Mode(예: `execute_node`)로 둔다.
- `auto_stage`, 계획·step `abort`, `timeout_s`, 비행 이벤트 등 지금 비행 계획 구조(0005-비행제어-설계.md)를 그대로 쓴다.
- 기각: 별도 MCP 도구가 연소를 수행하는 방식. 비행 계획과 별개의 제어 경로가 생겨 Controller 소유·중단 처리가 둘로 나뉜다.

### 3. 궤도 변경: 노드 계산 도구 + 노드 실행 Mode

- 목표 궤도(원지점·근지점·원궤도 고도·경사, Hohmann 전이 등)를 받아 기동 노드를 계산·생성하는 MCP 도구를 둔다.
- 실행은 결정 2의 공통 노드 실행 Mode가 한다. 노드는 실행 전에 조회해 Δv·시각을 확인할 수 있다.
- 기각: 목표 궤도를 직접 받는 Mode가 계산과 연소를 함께 하는 방식. 실행 전 확인이 안 되고 기동 종류마다 연소 로직이 늘어난다.

### 4. 천체 전이: Mun 전이 포함

- Mun 전이(전이 노드 계산, SOI 전환 뒤 근지점 보정, 포획 연소)를 범위에 넣고 실측한다.
- #17에서 미룬 대기가 없는 천체 착륙 실측의 전제가 된다(0028-동력착륙-방안.md 결정 2).
- 전이 계산은 천체에 관계없이 공통 로직으로 만들고, 실측은 Mun만 한다.
- 기각
  - 별도 이슈로 분리: #17 Mun 착륙 실측이 계속 막힌다.
  - Mun 전용 계산(경사 0 가정): Minmus처럼 경사가 있는 천체를 나중에 다시 손봐야 한다.

### 5. 연소 중 스테이지 소진: auto_stage에 맡김

- 계획의 `auto_stage`가 켜져 있으면 지금 있는 소진 판정(src/KspBridge.Logic/Flight/AutoStager.cs)으로 분리하고 연소를 이어 간다. 연소 시간은 다단의 가용 추력·질량으로 계산한다.
- `auto_stage`가 꺼져 있으면 지금 있는 Coordinator의 추력 없음 대기·`no_thrust` 처리를 따른다.
- 기각: 현재 단 Δv 안에서만 실행하고 모자라면 멈춤. Mun 전이처럼 단을 넘는 연소를 계획 하나로 쓸 수 없다.

### 6. 노드 시각까지 대기: Mode가 자동 가속

- `circularize`처럼 Mode가 연소 시작 시각을 `WarpToUt`로 요청하고, 자세 정렬 여유를 두고 가속을 푼다.
- 기각: 가속 없이 실시간 대기. Mun 전이처럼 노드까지 오래 걸리는 기동마다 사용자가 가속을 따로 지정해야 한다.

### 7. 랑데부: 노드 계산 + 근접 Mode

- 위상 맞추기 전이와 최근접점 보정은 결정 3의 노드 계산 도구가 목표(target) 기준으로 계산한다.
- 최근접 시각의 상대 속도 상쇄와 근접 접근은 target 기준으로 매 틱 제어하는 비행 계획 Mode가 한다.
- 목표 기체·천체를 지정·조회하는 도구를 둔다.
- 기각
  - 랑데부 전체를 한 Mode로: 위상 맞추기부터 근접까지 중간 확인이 어렵고 실패 위치를 가르기 어렵다.
  - 노드만 제공: 근거리 상대 속도 상쇄는 노드 정밀도가 모자랄 수 있다.

### 8. 도킹: 도킹 Mode

- 비행 계획의 도킹 Mode가 자기 쪽 포트와 목표 포트를 받아, 포트 축 정렬 자세와 RCS 병진을 매 틱 제어하고 결합을 판정한다.
- 자기 쪽 포트 선택("Control from Here")과 목표 포트 지정도 이 이슈에서 다룬다.
- 기각: 포트 선택·target 지정 도구와 지금 있는 `rcs_translate`·`set_sas`를 에이전트가 조합하는 방식. 매 틱 폐루프가 없어 정밀도가 낮다.

### 9. 노드 저장: KSP 실제 기동 노드

- 노드 계산 도구는 `vessel.patchedConicSolver`의 KSP 기동 노드(`ManeuverNode`)를 만든다. 게임 화면·`set_sas`의 `maneuver` 모드와 노드를 공유하고, SOI 전환을 포함한 예측 궤도는 KSP patched conics 계산을 쓴다.
- 커리어 등에서 기동 노드를 만들 수 없는 상태(추적소 레벨 등)면 도구가 오류로 알린다.
- 기각: 브리지 자체 노드. 예측 궤도·SOI 전환을 직접 계산해야 하고 게임 화면과 어긋난다.

### 10. circularize: 기존 유지

- `circularize` Mode는 지금 동작 그대로 둔다. 연소 시간 계산(`EngineModel.BurnTime`) 등 공통 부분만 노드 실행 Mode와 같이 쓴다.
- 기각: circularize를 노드 계산 + 노드 실행으로 재구성. 발사 계획 동작이 바뀌어 기존 실측을 다시 해야 한다.

### 11. 실측용 두 기체: 연속 발사 + 기체 목록 조회

- 첫 기체를 궤도에 둔 채 조립동에서 두 번째 기체를 발사하고, 기체 목록 조회 도구로 첫 기체를 찾아 target으로 지정한다.
- 활성 기체 전환은 하지 않는다. 제어는 지금처럼 활성 기체 하나만 한다.
- 기각: 활성 기체 전환 도구 포함. 0004-비행제어-방안.md "추후 대상"의 여러 기체 제어와 겹친다.

### 12. 노드 실행 완료: 남은 Δv + 증가 감지

- `circularize`와 같은 방식으로, 남은 Δv가 허용치 이하이거나 마지막 구간에서 연소 방향을 고정한 뒤 남은 Δv가 다시 커지면 완료하고 노드를 지운다.
- 실행 Δv, 연소 시간, 남은 Δv, 결과 궤도를 이벤트로 남긴다.
- 기각: 결과 궤도 요소 기준 완료. 기동 종류마다 기준이 달라져 공통 실행 Mode가 기동 종류를 알아야 한다.

## 설계로 넘기는 항목

- 기동 노드 조회·생성·수정·삭제 도구의 인자(UT 또는 궤도 위치 기준, prograde/normal/radial Δv)와 응답 필드
- 노드 계산 도구의 기동 종류(원지점·근지점 변경, 원궤도화, 경사 변경, Hohmann, 위상 전이, 최근접 보정, Mun 전이·포획)와 계산식, 기동 노드 생성 불가 시 오류
- 노드 실행 Mode의 연소 시작 시각(다단 연소 시간, 엔진 spool-up), 자세 게이트, 방향 고정 Δv, 허용치 기본값, 노드가 없거나 지나간 경우 처리
- 근접 Mode의 상대 속도 상쇄·접근 속도 프로파일, 정지 거리, 완료 기준(거리·상대 속도)
- 도킹 Mode의 포트 선택 인자, 포트 크기 호환 확인, 축 정렬 오차·RCS 병진 제어, 접촉 속도, 결합(`ModuleDockingNode` 상태) 판정, 실패·이탈 시 재시도·중단
- target 지정·조회 도구와 기체 목록 도구의 응답 필드(기체 식별자, 궤도, 거리)
- 도킹 뒤 결합 기체의 `get_flight` 표시와 Controller가 쥔 기체 식별(`FlightScene`, `Handover`)의 관계
- Mun 전이에서 SOI 전환 뒤 보정·포획 연소 순서와 이벤트
- 결과 이벤트 필드(실행 Δv, 연소 시간, 결과 궤도, 최근접 거리, 도킹 결과)
