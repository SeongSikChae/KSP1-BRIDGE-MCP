# 분리동압 설계

방안: 0025-분리동압-방안.md (병렬 분리만 동압 조건으로 지연, 기준값·대기 상한은 `staging_options`, 기본값은 실측).

## 현재 흐름 (`AutoStager.Update`)

`none` → `BurnedOut` → `tailoff`(잔여 추력 대기) → `separate`. `separate` 진입 때 `_parallel = IsParallel(v)`(남는 쪽 `K_next`에 작동 엔진이 있으면 병렬). 직렬이면 스로틀 0(`Override`)과 남는 엔진 스로틀 하강을 2초까지 기다린 뒤, 병렬이면 바로 `StageRequest`를 만든다. 분리 뒤 병렬은 `ignite`(작동 엔진이 있어 곧바로 완료), 직렬은 `settle`.

## 결정

| # | 결정 | 근거 |
|---|---|---|
| 1 | 동압 대기는 `separate` 상태에서 요청을 만들기 직전(`_request == null`), 기존 `out_of_stages` 판정 뒤에 둔다. 조건: `_parallel`이고 `v.dynamicPressurekPa > max_separate_q`이고 대기를 시작한 뒤 `max_separate_q_wait_s`가 지나지 않음 → 이번 틱은 분리하지 않는다. 대기 시작 = 처음으로 이 조건(동압 초과)에 걸린 틱 | 분리 가능 여부(`out_of_stages`)를 먼저 정해야 분리하지 않을 기체를 기다리게 하지 않는다. 상태를 새로 두지 않아 `staging` 값(`"separate"`)·`Pending`·핸드오버 구조가 그대로다. 상한은 대기 시작 기준이다(검토 R1 지적 5) |
| 2 | 기다리는 동안 매 틱 `_parallel = IsParallel(v)`를 다시 구한다. 코어가 다 타 거짓이 되면 그 틱부터 기존 직렬 경로(스로틀 0 → 남는 엔진 스로틀 하강 대기 → 분리 → `settle` → `ignite`)로 간다. 이때 직렬 대기 2초는 그 시점부터 잰다(`_since`를 다시 기록). 직렬로 넘어간 뒤의 연쇄는 기존 직렬 분리와 같다: 다 탄 측면 부스터를 분리하고(분리 대상은 `J_next` 그대로), `settle`에서 분리된 기체와의 거리를 기다린 뒤, `ignite`에서 작동 엔진이 없으므로 다음 스테이지에 엔진이 있으면 그 스테이지를 작동시키고 없으면 `ignite_blocked`. 코어가 다 탄 상태라 다음 단 점화가 의도한 동작이다 | 방안 결정 3(코어가 먼저 다 타면 직렬 분리). 직렬 대기 기준 시각이 동압 대기로 이미 지나 있으면 스로틀이 내려가기 전에 분리될 수 있다. 연쇄를 적어 둔다(검토 R1 지적 4) |
| 3 | 대기를 시작한 틱에 `separation_held {stage, q_kpa}` 이벤트를 한 번 낸다. 동압이 내려가지 않은 채 대기가 끝나면 그 틱에 `separation_forced {stage, q_kpa, reason}`을 낸다(`reason`: `timeout` = 상한이 지나 동압과 관계없이 분리, `serial` = 결정 2의 코어 소진으로 직렬 전환). `staged {reason: separate}`에 그 분리 요청을 확인한 틱의 동압 `q_kpa`를 더한다(다른 `reason`의 `staged`는 그대로). `staging_completed`에 `held_s`(대기 시작부터 대기가 끝난 틱(분리 요청·상한·직렬 전환)까지, 대기 없으면 0)를 더한다. 직렬 전환 뒤의 스로틀 하강·settle 시간은 `held_s`에 넣지 않는다(구현 검토 R6-2-B-3·B-4, R6-3-B-1·B-4) | 계획을 보는 쪽이 지연 여부·시간·실제 분리 동압을 이벤트만으로 알 수 있다(검토 R1 지적 3). `tailoff_s`는 지금처럼 연소 종료부터 `separate` 진입까지라 대기 시간과 섞이지 않는다 |
| 4 | `staging_options.max_separate_q`(kPa): 범위 0~1000. `staging_options.max_separate_q_wait_s`(초): 범위 0~600. 두 기본값 모두 개발 단계 실측으로 정한다. 실측 전 구현에서는 `max_separate_q` 기본 1000(지연 없음, 지금 동작), `max_separate_q_wait_s` 기본 30(잠정)으로 둔다 | 0이면 늘 대기(상한까지), 크게 두면 지연 없음. 다 탄 부스터를 매단 채 동압이 내려가는 속도는 재지 않았으므로 대기 상한도 실측으로 정한다(검토 R1 지적 2·6) |
| 5 | 대기 상태는 기존 핸드오버의 `state`·`since`·`parallel`에 더해 `held_ut`(대기 시작 시각, 없으면 0)와 `held_s`(끝난 대기 길이)로 저장한다. `ResetSequence`에서 0 | `separation_held`가 reload 뒤 다시 나오지 않고 `held_s`를 이어서 잰다 |
| 6 | 동압 값은 KSP `Vessel.dynamicPressurekPa`(조건 변수 `dynamic_pressure`와 같은 값)를 쓴다 | 계획 조건과 같은 값이라 사용자가 같은 수치로 기준을 정할 수 있다 |

## 충돌 판정 기준 (실측·완료 판정 공통)

분리 뒤 "충돌 있음"은 `staged {reason: separate}`부터 그 시퀀스의 `staging_completed` 뒤 10초까지의 `part_collision` 중 `kind: part`이고 코어가 한쪽인 것으로 본다. 코어가 한쪽인 충돌 = `active: true`(코어 부품에서 기록)이거나, `active: false`(잔해 부품에서 기록)이면서 `other`가 버린 쪽 부품의 표시 이름이 아닌 것. TestB에서 버린 쪽 부품은 RT-10(`solidBooster.v2`)과 TT-38K(`radialDecoupler`)다. 표시 이름은 `get_part`의 `title`에서 가져온다(`get_part solidBooster.v2` → `RT-10 "해머" 고체연료 부스터`로, 2026-11-14 1회차 이벤트의 `other` 값과 같은 형식임을 확인했다. 검토 R4 지적 1). TT-38K가 버린 쪽에 붙어 가는 것은 1회차 이벤트(`part_lost radialDecoupler`의 `vessel`이 `TestB 잔해물`)로 확인했고, 기준선 비행에서도 버린 쪽 부품의 `vessel_id`가 활성 기체와 다른지 다시 확인한다(검토 R4 지적 2). 같은 시각의 `part_lost`는 그 충돌의 결과로 함께 기록한다. 지면 충돌(`kind: crash`·`splashdown`)과 잔해끼리의 충돌은 세지 않되, 측정 표에는 모든 `kind: part` 충돌의 `part`·`other`·`vessel_id`·`active`·`speed`를 남긴다(검토 R1 지적 1, R3 지적 1).

- `other`는 KSP `EventReport.other`로, 실측에서 부품 표시 이름(`"FL-T800 연료통"`)이었고 `part` 필드(`partInfo.name`, 예 `fuelTank.long`)와 형식이 다르다. 2026-11-14 2회차의 SRB-코어 충돌은 SRB 쪽(`active: false`)에서만 기록됐다. 그래서 `active`만으로 거르지 않고, 잔해 쪽 기록은 `other`가 버린 쪽 부품인지로 가른다(검토 R2 지적 1). 버린 쪽 부품의 표시 이름 목록은 분리된 부품 종류가 정해져 있어 짧고 확정적이다.
- 창을 `staging_completed` 뒤 10초까지 두는 것은 지연 분리에서 상대 감속이 작아 접촉이 늦어질 수 있어서다(검토 R2 지적 3).
- 측정은 이 기준이 지금 동작의 충돌을 실제로 잡는지 먼저 확인한다(`max_separate_q` 1000 기준선에서 충돌 있음이 나와야 한다).

## 영향

- `AutoStager`: `StagingOptions`(두 항목), `separate` 분기, `Staged`(separate일 때 `q_kpa`), `Completed`(`held_s`), `ResetSequence`·`Save`·`Load`(`held_ut`·`held_s`).
- 0005-비행제어-설계.md: `staging_options` 행·예시, 스테이징 상태 표의 `separate` 행, 이벤트 표(`separation_held`·`separation_forced`, `staged.q_kpa`, `staging_completed.held_s`).
- `submit_flight_plan` 도구 설명(`staging_options` 기본값 목록과 병렬 분리 설명), `get_flight_events` 도구 설명(이벤트 종류·필드), ReadMe 234·235줄.
- 한계(검토 R1 지적 2): 부스터가 다 탄 뒤에도 동압이 계속 오르는 기체(가속이 큰 코어로 저고도 비행)에서는 상한이 지나 강제 분리할 때의 동압이 지금(연소 종료 즉시 분리)보다 높을 수 있다. 이때 `separation_forced {q_kpa}`와 `staged {q_kpa}`에 그 동압이 남아 계획을 보는 쪽이 알 수 있다. 동압이 오르는 동안 분리를 앞당기는 처리는 하지 않는다(비범위).

## 검증

- 기준 동압 실측: TestB 같은 계획에서 `max_separate_q`를 1000(지연 없음, 기준선: 위 기준으로 충돌 있음이 나와야 측정을 이어 간다. 안 나오면 기준을 다시 정한다)과 40·35·30·25·20 kPa로 내려 가며 띄운다. 값마다 분리 동압(`staged.q_kpa`), 대기 시간(`staging_completed.held_s`), `separation_forced` 유무, 위 기준의 충돌 유무를 기록한다. 충돌이 없는 가장 높은 값을 2회 더 띄워 재현을 확인한다. 기본값 = 재현까지 충돌이 없는 가장 높은 값 − 5 kPa(측정 간격 하나). X = 재현까지 충돌이 없는 가장 높은 측정값. 대기 상한 기본값 = 기본값(X − 5)을 `max_separate_q_wait_s` 120으로 한 번 띄운 비행의 `held_s` × 2를 5초 단위로 올림(최소 30). 그 비행에서 충돌이 나면 기본값을 5 kPa 더 내려 같은 비행을 다시 하고(그 값도 2회 더 띄워 재현을 확인한 뒤 확정), 15 kPa 아래로 내려가야 하면 멈추고 사용자에게 묻는다(검토 R4 지적 3·4). 20 kPa까지 모두 충돌이 나면 측정을 멈추고 사용자에게 묻는다(검토 R1 지적 7).
- 지연 분리(기본값): `separation_held` → `staged {separate, q_kpa ≤ 기본값}` → `staging_completed {held_s > 0}`, `separation_forced` 없음, 위 기준의 충돌 없음, 계획 `plan_completed`.
- 상한: `max_separate_q_wait_s` 1(짧게)·`max_separate_q` 1로 `separation_held` → 1초 뒤 `separation_forced` → `staged {separate}`.
- 직렬 분리 회귀: TestD(직렬: Swivel → TD-12 → Terrier, 0006 기체 A는 1단이라 직렬 분리가 없다)로 `stage_burnout` → `separate` → `settle` → `ignite`가 지금과 같고 `separation_held`가 없다.
- 코어 소진으로 직렬 전환(결정 2의 연쇄)은 실측 재현이 어려워(코어가 SRB보다 먼저 다 타야 함) 코드 리뷰로 확인한다.
- App 테스트(`dotnet test tests/KspBridge.App.Tests`) 통과.
