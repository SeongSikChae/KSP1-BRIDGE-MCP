# 디버그도구 방안

## 문제

일부 경로는 MCP 도구로 상황을 만들 수 없어 게임에서 실측하지 못했다. 코드 리뷰로 대신했거나, 개발 중에만 쓰고 지운 임시 훅으로 확인했다. 지금 빌드에서는 다시 검증할 수 없다(#7).

1. **틱 단위 타이밍 창**: `on_start` 중복 방지, 확인 틱 전 중단 시 요청 기록 보존, 스테이지 작동 확인 대기 중 `reload_mod`(0006 단위 3·8·11)
2. **만들 수 없는 상태**: `add_part` 메인 스레드 504 뒤 생성 부품 정리(0003), 남은 엔진 `currentThrottle` 2초 상한·점화 엔진 소멸 뒤 `ignite`·`ignite_blocked` 래치(0006 단위 8), `input_locks_error`·이름 없는 비트 hex 출력(0008)
3. **로더·핸드오버 경로**: `DropHandover` 이중 실패(0016), 핸드오버를 잃은 뒤의 reload·직렬화 3단계 실패·로딩 화면 중 reload(0017)

## 목표

- 위 1·2·3의 각 경로를 화면·키 입력 없이 MCP 도구만으로 재현한다.
- 재현 결과(이벤트 순서·수치·로그)를 문서에 기록할 수 있다.
- 평소 동작에는 영향이 없고, 디버그 상태가 해제·reload 뒤 남지 않는다.

## 결정 (사용자 합의)

### 1. 활성 조건: 설정 플래그

- 빌드가 배포하지 않는 별도 파일 `GameData/KspBridge/debug.cfg`에 플래그가 켜져 있을 때만 Logic이 디버그 라우트를 연다. 파일이 없으면 꺼짐이다(기본).
- 꺼져 있으면 디버그 도구 호출은 `debug_disabled` 오류를 돌려준다.
- 빌드 구성(Debug/Release)과 무관하게, 빌드를 바꾸지 않고 켜고 끌 수 있다.
- 처음에는 `settings.cfg`의 `debug_tools` 키로 정했으나, 빌드(`DeployToKsp`)가 `settings.cfg`를 매번 덮어써 배포본에 넣은 플래그가 지워지므로 별도 파일로 바꿨다(0020 검토 지적).
- 기각: Debug 빌드 전용(`#if DEBUG`)은 지금 배포가 Debug 구성이라 평소에도 항상 켜진다. 플래그와 Debug 빌드를 함께 요구하는 방식은 보수적이지만 Release에서 검증할 수 없다.

### 2. 도구 형태: 기능별 도구

- 기능마다 MCP 도구를 따로 둔다(예: 스테이지 확인 지연, 엔진 강제 정지, 엔진 스로틀 고정, 오류·지연 주입, 입력 잠금, 로직 시작·핸드오버 실패 주입). 정확한 이름·인수는 설계에서 정한다.
- 인수가 기능별로 명확해지는 대신 도구 수가 늘어난다.
- 기각: `debug_inject {kind}`·`debug_clear` 두 도구로 묶는 방식은 도구 목록이 작지만 kind별 인수 검증과 설명이 한 도구에 몰린다.

### 3. reload를 거치는 실패 주입: 핸드오버로 1회 전달

- 로직 시작·핸드오버 실패 주입만 핸드오버 JSON에 실어 다음 로직에 넘긴다. 나머지 디버그 상태는 `reload_mod` 때 초기화한다(#7 규칙 유지).
- 이전 로직은 `Stop`에서 핸드오버에 시작 실패 횟수를 넣는다. 1이면 새 로직만, 2면 새 로직과 재시작한 이전 로직이 모두 실패한다.
- 로직 시작은 횟수가 남아 있으면 하나 줄인 값으로 `context.Handover`를 고쳐 쓴 뒤 예외를 던진다. 로더는 같은 문자열로 이전 로직을 재시작하므로 줄어든 횟수가 전달된다. 2면 `DropHandover` 이중 실패 경로가 실행된다.
- 한 번 쓰면 사라진다. 로더(`KspBridge.Mod`)는 바꾸지 않으므로 KSP 재시작이 필요 없다.
- 핸드오버 직렬화 실패도 이전 로직의 `Stop`에서 일어나므로 같은 방식(주입 후 다음 `reload_mod` 한 번에 적용)으로 다룬다.
- 기각: 모든 디버그 상태를 핸드오버로 유지하는 방식은 "reload 때 초기화" 규칙을 깨고, 해제를 잊으면 상태가 남는다. 로더에 주입 지점을 두는 방식은 로더 변경이라 KSP 재시작이 필요하다.
- 한계: KSP 기동 때 Logic 로드 실패는 핸드오버가 없어 이 방식으로 만들 수 없다. 같은 결과(핸드오버 없는 reload)는 횟수 2로 만든 이중 실패 뒤의 `reload_mod`로 확인한다.

### 4. 대상별 주입 방식

| 대상 경로 | 주입 방식 |
|---|---|
| 틱 단위 타이밍 창(문제 1) | **스테이지 확인 지연**: Logic의 `StageRequest` 작동 확인(`currentStage` 감소 확인)을 N초 미룬다. 개발 중 지운 임시 훅을 상설화한다. |
| 점화 엔진 소멸 뒤 `ignite`, `ignite_blocked` 래치 | **엔진 강제 정지**: 부품 `persistentId`로 지정한 엔진을 비행 중에 정지·flameout 상태로 만든다. |
| 남은 엔진 `currentThrottle` 2초 상한 | **엔진 스로틀 고정**: 지정한 엔진의 `currentThrottle`을 매 물리 틱 지정 값으로 고정한다. |
| `add_part` 504 뒤 정리 | **`add_part` timeout**: 504 `timeout`을 유발한다. 방식은 설계에서 "Finish 단계 대기 시간 0"으로 정했다(0019 결정 3, 메인 스레드 지연은 기각). |
| `input_locks_error`, 이름 없는 비트 | **입력 잠금**: 잠금 조회 예외를 주입하고, 디버그 전용 잠금 id 하나로 임의 mask 잠금을 설정·해제한다. |
| 로더·핸드오버(문제 3) | 결정 3의 시작·직렬화 실패 주입 |
| 로딩 화면 중 reload | 주입 도구 없이 검증 절차(씬 로딩 중 `reload_mod`)로 확인한다. |

도구 이름·인수·정확한 훅 위치는 설계에서 정한다.

### 5. 해제·초기화와 표시

- 모든 디버그 상태는 해제 도구, `reload_mod`, 씬 전환 때 원래대로 돌린다. 디버그 도구로 건 입력 잠금도 이때 해제한다.
- 엔진 강제 정지는 디버그 상태가 아니라 한 번 적용한 게임 상태이므로 되돌리지 않는다(0019 결정 7).
- 예외: 결정 3의 시작·직렬화 실패 주입은 다음 `reload_mod` 한 번에 쓰이고 사라진다. 그 전에 해제 도구나 씬 전환이 오면 다른 상태와 함께 해제된다.
- `get_status.debug`에 현재 걸린 디버그 상태를 보여 준다. 설정 플래그가 꺼져 있으면 `null`이다.
