# 기체전환 설계

이슈: [#19 비행 도구: 다른 기체로 전환](https://github.com/SeongSikChae/KSP1-BRIDGE-MCP/issues/19)
방안: [0034-기체전환-방안.md](0034-기체전환-방안.md)

## 게임 동작 (디컴파일, Assembly-CSharp)

- `FlightGlobals.SetActiveVessel(v)` = `setActiveVessel(v, force: false, clearDeadVessels: true)`, `ForceSetActiveVessel(v)` = `force: true`. 둘 다 `bool`을 돌려준다.
- `setActiveVessel` 순서
  1. `v == null` 또는 `v == activeVessel`이면 false
  2. `OnFlightGlobalsReady.Fire(false)`, `ready = false` (아래 검사에서 실패해도 되돌리지 않는다)
  3. `force == false`면 `ClearToSave()`가 CLEAR가 아닐 때, 또는 `v.DiscoveryInfo.Level != Owned`일 때 화면 메시지를 띄우고 false
  4. 이전 활성 기체 `MakeInactive`, `ClearStaging`
  5. `!v.loaded`면 `onVesselSwitchingToUnloaded` → `GamePersistence.SaveGame("persistent", ..., GameScenes.FLIGHT)` → `FlightDriver.StartAndFocusVessel(HighLogic.CurrentGame.Updated(), vessels.IndexOf(v))` → true (장면 재로드)
  6. `v.packed`면 모든 기체 `GoOnRails`
  7. `onVesselSwitching`, `activeVessel = v`, 기준 좌표계·카메라 갱신, `v.MakeActive()`, `onVesselChange` → true
- `ClearToSave()`는 활성 기체 기준이다. 결과는 다음과 같다.
  - DEAD면 CLEAR
  - EVA가 사다리에 매달려 있으면 `NOT_WHILE_ON_A_LADDER`
  - FLYING·SUB_ORBITAL이면서 지형 높이가 최소 저장 고도보다 낮으면 `NOT_WHILE_ABOUT_TO_CRASH`
  - FLYING이면 `NOT_IN_ATMOSPHERE`
  - 착륙·착수가 아니면서 0.1g를 넘으면 `NOT_UNDER_ACCELERATION`
  - 지상에서 0.3 m/s를 넘으면 `NOT_WHILE_MOVING_OVER_SURFACE`
  - 다른 기체의 EVA가 사다리에 매달려 있으면 `NOT_WHILE_ON_A_LADDER`
  - `setActiveVessel`의 switch에 있는 `NOT_WHILE_THROTTLED_UP`은 `ClearToSave(bool)` 본문에서 돌려주지 않는다.
- `FlightDriver.StartAndFocusVessel(Game|string save, int idx)`는 `FocusVesselAfterLoad = idx`, `StartupBehaviour = RESUME_SAVED_CACHE`(Game)를 설정한 뒤 `HighLogic.LoadScene(FLIGHT)`를 부른다.
- Tracking Station의 Fly는 `GamePersistence.SaveGame("persistent", HighLogic.SaveFolder, OVERWRITE)`를 부른 뒤 `FlightDriver.StartAndFocusVessel("persistent", FlightGlobals.Vessels.IndexOf(v))`를 부른다.

## 도구·API

| MCP 도구 | HTTP | 비고 |
|---|---|---|
| `list_vessels(include_debris)` | `GET api/vessels?include_debris=` | 기존. FLIGHT·SPACECENTER·TRACKSTATION에서 동작 |
| `switch_vessel(vessel_id)` | `POST api/flight/switch` 본문 `{vessel_id}` | 신규 |

### `list_vessels` 확장

- FLIGHT는 지금과 같다(`Guard.ActiveVessel` 통과 필요).
- SPACECENTER·TRACKSTATION에서는 활성 기체 없이 기체 목록을 읽는다. 행마다 `active`는 false, `distance`는 null이다. 나머지 필드는 같고, 거리가 없으므로 원래 순서를 유지한다.
- 목록과 `switch_vessel`의 대상 조회는 같은 함수 `VesselSwitch.Candidates()`를 쓴다. 원본은 `FlightGlobals.Vessels`다. SPACECENTER에서 이 목록이 비어 있다고 실측되면, 원본을 바꾸는 일(저장 상태 `protoVessels` 사용, `StartAndFocusVessel` 인덱스 기준 변경)은 설계 회귀로 처리하고 다시 검토한다.
- 다른 장면은 기존처럼 409(`not_in_flight`)다.

### `switch_vessel` 응답

- 성공 접수: `{accepted: true, vessel, id, path: "in_scene"|"reload", warp_lowered: bool}`
- 이미 활성 기체: `{accepted: true, vessel, id, already_active: true}`. `reset.switch`는 바로 `done`이다.

### 오류

사전 검사 순서대로 적는다. 모두 접수 전에 던지며, 실패하면 아무 상태도 바꾸지 않는다.

| 코드 | HTTP | 조건 |
|---|---|---|
| `bad_request` | 400 | `vessel_id`가 없거나 양의 정수가 아님 |
| `recovery_pending` | 409 | 회수 대기 중(`RequireNoPendingRecovery`) |
| `switch_pending` | 409 | 다른 전환이 진행 중 |
| `scene_loading` | 409 | 장면 로드 중(`RequireSceneReady`) |
| `no_game`·`not_supported` | 409 | `RequireStockGame("switch_vessel")` |
| `scene_not_allowed` | 409 | FLIGHT·SPACECENTER·TRACKSTATION 이외 장면 |
| `no_active_vessel` | 409 | FLIGHT에서 활성 기체가 없음(`Guard.ActiveVessel`) |
| `plan_running` | 409 | `Coordinator.Running` (`abort_flight` 먼저) |
| `vessel_not_found` | 404 | `Candidates()`에 그 persistentId가 없거나 DEAD |
| `not_switchable` | 409 | Flag·SpaceObject, 또는 `DiscoveryInfo.Level != Owned` |
| `switch_unavailable` | 409 | FLIGHT의 장면 재로드 경로에서 `ClearToSave(false) != CLEAR`. 메시지에 상태 이름 |

실행 단계 오류(사전 검사를 통과한 뒤)

| 코드 | HTTP | 조건 |
|---|---|---|
| `switch_refused` | 409 | `ForceSetActiveVessel`·`SetActiveVessel`이 false. `reset.switch`는 `failed` |
| `switch_failed` | 500 | 실행 중 예외. `reset.switch`는 `failed`, error에 예외 이름과 메시지 |

`CanAutoSave`는 검사하지 않는다. stock Tracking Station Fly와 `setActiveVessel`도 이 설정과 관계없이 저장하고 전환한다(`leave_flight`와 같다).

## 구조

### `VesselSwitch` (신규, `src/KspBridge.Logic/Flight/VesselSwitch.cs`)

`FlightReset`의 회수 대기와 같은 형태의 정적 상태 하나를 둔다. 메인 스레드 전용이다.

- `_targetId`: 진행 중인 전환 대상의 persistentId. null이면 진행 중인 전환이 없다.
- `_path`: `in_scene` 또는 `reload`
- `_deadline`: realtime 제한 시각
- `_status`: `get_status reset.switch` 사전 `{state, vessel, id, path, warp_lowered, error}`

### 요청 처리 `Switch(RequestBody)`

1. 사전 검사(위 오류 표 순서)
2. 대상이 활성 기체면 `already_active` 응답, 상태 `done`
3. 경로 결정: FLIGHT이고 `target.loaded`면 `in_scene`, 아니면 `reload`
4. 시간 가속 중이면 정지하고 `warp_lowered = true`. 진행 중인 warp-to, `CurrentRateIndex > 0`, rails 배율이 아직 줄어드는 중(`Warp.cs`의 easing 판정: HIGH 모드이고 `CurrentRate > 1`)을 모두 가속 중으로 본다. 정지는 `TimeWarpControl.Set(0, …)`의 정지 부분(`setAutoWarp=false`, `CancelAutoWarp`, `SetRate(0, true)`)을 공용 메서드로 꺼내 같이 쓴다.
5. `ManualControl.StopPulse("switch")` (계획 없이 도는 RCS 펄스)
6. 상태를 `pending`으로 두고 제한 시각을 정한다(`in_scene` 30 s, `reload` 300 s). `switch_started` 이벤트를 남긴다.
7. 실행. 실행부 전체를 try/catch로 감싼다. 예외가 나면 `failed`(예외 이름: 메시지)로 끝내고 500 `switch_failed`로 응답한다. pending이 남아 다음 요청을 막지 않게 한다.
   - `in_scene`: `FlightGlobals.ForceSetActiveVessel(target)`. 소유 검사는 사전 검사에서 했다. false면 `failed`로 끝내고 409 `switch_refused`로 응답한다.
   - `reload` + FLIGHT: `ClearToSave` 사전 검사를 통과했으므로 `FlightGlobals.SetActiveVessel(target)`에 맡긴다. 이 함수는 저장과 `StartAndFocusVessel`을 직접 한다. 사전 검사를 통과한 뒤에는 false가 되지 않는다. false면 `in_scene`과 같이 처리한다.
   - `reload` + SPACECENTER·TRACKSTATION: Tracking Station 순서대로 `Save()`를 부른 뒤 `FlightDriver.StartAndFocusVessel("persistent", FlightGlobals.Vessels.IndexOf(target))`를 부른다.
   - 실행 단계에서 실패해도 4·5에서 한 가속 정지와 펄스 정지는 되돌리지 않는다. 오류 응답에도 `warp_lowered`를 넣는다.

### 완료 판정 `Tick()` (`BridgeLogic.FixedUpdate`, `FlightReset.Tick` 다음) + `Status()`

- 제한 시각을 넘으면 `failed`(`timeout`)다. `Status`에서도 검사한다(timeScale 0 대비, `FlightReset.CheckDeadline`과 같다). 단, 제한 시각에 FLIGHT가 준비됐고 활성 기체 id가 대상과 같으면 `done`으로 끝내고 `unpacked: false`를 남긴다. 게임이 일시정지되어 물리 안정이 늦어진 경우를 실패로 남기지 않는다.
- `reload`는 `FlightReset`의 장면 로드 추적이 FLIGHT 준비(`onFlightReady`)를 마칠 때까지 기다린다. 판정은 `FlightReset.SceneReady`(접근자 추가)와 `HighLogic.LoadedScene == FLIGHT`로 한다. FLIGHT의 `_sceneLoading`은 `onFlightReady`에서만 풀린다.
- 완료: `HighLogic.LoadedScene == FLIGHT`, 장면 준비 완료, `FlightGlobals.ActiveVessel?.persistentId == _targetId`, `!ActiveVessel.packed`이면 `done`
- 실패
  - FLIGHT가 준비됐는데 활성 기체 id가 다르면 `failed`(`wrong_vessel`)
  - 진행 중에 FLIGHT가 아닌 장면 로드가 요청되면 `failed`(`scene_changed`). `FlightReset.OnLoadRequested`처럼 `onGameSceneLoadRequested`를 구독한다.
  - `in_scene`에서 대상 기체가 사라지면 `failed`(`vessel_lost`)

### 비행 계획·이벤트

- 계획은 사전 검사로 실행 중이 아니므로 `Coordinator`는 바꾸지 않는다. `FlightScene.OnVesselChange`의 `vessel_changed` 경로는 계획이 없으면 펄스 정지만 한다.
- `FlightEvents`에 `switch_started`(id, vessel, path), `switch_done`, `switch_failed`(error)를 남긴다.
  - `reload`는 장면이 바뀌어도 `FlightEvents`가 남는지 확인이 필요하다(개발 단계 확인 항목).

## get_status

`reset`에 `switch`를 추가한다. 다른 필드는 그대로 둔다.

```json
"reset": {
  "scene_ready": true,
  "...": "...",
  "recovery": null,
  "switch": { "state": "done", "vessel": "Relay 1", "id": 123456, "path": "reload", "warp_lowered": false, "error": null }
}
```

- 전환 요청이 없었으면 null이다. 마지막 전환 결과를 다음 요청 때까지 둔다.
- 응답은 HTTP 스레드에서 직렬화하므로 복사본을 넣는다(`recovery`와 같다).

## reload_mod·씬 전환

- Logic reload(`Unhook`)에서 `VesselSwitch`의 상태를 지운다. 인계하지 않는다(설계 단계 사용자 합의, 회수와 같다). 게임 쪽 전환은 그대로 진행되고, 결과는 `get_flight`의 활성 기체로 확인한다.
- 새 상태가 hook되는 시점은 `FlightReset.Hook`과 같다.

## 결정 목록

1. 상태 위치는 `get_status.reset.switch`다.
2. 장면 재로드 경로의 대기권·가속 판정은 stock `FlightGlobals.ClearToSave(false)`를 쓴다. 대기권 비행 외에 가속 중·지상 이동 중·추락 직전·사다리 EVA도 거부한다(방안 7). 비행 밖 장면에서는 검사하지 않는다.
3. 진행 중인 전환은 Logic reload에서 인계하지 않는다.
4. 이미 활성인 기체를 요청하면 즉시 `done`(`already_active: true`)이다.
5. 로드된 기체는 `ForceSetActiveVessel`로 `ClearToSave` 없이 전환한다. 소유 검사(`Owned`)는 사전 검사에서 직접 한다.
   - stock `setActiveVessel`은 검사에 실패해도 `ready=false`를 남기므로, 검사는 모두 호출 전에 한다.
6. 비행 장면의 로드 범위 밖 전환은 stock `SetActiveVessel`에 맡긴다(저장 + `StartAndFocusVessel(Game.Updated())`).
7. 비행 밖 장면의 전환은 Tracking Station의 Fly 순서를 따른다.
8. 완료는 대상 id가 활성 기체이고 unpacked일 때다. 제한 시간은 `in_scene` 30 s, `reload` 300 s(회수와 같다)다. 제한 시각에 대상이 활성 기체이면 unpacked가 아니어도 `done`(`unpacked: false`)이다.
9. `list_vessels`와 `switch_vessel`은 같은 조회 `VesselSwitch.Candidates()`(`FlightGlobals.Vessels`)를 쓴다. 활성 기체가 없으면 `distance`는 null이다.
10. 장면 재로드 전환은 `CanAutoSave`를 검사하지 않는다(stock과 같다).
11. 실행 단계는 try/catch로 감싸 예외가 나도 pending을 남기지 않는다. `switch_refused`·`switch_failed`는 오류 응답이다.

## 개발 단계 확인 항목

- SPACECENTER에서 `FlightGlobals.Vessels`가 저장된 기체로 채워져 있는지. 비어 있으면 결정 9를 회귀한다.
- SPACECENTER·TRACKSTATION의 `FlightGlobals.Vessels.IndexOf(target)`가 저장 후 `flightState.protoVessels`의 같은 기체를 가리키는지. 실측 B에서 응답 id와 전환 뒤 활성 기체 id가 같은지로 확인한다.
- 장면 재로드 뒤에도 `FlightEvents`가 유지되는지
- `ForceSetActiveVessel` 직후 대상이 packed에서 unpacked로 바뀌는 데 걸리는 시간

## 남은 위험 (검토 합의로 반영하지 않음)

- 전환 대기 중(`in_scene`, 대상 packed)에는 다른 비행 도구(`submit_flight_plan`, `set_target`, `rcs_translate` 등)를 막지 않는다. 호출자는 `reset.switch.state == done`을 확인한 뒤 다음 도구를 부른다.
- 전환 뒤 `get_flight.plan`은 이전 기체에서 끝났거나 중단된 계획을 그대로 보여 준다(기존 `Coordinator.Describe` 동작, 분리 때와 같다).
- `in_scene` 대기 중에 사람이 다른 기체로 다시 바꾸면 `timeout`까지 pending이 남는다.
